## 0. 사용자 요청 (paraphrase)

> 딥리서치에서 자연스럽게 이어져 논문 주제와 읽기 목록까지 만들고, 초안 작성까지 돕는 진짜 논문 에이전트 플랫폼으로 거듭나자. 태그라인은 "질문으로 시작해 연구 자동화까지". 지금 딥리서치 결과 화면이 논문 검색과 다른 스타일로 따로 열리는 것도 함께 정리하자. 10월 말 도서관 대회에서 연구 논문·도서 전문가들이 직접 써 본다 — 범위는 시연에 맞추되, 미리 돌린 가짜 화면이 아니라 실제로 동작하고 DBpia AI 아이디어와 견줄 차별점이 있는 제품 품질로. 보안은 뒤에 보강한다.

**한 줄 설계:** 딥리서치 한 건이 그 자리에서 연구 한 건으로 자란다 — 보고서 → 주제 → 읽기 목록 → 연구계획서. 단계마다 AI 가 후보를 내고 사용자가 골라 확정한다. 연구 공백 주장은 내세우기 전에 코퍼스 전체에서 스스로 반증 검사를 거친다.

**대회 한 줄:** "질문하면 답과 근거를 함께 주고, 필요하면 그 자리에서 더 깊게 조사해 연구계획서 초안까지 이어 준다."

## 2. 범위

**하는 것:** §4 의 여정 S0~S7, §5 의 단계별 생성, §6 의 데이터·API·작업 큐, §7 의 품질·윤리 장치, critic·계획 보강(§5-1).

**하지 않는 것 (대회 뒤로):**
- 보충 탐색(딥리서치 재실행) — 종합 LLM 을 낭비하고 GPU 직렬 큐를 최대 25분 잡는다. 대신 LLM 없는 '주제로 넓히기' 검색 1회를 둔다(§5-4)
- 연구 단위 대화(새 RAG), 3단 작업공간, `/projects` 어휘
- PDF 업로드, 소유 확인·공유 링크, AI 배지
- 사용자 질문 열(격자의 사용자 정의 열), 개념 지도
- 여러 질문을 한 연구에 묶기(`research_work_runs`) — 테이블도 지금 만들지 않는다. 새 테이블은 나중에 만들어도 기존 칼럼을 고칠 일(ALTER)이 생기지 않는다
- 북마크 정리, 논문 상세의 [담기], BibTeX/RIS 내보내기, 보고서 참고문헌 포매터를 백엔드로 옮기기
- 임베딩 512 절단 재처리 라운드 — 적재가 끝난 직후 돌리면 리허설 중 검색 결과가 바뀐다

## 3. 핵심 개념·용어

| 용어 | 정의 |
|---|---|
| **연구 1건** | 사이드바 '딥리서치' 묶음의 한 줄. 출발 질문 1개 = 연구 1건, id = 출발 잡 id. 다른 질문은 새 줄로 시작한다 |
| **단계 4개·관문** | 탐색 → 주제 → 읽기 목록 → 계획서. 관문은 계획 승인 → 주제 고르기 → 목차 승인 → 절 수락 |
| **핵심 개념** | 원 질문의 핵심 개념 2~5개(상한은 코드). 계획과 함께 나오고 계획 승인 때 칩으로 고친다. 하위질문을 그대로 쓰지 않는다 |
| **근거 장부** | 탐색 중 채택 논문이 쌓이고 critic 이 뺀 논문이 '뺌' 더미로 내려가는 목록. 뺀 논문은 [되살리기] 로 후보에 넣을 수 있다 |
| **공백 칸** | 핵심 개념 × 방법 유형(코드 열거형 8개). 숫자 두 개를 따로 보인다 — ① 표본 수 "채택 48편 중 n편" ② 확인 검색 "적재분 N편 검색 상위 50편 중 임계 이상 m편" |
| **공백 판정** | m = 0 공백 후보 · 1~2 약한 공백 · 3 이상 공백 아님. 임계값은 제안값이고 06c 에서 보정한 뒤 이 spec 에 고정한다 |
| **주제 카드** | 슬롯 1개 = LLM 1회. 제목·연구 질문·근거 칩 3개 이상·[F#] 수치 문장·근거 중 최신 연도. 계보(빵부스러기)는 주제 단계에만 둔다 |
| **후보 / 읽기 목록** | 후보는 채택 근거·되살린 논문·주제로 넓히기·연관·[담기] 로 들어온다. 사용자가 체크한 것만 읽기 목록이 된다 |
| **들어온 경로** | 논문마다 하위질문·회차·매칭 대목·rank_score·critic 판정·되살림 여부를 남긴다 |
| **논문 특징** | 목적·방법 유형·대상·결과 + 각 값의 원문 인용구. 논문 단위 공용 캐시 |
| **[E#] / [F#]** | [E#] 은 호출마다 붙이는 로컬 인용 번호이고 서버가 `cnts_id` 로 바꿔 저장한다. [F#] 은 코드가 센 수치 마커다. 모델은 숫자를 직접 쓰지 않는다 |
| **문단 상태** | AI 제안 / AI 작성·수락 / 사용자가 고침 / 사용자 작성. 수락만 한 문단도 AI 작성으로 센다 |
| **코퍼스 스냅숏** | 계산할 때마다 저장하는 (적재분 N, 연도 범위, 시각). 바뀌면 '코퍼스 바뀜 — 다시 세기' 배지 |
| **다시 맞춤 필요** | 앞 단계를 바꿔도 뒤 단계를 지우지 않고 붙이는 배지 |
| **생성** | LLM 작업 한 건(주제 카드·자식 카드·특징 추출·목차·절·문단). `research_generations` 1행 |

**모든 단계 공통**
- 단계는 주소 `?s=` 에 싣는다 — 새로고침·뒤로 가기·새 탭이 그대로 된다. `?s=` 가 없으면 연구의 현재 단계가 아니라 탐색·보고서(S1·S2)를 연다(기존 링크 호환). 기존 `?at=&y=` 위치 복원은 그대로 동작한다.
- 끝난 단계는 진행 막대에서 눌러 언제든 다시 연다. 앞 단계를 바꿔도 뒤 단계는 지우지 않고 '다시 맞춤 필요' 배지만 붙인다.
- 자동 스크롤은 하지 않는다. 화면 밖이 바뀌면 "새 후보 3 ↓" 알약만 띄운다. `prefers-reduced-motion` 이면 즉시 전환한다.
- **온보딩 모달:** 연구를 처음 시작할 때 브라우저당 한 번 띄운다. "4단계로 연구계획서 초안까지 갑니다" + 단계마다 한 줄 설명과 사용자가 결정할 것. 진행 막대의 [?] 로 다시 본다.
- **진행 막대:** `① 탐색 ② 주제 ③ 읽기 목록 ④ 계획서` + "2/4 단계 · 주제 고르는 중". 끝난 단계는 누를 수 있다. 사이드바 연구 줄에도 같은 막대를 작게 넣는다.
- 범위 띠(고정): "소장 KCI 적재분 N편(~YYYY) 기준 · 편수 추이는 동향이 아님".

**대회 '와' 장면 3개**
1. **근거 장부가 자라고 보고서가 연구로 접힌다.** 회차가 끝날 때마다 채택 논문이 장부에 떨어지고, critic 이 뺀 논문은 바래며 '뺌' 더미로 내려간다. [이 연구 이어가기] 를 누르면 본문이 접혀 요약 띠가 되고 진행 막대 ①→② 가 차오르며, 같은 순간 사이드바 줄 문구도 바뀐다.
2. **빈칸을 누르면 AI 가 스스로 반증한다.** 격자 칸 숫자가 특징 추출 도착마다 실제로 오른다. 표본 0편 칸은 점선으로 맥박친다. 칸을 누르면 서랍에서 확인 검색이 라이브로 돌고 "상위 50편 안에서 교차 논문을 찾지 못함 — 공백 후보 유지" 또는 "3편 발견 — 공백 아님으로 강등"(찾은 논문을 함께)으로 갈린다.
3. **근거 실로 쓰고 흔적을 남긴 채 받아들인다.** [이 절 쓰기] 를 누르면 문장이 흘러나온다. 번호가 맞는 마커는 저자·연도 칩으로 튀어 오르고, 틀린 마커는 취소선 뒤 사라지며 "인용 1개 버림"이 남는다. 근거 표시 없는 문장에는 점선, 뒷받침 점수가 낮은 문장에는 '뒷받침 약함'. [수락] 해도 문단 왼쪽 'AI 작성' 띠는 남고, 내보낸 Word 끝에 "AI 제안 9문단 중 수락 7·수정 2"가 찍힌다.

**시연 정직성 규칙**
- 움직임은 실제 이벤트가 도착할 때만 일어난다. 인위적 지연·하드코딩된 화면 데이터는 금지다.
- 방문자용 **예시 연구**는 미리 돌린 실제 기록이고 실행 시각·코퍼스 범위를 표시하며 읽기 전용이다(`research_works.is_example`, 쓰기 API 는 409).
- 시연자는 미리 진행해 둔 **자기 연구**(실제 기록)에서 확인 검색·절 쓰기를 라이브로 보인다.

**3분 동선**
1. 새 질문을 라이브로 계획 승인 → 탐색 시작(실측 1분 42초).
2. 그동안 미리 진행해 둔 연구에서 장면 2·3 을 라이브로 보인다.
3. 돌아와 새 질문의 보고서가 완료된 것을 보이고 [이 연구 이어가기] 로 장면 1 을 마무리한다.

## 5. 단계별 생성

### 5-1. 계획·탐색 보강 (06a — 기존 코드 수정)

운영 잡 `2a56f8b6`("컴퓨팅 자원") 결과에 남은 세 가지 질 문제 — 계획 일반 틀, 과잉 제외, 무관 논문 잔존 — 를 겨냥한다.

- **계획(`research_plan.yaml`, `planner.py`):** 측면 나열 틀("개념·정의, 방법·기법, 적용 분야, 성과·평가, 한계·과제 중")을 없앤다. 출력은 JSON `{"concepts": [...], "subquestions": [...]}` — 개념 2~5개(코드가 자르고 중복을 지운다), 하위질문은 지금 규칙 그대로. JSON 을 못 읽으면 지금의 번호 목록 파서로 물러나고 개념은 비운다. 예시는 넣지 않는다(함정 15).
- **개념 저장:** `research_jobs.plan` 은 하위질문 문자열 목록 그대로 둔다(모양을 바꾸면 계획 카드·승인·실행이 모두 흔들린다). 개념은 `research_works.concepts` 에 둔다. 승인 API `POST /api/research/{id}/approve` 에 선택 필드 `concepts`(문자열 1~5개, 각 1~40자)를 더한다.
- **critic(`research_critique.yaml`, `critic.py`):** 원 질문(`job.question`)과 핵심 개념을 함께 넘긴다. 충분·부족은 지금처럼 하위질문 기준으로 판정하고, **off_topic 은 "원 질문의 핵심 개념과 무관한 것(같은 단어 다른 뜻 포함)"으로만 좁힌다** — 하위질문에서 벗어났을 뿐 원 질문에 관련된 논문은 빼지 않는다. 개념이 비어 있으면(옛 잡·파싱 실패) 원 질문만 넘긴다.
- **근거 장부·되살리기:** `state_snapshot` 이 회차마다 저장되는지 확인하고, 아니면 runner `search` 이벤트에 채택·제외 `cnts_id` 목록만 더하는 최소 수정을 한다. 장부는 이 이벤트와 `GET .../pool` 로 그린다. [되살리기] 는 보고서를 바꾸지 않고 그 논문을 후보(`research_reading`, origin `revived`)로 넣는다.
- **서지 버그:** `services/search/paper_citation.py` `build_citation` 의 학술지 자리를 `publisher` → `series_title` 로 고친다. 계획서 참고문헌은 이 백엔드 포매터를 쓰고, 출력은 `frontend/utils/reportDocument.ts` 의 보고서 참고문헌과 같은 고정 예제로 맞춘다.

### 5-2. 주제 카드 (06b 보고서 씨앗, 06c 격자 씨앗·가지치기)

- **씨앗 고르기(순수 함수):** 보고서 `sections[].future`(근거 달린 향후 과제)와 critic 이 insufficient 로 판정한 하위질문(`trail[].verdict/note`)에서, 서로 다른 절을 우선해 겹치지 않게 3개를 고른다. 4번째는 확인 검색을 통과한 격자 칸(공백 후보·약한 공백). 격자가 아직 없거나 통과한 칸이 없으면 4번째도 보고서 씨앗이다.
- **카드 생성:** 슬롯 1개 = 생성 1건 = LLM 1회(Qwen). 입력은 씨앗 + 그 씨앗에 묶인 근거 논문(로컬 [E#]) + 코드가 센 수치([F#]). 출력은 제목·연구 질문·근거 칩·[F#] 수치 문장. 근거 칩이 3개 미만이면 그 슬롯만 1회 다시 부르고, 그래도 미달이면 '근거 부족' 빈 슬롯으로 정직하게 보인다. 근거 중 최신 연도는 코드가 붙인다.
- **더 받기:** [다른 방향] = 쓰지 않은 씨앗으로 2장 더. [더 구체적으로] = 그 카드 아래 자식 카드 3장(메시지 3개, 계보 `parent_id`). [이 칸으로 주제 만들기](격자 칸). [직접 쓰기] = 사용자 카드(LLM 없음).
- **고르기:** 다음 단계는 고른 주제 하나로 진행한다. 나머지 카드는 지우지 않는다. 주제를 바꾸면 읽기 목록·계획서에 '다시 맞춤 필요'.
- **외부 확인:** 고르기 전에 카드 제목으로 KCI·RISS·DBpia 검색 링크를 보인다(새 탭, 질의만 넘긴다).
- **표현 통제:** "연구가 없다·전무·최초" 같은 표현은 후처리로 잡아 "소장 코퍼스 검색 상위 50편에서 찾지 못함" 투로 바꾼다. 연도별 편수 추이는 어디에도 근거로 쓰지 않는다(수집 단계의 연도별 1만 건 상한 때문).

### 5-3. 공백 격자 (06c — 자르는 순서 마지막)

- **행 = 핵심 개념.** 논문의 개념 소속은 개념 임베딩(BGE-M3)과 논문 메타청크 벡터의 유사도(임계값 제안값)로 정한다. LLM 을 쓰지 않는다.
- **열 = 방법 유형 8개(코드 열거형, 제안):** 실험·준실험 / 설문·조사 / 사례 연구 / 면담·관찰(질적) / 문헌 고찰·메타분석 / 내용·텍스트 분석 / 모델·시스템 개발 / 이론·개념 연구. 논문의 방법 유형은 특징 추출(§5-4) 결과로 정한다. 추출 전이거나 '미확인'인 논문은 칸에 세지 않고 "미분류 k편"으로 따로 보인다.
- **표본 수 n:** 채택 근거 중 그 칸에 드는 논문 수 — `GET .../grid`(동기, LLM 없음).
- **확인 검색 m:** `POST .../grid/check`(동기) — 질의 "개념 + 방법 유형"으로 코퍼스 전체를 하이브리드 검색해 상위 50편을 리랭커로 다시 매기고 임계값 이상을 센다. 결과·코퍼스 스냅숏을 `research_gap_checks` 에 저장하고 찾은 논문을 서랍에 펼친다.
- **확인 검색을 거치지 않은 칸은 주제 씨앗으로 쓰지 않는다.** 표본과 확인 검색은 문구·화면 모두에서 구분한다("채택 48편 중" ≠ "적재분 N편 검색 상위 50편").

### 5-4. 읽기 목록 (06b 기본, 06c 추출 열·넓히기·연관)

- **후보 갈래:** ① 채택 근거 전체(최대 90편 — `state_snapshot.evidence`, 이어가기 때 가져온다) ② 되살린 제외 논문 ③ [주제로 넓히기] — 고른 주제 질의로 검색 1회(동기, LLM 없음) ④ [연관 더 찾기] — 담은 논문 여러 편을 씨앗으로 `find_related_papers`(동기) ⑤ 빠른검색 결과의 [담기]. 보고서가 인용한 논문을 자동으로 '담음' 처리하지 않는다.
- **들어온 경로:** `origin_ref` JSONB — 하위질문·회차·매칭 대목·rank_score·critic 판정·되살림 여부, 넓히기·연관이면 질의·씨앗. 행의 [경로] 팝오버로 3번 누르면 원문 쪽까지 간다(계획서 문장 → 칩 → 원문 쪽 → 들어온 경로).
- **사용자 동작:** 체크(담음/뺌), 행 메모, 묶음 이름, 순서. 담음 5편 이상이면 [목차 만들기].
- **논문 특징 추출(06c):** 논문 1편 = 생성 1건 = LLM 1회(Qwen). 목적·방법 유형(§5-3 열거형)·대상·결과 + 값마다 원문 인용구.
  - 입력은 초록 + 섹션 원문 앞부분(Qwen 16K 안에 들게 글자 예산은 계획에서 정한다). 섹션 원문이 없으면 섹션 요약 → 초록 순으로 물러나고, 요약을 입력으로 쓴 값은 '요약 기반(원문 미확인)'으로 표시한다.
  - 인용구는 공백을 정규화한 뒤 입력 원문의 부분 문자열인지 대조한다(`quote_ok`). 대조 실패·원문 미확인 값은 격자 집계에서 빼고 '미확인'으로 보낸다. 쪽 번호는 쪽 범위가 있는 원문에서 찾았을 때만 붙인다.
  - `paper_facets` 는 (`cnts_id`, `schema_ver`) 단위 공용 캐시 — 다른 연구도 같이 쓴다.
  - 추출 순서: 읽기 목록 '담음' → 후보(rank_score 순). 이어가기 직후 배경으로 돌기 시작한다.

### 5-5. 계획서 (06b 선행연구·연구 공백 2절, 06c 나머지 4절)

- **고정 6절:** 주제 · 연구 배경 · 선행연구 검토 · 연구 공백 · 연구 질문 · 방법 제안. 결과·논의 자리에는 "연구 후 직접 씁니다" 안내만 둔다.
- **목차 만들기(생성 1건, gemma):** 선행연구 하위 묶음 수는 코드가 정한다 — 담은 논문 4편당 1개, 최소 1·최대 4개. 묶음 배정도 코드가 한다(개념 소속 → 방법 유형 순으로 결정적 분할). LLM 은 묶음 이름, 연구 질문 후보 3개, 방법 선택지의 한 줄 설명만 쓴다. 방법 선택지는 읽기 목록 논문이 쓴 방법 유형 가운데서만 코드가 뽑는다(06b 에서 특징이 없으면 선택지 없이 사용자 입력 칸).
- **목차 승인:** 사용자가 묶음 사이로 칩을 옮기고, 연구 질문 하나를 골라 다듬고, 방법을 고른 뒤 [목차 승인]. `research_proposals.version` 으로 동시 수정을 막는다(If-Match).
- **절 쓰기(생성 1건, gemma, 스트리밍):** 절마다 사용자가 [이 절 쓰기] 를 누른다(원클릭 전체 생성은 없다). 입력은 배정 논문 6편 이하 × (특징 + 원문 대목 1,200자)를 로컬 [E#] 로, 수치는 코드가 센 [F#] 으로 넣는다. `chat_stream` 델타를 Redis 로 중계한다.
- **검증(서버, 생성 끝과 사용자 수정 뒤 `PUT` 때마다):**
  - 인용 번호: 로컬 [E#] 이 그 절의 입력 번호인지 확인하고 `cnts_id` 로 바꿔 저장한다. 틀린 번호는 버리고 "인용 n개 버림"을 남긴다(`bind_markers` 와 같은 규칙).
  - 근거 표시 없는 문장 → 점선 밑줄.
  - [F#] 밖의 숫자가 문장에 있으면 '확인 필요'.
  - 뒷받침 점수: `POST .../sections/{key}/support`(동기, fastapi 리랭커) — 문장과 그 문장이 인용한 대목의 점수가 임계값 아래면 '뒷받침 약함'. 모델에 준 대목은 문장 옆에서 펼쳐 볼 수 있다.
- **문단:** 상태 4가지를 저장한다. [다시] = 같은 입력으로 그 문단만 다시(생성 1건). [고치기] = 직접 편집(상태 '사용자가 고침').
- **쓰지 않는 것:** 결과·논의, 예상 결과·가설 수치. 표본 규모 같은 수치는 사용자 입력 칸으로 둔다. 요청해도 만들지 않는다.

### 5-6. 내보내기 (06b Word, 06c PDF)

- 06b 의 첫 Word 부터 기본은 **수락한 문단만**(상태가 AI 작성·수락 / 사용자가 고침 / 사용자 작성). 미수락 문단은 사용자가 명시적으로 켜야 들어가고, 켜면 '미검토 AI 초안' 워터마크를 붙인다.

- `frontend/utils/proposalDocument.ts` 가 문서 모델을 만들고 기존 `reportDocx.ts`·인쇄 경로를 재사용한다.

### 6-3. 작업 큐·LLM

- 새 모듈 `app/workers/research_work_tasks.py` 를 `celery_app` 의 `include` 와 `task_routes` 둘 다에 등록하고 **`q_research_plan`**(GPU 없음, 동시 2)으로 보낸다. compose 는 바꾸지 않는다.
- **연구마다 생성 사슬 하나:** 메시지 1개 = LLM 1회. 하나가 끝나면 그 연구의 다음 대기 생성을 우선순위(사용자가 누른 생성 > 배경 특징 추출) 순으로 골라 다시 큐에 넣는다. 그 사이에 다른 사람의 계획 요청이 끼어든다.
- **동시 실행 제한:** 계획 승인 때 같은 브라우저 ID 의 딥리서치가 이미 approved·queued·running 이면 429 와 그 연구 링크를 돌려준다(승인 안 하고 둔 계획은 세지 않는다 — 버려 둔 계획이 새 연구를 막지 않게). 생성은 연구마다 사슬 1개. 모든 생성·딥리서치에 대기 순번·예상 시간(최근 완료분 소요 시간 중앙값 × 순번)·취소를 둔다.
- **모델 라우팅(코드 상수 `WORK_MODEL_ROUTES`):** 주제 카드·자식 카드·특징 추출 → Qwen(`VLM_BASE_URL`/`VLM_MODEL`), 목차·절·문단 → gemma(`LLM_BASE_URL`/`LLM_MODEL`). 계획·critic·종합은 지금처럼 gemma. 연결 실패·5xx·타임아웃이나 JSON 을 두 번 못 읽으면 다른 모델로 한 번 넘기고, 쓴 모델을 `research_generations.model` 에 남긴다(공개 부록에 쓴다). `llm_client` 에 호출별 `base_url`·`model` 지정을 더한다(round07 이 고친 `chat_full`·`chat_stream` 위에서).
- 비스트리밍 호출은 timeout 300초를 명시한다. 오래 `running` 에 머문 생성은 기존 `q_control` 회수 태스크 패턴으로 failed 로 떨어뜨린다.
- Qwen 은 round07 의 VLM 페이지 병렬 OCR 과 8석을 나눠 쓴다 — round06 쪽은 `q_research_plan` 동시 2 를 넘지 않는다.

## 7. 품질·윤리 장치

- **critic·계획 보강이 06a 머지 조건이다.** 합격 전에는 주제·읽기 목록 단계를 시연에 쓰지 않는다.
- **공백:** 표본과 확인 검색을 문구·화면 모두에서 나누고, 확인 검색을 거치지 않은 칸은 씨앗으로 쓰지 않으며, 금지 표현을 후처리하고, 편수 추이를 근거로 쓰지 않는다(§5-2·5-3).
- **인용이라는 말을 정확히 쓴다.** 인용 번호 검증은 번호가 맞는지까지다. 문장이 실제로 뒷받침되는지는 뒷받침 점수로 따로 보이고 모델에 준 대목을 펼쳐 볼 수 있게 한다. 대회 자료에 "문장마다 검증"이라고 쓰지 않는다.
- **원문 인용구·숫자:** §5-4·5-5. 수치는 [F#] 로만 들어간다.
- **범위:** 고정 띠, 산출물마다 코퍼스 스냅숏, 적재 뒤 바뀌면 '다시 세기' 배지.
- **AI 표시:** 문단 상태 4가지, 기여 비율은 문단 상태로 센다, 공개 부록.
- **생성 범위:** 원클릭 전체 생성 없음, 결과·논의·가설 수치 없음.

- **선행 조건:** 06a 의 `llm_client`·`celery_app`·`research_tasks`·`config` 수정은 round07 이 dev 에 머지된 뒤 dev 를 받아 한다(겹치는 파일). round05a 겹침 파일(§6-6 표의 기존 파일)은 round05a 머지 뒤에만 고친다.
- **배포 순서(하위 라운드마다):** celery-research(실행 중 잡이 없을 때)·celery-research-plan → fastapi → nuxt → `docker exec nl-lib-gateway nginx -s reload`(함정 20). 스키마는 06a 한 번(`create_all` + `stamp 0007`). 바뀐 컨테이너만 Recreate 하고 적재 in-flight 가 적은 시간에 한다.
- **구현이 일정보다 빠르면** 남는 날은 기능을 더 넣지 않고 안정화·리허설에 쓴다.
- **자르는 순서(뒤처지면):** 연관 더 찾기 → [더 구체적으로] 가지치기 → 격자(빠지면 주제 씨앗은 보고서 재료만) → PDF 내보내기. **자르지 않는 것:** critic 보강, 06b 수직 슬라이스, 공개 부록, 시연 정직성 규칙.
- **적재와의 관계:** 적재가 끝나기 전에는 기능 검증만 한다. 품질과 시간은 적재가 끝난 뒤 판정한다. 그동안 새 태스크의 LLM 동시 호출은 `q_research_plan` 2석 안에 머문다.
