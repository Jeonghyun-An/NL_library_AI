# round04c 교본 (2) — 프롬프트와 자기점검

> 이 교본 하나로 round04c 전체를 클론코딩할 수 있어야 한다. 코드는 저장소 파일을 그대로 수록했다(`GIT_WORKFLOW.md` §개발 가이드 문서).

전체 개요·검증·Q&A 는 [00-개요.md](00-개요.md) 참조.

## 이 챕터의 자리

LLM 에게 말을 거는 세 곳(계획·종합·자기점검 프롬프트)과, 자기점검 응답을 읽는 `critic.py`, 둘이 함께 쓰는 조사 고르기(`hangul.py`)를 다룬다. 기존 파일은 전부 **round04b 끝(`d845b8b` = `9b776d2^2`) 대비 diff** 이고, 새 파일(`hangul.py`)만 전체를 싣는다. round04c 는 round04b 브랜치 끝에서 땄다(`git merge-base 9b776d2^2 3dfeb45^2` = `d845b8b`).

```text
계획      research_plan.yaml        ── C: 핵심 개념 안에서·측면으로·핵심어 포함(예시 없음)
종합      research_synthesize.yaml  ── G: '~다' 문어체, 예시 값도 '~다'
자기점검  research_critique.yaml    ── B: off_topic 번호(예시는 빈 배열) · G: note 문체 · note 에 목록 번호 금지
            │
            ▼ 응답 문자열
          critic.critique()
            ├ parse_verdict(raw, listed=…, exclude_off_topic=…)   off_topic 해석 · '모두 빼며 충분'을 부족으로
            └ _titled_note(note, evidence)                         note 의 [2] → 「제목」, 뒤 조사는 hangul.josa
```

이 챕터를 관통하는 원칙은 round04a 와 같다 — **프롬프트는 부탁이고 강제는 코드가 한다.** 새로 생긴 규칙마다 코드 쪽 짝이 있는지가 설계의 대부분이다.

| 프롬프트 규칙 | 코드 쪽 짝 | 짝이 없으면 |
|---|---|---|
| off_topic 에 목록 번호(정수) | `_off_topic` — 보인 목록 안(1..`listed`)의 정수·정수 문자열·`"[3]"` 만, 순서대로·중복 없이 | 잘못 읽은 번호로 관련 있는 근거가 지워진다 |
| 모두 넣었으면 insufficient | `parse_verdict` — 보인 근거 전부가 off_topic 인데 sufficient 면 insufficient 로 읽고 note 를 비운다 | '충분·근거 0편' 이 보고서에 남는다 |
| note 에 목록 번호 금지 | `_titled_note` — 남은 `[2]`·`[2, 3]`·`[2-4]` 를 「제목」으로, 뒤 조사를 제목 받침에 맞춘다 | 보고서(.docx)가 `[2]` 를 참고문헌 번호로 읽게 렌더한다 |
| note·서술 '~다' 문체 | **없다** — 뜻이 바뀔 수 있어 코드로 고치지 않는다(spec §6) | 운영 비교로 본다 |
| 계획: 핵심 개념 안에서 | **없다** — 계획은 사용자가 승인 화면에서 고친다 | 운영 비교로 본다(§3-5 — 미달) |

예시를 넣지 않은 이유는 셋 다 같다. **gemma 는 프롬프트 예시의 개수·분야·문체를 견본으로 베낀다**(함정 15번 — round04a 에서 종합 예시의 배열 길이 1을 베껴 절 1개 보고서가 나왔다). 그래서 계획 규칙에는 예시가 없고, `off_topic` 예시는 빈 배열 `[]` 뿐이며, 종합 JSON 예시의 값도 '~다' 로 끝나게 고쳤다. 다만 운영에서는 **예시가 아닌 규칙 속 목록**이 견본 노릇을 한 정황이 나왔다(00-개요 Q7).

## 2. 구현 (클론코딩)

### 2.1 `research_plan.yaml` — 계획을 질문의 핵심 개념 안에 묶는다 (C)

운영 보고서("컴퓨팅 자원에 대한 연구가 궁금해")의 하위질문은 HPC·클라우드·분산·병렬·엣지·자원관리였다. 질문의 핵심인 "자원"은 마지막 하나뿐이고 나머지는 "컴퓨팅" 이웃 분야의 목록이다(spec §1). 원인은 계획 프롬프트에 "원 질문의 핵심 개념 안에 머물라"는 규칙이 없었던 것이다.

더한 규칙 넷(`e6d8039`).

- 최대 개수 규칙 뒤에 "핵심 개념이 좁으면 더 적어도 된다" — 최대 개수를 채우려고 이웃 분야를 끌어오지 않게.
- 모든 하위질문은 원 질문의 핵심 개념 안에 머문다. 이웃한 기술·분야를 나열하지 않는다.
- 넓으면 핵심 개념의 **측면**으로 나눈다 — 개념·정의, 방법·기법, 적용 분야, 성과·평가, 한계·과제 중 질문에 맞는 것만.
- 각 하위질문에 원 질문의 **핵심어**를 그대로 넣는다. 탐색은 하위질문 문자열을 그대로 검색어로 쓰므로(round04a — 쿼리 재작성 끔), 핵심어가 빠지면 검색이 주제를 벗어난다.

**버린 대안 — 예시 분해 하나를 보여 주기.** 가장 확실해 보이지만 gemma 는 예시의 개수·분야를 베낀다(함정 15번). "컴퓨팅 자원" 예시를 넣으면 모든 질문이 그 예시의 여섯 갈래로 나뉠 수 있다. 테스트가 `"예:"`·`"예시"` 가 프롬프트에 없는지까지 본다(§2.6).

**운영 결과.** 배포 뒤 첫 잡(`2a56f8b6`)의 계획은 여전히 "정의·방법론·적용 분야·성과·한계·동향" 같은 일반 틀이었다(사용자 확인, 00-개요 §3-5). 규칙에 넣은 측면 목록(개념·정의, 방법·기법, 적용 분야, 성과·평가, 한계·과제)과 겹친다. 예시를 빼도 **규칙 안의 열거가 견본이 될 수 있다**는 가설이고, 계획 프롬프트 재검토가 다음 과제다.

### 2.2 `research_synthesize.yaml` — 서술 문체를 '~다' 로 (G)

운영 보고서에서 5절만 "~합니다" 체였다(spec §1). 종합은 절마다 LLM 을 따로 부르므로(round04a — 하위질문마다 호출 1회) 절마다 문체가 갈릴 수 있다. 규칙 한 줄을 더하고(intro·summaries·future 모두), **JSON 예시의 값도 고쳤다** — `"문장마다 [E#] 를 답니다."` 가 `"… 단다."` 가 됐다(`4e5ea63`). 규칙이 '~다' 를 요구하는데 예시가 '~ㅂ니다' 로 끝나면 둘이 싸우고, gemma 는 예시 쪽을 따른다.

예시 문자열을 바꾸면 그 예시를 **베낀 출력을 흉내 낸 테스트 문자열**도 바꿔야 한다. `build_section` 은 지시문 원문(`[E#]` 가 남은 문장)을 걸러내는데, 그 검사 테스트의 입력이 옛 예시 문장이었다(02 챕터 §2.14 의 `test_research_synthesizer.py` diff 중 `"… [E#] 를 단다."`). 안 바꾸면 테스트는 통과해도 "지금 예시를 베낀 출력"을 거르는지는 보지 않는다.

모델이 섞어 쓴 '~합니다' 를 코드로 고치지는 않는다(spec §6) — 어미를 기계적으로 바꾸면 인용문이나 고유명사 안의 글자까지 건드려 뜻이 바뀔 수 있다.

### 2.3 `research_critique.yaml` — 무관 근거 번호와 note 규칙 (B·G)

"엣지 컴퓨팅" 절에 의료영상 *Edge method*, MPEG-7 *Edge Histogram*, CMOS *에지* 검출 회로가 실렸다(spec §1). 검색에 걸린 논문을 관련성 확인 없이 전부 채택했기 때문이다. 자기점검은 발췌까지 읽고 "엣지 컴퓨팅 핵심을 다루지 못한다"고 한계에 쓰면서도 논문을 빼지는 못했다 — 판정이 충분·부족 둘뿐이었다.

그래서 응답 JSON 에 `off_topic` 을 더했다(`8f49669`). 줄마다 이유가 있다.

| 줄 | 이유 |
|---|---|
| 형식 예시의 `"off_topic": []` | 빈 배열만 보인다. `[2]` 를 보이면 gemma 가 매번 한 편을 빼거나 2번을 뺄 수 있다(함정 15번) |
| "발췌가 하위질문의 핵심 개념을 다루지 않는 근거(같은 단어를 다른 뜻으로 쓴 논문 포함)" | 엣지·Edge 같은 동음이의가 이 기능의 표적이다. 판단 기준 첫 줄("제목만으로 짐작하지 말고 발췌를 보라")은 round04a 에 이미 있다 |
| "번호는 근거 목록 맨 앞 [ ] 안의 숫자" | 목록에 `[1]` 부터 번호를 붙였다(§2.5 `format_evidence_list`) |
| "여기에 넣은 근거는 이 하위질문의 근거에서 빠집니다" | 결과를 알려야 모델이 가볍게 넣지 않는다 |
| "모든 근거를 off_topic 에 넣었다면 … verdict 는 insufficient 로 하고 new_queries 에 다른 검색어를 제안하세요" | 두 단계로 들어왔다. 처음(`8f49669`)은 "검색어를 제안하라"만 — 원래 규칙은 "부족하다고 판단하면" 검색어를 제안하게 해서, 모두 빼고도 충분이라 답한 모델은 `new_queries` 를 비워 다시 찾을 검색어가 없었다. 최종 리뷰(`e10f873`)에서 "insufficient 로 하라"를 더했다 — 코드도 그렇게 읽는다(§2.5 `parse_verdict`) |
| note — "보고서의 한계 섹션에 실립니다 … '~다' 문어체" | note 는 `build_limitations` 가 한계 문장 끝에 그대로 잇는다. 서술은 '~다' 인데 note 만 '~합니다' 면 한 문단에서 문체가 갈린다(`4e5ea63`) |
| "사용자는 근거 목록을 보지 못합니다 … 논문 제목으로 쓰세요" | 목록에 번호가 붙자 모델이 note 에도 `[2]` 를 쓰기 쉬워졌다. 사용자는 그 목록을 못 보고, 내려받은 문서는 인용을 `[n]` 으로 렌더해 참고문헌 2번으로 읽힌다(`b3c2a29`). 그래도 남은 번호는 코드가 제목으로 바꾼다(§2.5 `_titled_note`) |

**제외 기준의 대상이 "하위질문"이라는 점.** off_topic 의 기준은 "하위질문의 핵심 개념"이다. critic 의 user 템플릿에는 하위질문·시도한 검색어·근거 수·근거 목록만 있고 **원 질문은 없다**(`critique()` 의 `render(...)` 인자). 운영에서는 이 기준이 과하게 작동했다 — 주제(컴퓨팅 자원)에 맞는 논문을 하위질문의 측면에 안 맞는다고 뺐다(00-개요 §3-5 ②). spec §11-4 가 미리 적어 둔 대응이 "원 질문 주제와 명백히 무관한 것만"으로 좁히기인데, 그러려면 critic 에 원 질문을 넘기는 것부터 해야 한다.

### 2.4 `hangul.py` — 조사 고르기 (새 파일)

코드가 이어 붙이는 말 두 곳의 조사를 받침에 맞춘다.

- 한계 문장의 주어 — `'고성능 컴퓨팅 (HPC)' 는` 처럼 `' 는'` 을 하드코딩했었다(spec §1). `synthesizer._topic` 이 쓴다(02 챕터 §2.11).
- note 의 목록 번호를 바꾼 「제목」 뒤 조사 — 모델은 번호를 읽는 소리([1]=일 → '은')에 맞춰 조사를 붙이므로, 제목으로 바꾸면 끝 받침과 어긋난다. `critic._titled_note` 가 쓴다(§2.5, `d9570ff`).

**받침 판정.** 한글 음절은 유니코드 `가`(U+AC00)부터 `(초성×21 + 중성)×28 + 종성` 순서로 놓여 있다. `(ord(글자) - ord("가")) % 28` 이 종성 번호이고 0 이면 받침이 없다. `pair` 는 받침 있을 때·없을 때 순서의 두 글자다(`'은는'`·`'이가'`·`'을를'`·`'과와'`).

**한글로 끝나지 않으면 병기한다.** `'HPC'` 는 '에이치피시'라 '는'이지만 `'LAN'` 은 '랜'이라 '은'이다. 읽는 소리는 코드가 알 수 없다. 마지막 한글 음절로 고르는 대안은 `'고성능 컴퓨팅 (HPC)'` 에서 '팅'(받침 ㅇ)을 보고 '은'을 고르지만, 실제로 읽히는 끝은 'HPC'(에이치피시)라 '는'이 맞다. 틀린 조사보다 `(은)는` 병기가 낫다(spec §6).

**파일**: `app/services/research/hangul.py` — 전체

```python
"""hangul.py — 조사 고르기

보고서에 코드가 이어 붙이는 말(한계 문장의 주어, note 의 논문 제목)은 앞말이 바뀌어도
조사가 맞아야 한다. 한계 섹션에 둘이 나란히 실려 한쪽만 틀려도 드러난다.
"""


def josa(word: str, pair: str) -> str:
    """word 뒤에 붙일 조사. pair 는 받침이 있을 때·없을 때 순서의 두 글자다('은는'·'이가'·'을를'·'과와').

    한글로 끝나지 않으면(영문·숫자·괄호) 읽는 소리를 코드가 알 수 없다 — 'HPC' 는 '는'(에이치피시)이지만
    'LAN' 은 '은'(랜)이다. 틀린 조사보다 '(은)는' 병기가 낫다.
    """
    last = word[-1:]
    if "가" <= last <= "힣":
        return pair[0] if (ord(last) - ord("가")) % 28 else pair[1]
    return f"({pair[0]}){pair[1]}"
```

### 2.5 `critic.py` — 번호 목록·off_topic 해석·note 의 번호 바꾸기

round04b 끝 대비 변경은 넷이다.

**① 근거 목록에 번호(`format_evidence_list`).** 줄 머리가 `- ` 에서 `[n] ` 이 됐다. 번호는 critic 에게 넘긴 순서이고, 그 순서는 러너가 넘긴 `subq.evidence_ids` 순서 그대로다(02 챕터 §2.10 `_exclude_off_topic` 이 `subq.evidence_ids[n - 1]` 로 되돌린다). 목록 상한(`_MAX_LISTED` = 20) 밖의 나머지는 **번호 없이** `…외 N편` 한 줄로만 적는다 — 그 줄을 다음 번호로 센 모델이 발췌를 보지도 못한 근거를 가리키게 두지 않는다.

**② `parse_verdict(raw, *, listed, exclude_off_topic)`.**

- `listed` 는 번호를 붙여 보인 근거 수 `min(len(evidence), _MAX_LISTED)` 다. 처음 구현에서 전체 근거 수를 넘기는 변이가 테스트를 통과해, 품질 검토가 경계 테스트를 더했다(`75da931` — 근거를 늘 1편만 넘기던 테스트로는 `listed=len(evidence)` 와 구별되지 않았다).
- `_off_topic` 은 보인 목록 안의 정수만 순서대로·중복 없이 받는다. 정수 문자열(`"3"`)과 목록 표기 그대로인 `"[3]"` 도 받는다(`d9570ff` — 목록 줄이 `[3] 제목 …` 모양이라 그 표기 그대로 답하기 쉽고, 괄호 하나에 숫자 하나면 뜻이 모호하지 않다). `true` 는 `int` 의 서브클래스라 막지 않으면 1번으로 읽힌다. 배열이 아니면 빈 목록이다. **버린 값이 있으면 원본을 경고 로그에 남긴다** — 응답 원문은 어디에도 저장되지 않아, 운영에서 "무관 0편 제외"가 모델 판단인지 형식이 어긋나 버린 것인지 가를 곳이 이 로그뿐이다.
- 판정을 못 읽으면(`parse_failed`) 기존대로 sufficient 로 떨어지고 off_topic 은 비어 있다 — **판정을 못 읽었는데 근거를 지우면 안 된다.**
- **보인 근거를 모두 off_topic 에 넣으면서 sufficient 라고 답하면 insufficient 로 읽고 note 를 비운다**(`e10f873`). 판정은 뺀 근거까지 보고 내린 것이라, 빼고 나면 남는 것은 0편이거나 발췌를 보이지 않은 목록 밖 근거뿐이다. note 는 뒤집은 판정의 이유("충분하다")라 싣지 않는다. 처음 구현은 이 규칙을 러너에 뒀다(`44e28a2` 의 `emptied` — "빼고 나니 0편이면 재검색 대상") — 최종 리뷰가 그 방식의 구멍 셋을 찾아 여기로 옮겼다(00-개요 Q9).
