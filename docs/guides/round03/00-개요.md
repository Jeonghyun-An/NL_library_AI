## 0. 사용자 프롬프트 (paraphrase)

> 검색 화면이 갑자기 깨졌다 — 논문도 도서도 카드에 제목 대신 `CNTS-…` 같은 내부 ID가 뜨고, `POST /api/books/curate` 가 404 를 낸다. 뭐가 꼬였는지 찾아서 고쳐달라.

조사해 보니 원인은 UI 가 아니었다. 운영 Postgres 의 `library_catalog` 테이블이 **통째로 비어 있었다.** 그래서 이 라운드는 세 단계로 이어졌다.

> (2) 복구할 수 있는 건 전부 복구하자. (3) 근데 진짜 왜 날아간 거지 — 원인을 밝히자. (4) 그래 백업 먼저 하자.

원인 조사가 끝난 뒤 사용자가 라운드 스코프를 확정했다.

> (5) 문학 41편 `doc_type` 재인덱싱하고 라운드로 정리하자.

즉 **사고 복구 + 재발 방지**가 앞에 붙고, 원래 하려던 **`doc_type` 오분류 교정**이 본 스코프인 라운드다.

### 1-1. 사고의 성격

| 항목 | 상태 |
|---|---|
| `library_catalog` (카탈로그 행) | **전멸** — 고아 문서 72,601건 |
| `book_sections` (원문) | 무사 |
| Milvus (청크·임베딩) | 무사 |
| MinIO (원본 파일·표지) | 무사 |
| 백업 | **존재하지 않음** |

메타데이터 테이블 하나만 날아가고 무거운 것들(원문·임베딩·파일)이 다 살아있었다는 점이 복구의 전제가 됐다. 카탈로그는 **다른 곳에 남은 사본에서 되살릴 수 있는 종류의 데이터**였다 — 원본 적재 파일이 `uploads/` 에 있었고, 초록·키워드는 Milvus 보강청크에 문자열로 남아 있었다.

**이건 운이었다.** 설계된 안전장치가 아니다. `docker-compose.yml` 에 백업 서비스가 없어 `pg_dump` 가 한 번도 돈 적이 없었다.

### 1-2. 원인 조사 — 미확정으로 남긴 이유

배제한 것:

- **API 경유 삭제** — 2026-09-03 이후 uvicorn 로그 전수 검색에서 대량 DELETE 흔적이 없었다.
- **적재 코드** — 카탈로그 로더는 전부 비파괴 upsert 다. 실행돼도 지우지 않는다.
- **셸에서의 실행** — `~/.bash_history` 에 흔적이 없었다.

남는 경로는 **Postgres 직접 SQL** 하나인데, `log_statement=none` 이라 증거가 없다. 서버는 동료와 공유하고 `postgres` 가 호스트 `15432` 로 노출돼 있어 GUI 클라이언트로 붙으면 셸 히스토리에도 남지 않는다. 그래서 **작업자 특정이 불가능**했고, 원인을 "직접 SQL 로 추정"까지만 적고 확정하지 않았다.

문서에 "아마 누가 그랬을 것"이라고 쓰지 않은 것은 의도적이다. 근거 없이 사람을 지목하는 기록은 남기지 않는다.

### 1-3. 그래서 무엇을 붙였나 — 우선순위의 근거

서버는 공유 자원이고 `docker` 그룹은 사실상 root 다. **포트 바인딩을 `127.0.0.1` 로 좁혀도 서버에 들어올 수 있는 사람은 그대로 붙는다.** 기술적으로 완전히 막을 방법이 없다는 전제에서 우선순위를 정했다.

1. **백업** — 못 막으면 되돌릴 수 있어야 한다. (`infra/backup/pg_backup.sh` + 호스트 cron, 복원 연습까지 완료)
2. **계정 분리** — 읽기 전용 역할 `nl_readonly` 신설. 조회 목적이면 이걸 쓴다.
3. **로깅** — `log_statement='ddl'` + `log_connections=on`. 다음에 같은 일이 나면 최소한 누가 언제 붙었는지는 남는다.
4. 부수적으로 `/api/admin`·`/docs` 게이트웨이 외부 차단 — 외부 노출 면적을 줄이는 것이지 내부자 대응은 아니다.

### 1-4. 본 스코프 — `doc_type` 오분류

검색 필터가 비대칭이다.

```
논문 검색:  doc_type == "paper" || book_id like "KCI_FI%"        ← ID 폴백 있음
도서 검색:  doc_type != "paper" && not (book_id like "KCI_FI%")  ← 폴백 없음
```

그래서 문학 문서의 Milvus `doc_type` 이 `paper` 로 잘못 들어가면 **도서 검색에서 사라지고 논문 검색에 섞여 나온다.** 논문 쪽은 ID 폴백이 받쳐주지만 도서 쪽은 스칼라 값이 곧 진실이다.

두 갈래로 처리했다.

- **재발 방지** — `detect_doc_type` 이 PDF 자동추출 `genre` 로 `paper` 를 판정하지 않게 고쳤다(§2.9). 빈 본문 인덱싱이 기존 청크를 전부 지우는 문제도 가드로 막았다(§2.8).
- **기존 데이터 교정** — 원문 재추출·재임베딩 없이 **스칼라 필드만 다시 쓰는** 도구를 만들었다(챕터 3). 임베딩은 멀쩡한데 라벨만 틀린 것이라 재인덱싱은 과잉이다.

### 3-5. 참고문헌 복구 (운영 실행)

복구 스크립트가 실제로 기록한 건수는 **1차 30,532 + 2차 6,931 = 37,463건**이다(각 실행의 `갱신: N건` 출력).

```bash
$ docker exec nl-lib-postgres psql -U admin -d nl_lib -c "SELECT count(*) FILTER (WHERE jsonb_array_length(coalesce(extra->'references','[]'::jsonb)) > 0) AS 실제있음, count(*) FILTER (WHERE extra ? 'references' AND jsonb_array_length(coalesce(extra->'references','[]'::jsonb)) = 0) AS 빈배열, count(*) AS 전체 FROM library_catalog WHERE doc_type='paper' AND is_embedded;"
 실제있음 | 빈배열 | 전체
----------+--------+-------
    37463 |      0 | 71931
(1 row)
```

**37,463건 / 71,931건 (52.1%)**. 남은 34,468건은 참고문헌 섹션 자체가 없거나 OCR 이 깨진 문서다.

처음 검증에 쓴 조건은 `extra ? 'references'` 였는데, 머지 게이트 리뷰가 이 조건의 결함을 지적했다 — `?` 는 **키 존재만** 보므로 값이 `[]` 여도 참이다. 적재 파이프라인(`app/services/ingestion/stages.py`)은 초록·목차·키워드 중 하나만 있어도 `extra["references"]` 를 빈 리스트째로 기록하므로, 이 조건은 원리상 빈 배열을 "있음"으로 세고 복구 대상에서도 빼버린다.

**다만 운영 데이터에는 해당 문서가 0건이었다.** 파이프라인이 기록한 `extra` 는 카탈로그 전멸 때 행과 함께 사라졌고, 이후 `extra` 를 다시 채운 것은 복구 스크립트뿐인데 그 스크립트는 `if not refs: continue` 로 빈 결과를 쓰지 않는다. 그래서 빈 배열이 생길 경로가 없었다. 위 두 숫자(37,463 / 0)가 그 확인이다.

조건 자체는 길이 기준(`_EMPTY_REFS`)으로 고쳐 뒀다 — 앞으로 재인덱싱이 돌면 빈 배열이 다시 생기고, 그때는 이 가드가 필요하다. **지금 재실행할 것은 없다.**

## 4. 면접식 Q&A

**Q1. 카탈로그가 통째로 날아갔는데 어떻게 복구했나?**
A. 날아간 것이 **메타데이터 한 테이블뿐**이었고 그 내용의 사본이 세 곳에 남아 있었기 때문이다. (1) 원본 적재 파일(`metadata.xlsx`·`marc_mods*.xlsx`)이 `uploads/` 에 있어 재적재로 대부분을 되살렸다. (2) 근대문학 41편처럼 적재 파일이 없는 것은 Milvus 메타청크(`chunk_idx = -1`)에 `제목 | 기관 | 저자 | …` 문자열이 남아 있어 역파싱했다. (3) 초록·키워드는 `[초록]`·`[키워드]` 보강청크에서 되살렸다. 무거운 것(원문·임베딩·파일)은 애초에 안 날아갔다.

**Q2. 원인을 왜 끝까지 특정하지 못했나?**
A. `log_statement=none` 이었기 때문이다. API 경유 삭제는 로그로 배제했고 적재 코드는 비파괴 upsert 이며 bash_history 에도 흔적이 없었다. 남는 경로는 직접 SQL 인데, 그걸 기록하는 설정이 꺼져 있었다. 게다가 서버를 공유하고 `postgres` 가 호스트 `15432` 로 노출돼 있어 GUI 클라이언트로 붙으면 셸 흔적조차 남지 않는다. **증거가 없으니 미확정으로 적었다.** 지금은 `log_statement='ddl'` + `log_connections=on` 을 켜서 다음에는 최소한 접속 기록이 남는다.

**Q3. Postgres 포트를 `127.0.0.1` 로만 바인딩하면 되지 않나?**
A. 공유 서버에서는 효과가 제한적이다. 서버에 SSH 로 들어올 수 있는 사람은 로컬 바인딩에도 그대로 붙는다. 더구나 `docker` 그룹 권한은 사실상 root 라 컨테이너를 통해 무엇이든 할 수 있다. 그래서 "막는다"가 아니라 **"되돌릴 수 있게 한다(백업) → 권한을 나눈다(읽기 전용 역할) → 남긴다(로깅)"** 순서로 갔다. 포트 바인딩은 외부 노출 면적을 줄이는 부수적 조치일 뿐 내부자 대응이 아니다.

**Q4. Milvus 에서 스칼라 필드 하나만 고치면 되는데 왜 청크를 통째로 다시 쓰나?**
A. Milvus 가 부분 업데이트를 지원하지 않기 때문이다. 한 필드만 바꾸려 해도 그 행 전체(임베딩·희소 임베딩 포함)를 다시 써야 한다. 그래서 대상 청크를 전부 읽어 `doc_type` 만 교체한 뒤 통째로 되쓰는 구조가 됐다. 다만 **재인덱싱은 아니다** — 원문 재추출도 재임베딩도 하지 않고 기존 벡터를 그대로 다시 넣는다.

**Q5. `delete` 후 `insert` 가 아니라 `upsert` 를 쓴 이유는?**
A. `delete + insert` 는 두 연산 사이에 창이 생긴다. 그 사이에 프로세스가 죽거나 insert 가 실패하면 **청크가 영구히 사라진다.** 운영 Milvus 를 건드리는 도구에서 이 위험은 받아들일 수 없다. `upsert` 는 같은 PK 에 대해 원자적으로 대체하므로 중간 상태가 없다. 그럼에도 쓰기 전에 대상 청크를 JSON 으로 백업하고 `restore()` 로 되돌릴 수 있게 했다.

**Q6. Milvus 스칼라 필드 순서를 왜 하드코딩하지 않았나?**
A. **스키마 필드 순서가 곧 insert 컬럼 순서**라서, 스키마에 필드가 하나라도 추가되면 하드코딩한 순서는 조용히 어긋난다. 값이 엉뚱한 컬럼에 들어가도 타입만 맞으면 에러가 나지 않는다 — 가장 위험한 종류의 버그다. 그래서 `scalar_order()` 로 런타임에 컬렉션 스키마를 읽어 순서를 만든다. 초안은 하드코딩이었고 리뷰에서 바꿨다.

**Q7. `float32` 버그는 왜 테스트에서 안 잡혔나?**
A. 테스트가 순수 파이썬 `list[float]` 를 입력으로 썼기 때문이다. 실제 Milvus 조회는 `numpy.float32` 배열을 돌려주는데, `list(row["embedding"])` 는 컨테이너만 바꿀 뿐 **원소 타입은 `numpy.float32` 그대로 남긴다.** 백업을 JSON 으로 쓰는 순간 `TypeError: Object of type float32 is not JSON serializable` 로 운영에서 터졌다. `[float(x) for x in row["embedding"]]` 로 고치고, `numpy.float32` 를 직접 넣는 회귀 테스트를 추가한 뒤 **수정을 되돌려 테스트가 실패하는 것까지 확인**했다. 교훈은 "mock 입력의 타입이 실제와 다르면 테스트는 통과하면서 거짓말을 한다"는 것이다.

**Q8. 빈 본문 인덱싱 가드가 왜 필요한가?**
A. 인덱싱 파이프라인은 같은 문서를 다시 넣을 때 **기존 청크를 지우고 새로 쓴다.** 그런데 추출 아티팩트도 폴백 텍스트도 없어 본문이 빈 문자열이면, 지우기만 하고 쓸 것이 없어 **멀쩡하던 청크가 전부 사라진다.** 조용히 데이터를 잃는 경로라서 `StageError("empty_body", …)` 로 아예 중단시킨다. 실패로 드러나는 편이 성공을 가장한 삭제보다 낫다.

**Q9. PDF 의 `genre` 로 `doc_type=paper` 를 판정하면 왜 안 되나?**
A. `genre` 가 PDF 에서 자동 추출된 값이면 신뢰할 수 없기 때문이다. 근대문학 PDF 의 메타에 `report` 같은 값이 들어 있어 논문으로 분류됐다. 그래서 `genre in ("paper","thesis","report")` 만으로 판정하지 않고 `source_format != "PDF"` 조건을 함께 걸었다 — 출처가 명시적인 메타(KCI 등)일 때만 `genre` 를 신뢰한다.

**Q10. 참고문헌은 왜 Milvus 에서 복구할 수 없었나?**
A. enrichment 청크로 만들어지는 것은 `[초록]`·`[키워드]`·`[표]`·`[표 설명]`·`[그림 설명]` 뿐이고 **참고문헌 청크는 없다.** 그래서 Milvus 에 사본이 없었다. 대신 `extract_references()` 가 LLM 이 아니라 **패턴 기반**이고 그 입력인 본문이 `book_sections` 에 살아있어서, 섹션을 이어붙여 같은 규칙으로 다시 뽑을 수 있었다. Milvus·OCR·LLM 없이 Postgres 안에서 끝났고 비용은 0 이다.

**Q11. 참고문헌 dry-run 은 25.4% 였는데 실제는 왜 16.7% 인가?**
A. **표본이 무작위가 아니었다.** dry-run 의 500건은 `ORDER BY cnts_id LIMIT 500` 으로 뽑혀 ID 앞쪽에 몰려 있었고, 그 구간에 추출 성공률이 높은 문서가 편중돼 있었다. 그 비율을 전체 41,399건에 곱해 "1만 건"을 기대했지만 실제는 6,931건이었다. **정렬이 걸린 `LIMIT` 은 표본이 아니다** — 비율을 외삽하려면 `ORDER BY random()` 이 필요했다.

**Q12. 설계 spec 의 "문학 41편이 전부 `paper`" 전제는 어떻게 틀린 게 드러났나?**
A. dry-run 이다. 실제로 세어보니 `paper` 5건 / `book` 10건 / 이미 `literature` 26건이었고, 재기록 대상은 41편이 아니라 **15건**이었다. 증상(도서 검색에서 안 보임)만 보고 원인을 단정한 spec 이 틀렸던 것이다. 코드를 돌려 세기 전까지는 숫자를 확정하지 않는다는 원칙을 어긴 사례라 spec·plan·완료노트 세 곳을 모두 정정했다.

**Q13. SQLAlchemy `text()` 에서 `:param::jsonb` 는 왜 깨지나?**
A. SQLAlchemy 가 `:` 로 바인드 파라미터를 찾는데, Postgres 캐스트 연산자도 `::` 라서 파서가 혼동한다. `:ext::jsonb` 는 `syntax error at or near ":"` 로 실패한다. `CAST(:ext AS jsonb)` 로 쓰면 `:` 가 하나뿐이라 문제가 없다. 이걸 모르고 돌렸다가 **0행이 쓰이는 채로 "성공"한** 적이 있어, 복구 스크립트는 반드시 갱신 행 수를 출력하게 했다.

**Q14. 백업을 daily 와 weekly 로 나눈 이유는?**
A. 크기 차이 때문이다. 실측으로 DB 전체 4.8GB 중 `book_sections`(원문 100만행 이상)가 4.1GB 이고 `library_catalog` 는 381MB(압축 77MB)다. **실제로 날아간 것이 `library_catalog` 이고 작아서 매일 돌려도 부담이 없다.** 반면 원문은 재추출에 OCR 비용이 들어 반드시 지켜야 하지만 자주 바뀌지 않으니 주 1회로 충분하다. 덤프는 `.part` 로 받고 성공했을 때만 제자리로 옮긴다 — 중단된 덤프가 백업인 척하면 안 된다. weekly 전체 덤프에는 `search_history.query`(사용자 검색어 원문)가 들어가므로 `umask 077` 로 소유자만 읽게 한다.

**Q15. jsonb 에서 "값이 있는가"를 `?` 로 물으면 왜 안 되나?**
A. `extra ? 'references'` 는 **키가 존재하는가**만 본다. 값이 `[]` 여도 참이다. 적재 파이프라인이 추출 결과가 비어도 키를 기록하므로, 이 조건으로 "참고문헌이 없는 문서"를 고르면 원리상 빈 배열 문서가 통째로 빠진다. 존재가 아니라 **길이**를 물어야 한다 — `jsonb_array_length(coalesce(extra->'references','[]'::jsonb)) = 0`.

여기엔 덧붙일 교훈이 하나 더 있다. 리뷰에서 이 결함을 지적받고 **측정 없이 "보고한 수치가 과대하다"고 단정했는데, 실제로 세어보니 빈 배열은 0건이었다**(§3-5). 코드 경로가 존재한다는 것과 그 경로를 탄 데이터가 존재한다는 것은 다른 명제다. 리뷰 지적을 반영하는 것과 그 지적의 영향 범위를 확정하는 것도 다른 일이다 — 후자는 세어봐야 한다.

**Q16. 이 라운드에서 범위 밖으로 남긴 것은?**
A. 네 가지. (1) `app/api/admin.py` 의 Milvus expression injection — round01 부터 이월된 것으로, **도서관 대회 시연 이후로 미루기로 사용자가 지시**했다. (2) 논문 `summary` 29,006건 재생성 — 복원 소스가 없어 LLM 만 가능하고(4병렬 16시간) 초록이 채워져 화면은 정상이라 급하지 않다. (3) 참고문헌 2차 반영분 중 **한 줄에 여러 항목이 뭉친 문서는 항목이 합쳐진 채로** 저장됐다 — 줄 내부 분할을 넣으면 `--force` 로 덮어쓸 수 있게 플래그를 미리 만들어 뒀다. (4) `_BACKFILL_DOC_TYPES` 가 `admin.py`·`tasks.py` 에 중복 정의돼 있다.
