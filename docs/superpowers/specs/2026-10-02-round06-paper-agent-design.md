## 0. 사용자 요청 (paraphrase)

> 딥리서치에서 자연스럽게 이어져 논문 주제와 읽기 목록까지 만들고, 초안 작성까지 돕는 진짜 논문 에이전트 플랫폼으로 거듭나자. 태그라인은 "질문으로 시작해 연구 자동화까지". 지금 딥리서치 결과 화면이 논문 검색과 다른 스타일로 따로 열리는 것도 함께 정리하자. 10월 말 도서관 대회에서 연구 논문·도서 전문가들이 직접 써 본다 — 범위는 시연에 맞추되, 미리 돌린 가짜 화면이 아니라 실제로 동작하고 DBpia AI 아이디어와 견줄 차별점이 있는 제품 품질로. 보안은 뒤에 보강한다. (검토 때) 지금 딥리서치 기능은 있고, 그다음으로 연구 주제 만들기 등이 이어지는 것이다.

**한 줄 설계:** 딥리서치는 지금 그대로 두고, 보고서 끝 [이 연구 이어가기] 를 누른 딥리서치가 그 자리에서 연구 한 건으로 자란다 — 주제 → 읽기 목록 → 연구계획서. 이 이어가기 뒤의 흐름을 **연구 어시스턴트**라고 부른다. 단계마다 AI 가 후보를 내고 사용자가 골라 확정한다. 연구 공백 주장은 내세우기 전에 코퍼스 전체에서 스스로 반증 검사를 거친다.

**대회 한 줄:** "질문하면 답과 근거를 함께 주고, 필요하면 그 자리에서 더 깊게 조사해 연구계획서 초안까지 이어 준다."

## 2. 범위

**하는 것:** §4 의 여정 S0~S7, §5 의 단계별 생성, §6 의 데이터·API·작업 큐, §7 의 품질·윤리 장치, critic 보강(§5-1).

**딥리서치에서 바꾸지 않는 것(D15·D16):** 계획 프롬프트·계획 출력 형식, 계획 카드(PlanCard)·승인 API 의 요청 본문, 진행 패널·상태 배지·보고서 작성 진행 막대의 지금 표시, 보고서 본문, 보고서의 제외 논문 문구(`EXCLUDED_WHY`). 딥리서치에 더하는 것은 D15 의 다섯 가지다.

**하지 않는 것 (대회 뒤로):**
- 보충 탐색(딥리서치 재실행) — 종합 LLM 을 낭비하고 GPU 직렬 큐를 최대 25분 잡는다. 대신 LLM 없는 '주제로 넓히기' 검색 1회를 둔다(§5-4)
- 연구 단위 대화(새 RAG), 3단 작업공간, `/projects` 어휘
- PDF 업로드, 소유 확인·공유 링크, AI 배지
- 사용자 질문 열(격자의 사용자 정의 열), 개념 지도
- 여러 질문을 한 연구에 묶기(`research_work_runs`) — 테이블도 지금 만들지 않는다. 새 테이블은 나중에 만들어도 기존 칼럼을 고칠 일(ALTER)이 생기지 않는다
- 계획 프롬프트의 측면 나열 틀 정리(D16) — critic 합격선 미달의 원인이 계획이면 그때 다시 묻는다
- 북마크 정리, 논문 상세의 [담기], BibTeX/RIS 내보내기, 보고서 참고문헌 포매터를 백엔드로 옮기기
- 임베딩 512 절단 재처리 라운드 — 적재가 끝난 직후 돌리면 리허설 중 검색 결과가 바뀐다

## 3. 핵심 개념·용어

| 용어 | 정의 |
|---|---|
| **연구 어시스턴트** | 보고서 끝 [이 연구 이어가기] 뒤의 흐름 — 주제 → 읽기 목록 → 계획서. 이어가지 않은 딥리서치는 지금과 같다 |
| **연구 1건** | 이어간 딥리서치. id = 출발 잡 id, 사이드바에서는 그 딥리서치 줄 그대로다. 다른 질문은 새 딥리서치로 시작한다 |
| **단계 4개·관문** | 진행 막대는 ① 탐색(딥리서치 — 이어가기 때 이미 끝나 있다) ② 주제 ③ 읽기 목록 ④ 계획서. 어시스턴트의 관문은 주제 고르기 → 목차 승인 → 절 수락. 계획 승인은 딥리서치의 관문으로 지금처럼 남는다 |
| **핵심 개념** | 원 질문의 핵심 개념 2~5개(상한은 코드). 이어가기 때 원 질문·하위질문·보고서 절 제목에서 생성 1건으로 뽑고, 주제 단계 맨 위 칩으로 고친다. 공백 격자의 행과 선행연구 묶음에 쓴다 |
| **개념 소속** | 논문이 어느 핵심 개념에 드는가. 개념 임베딩(BGE-M3)과 논문 메타청크 벡터의 유사도로 FastAPI 가 계산해 `research_works.concept_members` 에 저장한다(§5-3) |
| **근거 장부** | 탐색 중 채택 논문이 쌓이고 critic 이 뺀 논문이 '뺌' 더미로 내려가는 딥리서치 화면의 시각화. 뺀 논문은 읽기 목록 단계 후보 서랍의 'critic 이 뺀 논문' 묶음에서 [되살리기] 로 후보에 넣는다 |
| **critic 기준 스위치** | 잡 파라미터 `critic_scope` — 0 = 지금 기준(프롬프트·입력을 글자 그대로 보존), 1 = 원 질문 기준(§5-1). 기본값은 0 이고 합격하면 1 로 바꾼다(D11) |
| **공백 칸** | 핵심 개념 × 방법 유형(코드 열거형 8개). 숫자 두 개를 따로 보인다 — ① 표본 수 "채택 48편 중 n편" ② 확인 검색 "적재분 N편 검색 상위 50편 중 임계 이상 m편" |
| **공백 판정** | m = 0 공백 후보 · 1~2 약한 공백 · 3 이상 공백 아님. 임계값은 제안값이고 06c 에서 보정한 뒤 이 spec 에 고정한다 |
| **주제 카드** | 슬롯 1개 = 생성 1건. 제목·연구 질문·근거 칩 3개 이상·[F#] 수치 문장·근거 중 최신 연도. 계보(빵부스러기)는 주제 단계에만 둔다 |
| **후보 / 읽기 목록** | 후보는 채택 근거·되살린 논문·주제로 넓히기·연관·[담기] 로 들어온다. 사용자가 체크한 것만 읽기 목록('담음')이 된다 |
| **들어온 경로** | 논문마다 저장된 값만으로 남긴다 — 하위질문, 그 하위질문 안 순위, 매칭 대목과 그 점수, critic 판정, 처음 채택된 회차(06a 뒤 잡부터), 되살림 여부 |
| **논문 특징** | 목적·방법 유형·대상·결과 + 각 값의 원문 인용구. 논문 단위 공용 캐시 |
| **[E#] / [F#]** | [E#] 은 호출마다 붙이는 로컬 인용 번호이고 서버가 `cnts_id` 로 바꿔 저장한다. [F#] 은 코드가 센 수치 마커다(06b 부터). 모델은 숫자를 직접 쓰지 않는다 |
| **문단 상태** | AI 제안 / AI 작성·수락 / 사용자가 고침 / 사용자 작성. 수락만 한 문단도 AI 작성으로 센다 |
| **코퍼스 스냅숏** | 계산할 때마다 저장하는 (적재분 N, 연도 범위, 시각). 바뀌면 '코퍼스 바뀜 — 다시 세기' 배지 |
| **다시 맞춤 필요** | 앞 단계를 바꿔도 뒤 단계를 지우지 않고 붙이는 배지 |
| **생성** | LLM 작업 한 건(핵심 개념·주제 카드·자식 카드·특징 추출·목차·절·문단) = `research_generations` 1행 = Celery 메시지 1개 = LLM 최대 3회(§6-3) |

**연구 어시스턴트 단계 공통(S2′~S7)**
- 단계는 주소 `?s=` 에 싣는다 — 새로고침·뒤로 가기·새 탭이 그대로 된다. `?s=` 가 없으면 탐색·보고서(S1·S2)를 연다(기존 링크 호환). 기존 `?at=&y=` 위치 복원은 그대로 동작한다. 사이드바에서 이어간 연구 줄을 누르면 그 연구의 현재 단계 `?s=` 로 간다.
- 끝난 단계는 진행 막대에서 눌러 언제든 다시 연다(① 탐색 = 보고서). 앞 단계를 바꿔도 뒤 단계는 지우지 않고 '다시 맞춤 필요' 배지만 붙인다.
- 자동 스크롤은 하지 않는다. 화면 밖이 바뀌면 "새 후보 3 ↓" 알약만 띄운다. `prefers-reduced-motion` 이면 즉시 전환한다.
- **온보딩 모달:** [이 연구 이어가기] 를 브라우저에서 처음 누를 때 한 번 띄운다. "탐색은 끝났습니다. 주제 → 읽기 목록 → 계획서 3단계를 거쳐 연구계획서 초안까지 갑니다" + 단계마다 한 줄 설명과 사용자가 결정할 것. 진행 막대의 [?] 로 다시 본다.
- **4단계 진행 막대:** 이어간 연구에만 보인다. `① 탐색 ② 주제 ③ 읽기 목록 ④ 계획서` + "2/4 단계 · 주제 고르는 중". 끝난 단계는 누를 수 있다. 사이드바의 이어간 연구 줄에는 지금의 진행 표시 옆에 같은 막대를 작게 넣는다. 이어가지 않은 딥리서치의 화면·사이드바 줄은 지금과 같다.
- 범위 띠(고정): "소장 KCI 적재분 N편(~YYYY) 기준 · 편수 추이는 동향이 아님".

**대회 '와' 장면 3개**
1. **근거 장부가 자라고 보고서가 연구로 접힌다.** 회차가 끝날 때마다 채택 논문이 장부에 떨어지고, critic 이 뺀 논문은 바래며 '뺌' 더미로 내려간다. [이 연구 이어가기] 를 누르면 본문이 접혀 요약 띠가 되고, 4단계 진행 막대가 나타나 ① 탐색이 채워진 채 ② 주제로 넘어가며, 사이드바 그 줄에도 단계 표시가 붙는다.
2. **빈칸을 누르면 AI 가 스스로 반증하고, 살아남은 빈칸이 주제가 된다.** 격자 칸 숫자가 특징 추출 도착마다 실제로 오른다. 표본 0편 칸은 점선으로 맥박친다. 칸을 누르면 서랍에서 확인 검색이 라이브로 돌고 "상위 50편 안에서 교차 논문을 찾지 못함 — 공백 후보 유지" 또는 "3편 발견 — 공백 아님으로 강등"(찾은 논문을 함께)으로 갈린다. 처음 살아남은 칸에서는 비어 있던 4번째 자리에 격자 카드가 날아든다(D8).
3. **근거 실로 쓰고 흔적을 남긴 채 받아들인다.** [이 절 쓰기] 를 누르면 문장이 흘러나온다. 번호가 맞는 마커는 저자·연도 칩으로 튀어 오르고, 틀린 마커는 취소선 뒤 사라지며 "인용 1개 버림"이 남는다. 근거 표시 없는 문장에는 점선, 뒷받침 점수가 낮은 문장에는 '뒷받침 약함'. [수락] 해도 문단 왼쪽 'AI 작성' 띠는 남고, 내보낸 Word 끝에 "AI 제안 9문단 중 수락 7·수정 2"가 찍힌다.

**시연 정직성 규칙**
- 움직임은 실제 이벤트가 도착할 때만 일어난다. 인위적 지연·하드코딩된 화면 데이터는 금지다.
- 방문자용 **예시 연구**는 미리 돌린 실제 기록이고 실행 시각·코퍼스 범위를 표시하며 읽기 전용이다(`research_works.is_example`, 쓰기 API 는 409). 예시 지정은 운영 스크립트로만 한다(§6-1).
- 시연자는 미리 진행해 둔 **자기 연구**(실제 기록)에서 확인 검색·절 쓰기를 라이브로 보인다.

**3분 동선**
1. 새 질문을 라이브로 계획 승인 → 탐색 시작(실측 1분 42초).
2. 그동안 미리 진행해 둔 연구에서 장면 2·3 을 라이브로 보인다.
3. 돌아와 새 질문의 보고서가 완료된 것을 보이고 [이 연구 이어가기] 로 장면 1 을 마무리한다.

### 5-1. 딥리서치 품질 보강 (06a — 화면·흐름 그대로)

운영 잡 `2a56f8b6`("컴퓨팅 자원") 결과에 남은 질 문제 가운데 과잉 제외와 무관 논문 잔존을 겨냥한다. 읽기 목록 후보가 딥리서치 채택 논문에서 오므로 어시스턴트 품질이 여기에 바로 달려 있다. 계획 일반 틀 문제는 계획 프롬프트를 건드려야 해서 이번 범위에서 뺀다(D16).

- **critic(`research_critique.yaml`, `critic.py`, `runner.py`, `state.py`):** 잡 파라미터 `critic_scope`(`DEFAULT_PARAMS` 에 더하고 기본 0)로 두 기준을 고른다.
  - 0 = 지금 기준. 프롬프트·입력을 글자 그대로 보존한다(옛 프롬프트를 지우지 않는다).
  - 1 = 원 질문 기준. 원 질문(`job.question`)을 함께 넘긴다. 충분·부족은 지금처럼 하위질문 기준으로 판정하고, **off_topic 은 "원 질문의 주제와 무관한 것(같은 단어 다른 뜻 포함)"으로만 좁힌다** — 하위질문에서 벗어났을 뿐 원 질문에 관련된 논문은 빼지 않는다.
  - 두 갈래 모두 출력 JSON 형식·파서·`exclude_off_topic` 동작은 그대로다. 예시는 넣지 않는다(함정 15). `research_jobs.params` 는 기존 JSONB 라 스키마 변경이 없다.
  - 판정·켜기 절차는 D11·§8. 켜는 것은 `DEFAULT_PARAMS` 기본값을 1 로 바꾸는 작은 커밋(06b 전)이다.
- **계획은 손대지 않는다:** `research_plan.yaml`·`planner.py`·`research_jobs.plan`·PlanCard·승인 API 요청 본문은 그대로 둔다. 핵심 개념은 이어가기 때 뽑는다(§5-2).
- **근거 장부 데이터(06a 백엔드, 06b 화면):** `state_snapshot` 은 탐색이 끝날 때(stage=explored) 한 번만 저장되고, `search` 이벤트는 그 회차의 critic 보다 먼저 나가 채택·제외를 모른다. 제외 서지는 이미 회차 끝 `critique` 이벤트와 search 단계 `result.rounds[].excluded_papers` 에 실린다. 빠진 채택 목록을 같은 두 곳에 `adopted_papers` 로 더한다 — 그 회차 끝 하위질문의 `evidence_ids` 순서 `[{cnts_id, rank}]` 에, 그 회차에 새로 채택된 논문은 `_paper_brief`(cnts_id·title·personal_author·pub_date)를 함께 싣는다. 그러면 탐색 중 재접속 때도 `steps[].result.rounds` 만으로 장부를 다시 그린다. 장부에는 [되살리기] 를 두지 않는다(§5-4).
- **서지 버그:** `services/search/paper_citation.py` `build_citation` 의 학술지 자리를 `publisher` → `series_title` 로 바꾸는 것만 한다(`series_title` 이 없으면 비우고 `publisher` 로 물러나지 않는다). 저자 규칙·UCI·영문 인용 등 논문 상세 CitationModal 출력의 나머지는 그대로다. 같은 서지 고정 예제(저자 3인·series_title·vol_issue·UCI)로 국문 인용의 "저자 (연도). 제목. 학술지, 권호." 부분이 `frontend/utils/reportDocument.ts` 의 `referenceText` 와 같은지 테스트한다. 계획서 참고문헌 함수(UCI·인용 쪽 포함 여부)는 06b 에서 정한다.

### 5-2. 이어가기·핵심 개념·주제 카드 (06a 이어가기·개념, 06b 보고서 씨앗, 06c 격자 카드·가지치기)

- **이어가기(`POST .../work/continue`, completed 잡만, 멱등):** 하위 라운드마다 하는 일이 늘어난다.
  - 06a: 연구 행(`research_works`, `owner_sid` = 누른 브라우저 ID)을 만들고, 채택 근거를 후보로 가져오고(§5-4), 핵심 개념 생성 1건을 넣는다.
  - 06b: 보고서 씨앗 주제 카드 생성 3건(06b 에서는 4번째도 보고서 씨앗)을 더 넣는다.
  - 06c: 후보 전원의 특징 추출 생성을 배경 우선순위로 더 넣는다.
  - 두 번 눌러도 행·후보·생성이 한 벌이다. round06 이전 잡도 같은 경로다.
- **핵심 개념(생성 1건, Qwen):** 입력은 원 질문 + 하위질문 + 보고서 절 제목, 출력은 2~5개(코드가 자르고 중복을 지운다). 재시도·넘김은 §6-3 공통 규칙을 따르고, 끝내 못 얻으면 비운 채 done — 주제 단계 맨 위에 '핵심 개념 넣기' 칩 입력을 보인다(다시 부르기는 `POST .../generations/{gid}/retry`). 사용자가 칩을 고치면 `PATCH .../work` 로 저장하고 FastAPI 가 개념 소속을 다시 계산한다(§5-3). 주제 카드는 개념을 기다리지 않는다(씨앗이 보고서 재료라서).
- **씨앗 고르기(순수 함수):** 보고서 `sections[].future`(근거 달린 향후 과제)와 critic 이 insufficient 로 판정한 하위질문(`trail[].verdict/note`)에서, 서로 다른 절을 우선해 겹치지 않게 3개를 고른다(06b·격자를 자른 경우 4개).
- **4번째 '공백 격자 카드' 자리(06c, D8):** 이어가기 때는 비워 두고 "격자 칸을 확인하면 채워집니다"를 보인다. 그 연구에서 확인 검색(§5-3)이 처음으로 공백 후보·약한 공백을 내면, 그 칸으로 grid_seed 카드 생성 1건을 자동으로 넣어 4번째 자리를 채운다. 그 뒤 통과한 칸은 [이 칸으로 주제 만들기] 로 사용자가 직접 만든다. 4번째 자리가 이미 차 있으면(06c 이전에 이어간 연구) 자동으로 만들지 않고 [이 칸으로 주제 만들기] 만 보인다(`research_topics` 의 (work_id, slot) 은 처음 4장에서 유일). 격자를 자르면 06b 처럼 보고서 씨앗으로 채우고 카드에 "격자 없음 — 보고서 씨앗"을 적는다.
- **카드 생성(Qwen):** 입력은 씨앗 + 그 씨앗에 묶인 근거 논문(로컬 [E#]) + 코드가 센 수치([F#]). 보고서 씨앗 카드의 [F#] 는 그 절의 채택 편수·근거 중 최신 연도·적재분 N, 격자 카드의 [F#] 는 그 칸의 n·m·적재분 N 이다. 출력은 제목·연구 질문·근거 칩·[F#] 수치 문장. 근거 칩이 3개 미만이면 §6-3 규칙의 '내용 검사 미달'로 다시 부르고, 그래도 미달이면 '근거 부족' 빈 슬롯으로 정직하게 보인다. 근거 중 최신 연도는 코드가 붙인다.
- **더 받기·다듬기:** [다른 방향] = 쓰지 않은 씨앗으로 2장 더. [더 구체적으로] = 그 카드 아래 자식 카드 3장(생성 3건, 계보 `parent_id`). [이 칸으로 주제 만들기](격자 칸). [직접 쓰기] = 사용자 카드(LLM 없음). [직접 고치기] = 카드의 제목·연구 질문을 사용자가 고친다 — `card` JSONB 만 바꾸고 origin 은 그대로다. `card.edited` 는 데이터로만 남기고(계보·공개 부록용) 카드 화면에는 출처 표시를 달지 않는다(D7·D9).
- **고르기:** 다음 단계는 고른 주제 하나로 진행한다. 나머지 카드는 지우지 않는다. 주제를 바꾸면 읽기 목록·계획서에 '다시 맞춤 필요'.
- **외부 확인:** 고르기 전에 카드 제목으로 KCI·RISS·DBpia 검색 링크를 보인다(새 탭, 질의만 넘긴다).
- **표현 통제:** "연구가 없다·전무·최초" 같은 표현은 후처리로 잡아 "소장 코퍼스 검색 상위 50편에서 찾지 못함" 투로 바꾼다. 연도별 편수 추이는 어디에도 근거로 쓰지 않는다(수집 단계의 연도별 1만 건 상한 때문).

### 5-3. 공백 격자 (06c — 자르는 순서 마지막)

- **행 = 핵심 개념.** 개념 소속은 FastAPI 에서만 계산한다(BGE-M3 가 lifespan 에 올라 있다). 개념이 done 인데 `concept_members` 가 비었거나 개념보다 오래된 때의 `GET .../grid`, 그리고 `PATCH .../work`(개념 변경) 때 개념 임베딩과 후보 논문의 메타청크 벡터 유사도(임계값 제안값)로 계산해 `research_works.concept_members` 에 저장한다. 프론트는 kind=concepts 생성이 done 이면 grid 를 다시 읽는다(§6-4) — 이어가기 직후 ?s=topics 의 첫 grid 조회는 개념 생성 전이라서다. 워커는 임베딩을 하지 않는다 — `celery-research-plan` 에는 GPU 도 모델 캐시도 없다(함정 17). LLM 을 쓰지 않는다.
- **열 = 방법 유형 8개(코드 열거형, 제안):** 실험·준실험 / 설문·조사 / 사례 연구 / 면담·관찰(질적) / 문헌 고찰·메타분석 / 내용·텍스트 분석 / 모델·시스템 개발 / 이론·개념 연구. 논문의 방법 유형은 특징 추출(§5-4) 결과로 정한다. 추출 전이거나 '미확인'인 논문은 칸에 세지 않고 "미분류 k편"으로 따로 보인다.
- **표본 수 n:** 채택 근거 중 그 칸에 드는 논문 수 — `GET .../grid`(동기, LLM 없음). 특징 추출이 끝날 때마다 워커가 저장된 개념 소속과 `paper_facets` 로 칸 숫자만 다시 세어 `grid` 이벤트를 보낸다(`concept_members` 가 비었으면 보내지 않는다).
- **확인 검색 m:** `POST .../grid/check`(동기, FastAPI — 하이브리드 검색과 리랭커가 있는 곳) — 질의 "개념 + 방법 유형"으로 코퍼스 전체를 하이브리드 검색해 상위 50편을 리랭커로 다시 매기고 임계값 이상을 센다. 결과·코퍼스 스냅숏을 `research_gap_checks` 에 저장하고 찾은 논문을 서랍에 펼친다. 확인은 사용자가 칸을 눌러 돌린다(와 장면 2) — 화면이 자동으로 돌리지 않는다.
- **확인 검색을 거치지 않은 칸은 주제 씨앗으로 쓰지 않는다.** 표본과 확인 검색은 문구·화면 모두에서 구분한다("채택 48편 중" ≠ "적재분 N편 검색 상위 50편").

### 5-4. 읽기 목록 (06b 기본, 06c 추출 열·넓히기·연관)

- **후보 갈래:**
  - ① 채택 근거 전체(최대 90편 — `state_snapshot.evidence`, 이어가기 때 가져온다).
  - ② 되살린 제외 논문 — 후보 서랍의 'critic 이 뺀 논문' 묶음(`trail[].excluded_papers`). 논문별 제외 사유는 저장된 곳이 없으므로(critic 출력은 번호 배열뿐이고 D16 으로 형식을 바꾸지 않는다) 어느 하위질문의 몇 회차에서 뺐는지와 그 회차의 critic note(`rounds[].note`)를 함께 보인다. [되살리기] 로 후보에 넣는다(origin `revived`, 보고서는 바꾸지 않는다).
  - ③ [주제로 넓히기] — 고른 주제 질의로 검색 1회(동기, LLM 없음).
  - ④ [연관 더 찾기] — 담은 논문마다 `find_related_papers`(한 편 씨앗 함수)를 부른다. 씨앗은 최대 5편, 결과를 합쳐 이미 후보·담음인 논문을 빼고 점수순으로 자른다(동기).
  - ⑤ 빠른검색 결과의 [담기](D17, origin `user`).
  - 보고서가 인용한 논문을 자동으로 '담음' 처리하지 않는다.
- **들어온 경로(`origin_ref` JSONB) — 저장된 값만 쓴다:** 하위질문(`subquestions[].evidence_ids` 소속), 그 하위질문 안 순위(`evidence_ids` 순서), 매칭 대목과 점수(`evidence_chunks`·`chunk_scores`), critic 판정(하위질문 verdict), 처음 채택된 회차(§5-1 의 `adopted_papers` — 06a 뒤 잡부터, 그 전 잡은 비운다), 되살림 여부. 넓히기·연관이면 질의·씨앗. 탐색 때만 있던 `rank_score` 는 저장되지 않으므로 쓰지 않는다. 행의 [경로] 팝오버로 3번 누르면 원문 쪽까지 간다(계획서 문장 → 칩 → 원문 쪽 → 들어온 경로).
- **사용자 동작:** 체크(담음/뺌), 행 메모, 묶음 이름, 순서. 담음 5편 이상이면 [목차 만들기].
- **논문 특징 추출(06c):** 논문 1편 = 생성 1건(Qwen). 목적·방법 유형(§5-3 열거형)·대상·결과 + 값마다 원문 인용구.
  - 입력은 DB 텍스트만 쓴다(워커가 읽는다): 초록 + 섹션 원문 앞부분(Qwen 16K 안에 들게 글자 예산은 계획에서 정한다). 섹션 원문이 없으면 섹션 요약 → 초록 순으로 물러나고, 요약을 입력으로 쓴 값은 '요약 기반(원문 미확인)'으로 표시한다.
  - 인용구는 공백을 정규화한 뒤 입력 원문의 부분 문자열인지 대조한다(`quote_ok`). 대조 실패·원문 미확인 값은 격자 집계에서 빼고 '미확인'으로 보낸다. 쪽 번호는 쪽 범위가 있는 원문에서 찾았을 때만 붙인다.
  - `paper_facets` 는 (`cnts_id`, `schema_ver`) 단위 공용 캐시 — 다른 연구도 같이 쓴다.
  - 순서: 읽기 목록 '담음' → 후보(하위질문 안 순위 순). 06c 부터 이어가기 때 배경으로 넣고, `POST .../extract` 는 06c 이전에 이어간 연구·새로 들어온 후보를 넣거나 특정 `cnts_id` 의 우선순위를 올린다.

### 5-5. 계획서 (06b 선행연구·연구 공백 2절, 06c 나머지 4절)

- **고정 6절:** 주제 · 연구 배경 · 선행연구 검토 · 연구 공백 · 연구 질문 · 방법 제안. 결과·논의 자리에는 "연구 후 직접 씁니다" 안내만 둔다. 진행 표시 'n/6절'은 그 절의 생성이 모두 끝난 절을 센다(선행연구 검토는 묶음이 모두 써져야 1절).
- **목차 만들기(생성 1건, gemma):**
  - 선행연구 하위 묶음 수는 서버 코드가 정한다 — 담은 논문 4편당 1개, 최소 1·최대 4개.
  - 묶음 배정도 서버 코드가 한다. 06c 는 개념 소속 → 방법 유형 순의 결정적 분할, 06b 는 개념 소속만(개념이 비면 하위질문 소속). 개념 소속은 목차 요청 때 FastAPI 가 계산해 생성 입력에 담는다(§6-3).
  - LLM 은 묶음 이름, 연구 질문 후보 3개, 방법 선택지의 한 줄 설명만 쓴다. 방법 선택지는 읽기 목록 논문의 방법 유형 가운데서만 코드가 뽑는다(06b 는 특징이 없어 선택지 없이 사용자 입력 칸).
  - 프론트는 서버가 준 묶음을 그대로 그리고, 사용자가 옮긴 결과만 저장한다.
- **목차 승인:** 사용자가 묶음 사이로 칩을 옮기고, 연구 질문 하나를 골라 다듬고, 방법을 고른 뒤 [목차 승인]. `research_proposals.version` 으로 동시 수정을 막는다(If-Match).
- **절 쓰기(생성 1건, gemma, 스트리밍):** 절마다 사용자가 [이 절 쓰기] 를 누른다(원클릭 전체 생성은 없다).
  - 선행연구 검토는 하위 묶음마다 생성 1건(절 키 `prior.g1`~`prior.g4`)이다. 묶음당 6편을 넘으면 하위질문 안 순위 → 담은 순서로 6편만 넣고, 나머지는 참고문헌 후보로만 남긴다.
  - 입력은 배정 논문 6편 이하 × (특징 + 원문 대목 1,200자)를 로컬 [E#] 로, 수치는 코드가 센 [F#] 으로. 06b 는 특징 자리를 초록으로 대신한다. 원문 대목 고르기(리랭커)는 생성을 넣는 FastAPI 가 해서 입력에 담는다(§6-3).
  - **연구 공백 절의 입력:** 확인 검색을 통과한 칸(`research_gap_checks` — 찾은 논문·m·스냅숏)이 있으면 그것이고(06c), 없으면(06b, 격자를 잘랐을 때) 보고서 `future` 와 critic 이 insufficient 로 본 하위질문 note 로 한정한다. 후자는 "소장 코퍼스에서 확인하지 않은 공백 후보" 문구로 고정하고 금지 표현 후처리를 거친다. 배정 논문은 씨앗에 묶인 근거 논문이다.
  - `chat_stream` 델타를 Redis 로 중계한다.
- **검증(서버, 생성 끝과 사용자 수정 뒤 `PUT` 때마다):**
  - 인용 번호: 로컬 [E#] 이 그 절의 입력 번호인지 확인하고 `cnts_id` 로 바꿔 저장한다. 틀린 번호는 버리고 "인용 n개 버림"을 남긴다(`bind_markers` 와 같은 규칙).
  - 근거 표시 없는 문장 → 점선 밑줄.
  - [F#] 밖의 숫자가 문장에 있으면 '확인 필요'(06b 부터).
  - 뒷받침 점수(06c): `POST .../sections/{key}/support`(동기, FastAPI 리랭커) — 문장과 그 문장이 인용한 대목의 점수가 임계값 아래면 '뒷받침 약함'. 모델에 준 대목은 문장 옆에서 펼쳐 볼 수 있다.
- **문단:** 상태 4가지를 저장한다. [다시] = 같은 입력으로 그 문단만 다시(생성 1건, `POST .../sections/{key}/paragraphs/{pid}/regenerate`). [고치기] = 직접 편집(상태 '사용자가 고침').
- **쓰지 않는 것:** 결과·논의, 예상 결과·가설 수치. 표본 규모 같은 수치는 사용자 입력 칸으로 둔다. 요청해도 만들지 않는다.

### 6-3. 작업 큐·LLM

- **큐:** 새 모듈 `app/workers/research_work_tasks.py` 를 `celery_app` 의 `include` 와 `task_routes` 둘 다에 등록한다. 큐는 설정값(`cfg.RESEARCH_PLAN_QUEUE`)이 아니라 **문자열 `"q_research_plan"` 으로 고정**한다(`task_routes` 와 `@celery_app.task(queue=…)` 둘 다). 회수기가 도는 celery-control·celery-beat 는 `RESEARCH_PLAN_QUEUE` env 를 받지 않아 설정값이면 `q_llm`(적재 워커)으로 떨어진다. `q_research_plan` 은 GPU 없음, 동시 2. compose 는 바꾸지 않는다.
- **생성 디스패처 — 전체에서 한 번에 1건:** 생성 1건 = Celery 메시지 1개. `q_research_plan` 의 두 자리 중 하나는 늘 딥리서치 계획(`tasks.plan_deep_research`)에 남긴다 — 생성이 두 자리를 채우면 새 딥리서치의 '계획 세우는 중'이 생성 1건 길이(최대 약 16~18분 — 호출 3회 × (300초 + 연결 10초) + 30초 = asyncio 데드라인 960초, Celery 하드 리밋 1080초)만큼 밀려 D15 를 깬다.
  - 생성을 넣는 API 는 늘 디스패치 태스크를 보낸다. 디스패치 태스크는 전역 advisory lock 안에서 running 생성 수를 세고, 1건 이상이면 아무것도 집지 않고 끝난다. 0건이면 모든 연구의 queued 생성 가운데 우선순위(사용자가 누른 생성 > 배경 특징 추출) → 오래된 순으로 1건을 `FOR UPDATE SKIP LOCKED` 로 집어 running 으로 바꾸고 실행한다. 부분 유니크 인덱스 `(work_id) WHERE status='running'` 은 이중 안전장치로 둔다.
  - 하나가 끝나면 queued 가 남았을 때(어느 연구든) 디스패치 태스크를 다시 보낸다. 생성 사이에 계획 요청은 남은 한 자리로 바로 돈다.
  - 처리량이 1건으로 묶이므로 동시에 여러 사람이 생성을 누르면 줄을 선다 — 대기 순번으로 보인다(아래).
- **재시도·넘김 공통 규칙:** 생성 1건 = `chat_full` 최대 3회. 주 모델 1회 → 해석 실패나 내용 검사 미달(예: 근거 칩 3개 미만)이면 주 모델 1회 더 → 전송 실패(`chat_full` 이 포기)면 곧바로, 해석·내용 미달이 두 번이면 다른 모델 1회 → 그래도 안 되면 kind 별 빈 결과(개념 비움, 카드 '근거 부족')로 done. `chat_full` 안의 일시적 실패 재시도는 이 횟수에 세지 않는다. `model` 에는 결과를 낸 모델을, `output.attempts` 에 시도 목록을 남긴다(공개 부록에 쓴다).
- **시간 한도:** 비스트리밍 호출은 timeout 300초를 명시한다. kind 별 asyncio 데드라인 = 최대 호출 수 × (호출 timeout + 연결 10초) + 여유, Celery soft/hard limit 은 그보다 크게 둔다(함정 19). 기존 회수 태스크 `tasks.reap_stale_research`(q_control, 기존 beat 일정)를 넓혀, running 이 hard limit + 60초를 넘은 생성을 failed 로 두고, queued 가 남았는데 running 이 없으면 디스패치 태스크를 `"q_research_plan"` 으로 다시 보낸다.
- **입력 만드는 곳:** 임베딩·리랭커·Milvus 가 필요한 입력(개념 소속, 목차의 묶음 배정, 절의 원문 대목 고르기)은 생성을 넣는 FastAPI 가 만들어 `research_generations.input` 에 담는다. 워커는 DB 텍스트 조회와 LLM 호출만 한다.
- **동시 실행 제한(딥리서치):** 기준은 잡의 `created_by`(브라우저 ID)다 — 요청 헤더에 기대지 않고, NULL 이면 제한하지 않는다. approve 와 retry 가 함께 쓰는 `_to_run_queue` 안에서, `created_by` 해시로 `pg_advisory_xact_lock` 을 늘 잡은 뒤 같은 브라우저의 approved·queued·running 잡을 센다(승인 안 하고 둔 계획은 세지 않는다). 있으면 429 `{code: "browser_active", job_id}`.
- **대기 순번(딥리서치):** research_jobs 에 승인 시각 칼럼이 없으므로 Redis ZSET `research:run_queue`(member = job id, score = 넣은 시각)를 쓴다. approve·retry 가 큐에 넣을 때 더하고, 워커가 잡을 집을 때·취소·종료 때 뺀다. 순번 = running 잡 수 + ZSET 에서 내 점수보다 앞선 원소 가운데 DB 상태가 지금 approved·queued 인 잡 수(빼기가 Redis 실패를 삼켜 끝난 잡이 줄에 남아도 순번이 밀리지 않게 읽을 때 거른다 — 지우지는 않는다). 다시 줄에 선 잡은 넣은 시각을 새로 쓴다(NX 아님). ZSET 에 없으면(Redis 재기동) `created_at` 순으로 근사한다. 기다리는 잡의 스트림은 기존 15초 하트비트 때 순번을 다시 세어 바뀌었을 때만 `queue` 이벤트(ahead, eta_sec)를 보낸다. 예상 시간 = 최근 완료분 소요 시간 중앙값 × 순번.
- **대기 순번(생성):** 디스패처가 전역 한 줄이므로 DB 로 센다 — 내 앞의 queued 생성 수(우선순위 → 오래된 순) + running 1건. 예상 시간 = kind 별 최근 완료분 소요 시간 중앙값의 합. 다른 연구의 생성이 앞에 있으면 "다른 연구 작업 진행 중"을 함께 보인다.
- **모델 라우팅(코드 상수 `WORK_MODEL_ROUTES`):** 핵심 개념·주제 카드·자식 카드·특징 추출 → Qwen(`VLM_BASE_URL`/`VLM_MODEL`, dev 의 config 에 이미 있다), 목차·절·문단 → gemma(`LLM_BASE_URL`/`LLM_MODEL`). 계획·critic·종합은 지금처럼 gemma. `llm_client` 의 `chat_full`(round07 — 재시도 포함)과 `chat_stream`(재시도 없음)에 호출별 `base_url`·`model` 을 더한다. 스트리밍 절의 연결 실패·5xx 넘김은 첫 델타 전에만 호출부가 한다.
- **Qwen 자리:** round07 로 OCR 이 8석을 다 쓰게 맞춰졌다(celery-cpu 4 × VLM 페이지 동시 2 = max-num-seqs 8). 스캔본이 몰리는 적재 구간에는 Qwen 생성이 vLLM 대기열에서 기다리고, 300초 timeout 뒤 gemma 로 넘어간다. round06 쪽 상한(생성 전역 1건)은 자리를 보장하지 않는다.

### 6-4. 실시간 이벤트

  - **06b 넘김(06a 최종 리뷰):** 06a 의 연구 SSE 는 하트비트 때 DB 를 다시 읽지 않고, 회수기가 오래 running 인 생성을 failed 로 바꿀 때 연구 채널에 알리지 않는다. 하드 리밋으로 디스패치 자식 프로세스가 죽거나 `celery-research-plan` 이 Recreate 되면 그 생성은 이벤트 없이 failed 가 되고, snapshot 을 읽은 뒤 구독이 붙기 전에 나간 done 이벤트도 다시 받을 길이 없다 — 화면은 새로고침 전까지 '진행 중'에 멈춘다. 06b 의 연구 화면 Task 가 하트비트 재동기화를 더한다: `stream_research` 처럼 하트비트마다 짧은 세션(`AsyncSessionLocal` — 요청 세션은 핸들러가 반환하면 닫힌다)을 열어 열린 생성(queued·running)의 (id, status) 집합을 읽고, 화면이 마지막으로 받은 값과 다르면 snapshot 을 다시 보낸다. 회수된 행이 열린 집합에서 빠져 15초 안에 드러나고 구독 전에 놓친 이벤트도 함께 풀린다. 회수기 publish(RETURNING 결과를 커밋 뒤 동기 Redis 로, 실패는 삼킴)는 지연만 줄이는 선택 사항이다.
- 이벤트: `generation`(kind·target·status·순번 — done 을 받으면 프론트가 해당 GET 을 다시 읽는다: concepts → `work`·`grid`, topic_card·refine → `topics`, facet → `reading`, outline·section·paragraph → `proposal`), `topic`(카드 도착), `facet`(논문 특징 도착), `grid`(칸 숫자), `section_delta`(문장 조각), `section_done`(검증 결과), `work`(phase·progress). 되살리기·넓히기·연관은 동기 응답으로 돌아오므로 SSE 가 필요 없다.
- 프론트는 순수 리듀서 `utils/workEvents.ts` 로 상태를 만든다(Vitest 대상).
- 탐색 중 근거 장부는 기존 연구 SSE 의 `critique` 이벤트(`adopted_papers`·`excluded_papers`)와 재접속 때 `steps[].result.rounds` 로 그린다. 대기 순번은 기존 연구 SSE 의 새 `queue` 이벤트다.
- **사이드바 갱신:** 사이드바는 서버 push 를 받지 않고, 진행 중 딥리서치가 있을 때만 30초 폴링한다(`AppSidebar.vue` `LIVE_STATUSES`·`POLL_MS`). 이어가기는 completed 잡에서 일어나므로 폴링이 이미 멈춰 있다. 그래서 `useResearchWork` 는 [이 연구 이어가기]·고르기·목차 승인 같은 사용자 동작 직후와 `work` 이벤트를 받을 때(짧게 묶어) `history.refresh('research')` 를 부르고, 06d 에서 사이드바 폴링 조건에 '진행 중 생성이 있는 이어간 연구'(history 응답 플래그)를 더한다.

## 7. 품질·윤리 장치

- **critic 새 기준은 합격해야 켠다(D11).** 미달이면 `critic_scope` 0(지금 기준)으로 둔 채 06b 이후를 그대로 진행하고, 계획 프롬프트 수정 여부를 사용자에게 묻는다. 오판은 읽기 목록의 [되살리기]·빼기로 고친다.
- **공백:** 표본과 확인 검색을 문구·화면 모두에서 나누고, 확인 검색을 거치지 않은 칸은 씨앗으로 쓰지 않으며, 확인하지 않은 공백은 "확인하지 않은 공백 후보"로만 쓰고, 금지 표현을 후처리하고, 편수 추이를 근거로 쓰지 않는다(§5-2·5-3·5-5).
- **인용이라는 말을 정확히 쓴다.** 인용 번호 검증은 번호가 맞는지까지다. 문장이 실제로 뒷받침되는지는 뒷받침 점수로 따로 보이고 모델에 준 대목을 펼쳐 볼 수 있게 한다. 대회 자료에 "문장마다 검증"이라고 쓰지 않는다.
- **원문 인용구·숫자:** §5-4·5-5. 수치는 [F#] 로만 들어간다.
- **범위:** 고정 띠, 산출물마다 코퍼스 스냅숏, 적재 뒤 바뀌면 '다시 세기' 배지.
- **AI 표시:** 문단 상태 4가지, 기여 비율은 문단 상태로 센다, 공개 부록.
- **생성 범위:** 원클릭 전체 생성 없음, 결과·논의·가설 수치 없음.
