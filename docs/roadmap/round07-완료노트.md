## 1. 왜 했나

사용자는 이 적재 파이프라인을 nanet 에 이식해 운영하면서 세 가지(병렬화·섹션 요약 뒤 버림·섹션 과대 분할)를 고쳤다. SKOVIX 도 같은 이유로 느린지 2026-10-01 운영에 GET 만 보내 쟀다(spec §0~1).

- **처리량** — 48시간 완료 11,510건(하루 5,755건). 막는 곳이 둘이고 번갈아 막는다.
  - 일반 PDF(ODL) 문서는 약 300건/h. `celery-embed` 1칸 안에서 논문 보강 LLM 을 기다리는 시간이 embed 의 46~59% 였다(표 9개 이상 문서 embed 중앙 24.6초).
  - 스캔본은 약 50건/h. 쪽을 하나씩 OCR 하는 추출 4칸이 막는다(쪽당 14초 ≈ VLM 요청 1건).
  - GPU 는 여유가 있었다(gemma 평균 5~8/16석, VLM 1.9/8석). 잡 API 의 ETA 856시간은 스캔본이 몰린 1시간 창 값이었다.
- **결함** — 데이터를 잃거나 버리는 경로가 여럿 있었다.
  - 텍스트 층에 스탬프 몇 글자만 남은 스캔본이 VLM 을 건너뛰어 섹션 0개로 영구 실패했다(10-01 「한국문학연구」 블록 281건, 함정 21번).
  - 섹션 0개를 추출 성공으로 넘기고 재시도는 요약부터 해, 같은 실패를 세 번 되풀이하며 시도를 다 썼다.
  - 문서 요약 입력을 균등 샘플링해 마지막 섹션이 늘 빠졌다. LLM·VLM 잘림을 감지하지 않았다(gemma 응답 5.3% — 대부분 표 해석, VLM 3.8%).
  - 문장 5개 이하 청킹 분기에 크기 상한이 없고 줄바꿈 폴백이 없었다(nanet 7128e09·493f760 미반영). `<br>` 를 본문 길이로 세어 빈 표 격자 쪽이 VLM 을 건너뛰었다.
  - 빈 본문으로 완료된 문서가 약 907건(추정)이었다. LLM 재시도 백오프가 없어 `llm_error` 264건이 영구 실패했다. ODL 에 타임아웃이 없었다.
  - 중복 체인이 논문 본문을 초록으로 덮는 경로(함정 16번)가 배포·재시작 때 열려 있었다.
- **실패분** — 1,099건(`not_found` 560 — '섹션 없음' 545 · '카탈로그 row 없음' 15, `extract_empty` 275, `llm_error` 264).

사용자는 "일단 pause 해둘테니깐 전수 바꾸자"로 18개 모두를 한 라운드에 고치기로 했다(10-01). 본 잡 `kci-full-236k` 는 그날 pause 했다(in-flight 0, 08:11 UTC).

2. **빈 본문 832건 — 끝남(2026-10-04)** — 783건이 다시 끝나 771건이 쪽당 150자를 넘었다(§5-4). 실패한 49건의 그룹은 아직 보지 않았다 — `no_text` 면 그대로 둔다.

5. **원본을 다시 받아야 하는 문서** — '카탈로그 row 없음' 15건(카탈로그 문제 — `catalog_missing.txt`)과 `extract_empty` 275건(원본 PDF 를 열 수 없다 — 잘린 다운로드로 보인다). 본 잡이 끝날 무렵 `book_id` 목록을 뽑아 원본을 다시 받고 retry 한다.
6. **적재가 끝난 뒤** — 임베딩 512 절단(spec §3), 표 설명·요약·VLM 잘린 쪽 과거분 재처리, 모델 교체(Qwen3.6-35B-A3B-FP8 로 OCR·텍스트 통합 검토), 추가 수집(메타 없는 PDF 28,074편 등), 같은 통권 PDF 중복 목록.
7. **운영 스택과 저장소 compose 맞추기** — 이번에도 운영 스택에 round07 만 얹었다. FLUX·PaddleOCR 주석, DB·MinIO 기본값, Milvus 파라미터, `VLM_MAX_PAGES_PER_DOC` 선언 차이가 남아 있다(round04a 완료노트 §8 과 같은 항목).
