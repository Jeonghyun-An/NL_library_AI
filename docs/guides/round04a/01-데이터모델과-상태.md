## 2. 구현 (클론코딩)

### 2.1 `models/research.py` — 잡·단계 테이블과 상태 상수

**책임.** 리서치 1건(질문 1개)이 `research_jobs` 1행이고, 그 실행 단계가 `research_steps` 행들이다. 그리고 워커와 API 가 함께 쓰는 상태 어휘 — `JOB_STATUSES`·`JOB_STAGES`·`RUNNABLE_STATUSES`·`TERMINAL_STATUSES`·`STEP_KINDS`·`STEP_STATUSES` — 의 단일 정본이다.

**왜 이렇게 짰나.**

- **`status` 와 `stage` 를 나눴다.** `status` 는 "지금 무슨 상태인가"(`created → planning → awaiting_approval → approved → running → completed | failed | canceled`, 재시도는 `failed → queued → running`), `stage` 는 "어디까지 끝냈는가"(`created → planned → explored → synthesized`)다. 한 컬럼이면 `failed` 하나로는 계획에서 죽었는지 종합에서 죽었는지 구분되지 않아, 종합 LLM 이 한 번 실패할 때마다 탐색(spec 설계값 5~7분)부터 전부 다시 돈다. 나눠 두면 종합이 실패해도 `stage='explored'` 와 `state_snapshot` 이 남고, `POST /api/research/{job_id}/retry` 가 잡을 `queued` 로 돌리면 워커가 탐색을 건너뛰고 종합만 다시 한다. `stage` 가 `NOT NULL DEFAULT 'created'` 인 것도 같은 이유다 — NULL 이면 재개 분기(`stage == "explored"`)가 조용히 빗나가 탐색부터 다시 돈다.
- **`state_snapshot` 은 종합만 다시 돌리기 위한 체크포인트다.** 워커가 탐색을 끝내고 `stage` 를 `explored` 로 넘기는 같은 조건부 UPDATE 에 `snapshot_state(state)` 결과(§2.5)를 싣는다. 이 컬럼을 읽는 곳은 워커의 `stage == "explored"` 분기 하나이고, 그 분기에 닿는 경로는 retry 엔드포인트 하나다. 자동 재개는 없다(spec §6 구현 시 변경).
- **실행 가능한 상태를 상수로 묶었다(`RUNNABLE_STATUSES`).** 실행 태스크(`run_deep_research`)의 선점(`_claim`)은 `approved`·`queued` 인 잡만 집는다. API 의 approve·retry 와 워커가 같은 상수 묶음을 import 하게 해, 한쪽이 다른 값을 써 넣어 워커가 그 잡을 영원히 건너뛰는 일을 막는다.
- **철자는 `canceled`(l 하나)다.** `models/ingest_job.py` 가 이미 그 철자다. 두 잡 계열이 철자를 달리 쓰면 상태 비교가 예외 없이 조용히 빗나간다.
- **진행 기록은 두 계층이다.** 굵은 단계는 `research_steps`(영구), 잔이벤트는 Redis pub/sub(휘발)으로만 흘린다 — 설계는 카운터 같은 초 단위 이벤트였지만 구현에서 흐르는 것은 `search`·`critique`·종료 이벤트뿐이다(spec §2-3 구현 시 변경). 남을 것과 몇 초 뒤 사라질 것을 한 테이블에 섞으면 보존 정책과 append/update 성격이 충돌한다(spec §2-3). 그리고 `research_steps` 는 **실행 이력**이지 보고서의 탐색 경로가 아니다 — 재시도마다 행이 쌓이고 시도를 구분하는 컬럼이 없다. 보고서의 탐색 경로 정본은 `report.trail`(그 보고서를 만든 시도만 담는다), 계획 목록 정본은 `research_jobs.plan`(사용자 승인본)이고, plan step 의 `result` 는 LLM 원안이다.
- **`result` 는 JSONB 한 컬럼에 kind 별 모양을 담는다.** API 가 가공 없이 넘기고 프론트가 kind 로 분기한다. 모양은 컬럼 위 주석이 정본이다 — `search` 행의 `verdict`·`note` 는 마지막 재검색 라운드의 값이다. `STEP_STATUSES` 의 `pending` 은 모델 기본값으로 남아 있지만, 워커는 행을 처음부터 `running` 으로 만든다(spec §3-2 구현 시 변경).
- **`(job_id, seq)` 는 인덱스가 아니라 유일 제약이다.** seq 는 잡 안에서 유일해야 하는데 DB 가 보장하지 않으면 중복 step 이 조용히 쌓인다. `job_id` 를 앞에 둔 것은 이 제약의 인덱스가 `job_id` 단독 조회에도 쓰이게 하기 위해서다(테스트가 컬럼 순서까지 고정한다).
- **부분 인덱스 `ix_research_steps_inflight`** 는 `status = 'running'` 인 행의 `updated_at` 만 담는다. 회수기(`reap_stale_research`)가 45분 넘게 `running` 인 step 을 찾는 조건과 같은 모양이다 — 끝난 step 은 인덱스에 들어가지 않는다.
- **`id` 는 애플리케이션이 만든다**(`default=uuid.uuid4`). `status` 도 파이썬 측 `default="created"` 다. 이 차이가 `create_all` 로 만든 운영 테이블에 흔적을 남긴다(§2.2).
- `created_by` 는 컬럼만 있고 아무도 채우지 않는다. 잡 목록 API 가 없어 다시 열려면 `job_id` 를 보관해야 한다 — round04b 착수 전 보강 목록이다(완료노트 §8, 리뷰 119).

**바뀐 점.**

- `680af5c`(Task 1 리뷰) — `(job_id, seq)` 를 인덱스에서 유일 제약으로 바꿨다. `result` 주석의 예시가 실제 모양과 달라 kind 별 실제 모양으로 고쳤다.
- `f1ba3e1`(Task 10) — `stage`·`state_snapshot` 컬럼과 `approved`·`queued` 상태, `RUNNABLE_STATUSES` 가 들어왔다. 계획 단계에서 닫히지 않은 구멍 둘을 구현 중에 찾은 것이다. approve 가 status 를 바꾸지 않아 워커의 선점이 늘 0행을 잡았고, `failed` 잡을 다시 집을 경로가 없어 `stage`·`state_snapshot` 은 쓰기만 하고 아무도 읽지 않는 컬럼이 될 뻔했다(retry 엔드포인트로 닫았다).
- `2bac7ee`(머지 전 리뷰) — 세 가지.
  - **`TERMINAL_STATUSES` 추가.** 리뷰의 high 5건(리뷰 0~4)은 전부 취소 덮어쓰기 한 원인이었다 — 취소한 잡이 `completed`·`awaiting_approval` 로 되살아났다(경위는 00 Q9, 워커 쪽 원인과 수정은 §2.36 ②). 고친 규칙은 "워커도 API 도 ORM 객체에 상태를 대입하지 않고, 기대한 이전 상태를 `WHERE` 에 건 조건부 UPDATE 로만 전이한다" 이다. 이 상수가 종료 상태의 집합이다 — 워커가 전이에 실패해 멈출 때 종료 이벤트를 보낼지, SSE 가 스트림을 닫을지를 이것으로 가른다. 종료 상태를 벗어나는 전이는 사용자의 `POST /retry` 가 `failed` 를 `queued` 로 되돌리는 것 하나뿐이다 — 모델 주석의 "워커도 API 도 이 상태를 다시 바꾸지 않는다" 는 이 예외를 적지 않았다. 전이 코드는 [04-오케스트레이션-워커-API.md](04-오케스트레이션-워커-API.md) §2.36 ②·§2.37 ① 에 있다.
  - **`STEP_KINDS` 에서 `critique` 삭제.** 자기점검은 별도 행이 아니라 그 하위질문의 `search` 행에 `verdict`·`note` 로 접히고, 라이브 진행은 SSE `critique` 이벤트로만 나간다. 허용값에만 있고 기록되지 않는 kind 는 프론트에 영원히 안 도는 분기를 만든다. 모델 테스트가 워커 소스를 AST 로 읽어 실제로 기록되는 kind 와 이 튜플이 같은지 고정한다(§2.9).
  - **docstring 과 `result` 주석 정정.** "steps 가 곧 보고서의 탐색 경로" 라는 초안 서술을 steps(실행 이력)·`report.trail`(탐색 경로 정본)·`job.plan`(계획 정본)의 구분으로 바꿨다 — 탐색 경로의 원천이 둘인데 어느 쪽이 정본인지 규칙이 없다는 지적이다(리뷰 80). `search` 의 `result` 에 `parse_failed`·`capped` 가 추가됐다.

```python
research_jobs  : 리서치 1건 (질문 1개 = 잡 1개)
research_steps : 의미 있는 단계 (계획 · 하위질문별 탐색 · 종합). 자기점검은 그
                 하위질문의 탐색 행에 접히고 SSE 이벤트로만 따로 나간다.

research_steps 는 진행 패널(실행 이력 — 재시도마다 행이 쌓인다)이다. 보고서의
탐색 경로 정본은 report.trail, 계획 목록은 research_jobs.plan 이다 — 재시도가
끼면 steps 에는 모든 시도가, trail 에는 그 보고서를 만든 시도만 남는다.
초당 갱신되는 잔이벤트(카운터 등)는 여기 쓰지 않고 Redis pub/sub 으로만
흘린다 — 입자가 다르고, 남을 것과 몇 초 뒤 사라질 것을 한 테이블에 섞으면
보존 정책과 append/update 성격이 충돌한다.
"""
import uuid

from sqlalchemy import (
    BigInteger, Column, DateTime, ForeignKey, Index, Integer,
    String, Text, UniqueConstraint, func, text,
)
from sqlalchemy.dialects.postgresql import JSONB, UUID

from models.book import Base

JOB_STATUSES = (
    "created", "planning", "awaiting_approval",
    "approved", "queued", "running",
    "completed", "failed", "canceled",
)
# status 는 "지금 무슨 상태인가", stage 는 "어디까지 끝냈는가"다. 둘을 한 컬럼으로
# 합치면 실패했을 때 어디부터 다시 할지 알 수 없다 — failed 하나로는 계획에서
# 죽었는지 종합에서 죽었는지 구분되지 않아 5~7분짜리 탐색을 매번 다시 돌게 된다.

# run_deep_research 가 선점(_claim)할 수 있는 상태. API 의 approve·retry 가 여기
# 없는 값을 써 넣으면 워커가 그 잡을 영원히 건너뛰고, stage·state_snapshot 은

STATUS_APPROVED = "approved"     # 사용자가 계획을 승인해 큐에 넣었다
STATUS_QUEUED = "queued"         # 실패한 잡을 재시도로 다시 큐에 넣었다
# 철자는 canceled(l 하나) 로 통일한다 — models/ingest_job.py 의 JOB_STATUSES·
# ITEM_STATUSES 가 이미 그 철자다. 두 잡 계열이 서로 다른 철자를 쓰면 상태
# 비교가 조용히 빗나간다.
STATUS_CANCELED = "canceled"
RUNNABLE_STATUSES = (STATUS_APPROVED, STATUS_QUEUED)
# 끝난 잡. 워커도 API 도 이 상태를 다시 바꾸지 않는다 — 워커의 상태 쓰기가
# 조건부 UPDATE 인 이유가 이것이다.
TERMINAL_STATUSES = ("completed", "failed", STATUS_CANCELED)

# 워커가 실제로 기록하는 kind 만 둔다. 쓰이지 않는 허용값은 프론트에 영원히

STEP_STATUSES = ("pending", "running", "done", "failed")


class ResearchJob(Base):
    __tablename__ = "research_jobs"

    id          = Column(UUID(as_uuid=True), primary_key=True, default=uuid.uuid4)
    question    = Column(Text, nullable=False)
    status      = Column(String(24), nullable=False, default="created", index=True)
    params      = Column(JSONB, nullable=False, server_default=text("'{}'::jsonb"))
    plan        = Column(JSONB)      # 사용자 수정이 반영된 하위질문 목록
    report      = Column(JSONB)

    # 탐색이 끝난 시점의 ResearchState 스냅샷. 종합만 재실행하기 위한 체크포인트다.
    # 이게 없으면 종합 LLM 이 실패할 때 5~7분짜리 탐색을 통째로 다시 돌려야 한다.
    # 읽는 쪽은 workers/research_tasks.py 의 stage == "explored" 분기이고, 그
    # 분기에 닿는 유일한 경로가 POST /api/research/{job_id}/retry 다.
    state_snapshot = Column(JSONB)
    last_error  = Column(Text)
    created_by  = Column(String(64))
    created_at  = Column(DateTime(timezone=True), server_default=func.now())
    started_at  = Column(DateTime(timezone=True))
    finished_at = Column(DateTime(timezone=True))

    __tablename__ = "research_steps"
    __table_args__ = (
```

### 2.2 `0005_research_jobs.py` — 모델과 같은 두 테이블을 만드는 마이그레이션

**책임.** `0004_doc_type_extra_ingest_jobs` 뒤에 `research_jobs`·`research_steps` 와 인덱스 둘(`ix_research_jobs_status`·`ix_research_steps_inflight`), 유일 제약 하나를 만든다. `downgrade` 는 FK 때문에 `research_steps` 부터 지운다.

**왜 이렇게 짰나 — 그리고 운영에서는 이 DDL 이 돌지 않았다.** 이 저장소에서 운영 스키마를 만드는 경로는 셋이다(함정 14번).

1. `app/main.py` lifespan 의 `Base.metadata.create_all` — 새 **테이블**을 모델에서 만든다.
2. 같은 lifespan 의 `ALTER TABLE … ADD COLUMN IF NOT EXISTS` 블록 — 기존 테이블에 컬럼을 넣는다.
3. Alembic.

`research_*` 는 1번이 만든다. lifespan 은 `models.research` 를 직접 import 하지 않지만, `main.py` 13행의 `from api.research import router` 가 모듈 로드 때 `models.research` 를 끌어오므로 lifespan 이 돌 때는 이미 `Base.metadata` 에 등록돼 있다. 새 이미지의 API 가 뜨는 순간 테이블이 생기고, 그 뒤에 `alembic upgrade head` 를 돌리면 `DuplicateTable` 로 죽는다. 그래서 운영 절차는 DDL 을 돌리지 않고 테이블을 눈으로 확인한 뒤 **`alembic stamp 0005_research_jobs`** 로 버전만 맞추는 것이다. 서버의 `alembic_version` 이 `0005_research_jobs` 인 것을 2026-09-23 에 확인했다. 그 전의 서버는 `0003` 에 머물러 있었는데 `0004` 가 만드는 객체는 이미 전부 실재했다(`ingest_jobs` 계열은 1번, `library_catalog.doc_type`·`extra` 는 2번 경로가 만들었다). 그래서 plan 초안의 `upgrade head` 는 `0004` 의 `add_column` 에서 `DuplicateColumn` 으로 죽는 상태였고, 절차를 "`0004`·`0005` 를 차례로 객체 확인 뒤 stamp" 로 고쳤다. `stamp` 는 마이그레이션 안의 데이터 백필(`op.execute(UPDATE …)`)까지 건너뛰므로 `0004` 의 KCI `doc_type` 백필은 잔량을 따로 세야 하는데, 그 확인(plan Task 11 Step 0-a)은 실행 기록이 없다. `0005` 에는 백필이 없다.

`create_all` 이 만든 테이블은 이 마이그레이션이 만들었을 테이블과 한 곳이 다르다. `create_all` 은 모델의 `server_default` 만 DB 기본값으로 만들고 파이썬 측 `default=` 는 반영하지 않는다. 모델이 `status` 를 `default="created"`(잡)·`default="pending"`(단계)로만 선언했으므로, `create_all` 이 만든 운영 테이블의 두 `status` 는 `NOT NULL` 이지만 **DB 기본값이 없다**(마이그레이션은 `server_default` 를 준다). 앱 경로는 항상 값을 채우므로 정상이고, 손으로 INSERT 할 때만 걸린다 — plan Task 11 Step 2 가 `research_jobs.status` 를 확인 항목으로 둔 이유다. 반대로 `stage`·`params`·`research_steps.result` 는 모델이 `server_default` 를 쓰므로 어느 경로로 만들어도 같다.

### 2.5 `state.py` — 실행 상태·깊이 파라미터·스냅샷

**책임.** 딥리서치 한 잡의 실행 상태(`ResearchState`)와 그 구성 요소(`SubQuestion`·`Evidence`·`Chunk`), 검색 결과 한 건의 타입(`HitRow`), 깊이 파라미터의 기본값과 검증(`merge_params`), 종합만 재실행하기 위한 스냅샷 왕복(`snapshot_state`·`restore_state`).

**왜 이렇게 짰나.**

- **단계 사이를 오가는 것은 이 모듈의 타입이다.** `ResearchState` 를 받아 갱신하는 것은 탐색 루프(`runner.explore_subquestion`)와 종합(`synthesizer.synthesize`)이고, 점검은 `SubQuestion`·`Evidence` 를, 탐색은 `HitRow` 를 주고받으며, 계획만 문자열 목록을 돌려준다(모듈 docstring 의 "각 단계는 ResearchState 를 받아 갱신해 돌려준다" 는 앞의 두 단계에만 맞다). 그래서 LLM·DB 호출만 대역으로 바꾸면 Celery·Redis·Milvus 없이 단계별로 테스트된다. LangGraph 를 들이지 않은 대신(spec §2-2 — 분기가 "한 번 더 돌까" 와 "승인 대기" 둘뿐이다) 단계 함수를 나중에 그래프 노드로 그대로 꽂을 수 있는 모양으로 둔 것이다.
- **깊이 파라미터는 하드코딩하지 않는다.** `DEFAULT_PARAMS` 7개를 `research_jobs.params` 로 덮어쓴다. 시연 직전에 값만 바꿔 짧게 돌릴 수 있어야 하기 때문이다 — Task 11 라이브 검증도 리허설용 축소값 `max_subquestions=3 · max_recheck=1 · per_subq_top_k=8` 로 돌았다(완료노트 §2). 기본값을 `MappingProxyType` 으로 잠근 이유는, 워커 프로세스가 이 모듈 전역을 한 번이라도 mutate 하면 그 오염이 프로세스 수명 내내 다음 잡들에 남기 때문이다. `merge_params` 는 항상 새 dict 를 돌려준다.
- **`merge_params` 가 유일한 검증 지점이다.** API 의 요청 모델은 `params: dict` 라 값 타입을 보지 않는다. 그래서 여기서 키·타입·범위를 전부 본다.
  - 모르는 키는 거부한다. 오타(`max_rechecks`)가 조용히 무시되면 시연 직전에 값을 바꿔도 안 먹는다.
  - `bool` 을 먼저 거른다. `bool` 은 `int` 의 서브클래스라 `isinstance(True, int)` 가 참이다.
  - float 파라미터(`citation_weight`)는 `int` 도 받는다. JSON 본문의 `1` 은 `int` 로 들어온다.
  - 하한이 있는 이유는 값마다 다르다. `chunks_per_evidence=0` 이면 청크 없는 근거가 생겨 인용칩 호버가 빈다. `citation_weight` 가 음수면 영향력 높은 논문의 점수를 깎아 순위가 조용히 뒤집힌다.
  - 상한이 있는 이유는 자해 방지다. 예컨대 `per_subq_top_k` 는 그대로 Milvus `AnnSearchRequest(limit=...)` 까지 흘러가므로, 상한이 없으면 요청 하나로 워커를 묶을 수 있다. 상한값은 시연 현실치 기준이다.
  - API 는 `ValueError` 만 422 로 바꾼다(`api/research.py`). 그래서 검증 실패는 반드시 `ValueError` 여야 하고, `_PARAM_BOUNDS` 와 `DEFAULT_PARAMS` 의 키 집합이 어긋나 `KeyError` 가 나면 500 이 된다 — 테스트가 두 키 집합이 같은지 고정한다.
- **`HitRow` 는 `state.py` 에 둔다.** 탐색(`explorer`)이 만들고 `citations.build_evidence` 가 받는 타입이다. `state.py` 는 패키지 안 어떤 모듈도 import 하지 않는 바닥 모듈이라, 공용 타입을 여기 두면 import 방향이 한쪽으로만 흐른다. `score`(리랭크 생값 — 화면에 유사도로 나간다)와 `rank_score`(피인용을 얹은 정렬용 값)를 나눈 이유는 §2.6 에 있다.
- **`Evidence.id` 는 보고서 안에서만 유효한 지역 ID(`E12`)다.** 서지(`meta`)는 DB 레코드에서 온다 — 논문 제목·저자·연도를 모델 출력에서 가져오면 언젠가 없는 논문을 만들어낸다(spec §4-1).
- **`LLM_VERDICTS` 는 값 기준으로 만든다.** `VERDICTS[1:]` 로 쓰면 튜플 순서만 바뀌어도 `sufficient` 가 빠져 모든 정상 판정이 "알 수 없는 verdict" 로 떨어진다(`a29c9a7`). 부분집합 테스트는 그 경우에도 통과했다.
- **`SubQuestion` 의 필드는 하나하나가 "보고서가 거짓말하지 않게" 하는 구분이다.**
  - `queries` — 시도한 검색어 이력. 러너가 재검색어를 고를 때 이미 시도한 검색어를 뺀다(리뷰 93·101).
  - `evidence_ids` — **하위질문 안의 순위순.** 자기점검은 앞 20편, 절은 앞 5편만 자르므로 순서가 곧 선택이다. 초기에는 채택 순서여서 재검색으로 찾은 보완 근거가 점검과 절에서 체계적으로 잘렸다(리뷰 18·27·40·67). 정렬은 러너가 라운드마다 한다 — 라운드마다 새로 찾은 근거 중 1위는 앞자리를 보장하고 나머지는 `rank_score` 순이다([04](04-오케스트레이션-워커-API.md) 의 `runner.py`).
  - `parse_failed` — 판정을 받지 못한 경우. 처음엔 "응답을 못 읽음" 만 뜻했는데, critic 호출의 타임아웃·5xx 가 하위질문 전체를 `failed` 로 만들어 이미 모은 근거가 절에서 빠지던 것을 리뷰가 잡아 **호출 실패도 여기로** 낮췄다(리뷰 20·24).
  - `failed` — 탐색이 예외로 중단됨. "근거 없음"(연구 결과)과 구분하지 않으면 보고서가 우리 쪽 장애를 "…에 대해서는 근거를 찾지 못했다" 로 써서 코퍼스에 자료가 없는 것처럼 보이게 만든다.
  - `capped` — `max_evidence` 상한 때문에 채택하지 못한 후보 수. 상한은 잡 전역 선착순이라 앞 하위질문이 채우면 뒤 하위질문이 굶는데, 이 필드가 없으면 그게 "근거를 찾지 못했다"(코퍼스 빈틈)로 보고되고 재검색이 헛돈다(리뷰 21·25·48). **굶김 자체는 고치지 않았다** — 하위질문별 예산은 절당 5편 상한과 함께 정할 제품 결정이라 이월했다(완료노트 §8).
  - `evidence_chunks`·`chunk_scores` — 한 논문이 여러 하위질문의 근거가 될 때 "이 하위질문은 그 논문의 어느 대목을, 어떤 점수로 찾았나" 를 따로 적는다. 이유와 쓰는 법은 §2.7 의 `chunks_for`·`link_chunks`.
- **`ResearchState` 에 없는 것도 설계다.** 보고서(`report`)는 두지 않는다 — `synthesize()` 반환값을 워커가 `research_jobs.report` 에 바로 쓴다. 항상 `None` 인 필드를 남기면 화면을 붙이는 쪽이 그걸 집어들고 조용히 빈 보고서를 그린다(`944f1d3`). `corpus_range` 는 코퍼스가 계속 자라므로 보고서에 고정 문구로 박지 않고 실행마다 질의해 넣는다.
- **스냅샷은 버전을 건너 쓰인다.** 재개는 "종합 수정 → 배포 → 옛 잡 retry" 처럼 쓰이므로, 스냅샷을 만든 코드와 읽는 코드가 다를 수 있다. 그래서 세 가지를 한다.
  - `snapshot_state` 는 필드를 손으로 나열하지 않고 `asdict` 로 담는다. 필드를 추가하고 나열에서 빠뜨리면 **재개한 잡에서만** 그 값이 조용히 기본값으로 돌아간다 — `parse_failed`·`failed` 로 이 모듈에서 실제로 반복된 실수다(떨어지면 재개한 잡의 한계 섹션이 비어 "한계 없음" 으로 보인다).
  - `restore_state` 는 `_known_fields` 로 dataclass 가 아는 키만 넘기고 모르는 키는 경고 로그를 남기고 버린다. 없는 키는 dataclass 기본값이 채운다. 필드가 빠지거나 이름이 바뀐 뒤 옛 스냅샷의 여분 키로 `TypeError` 가 나면 그 잡의 체크포인트는 영구히 못 쓴다.
  - `params` 는 기본값에 다시 얹는다(`merge_params`). 스냅샷 이후 추가된 파라미터를 읽는 쪽이 `KeyError` 로 터지지 않게 하고, 없어진 파라미터는 `merge_params` 가 "알 수 없는 파라미터" 로 거부하기 전에 걸러낸다.
- **남은 공백.** `Evidence` 는 여전히 손으로 나열한다 — `id` 는 스냅샷 dict 의 키라 빼고 `cnts_id`·`meta`·`chunks` 를 담는다. 필드 집합 테스트는 `SubQuestion`·`Chunk` 만 보므로 `Evidence` 에 필드를 추가하면 같은 실수가 가능하다. 그리고 재개(retry) 경로는 **라이브에서 한 번도 돌지 않았다** — 종합 실패가 자연발생하지 않았고 억지로 실패시키지 않았다. 단위 테스트만 체인의 세 구간을 덮는다(완료노트 §8).

```python
"""state.py — 딥리서치 실행 상태

각 단계는 ResearchState 를 받아 갱신해 돌려준다. Celery·Redis·Milvus 없이
테스트되고, 나중에 다른 오케스트레이션 런타임으로 옮겨도 그대로 쓴다.
"""
import logging
import math
from dataclasses import asdict, dataclass, field, fields
from types import MappingProxyType
from typing import NotRequired, TypedDict

log = logging.getLogger(__name__)

# 깊이 파라미터 — research_jobs.params 로 덮어쓴다.
# 시연 직전에 값만 바꿔 짧게 돌릴 수 있어야 하므로 하드코딩하지 않는다.
# MappingProxyType 로 감싼 이유: 워커 프로세스가 이 모듈 전역을 한 번이라도
# 실수로 mutate 하면 그 오염이 프로세스 수명 내내 남는다.
DEFAULT_PARAMS: MappingProxyType[str, int | float] = MappingProxyType({
    "max_subquestions": 6,
    "max_recheck": 3,
    "max_evidence": 60,
    "per_subq_top_k": 12,
    "chunks_per_evidence": 2,
    "citation_weight": 0.2,
    "min_evidence_per_subq": 5,
})

# (타입, 하한, 상한). ResearchCreate.params: dict 가 값 타입을 검증하지
# 않으므로 여기가 유일한 검증 지점이다 — 상한이 없으면 per_subq_top_k 같은
# 값이 그대로 Milvus AnnSearchRequest(limit=...) 까지 흘러가 요청 하나로
# 워커를 묶는 자해 경로가 된다. 상한은 시연 현실치 기준.
_PARAM_BOUNDS: dict[str, tuple[type, int | float, int | float | None]] = {
    "max_subquestions": (int, 1, 12),
    "max_recheck": (int, 0, 10),
    "max_evidence": (int, 1, 200),
    "per_subq_top_k": (int, 1, 50),
    "chunks_per_evidence": (int, 1, 5),
    "citation_weight": (float, 0.0, 1.0),
    "min_evidence_per_subq": (int, 0, 50),
}


def merge_params(override: dict | None) -> dict:
    """기본값에 override 를 얹는다. 모르는 키·타입·범위를 벗어난 값은 거부한다."""
    merged = dict(DEFAULT_PARAMS)
    for key, value in (override or {}).items():
        if key not in DEFAULT_PARAMS:
            raise ValueError(f"알 수 없는 파라미터: {key}")
        _validate_param(key, value)
        merged[key] = value
    return merged


def _validate_param(key: str, value: object) -> None:
    expected_type, lo, hi = _PARAM_BOUNDS[key]
    # bool 은 int 의 서브클래스라 isinstance(value, int) 를 그냥 쓰면 True 가 통과해버린다.
    if isinstance(value, bool):
        raise ValueError(f"파라미터 {key} 에 bool 값은 쓸 수 없다: {value!r}")
    if expected_type is int and not isinstance(value, int):
        raise ValueError(f"파라미터 {key} 는 int 여야 한다: {value!r}")
    if expected_type is float and not isinstance(value, (int, float)):
        raise ValueError(f"파라미터 {key} 는 float 여야 한다: {value!r}")
    # NaN 은 아래 범위 비교가 전부 False 라 그대로 통과한다. 표준 json.loads 가
    # NaN 리터럴을 받아들이므로 실제로 들어오고, JSONB 가 거부해 422 가 아니라 500 이 된다.
    if isinstance(value, float) and not math.isfinite(value):
        raise ValueError(f"파라미터 {key} 는 유한한 수여야 한다: {value!r}")
    if value < lo or (hi is not None and value > hi):
        raise ValueError(f"파라미터 {key} 가 허용 범위({lo}~{hi})를 벗어났다: {value!r}")


class HitRow(TypedDict):
    """검색 결과 1건 — Milvus 검색 계층(explore)이 만들어 citations.build_evidence 로 넘긴다.

    score 와 rank_score 를 나눈 이유: 순위용 혼합값은 1.0 을 넘을 수 있어
    유사도로 표시하면 141% 같은 값이 나간다. score 는 생값 그대로 두고 순위는
    rank_score 로만 매긴다(explorer.rank_hits).
    """
    book_id: str
    chunk_id: str
    text: str
    page_start: int
    page_end: int
    score: float                      # 리랭킹(없으면 RRF) 생값 — 화면에 유사도로 나간다
    rank_score: NotRequired[float]    # 피인용을 얹은 정렬용 값 — rank_hits 가 채운다

    text: str

    page_end: int

    cnts_id: str

VERDICTS = ("pending", "sufficient", "insufficient")

@dataclass
class SubQuestion:
    idx: int
    text: str
    queries: list[str] = field(default_factory=list)   # 시도한 검색어 (재검색 이력)
    # 이 하위질문 안의 순위순 — critic(20편)과 절(5편)이 앞에서 자르므로 순서가 곧
    # 선택이다. runner 가 라운드마다 다시 정렬한다.
    evidence_ids: list[str] = field(default_factory=list)
    verdict: str = "pending"
    # 판정을 받지 못해(응답 해석 실패·호출 실패) 점검이 사실상 건너뛰어진 경우
    parse_failed: bool = False
    # 탐색이 예외로 중단됨 — "근거 없음"(연구 결과)과 구분한다. 구분이 없으면
    # 보고서가 시스템 장애를 "…에 대해서는 근거를 찾지 못했다"로 써서, 우리 쪽이
    # 터진 것을 코퍼스에 자료가 없는 것처럼 보이게 만든다.
    failed: bool = False
    note: str = ""                                      # 자기점검 판단 근거
    # max_evidence 상한 때문에 채택하지 못한 후보 논문 수. failed 와 같은 이유로
    # 따로 둔다 — 없으면 시스템 상한이 "근거를 찾지 못했다"(코퍼스 빈틈)로 보고된다.
    capped: int = 0
    # 근거 ID → 이 하위질문 검색에서 매칭된 청크 ID(점수순). 한 논문이 여러
    # 하위질문에서 재사용되면 Evidence.chunks 는 그 합집합이라, 이게 없으면 critic
    # 발췌·절 요약·호버가 처음 채택한 하위질문의 대목으로 고정된다.
    evidence_chunks: dict[str, list[str]] = field(default_factory=dict)
    # 청크 ID → 이 하위질문의 검색어로 받은 점수. 한 청크를 여러 하위질문이 매칭하면
    # Chunk.score 는 하나뿐이라, 이게 없으면 재검색 비교·발췌·절 호버가 다른 하위질문의
    # 점수로 돈다(0.95 로 찾은 대목이 남의 0.2 로 비교돼 밀려난다).
    chunk_scores: dict[str, float] = field(default_factory=dict)


@dataclass
class ResearchState:
    job_id: str
    question: str
    params: dict
    subquestions: list[SubQuestion] = field(default_factory=list)
    evidence: dict[str, Evidence] = field(default_factory=dict)
    # 실행 시점의 수록 범위 — 코퍼스가 계속 자라므로 보고서에 고정 문구로
    # 박지 않고 매번 질의해 넣는다. {"from": "2002", "to": "2026", "n_papers": 72054}
    corpus_range: dict | None = None
    # 보고서는 여기에 두지 않는다. synthesize() 가 반환값으로 넘기고 Celery
    # 태스크가 research_jobs.report 에 바로 쓴다. 항상 None 인 report 필드를
    # 남겨두면 화면을 붙이는 쪽이 그걸 집어들고 조용히 빈 보고서를 그린다.


def snapshot_state(state: ResearchState) -> dict:
    """탐색이 끝난 상태를 JSONB 에 넣을 수 있는 형태로 만든다.

    필드를 손으로 나열하지 않고 asdict 로 담는다 — 필드를 추가하고 여기에
    빠뜨리면 재개한 잡에서만 그 값이 조용히 기본값으로 돌아간다. 이 모듈에서
    parse_failed·failed 로 실제로 반복된 실수다.
    """
    return {
        "question": state.question,
        "params": state.params,
        "corpus_range": state.corpus_range,
        "subquestions": [asdict(s) for s in state.subquestions],
        "evidence": {
            eid: {
                "cnts_id": ev.cnts_id, "meta": ev.meta,
                "chunks": [asdict(c) for c in ev.chunks],
            }
            for eid, ev in state.evidence.items()
        },
    }


def _known_fields(cls: type, raw: dict, where: str) -> dict:
    """스냅샷 한 항목에서 dataclass 가 아는 키만 남긴다.

    재개는 "종합 수정 → 배포 → 옛 잡 retry" 처럼 버전을 건너 쓰인다. 필드가
    빠지거나 이름이 바뀐 뒤 옛 스냅샷의 여분 키로 TypeError 가 나면 그 잡의
    체크포인트는 영구히 못 쓴다. 없는 키는 dataclass 기본값이 채운다.
    """
    names = {f.name for f in fields(cls)}
    extra = sorted(set(raw) - names)
    if extra:
        log.warning("[research] 스냅샷의 모르는 키를 무시한다 — %s: %s", where, extra)
    return {k: v for k, v in raw.items() if k in names}


def restore_state(job_id: str, snap: dict) -> ResearchState:
    """snapshot_state 의 역. 종합 단계부터 재개할 때 쓴다.

    parse_failed·failed 가 왕복에서 떨어지면 재개한 잡의 한계 섹션이 조용히
    비고, 보고서가 "한계 없음"으로 보인다.

    params 는 기본값에 다시 얹는다. 스냅샷 이후 추가된 파라미터를 읽는 쪽이
    KeyError 로 터지지 않게 하고, 없어진 파라미터는 merge_params 가 거부하기
    전에 걸러낸다.
    """
    raw_params = snap.get("params") or {}
    retired = sorted(set(raw_params) - set(DEFAULT_PARAMS))
    if retired:
        log.warning("[research] 스냅샷의 없어진 파라미터를 무시한다 — %s", retired)
    st = ResearchState(
        job_id=job_id, question=snap["question"],
        params=merge_params({k: v for k, v in raw_params.items() if k in DEFAULT_PARAMS}),
        corpus_range=snap.get("corpus_range"),
    )
    st.subquestions = [
        SubQuestion(**_known_fields(SubQuestion, sq, "subquestion"))
        for sq in snap["subquestions"]
    ]
    st.evidence = {
        eid: Evidence(
            id=eid, cnts_id=e["cnts_id"], meta=e["meta"],
            chunks=[Chunk(**_known_fields(Chunk, c, "chunk")) for c in e["chunks"]],
        )
        for eid, e in snap["evidence"].items()
    }
    return st
```

### 2.6 `scoring.py` — 피인용 연차 정규화와 점수 혼합

**책임.** 발행 연월 문자열에서 연도를 읽고(`parse_pub_year`), 피인용을 연간 값으로 정규화하고(`impact_per_year`), 리랭크 점수에 영향력을 보조 가중으로 얹는다(`blend_score`). 호출부는 `explorer.rank_hits` 다.

**왜 이렇게 짰나.**

- **피인용 생값을 쓰면 오래된 논문이 항상 이긴다.** 2026년 기준 2002년 논문은 25년(발행연도 포함 +1) 동안 쌓았고 2024년 논문은 3년이다. "최근 동향" 을 물었는데 2000년대 초 논문만 올라오지 않으려면 연간 피인용으로 나눠야 한다. 테스트의 예: 피인용 50회인 2002년 논문은 연 2.0, 40회인 2024년 논문은 연 13.3 — 생값 순서가 뒤집힌다.
- **분모의 +1 과 `max(1, …)`.** 발행 당해 연도를 1년으로 센다. 같은 해 논문이 0으로 나뉘지 않고, 발행연도가 `now_year` 보다 뒤인 잘못된 값도 1년으로 눌린다.
- **모르는 것은 0이다.** 연도를 못 읽거나 피인용이 `None`·0 이면 영향력 0 — 혼합식에서 가산이 없을 뿐 감점도 아니다. `kci_citations` 는 nullable 컬럼이라 `None` 검사가 비교(`<= 0`)보다 **먼저** 와야 한다. 순서가 바뀌면 `TypeError` 다.
- **`log1p` 로 감쇠하고 곱셈으로 얹는다.** 코드는 아래 한 줄이다. 영향력이 100배라고 점수가 100배가 되면 의미 유사도가 뜻을 잃고 "많이 인용된 논문 목록" 이 된다. `log1p` 는 영향력 0 에서 정확히 0 이라 "영향력 없음 = 리랭크 점수 그대로" 가 성립한다. 곱셈 형태라서 리랭크 점수가 주(主)이고 영향력은 그 위의 배율이다 — 리랭크 점수가 0 인 청크는 피인용이 아무리 많아도 0 이다. `weight` 는 `citation_weight`(0~1, §2.5)다.
- **정규화는 순위에만 쓴다.** 화면에는 생값(`피인용 41회`)을 그대로 보여준다 — 사용자가 검증할 수 있어야 한다(spec §4-4). 같은 이유로 혼합값은 `HitRow.score` 를 덮지 않고 `rank_score` 에 따로 둔다. 혼합값은 1.0 을 넘는다 — 리랭크 0.8·연 13.3회·가중 0.2 면 약 1.226 이라, 이 값을 유사도로 그리면 123% 가 나간다. `grade`(KCI 등재 구분)는 서지로 싣기만 하고 순위에는 쓰지 않는다.
- **`now_year` 는 키워드 인자로 주입한다.** 테스트가 연도에 묶이지 않고, 호출부(`explorer`)가 `datetime.now().year` 를 넘긴다.

혼합식 한 줄:

```python
    return rerank_score * (1.0 + weight * math.log1p(impact))
```

**바뀐 점.** `2d2221a` 에서 죽은 방어 코드를 정리했다 — 음수가 될 수 없는 `impact` 에 걸던 `max(0.0, impact)` 를 지웠고, `not kci_citations` 를 의도가 드러나는 `kci_citations is None` 검사로 바꿨다. docstring 의 연수 계산(24년 → 25년, 발행연도 포함)도 코드에 맞췄다. `a168e1d` 에서 `None` 피인용 테스트가 붙었다. 그 뒤로 바뀌지 않았다.

**파일**: `app/services/research/scoring.py` — 전체 36줄

```python
"""scoring.py — 근거 순위 계산 (순수 함수)

피인용을 생값으로 쓰면 오래된 논문이 항상 이긴다. now_year 기준 2002년
논문은 25년간(+1, 발행연도 포함) 쌓았고 2024년 논문은 3년이다. 연간
피인용으로 정규화해야 "최근 동향" 질문에서 2000년대 초 논문만 올라오지
않는다.

화면에는 생값(피인용 41회)을 그대로 보여준다 — 정규화는 순위에만 쓴다.
"""
import math
import re

_YEAR = re.compile(r"(19|20)\d{2}")


def parse_pub_year(pub_date: str | None) -> int | None:
    """'2008-06' · '200806' · '2008' → 2008. 해석 불가면 None."""
    m = _YEAR.search(pub_date or "")
    return int(m.group(0)) if m else None


def impact_per_year(kci_citations: int | None, pub_year: int | None, *, now_year: int) -> float:
    """연간 피인용. 연도를 모르거나 피인용이 없으면 0."""
    if kci_citations is None or kci_citations <= 0 or pub_year is None:
        return 0.0
    years = max(1, now_year - pub_year + 1)
    return kci_citations / years


def blend_score(rerank_score: float, *, impact: float, weight: float) -> float:
    """리랭킹 점수를 주로 하고 영향력을 보조 가중으로 얹는다.

    log1p 로 감쇠시키는 이유: 영향력이 100배여도 점수가 100배가 되면
    의미 유사도가 의미를 잃고 "많이 인용된 논문 목록"이 되어버린다.
    """
    return rerank_score * (1.0 + weight * math.log1p(impact))
```

### 2.7 `citations.py` — 근거 조립·하위질문별 청크·인용 마커 검증

**책임.** 검색 결과를 논문 단위 근거로 묶고(`build_evidence`), 재사용 근거에서 하위질문마다 제 몫의 대목을 기록·조회하고(`link_chunks`·`chunks_for`), 모델이 단 인용 마커를 검증·정규화하고(`bind_markers`), 인용이 이미 구조로 정해진 자리에서 마커를 걷어낸다(`strip_markers`). 이 계층에서 가장 중요한 파일이다 — 모델이 없는 `[E99]` 를 뱉었을 때 칩이 만들어지지 않는 것이 인용 무결성의 마지막 방어선이다.

**왜 이렇게 짰나 — 인용은 두 갈래다.**

- **구조적 인용(대표 논문 요약).** 불릿 하나가 논문 하나라, 어느 논문이 실리고 칩이 어디를 가리키는지는 코드가 정한다. 다만 절의 논문 여러 편을 한 호출에 넣고 번호별로 요약을 받으므로, **요약 문장이 그 논문 내용인지는 모델의 번호 배정(추론)에 달려 있다.** 논문별 호출은 호출 수가 절당 최대 5배라 이번에 하지 않았고, 오배정 비율도 재지 않았다(spec §4-1 구현 시 변경). 그래서 이 자리는 "절반만 구조" 라고 적는다.
- **마커 인용(도입 문단·향후 과제).** 여러 논문을 가로지르므로 구조로 못 정한다. 모델이 `[E3]` 로 달게 하고 여기서 전수 검증한다. 해석 안 되는 마커는 조용히 통과시키지 않고 지운 뒤 개수를 보고한다.

**근거 ID 는 `state.evidence` 를 소유한 쪽이 붙인다.** `build_evidence` 는 같은 논문의 청크를 근거 하나로 묶고 점수순 `chunks_per_evidence` 개만 남기며, 카탈로그에 서지가 없는 청크는 버린다(서지를 못 보여주면 근거가 아니다). 반환은 `id=""` 인 `list[Evidence]` 이고 순서는 hits 안에서 각 논문이 처음 등장한 순서다. 번호는 러너가 `state.evidence` 에 넣는 순간 `evidence_id(len(state.evidence))` 로 붙인다. 초안은 `build_evidence` 가 `start_index` 로 번호를 붙였는데 plan 의 러너가 그걸 버리고 다시 붙이게 돼 있어서, 테스트가 **버려지는 쪽만** 덮고 있었다(`2d2221a`). 러너는 같은 논문이 다른 하위질문에서 다시 나오면 새 번호를 만들지 않고 기존 번호를 재사용한다 — 안 그러면 한 논문이 `E3`·`E17` 로 갈라져 칩 두 개가 같은 출처를 다른 번호로 가리킨다. 결과적으로 **근거 번호는 `E1…En` 으로 빈틈없이 이어진다.** 이 사실이 아래 검증 집합 문제의 원인이 된다.

**`link_chunks`·`chunks_for` — 재사용 근거의 대목과 점수를 하위질문별로.** 번호를 재사용하면 새 문제가 생긴다. 초안은 처음 채택한 하위질문의 청크만 남겨서, 다른 하위질문의 자기점검 발췌·절 요약·칩 호버가 그 하위질문과 무관한 대목을 썼다(리뷰 19·26·66). 그래서 저장소와 가리킴을 나눴다.

| 자료 | 뜻 |
|---|---|
| `Evidence.chunks` | 그 논문에서 매칭된 적 있는 청크의 저장소(합집합). 청크마다 점수 하나 — 매칭한 하위질문 중 최고값 |
| `SubQuestion.evidence_chunks` | 이 하위질문이 그 근거에서 가리키는 청크 ID(점수순, 최대 `chunks_per_evidence`) |
| `SubQuestion.chunk_scores` | 이 하위질문의 검색어로 받은 청크별 점수 |

`link_chunks` 는 이번 검색에서 매칭된 청크를 이 하위질문의 몫으로 기록한다. 이미 가리키던 청크와 새 청크를 **이 하위질문의 점수로** 비교해 상위 `limit` 개로 갈아끼운다. 새 청크는 이 하위질문이 가리킬 때만 저장소에 더하고, 갈아끼워진 청크는 다른 하위질문이 가리킬 수 있어 저장소에서 지우지 않는다(보고서에는 지금 가리키는 것만 싣는다 — [03-보고서-종합과-인용.md](03-보고서-종합과-인용.md)). `chunk_scores` 가 필요한 이유는 테스트의 시나리오 그대로다 — 하위질문 A 가 청크 `P-c1` 을 0.2 로, B 가 같은 청크를 0.95 로 찾았다. B 의 재검색이 `P-c2` 를 0.5 로 찾으면, 청크 점수 하나만 보는 구현은 B 의 0.95 짜리 대목을 A 의 0.2 로 비교해 0.5 짜리에 밀어낸다(완료노트 §4 "근거 순서·청크·상한").

`chunks_for` 는 그 하위질문이 가리키는 청크를 그 하위질문의 점수를 담은 **사본**(`dataclasses.replace`)으로 준다. 원본을 넘기면 저장소의 최고값 점수가 다른 하위질문의 발췌·호버에 나가고, 받은 쪽이 점수를 고치면 저장소가 오염된다. 매핑이 없는 옛 스냅샷은 청크 전부를, 점수 기록이 없는 옛 스냅샷은 `Chunk.score` 를 준다 — §2.5 의 스냅샷 진화 내성과 같은 이유다.

**`bind_markers` — 괄호 하나를 통째로 해석한다.** 프롬프트는 "`[E3]` 형태만" 이라고 지시하지만 모델은 묶음·범위·전각 괄호·소문자·0패딩을 낸다. 초안의 정규식은 `[E\d+]` 단일형만 잡아서, `[E2, E99]` 는 매칭되지 않아 **검증도 제거도 안 된 채** 본문에 실렸고, `[E01]` 은 매칭되지만 `'E01' ∉ valid_ids` 라 맞는 인용이 "없는 번호" 로 지워지며 오보됐다(리뷰 17·36). 라이브 검증 스크립트도 같은 단일형으로 세서 "미해석 0" 이 이런 표기가 없다는 증거가 되지 못했다. 지금은 세 단계다.

**① 괄호를 잡는다.** 반각 `[ ]` 와 전각 `［ ］`·`【 】` 을 모두 잡되, 괄호 안에 다른 괄호나 개행이 있으면 잡지 않는다 — 짝 없는 `[` 하나가 문단을 삼키지 않게 하기 위해서다. 첫 그룹은 괄호 앞 공백이다(지울 때 함께 지운다).

```python
_BRACKET = re.compile(r"([ \t]*)[\[［【]([^\[\]［］【】\n]*)[\]］】]")
```

**② 인용처럼 생겼는지 본다.** 영문자·숫자·소수점에 붙지 않은 `E`(대소문자) 뒤에 숫자가 오면 인용 후보다. `[ICE 2019]`(E 가 영문자에 붙음)·`[표 1]`(E 없음)은 인용이 아니다. 숫자·소수점 뒤의 `e` 는 지수 표기다 — `[1.2e3, 4.5e3]`·`[n=2E5]` 를 인용으로 보면 괄호째 지워 수치가 사라지고, 한계 섹션에 "해석할 수 없는 인용 표기" 가 거짓으로 실린다. 룩비하인드에 숫자와 `.` 가 들어간 이유다.

```python
_CITATION_LIKE = re.compile(r"(?<![A-Za-z0-9.])[Ee]\s*\d")
```

**③ 안을 읽고 번호를 가른다.** `_parse_ids` 가 목록 구분자(`,` `，` `;` `；`)로 쪼개고 항목마다 `E3` 또는 범위(`E3-E7`·`E3~7`, 구분자 `-` `~` `–` `—` `～`)로 읽는다. 문법을 벗어나면(`[E1 참조]`) 해석 불가(`unparsed`)다. 번호는 정수로 읽으므로 `E01` 은 `E1` 이 된다. `_resolve` 는 범위의 **끝점만** 모델이 쓴 번호로 본다 — 사이 번호는 유효한 것만 싣고 없는 것은 세지 않는다. `[E3-E7]` 을 E4·E5·E6 까지 지어낸 것으로 보고하면 과장이기 때문이다.

그 뒤 유효한 번호만 **표준형 `[E#]`** 로 다시 쓰고(공백으로 이어 붙인다), 유효한 번호가 하나도 없으면 괄호를 그 앞 공백째 지운다(이중 공백이 남지 않는다). 표준형으로 다시 쓰는 것이 핵심이다 — 반환 텍스트에는 한 가지 문법만 남으므로 프론트·계수 로직(`_MARKER`)·라이브 검증 스크립트가 단일형 `[E#]` 하나만 알면 된다. 테스트가 고정한 입출력은 이렇다.

| 입력 | 유효 집합 | 반환 텍스트 | 보고 |
|---|---|---|---|
| `측정돼 왔다 [E1, E2].` | E1·E2 | `측정돼 왔다 [E1] [E2].` | used E1·E2 |
| `측정돼 왔다 [E2, E99].` | E1·E2 | `측정돼 왔다 [E2].` | dropped E99 |
| `지어냈다 [E98,E99].` | E1 | `지어냈다.` | dropped E98·E99 |
| `연구가 있다 [E3~E9].` | E3·E7·E12 | `연구가 있다 [E3] [E7].` | dropped E9 |
| `근거다 ［E1］ 【E2】.` | E1·E2 | `근거다 [E1] [E2].` | — |
| `근거다 [e1] [E02].` | E1·E2 | `근거다 [E1] [E2].` | dropped 없음 |
| `근거다 [E1 참조].` | E1 | `근거다.` | unparsed `[E1 참조]` |
| `95% CI [1.2e3, 4.5e3] 이다 [E2].` | E2 | 그대로 | — |

**나머지는 바이트 단위로 보존한다.** 초안은 마커를 지운 뒤 전역으로 공백·구두점을 정리했는데(`re.sub(r"\s+([.,!?])", r"\1", cleaned)` 류), 이것이 사회과학 논문의 `p < .05` 를 `p <.05` 로 훼손했다. `2d2221a` 에서 정리를 마커 주변(괄호 앞 공백)으로 한정했다.

**반환값(`MarkerResult`).** `dropped`(없는 번호)와 `unparsed`(읽을 수 없는 표기)를 따로 센다 — 앞은 모델이 번호를 지어낸 것이고 뒤는 프롬프트 형식 문제라 원인이 다르다. `used` 는 등장 순서·중복 제거로 유효 번호를 돌려준다. 종합이 향후 과제의 칩 목록을 이것으로 만든다 — 호출부에서 정규식으로 다시 훑으면 마커 문법이 세 번째로 복제된다(`2d2221a`). `unparsed` 의 기본값 `[]` 은 필드 4개로 만든 `MarkerResult` 도 유효하게 두기 위한 것이고, `bind_markers` 는 항상 새 리스트를 넘긴다.

**근거 없는 문장 수(`unmarked`).** 반환 텍스트를 문장으로 쪼개 마커 없는 문장을 센다(종합이 3건부터 한계에 보고한다). 모델은 마커를 마침표 **뒤**에 다는 일이 흔해서(`문장이다. [E1]`), 그대로 세면 근거 있는 문장이 무근거로 잡히고 마커는 다음 문장 소속이 된다. 그래서 **계수용 사본에서만** 마침표 뒤의 마커 묶음을 통째로 문장 앞으로 당긴다(`_TRAILING_MARKER`). 처음엔 마커 하나만 당겨서 `. [E1] [E2]` 의 `[E2]` 가 다음 문장 소속으로 잡혀 과소 계수됐다(`e0a759c` 에서 묶음 전체로). 반환 텍스트에는 적용하지 않는다.

**검증 집합은 호출부가 정한다 — 그 절에 준 번호뿐이다.** `bind_markers` 는 `valid_ids` 를 인자로 받을 뿐이고, 종합(`synthesizer.assemble_report`)이 절마다 그 절의 논문 번호만 넘긴다. 초안은 전역 집합(`state.evidence` 의 키 전부)으로 검증했는데, 위에서 본 대로 번호가 `E1…En` 으로 빈틈없이 이어지므로 모델이 지어낸 작은 번호는 거의 다 "유효" 로 통과했다 — `E6~E10` 만 받은 절이 `[E3]` 을 달면 모델이 본 적도 없는 논문을 가리키는 칩이 생기고 한계 섹션은 조용했다(리뷰 35). 절 밖 번호는 지금 `dropped` 로 잡혀 1건부터 한계에 보고된다.

**`strip_markers` — 라이브에서 나온 함수다.** 라이브 검증 중 종합 버그를 고친 뒤 같은 잡의 스냅샷으로 드라이런했더니 모델이 시키지 않은 `[E7]` 을 **대표 논문 요약** 끝에 달았다(2026-09-23, `b6360b8`). 요약은 `bind_markers` 를 거치지 않으므로 남겨두면 지어낸 번호가 검증 없이 화면에 나가고, 유효한 번호라도 불릿의 칩과 중복이다. 그래서 그 자리에서는 인용처럼 생긴 괄호를 전부 지운다. 검증을 거치지 않는 필드에 모델 출력이 들어가면 그 필드도 정리해야 한다는 교훈은 함정 15번에 함께 적었다. 머지 전 리뷰에서 `bind_markers` 와 같은 괄호 규칙(`_BRACKET`·`_CITATION_LIKE`)을 쓰게 바꿨다 — 단일형만 지우면 요약 속 `[E1, E4]` 가 그대로 나간다.

**남은 공백(이월).**

- 마커가 마침표에 **붙은** 경우(`했다.[E1] 다음 문장.`)와 구두점 없이 개행으로 끝나는 문장에서 `unmarked` 를 적게 센다(리뷰 95, low). 확인한 예: `A를 분석했다.[E1] B는 다르다. C도 있다.[E2] D도 그렇다.` 는 무근거 문장이 둘(B·D)인데 0 으로 센다. 한계를 과소 보고할 뿐 데이터를 해치지 않아 이월했다(완료노트 §8).
- 괄호 안에 개행이 들어간 표기(`[E1,` 줄바꿈 `E2]`)는 `_BRACKET` 이 잡지 않아 해석도 제거도 없이 그대로 남는다. 위 ①의 개행 제외가 만드는 대가다.

**바뀐 점 요약.** `2d2221a` — 번호 권한 이관, 공백 정리 한정, `MarkerResult`·`used`, 계수용 마커 당기기. `e0a759c` — 마커 묶음 전체 당기기. `b6360b8` — `strip_markers`. `2bac7ee` — 괄호 단위 해석(`_BRACKET`·`_CITATION_LIKE`·`_parse_ids`·`_resolve`)과 `unparsed`, `strip_markers` 의 같은 기준 적용, `chunks_for`·`link_chunks`, 구조적 인용의 한계를 docstring 에 명시.

```python
"""citations.py — 근거 조립과 인용 마커 검증 (순수 함수)

인용은 두 종류다.

구조적 인용 — `대표 논문 요약`은 불릿 하나가 논문 하나라, 어느 논문이 실리고
칩이 어디를 가리키는지는 코드가 정한다. 다만 절의 논문 여러 편을 한 호출에 넣고
번호별로 요약을 받으므로, 요약 문장이 그 논문의 내용인지는 모델의 번호 배정에
달려 있다 — 인용은 구조지만 요약의 배정은 추론이다(spec §4-1 구현 시 변경).

마커 인용 — `도입 문단`·`향후 과제`는 여러 논문을 가로지르므로 구조로 못
정한다. 모델이 [E3] 로 달게 하고 여기서 전수 검증한다. 해석 안 되는 마커는
조용히 통과시키지 않고 제거한 뒤 개수를 보고한다.

근거 ID(E1·E2·...) 는 runner 가 state.evidence 에 넣는 시점에 붙인다 —
evidence 네임스페이스를 소유한 쪽이 번호도 소유해야 한다. build_evidence
는 순서만 보장하고(hits 등장 순서) 번호는 매기지 않는다.
"""
import re
from dataclasses import replace
from typing import NamedTuple

from services.research.state import Chunk, Evidence, HitRow, SubQuestion

# 반환 텍스트의 표준형. bind_markers 는 인식한 표기를 전부 이 모양으로 다시 쓴다 —
# 프론트와 계수 로직은 이 한 가지 문법만 알면 된다.
_MARKER = re.compile(r"[ \t]*\[(E\d+)\]")
# 모델은 지시("[E3] 형태만")를 어기고 묶음·범위·전각·소문자·0패딩을 낸다.
# 괄호 하나를 통째로 잡아 안을 해석한다 — 단일형만 보면 "[E2, E99]" 속 없는 번호가
# 검증도 제거도 안 된 채 본문에 실린다.
_BRACKET = re.compile(r"([ \t]*)[\[［【]([^\[\]［］【】\n]*)[\]］】]")
# 인용으로 보는 괄호: 영문자에 붙지 않은 E 뒤에 숫자. "[ICE 2019]"·"[표 1]" 은 제외.
# 숫자·소수점 뒤의 e 는 지수 표기다("[1.2e3, 4.5e3]"·"[n=2E5]") — 인용으로 보면
# 괄호째 지워 수치가 사라진다.
_CITATION_LIKE = re.compile(r"(?<![A-Za-z0-9.])[Ee]\s*\d")
_ID = r"[Ee]\s*(\d+)"
_RANGE_SEP = r"\s*[-~–—～]\s*"
_ITEM = re.compile(rf"{_ID}(?:{_RANGE_SEP}[Ee]?\s*(\d+))?")
_LIST_SEP = re.compile(r"\s*[,，;；]\s*")
_SENT_SPLIT = re.compile(r"(?<=[.!?。])\s+")
# 마침표 뒤에 붙는 마커 묶음("문장이다. [E1] [E2]")을 셀 때만 통째로 문장
# 앞으로 당긴다 — LLM 이 마커를 문장 끝 마침표 뒤에 다는 게 흔해서, 그대로
# 세면 근거가 있는 문장이 무근거로 오분류된다. 마커 하나만 당기면 뒤에
# 남은 마커가 다음 문장 소속으로 잘못 잡혀 과소 계수된다. 계수용 사본에만
# 쓰므로 치환 뒤 공백이 지저분해도 무해하다. 반환 텍스트에는 적용하지 않는다.
_TRAILING_MARKER = re.compile(r"([.!?。])(\s+)((?:\[E\d+\][ \t]*)+)")


def evidence_id(index: int) -> str:
    return f"E{index + 1}"


def build_evidence(
    hits: list[HitRow],
    meta_by_id: dict[str, dict],
    *,
    chunks_per_evidence: int,
) -> list[Evidence]:
    """검색 결과를 논문 단위 근거로 묶는다.

    같은 논문의 청크 여러 개는 근거 하나가 되고, 점수 높은 순으로
    chunks_per_evidence 개만 남긴다(호버 팝업의 1/2 페이지네이션).
    카탈로그에 메타가 없는 청크는 버린다 — 서지를 못 보여주면 근거가 아니다.

    반환 순서는 hits 안에서 각 논문이 처음 등장한 순서다(hits 는 호출 전에
    점수 내림차순으로 정렬돼 들어온다는 전제). id 는 비워둔다 — runner 가
    state.evidence 에 넣으며 evidence_id() 로 채운다.
    """
    grouped: dict[str, list[HitRow]] = {}
    for hit in hits:
        cnts_id = hit["book_id"]
        if cnts_id not in meta_by_id:
            continue
        grouped.setdefault(cnts_id, []).append(hit)

    result: list[Evidence] = []
    for cnts_id, rows in grouped.items():
        rows.sort(key=lambda r: r["score"], reverse=True)
        result.append(Evidence(
            id="",
            cnts_id=cnts_id,
            meta=meta_by_id[cnts_id],
            chunks=[
                Chunk(
                    chunk_id=r["chunk_id"], text=r["text"],
                    page_start=r["page_start"], page_end=r["page_end"],
                    score=r["score"],
                )
                for r in rows[:chunks_per_evidence]
            ],
        ))
    return result


def chunks_for(ev: Evidence, sq: SubQuestion) -> list[Chunk]:
    """그 하위질문 검색에서 매칭된 청크(점수순). 점수는 그 하위질문의 검색어로 받은 값이다.

    사본을 돌려준다 — Evidence.chunks 의 점수는 매칭한 하위질문 중 최고값이라 그대로
    넘기면 다른 하위질문의 점수가 발췌·호버에 나간다. 점수 기록이 없는 옛 스냅샷은
    Chunk.score 를, 매핑이 없는 옛 스냅샷은 청크 전부를 준다.
    """
    ids = sq.evidence_chunks.get(ev.id)
    if not ids:
        return list(ev.chunks)
    by_id = {c.chunk_id: c for c in ev.chunks}
    return [replace(by_id[i], score=sq.chunk_scores.get(i, by_id[i].score))
            for i in ids if i in by_id]


def link_chunks(ev: Evidence, sq: SubQuestion, found: list[Chunk], *, limit: int) -> None:
    """이번 검색에서 매칭된 청크를 그 하위질문의 몫으로 기록한다.

    같은 하위질문의 재검색이 더 잘 맞는 대목을 찾으면 점수순으로 갈아끼운다. 이미 매핑한
    청크는 이 하위질문이 받은 점수(sq.chunk_scores)로 비교한다 — Chunk.score 는 다른
    하위질문의 검색어로 받은 값일 수 있다.

    Evidence.chunks 는 매칭된 적 있는 청크의 저장소다. 새 청크는 이 하위질문이 가리킬 때만
    더하고, 점수는 매칭한 하위질문 중 최고값으로 둔다. 갈아끼워진 청크는 다른 하위질문이
    가리킬 수 있어 여기서 지우지 않는다 — 보고서에는 지금 가리키는 것만 싣는다
    (synthesizer._serialize_evidence).
    """
    by_id = {c.chunk_id: c for c in ev.chunks}
    scores = {i: sq.chunk_scores.get(i, by_id[i].score)
              for i in sq.evidence_chunks.get(ev.id, []) if i in by_id}
    found_by_id: dict[str, Chunk] = {}
    for c in found:
        if c.score > scores.get(c.chunk_id, float("-inf")):
            scores[c.chunk_id] = c.score
            found_by_id[c.chunk_id] = c
    ranked = sorted(scores, key=scores.__getitem__, reverse=True)[:limit]

    for i in ranked:
        chunk = by_id.get(i)
        if chunk is None:
            chunk = found_by_id[i]
            ev.chunks.append(chunk)
            by_id[i] = chunk
        chunk.score = max(chunk.score, scores[i])
    for i in sq.evidence_chunks.get(ev.id, []):
        if i not in ranked:
            sq.chunk_scores.pop(i, None)
    sq.evidence_chunks[ev.id] = ranked
    sq.chunk_scores.update({i: scores[i] for i in ranked})


class MarkerResult(NamedTuple):
    text: str
    dropped: list[str]
    used: list[str]      # 등장 순서, 중복 제거 — 유효한 마커를 다시 정규식으로 훑지 않고 여기서 재사용한다
    unmarked: int
    # 인용처럼 생겼지만 번호를 읽을 수 없는 괄호("[E1 참조]"). 없는 번호(dropped)와
    # 원인이 달라 따로 센다 — 이쪽은 프롬프트 형식 문제다.
    unparsed: list[str] = []


def _parse_ids(inner: str) -> list[tuple[int, int | None]] | None:
    """괄호 안을 (번호, 범위 끝) 목록으로 읽는다. 문법을 벗어나면 None."""
    items = []
    for part in _LIST_SEP.split(inner.strip()):
        m = _ITEM.fullmatch(part)
        if m is None:
            return None
        items.append((int(m.group(1)), int(m.group(2)) if m.group(2) else None))
    return items


def _resolve(items: list[tuple[int, int | None]], valid_ids: set[str]) -> tuple[list[str], list[str]]:
    """(유효 번호, 없는 번호). 0패딩은 정수로 읽어 E01 → E1 로 맞춘다.

    범위는 끝점만 모델이 쓴 번호다. 사이 번호는 주어진 것만 싣고 없는 것은
    세지 않는다 — "[E3-E7]" 을 E4·E5·E6 까지 지어낸 것으로 보고하면 과장이다.
    """
    valid_nums = sorted(int(v[1:]) for v in valid_ids if v[1:].isdigit())
    ok: list[str] = []
    bad: list[str] = []
    for start, end in items:
        if end is None or end == start:
            nums, ends = [start], {start}
        else:
            nums = [start, *(n for n in valid_nums if start < n < end), end]
            ends = {start, end}
        for n in nums:
            eid = f"E{n}"
            if eid in valid_ids:
                if eid not in ok:
                    ok.append(eid)
            elif n in ends:
                bad.append(eid)
    return ok, bad


def bind_markers(text: str, valid_ids: set[str]) -> MarkerResult:
    """인용 마커를 검증한다.

    인식한 표기는 유효한 번호만 표준형 `[E#]` 으로 다시 쓰고, 없는 번호와
    해석 못 한 표기는 (그 앞 공백과 함께) 지운다. 나머지는 바이트 단위로
    보존한다 — "p < .05" 같은 논문 통계 표기를 건드리지 않는다.
    """
    dropped: list[str] = []
    unparsed: list[str] = []
    used: list[str] = []

    def _check(m: re.Match) -> str:
        inner = m.group(2)
        if not _CITATION_LIKE.search(inner):
            return m.group(0)
        items = _parse_ids(inner)
        if items is None:
            unparsed.append(m.group(0).strip())
            return ""
        ok, bad = _resolve(items, valid_ids)
        dropped.extend(bad)
        for eid in ok:
            if eid not in used:
                used.append(eid)
        if not ok:
            return ""
        return m.group(1) + " ".join(f"[{eid}]" for eid in ok)

    cleaned = _BRACKET.sub(_check, text).strip()

    count_text = _TRAILING_MARKER.sub(r"\3\1\2", cleaned)
    sentences = [s for s in _SENT_SPLIT.split(count_text) if s.strip()]
    unmarked = sum(1 for s in sentences if not _MARKER.search(s))

    return MarkerResult(cleaned, dropped, used, unmarked, unparsed)


def strip_markers(text: str) -> str:
    """구조적 인용 자리(대표 논문 요약)에서 마커를 전부 걷어낸다.

    그 자리의 인용은 불릿의 논문으로 이미 정해져 있어 마커가 필요 없다. 그런데
    모델은 시키지 않아도 요약 끝에 [E7] 을 단다(2026-09-23 실측). 요약은
    bind_markers 를 거치지 않으므로 남겨두면 지어낸 번호가 검증 없이 화면에
    나간다 — 유효한 번호도 칩과 중복이라 함께 지운다. 묶음·전각 표기도
    bind_markers 와 같은 기준으로 인용으로 본다.
    """
    def _drop(m: re.Match) -> str:
        return "" if _CITATION_LIKE.search(m.group(2)) else m.group(0)

    return _BRACKET.sub(_drop, text).strip()
```

### 2.8 `llm_json.py` — LLM 이 산문에 섞어 낸 JSON 꺼내기

**책임.** 모델 응답 문자열에서 첫 `{` 위치부터 JSON **객체** 하나를 꺼낸다. 코드펜스(언어 표기 `json` 이 붙은 것이든 맨 펜스든)가 있으면 그 안에서, 없으면 원문에서 찾는다. 못 찾거나 그 위치에서 디코딩이 실패하면 `None`.

**왜 이렇게 짰나.**

- **공용 함수로 한 곳에 둔다.** 자기점검(`critic`)과 종합(`synthesizer`)이 같은 일을 한다. 마커 정규식을 두 곳에 두면 갈라지는 것과 같은 이유로, JSON 추출 규칙도 하나만 둔다(`a29c9a7`).
- **`raw_decode` 로 첫 JSON 에서 멈춘다.** 흔한 구현인 `body[body.index("{"):body.rindex("}") + 1]` 은 JSON 뒤에 `}` 가 든 산문이 붙으면(`{"a": 1} 참고: {예시}`) 그 끝까지 먹어 파싱이 깨진다. 첫 `{` 위치에서 `JSONDecoder().raw_decode` 를 부르면 첫 유효 JSON 이 끝나는 자리에서 멈추고 뒤는 무시한다(아래 인용).
- **dict 만 돌려준다.** 호출부는 `.get` 으로 필드를 읽으므로 리스트가 넘어가면 `AttributeError` 로 터진다. 디코딩을 `{` 에서 시작하므로 성공하면 항상 dict 이고, 마지막 `isinstance` 검사는 그 계약을 코드로 못 박아 둔 방어다. 그래서 `[1, 2, 3]` 처럼 `{` 가 없는 배열은 `None` 이지만, `[{"a": 1}, {"b": 2}]` 처럼 객체를 담은 배열은 첫 원소 `{"a": 1}` 이 나온다.
- **실패는 예외가 아니라 `None` 이다.** 호출부가 그 의미를 정한다 — critic 에서는 판정 불가(`parse_failed`), 종합에서는 그 시도의 실패다(절마다 최대 2회 시도 — `_SECTION_ATTEMPTS` — 뒤에도 실패하면 그 절은 논문 목록만 싣고 한계에 보고).

```python
        data, _ = json.JSONDecoder().raw_decode(body[start:])
```

**남은 공백(이월).** 첫 `{` 한 곳에서만 시도하고 strict 로 디코딩한다(리뷰 97, low). JSON 앞 산문에 `{요약}` 같은 중괄호가 있으면 뒤의 정상 JSON 을 놓치고, 문자열 값 안의 실제 개행은 strict 디코더가 거부하며, 펜스 안에 JSON 이 없으면 펜스 밖을 다시 보지 않는다. 실패하면 판정 불가·절 실패로 **드러나고** 데이터를 해치지 않아 이월했다(완료노트 §4·§8). 고친다면 각 `{` 위치에서 차례로 시도하고 `strict=False` 를 쓰며, 펜스 안에서 못 찾으면 원문으로 다시 보는 방향이다(리뷰 97 의 제안).

**파일**: `app/services/research/llm_json.py` — 전체 30줄

````python
"""llm_json.py — LLM 이 산문에 섞어 내보낸 JSON 을 꺼낸다

critic 과 synthesizer 가 같은 일을 하므로 한 곳에 둔다. 마커 정규식을
두 곳에 두면 갈라지는 것과 같은 이유다.

raw_decode 를 쓰는 이유: `body[index("{"):rindex("}")+1]` 는 JSON 뒤에
`}` 를 포함한 산문이 붙으면 그 끝까지 먹어 파싱이 깨진다. raw_decode 는
첫 유효 JSON 에서 멈춘다.
"""
import json
import re

_FENCE = re.compile(r"```(?:json)?\s*(.*?)\s*```", re.S)


def extract_json(raw: str) -> dict | None:
    """첫 유효 JSON 객체를 반환한다. 못 찾으면 None."""
    body = raw or ""
    m = _FENCE.search(body)
    if m:
        body = m.group(1)

    start = body.find("{")
    if start < 0:
        return None
    try:
        data, _ = json.JSONDecoder().raw_decode(body[start:])
    except ValueError:
        return None
    return data if isinstance(data, dict) else None
````

**무엇을 고정하나.** 18건. 모델 모양 15건과 마이그레이션 정합 3건이다.

- **모델↔마이그레이션 정합.** `0005` 의 `upgrade()` 를 **실제로 실행**한다. 로컬 venv 에는 alembic 이 설치돼 있지 않아(`app/requirements.txt` 에는 있다) `alembic.op` 를 흉내 내는 최소 스텁을 `sys.modules` 에 꽂는다 — `upgrade()` 는 `create_table`·`create_index` 만 부르므로 둘만 있으면 된다. 스텁의 `create_table` 은 넘어온 인자로 **진짜 `sa.Table` 을 만들어** 타입·nullable·기본값 유무·유일 제약을 SQLAlchemy introspection 으로 읽는다. 인자를 직접 파싱하면 캡처 로직이 또 하나의 정합 리스크가 되기 때문이다(`a326203` — 그 전에는 컬럼 이름 집합만 비교했고, `create_index` 스텁은 호출을 전부 삼켰다). def _column_signature(col, include_default=True):
```python
    """(타입, nullable[, 기본값 유무]) — 컬럼 하나의 스키마 정합성 지문.

    PK 는 include_default=False 로 호출한다: 모델의 id 는 default=uuid.uuid4

    """
    sig = [str(col.type), col.nullable]
    if include_default:
        sig.append(col.server_default is not None or col.default is not None)
    return tuple(sig)


def _table_signature(table):
    return {
        c.name: _column_signature(c, include_default=not c.primary_key)
        for c in table.columns
    }

            "table_name": table.name,
            "columns": [c.name for c in ix.columns],
            "postgresql_where": str(where) if where is not None else None,
        }
    return sig

    """0005 의 upgrade() 를 실제 alembic 없이 실행하고 create_table/create_index 호출을 캡처한다.

    로컬 venv 에 alembic 이 설치돼 있지 않아 (app/requirements.txt 에는 있으나 미설치)
    `from alembic import op` 를 만족시키는 최소 스텁만 넣는다 — upgrade() 는 op.create_table /
    op.create_index 만 호출하므로 그 둘만 흉내 내면 충분하다.

    create_table 은 넘어온 Column/UniqueConstraint 인자로 실제 sa.Table 을 만들어 바인딩한다
    (컬럼 이름만이 아니라 타입·nullable·기본값·제약까지 실제 SQLAlchemy introspection 으로
    읽기 위해서 — 인자를 훑어 직접 파싱하면 캡처 로직 자체가 또 하나의 정합 리스크가 된다).
    """
    import importlib.util as u

    tables = {}
    unique_constraints = {}
    indexes = []

    def fake_create_table(name, *args, **kwargs):
        table = sa.Table(name, sa.MetaData(), *args)
        tables[name] = _table_signature(table)
        unique_constraints[name] = {
            c.name: [col.name for col in c.columns]
            for c in table.constraints
            if isinstance(c, sa.UniqueConstraint)
        }

    def fake_create_index(name, table_name, columns, **kwargs):
        where = kwargs.get("postgresql_where")
        indexes.append({
            "name": name,
            "table_name": table_name,
            "columns": list(columns),
            "postgresql_where": str(where) if where is not None else None,
        })

    fake_op = types.ModuleType("alembic.op")
    fake_op.create_table = fake_create_table
    fake_op.create_index = fake_create_index

    fake_alembic = types.ModuleType("alembic")
    fake_alembic.op = fake_op

    monkeypatch.setitem(sys.modules, "alembic", fake_alembic)
    monkeypatch.setitem(sys.modules, "alembic.op", fake_op)

    spec = u.spec_from_file_location("_migration_0005", migration_path)
    module = u.module_from_spec(spec)
    spec.loader.exec_module(module)
    module.upgrade()
    return {"tables": tables, "unique_constraints": unique_constraints, "indexes": indexes}
```

```python
class TestLinkChunks:
    """점수는 청크를 매칭한 하위질문의 검색어로 받은 값이다 — 같은 청크를 다른 하위질문이
    먼저 찾았어도 이 하위질문의 비교·발췌·호버는 자기 점수로 한다."""

    def _chunk(self, chunk_id, score):
        return Chunk(chunk_id, f"대목 {chunk_id}", 1, 1, score)

    def test_shared_chunk_keeps_each_subquestions_score(self):
        ev = Evidence(id="E1", cnts_id="P", meta={})
        a, b = SubQuestion(idx=0, text="A"), SubQuestion(idx=1, text="B")
        link_chunks(ev, a, [self._chunk("P-c1", 0.2)], limit=1)
        link_chunks(ev, b, [self._chunk("P-c1", 0.95)], limit=1)

        assert [(c.chunk_id, c.score) for c in chunks_for(ev, a)] == [("P-c1", 0.2)]
        assert [(c.chunk_id, c.score) for c in chunks_for(ev, b)] == [("P-c1", 0.95)]

    def test_research_compares_with_this_subquestions_score(self):
        """B 가 0.95 로 찾은 대목을 A 의 점수(0.2)로 비교하면 재검색의 0.5 짜리에 밀린다."""
        ev = Evidence(id="E1", cnts_id="P", meta={})
        a, b = SubQuestion(idx=0, text="A"), SubQuestion(idx=1, text="B")
        link_chunks(ev, a, [self._chunk("P-c1", 0.2)], limit=1)
        link_chunks(ev, b, [self._chunk("P-c1", 0.95)], limit=1)
        link_chunks(ev, b, [self._chunk("P-c2", 0.5)], limit=1)

        assert b.evidence_chunks == {"E1": ["P-c1"]}
        assert a.evidence_chunks == {"E1": ["P-c1"]}

    def test_evidence_level_score_is_the_best_match(self):
        """보고서 근거 목록에는 청크 하나에 점수 하나다 — 먼저 찾은 쪽이 아니라 최고값을 싣는다."""
        ev = Evidence(id="E1", cnts_id="P", meta={})
        link_chunks(ev, SubQuestion(idx=0, text="A"), [self._chunk("P-c1", 0.2)], limit=1)
        link_chunks(ev, SubQuestion(idx=1, text="B"), [self._chunk("P-c1", 0.95)], limit=1)

        assert [(c.chunk_id, c.score) for c in ev.chunks] == [("P-c1", 0.95)]

    def test_replaced_chunk_leaves_the_subquestion(self):
        ev = Evidence(id="E1", cnts_id="P", meta={})
        sq = SubQuestion(idx=0, text="가")
        link_chunks(ev, sq, [self._chunk("P-가", 0.3)], limit=1)
        link_chunks(ev, sq, [self._chunk("P-재1", 0.9)], limit=1)

        assert sq.evidence_chunks == {"E1": ["P-재1"]}
        assert sq.chunk_scores == {"P-재1": 0.9}

    def test_chunks_for_without_scores_uses_chunk_score(self):
        """점수 기록이 없는 옛 스냅샷은 Chunk.score 로 되돌아간다."""
        ev = Evidence(id="E1", cnts_id="P", meta={}, chunks=[self._chunk("P-c1", 0.7)])
        sq = SubQuestion(idx=0, text="가", evidence_chunks={"E1": ["P-c1"]})
        assert [c.score for c in chunks_for(ev, sq)] == [0.7]

    def test_chunks_for_does_not_mutate_the_evidence(self):

        a, b = SubQuestion(idx=0, text="A"), SubQuestion(idx=1, text="B")
        link_chunks(ev, a, [self._chunk("P-c1", 0.2)], limit=1)
        link_chunks(ev, b, [self._chunk("P-c1", 0.95)], limit=1)
        chunks_for(ev, a)[0].score = -1.0
        assert ev.chunks[0].score == 0.95
```
