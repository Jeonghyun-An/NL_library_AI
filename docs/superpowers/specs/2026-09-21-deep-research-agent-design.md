# 논문 딥리서치 에이전트 설계

작성일: 2026-09-21
상태: **설계 확정** (구현 미착수)

## 0. 사용자 요청

> 논문 검색이 데이터도 많고 분석 취지에 더 맞으니 이걸 킥으로 가져간다. 리랭킹·자기분석·심층분석·다단계 탐색을 통해 '딥리서치' 기능을 넣고, 산출물까지 생성하는 에이전트를 만든다. 디비피아 AI 에이전트 같은 그림이다.
>
> 왜 넣고 싶냐면, 일반 도서·논문 검색과 1:1 대화를 넘어서 **"시간은 좀 오래 걸리지만 실제 논문 탐색에 사용할 수 있는 전문 AI 에이전트가 있다"** 를 전달하고 싶고 그걸 킥으로 만들고 싶기 때문이다.
>
> 슬래시 명령(`/deep-research`)으로 진입하고, RAG 기반이니 끝에 인용이 달리는 것도 넣는다. 대회 시연용이니 다이나믹하게 보여주는 게 좋고, 실사용에서도 지루하지 않아야 한다.

**이 문장이 설계 지침이다** — "시간이 오래 걸린다"는 변명이 아니라 사양이다. 오래 걸린다는 걸 숨기면 느린 챗봇이 되고, 드러내면 일하는 전문가가 된다. 그래서 이 기능의 값은 최종 보고서 못지않게 **과정을 보여주는 화면**에 있다.

## 1. 배경

### 1-1. 경쟁 제품 — 디비피아 AI

실제 서비스 화면과 산출물을 확인했다(2026-09-21). 라인업은 넷이다.

| 디비피아 | NL-Lib 현재 |
|---|---|
| AI 에이전트 (검색 기반 답변) | AI 검색 + 큐레이션 — 있음 |
| AI 리더 (요약·번역·대화) | 논문/책과의 대화 + `paper_summary` — 있음 |
| AI 아이디어 (주제·목차 추천) | 없음 |
| **AI 딥리서치 (심층 보고서)** | **없음 ← 이번 대상** |

확인된 동작:

- **계획 승인 단계가 있다.** 하위주제 6개를 제안하고 `수정` / `승인 및 진행` 버튼을 띄운다. 확인한 세션에서는 제안된 계획과 실행된 계획이 서로 달랐다 — 수정 기능이 실제로 쓰인다.
- **비동기다.** "리서치 계획과 연관된 출처 자료를 검색합니다. 보다 깊이 있는 분석을 위해 잠시 시간이 필요합니다. 완료되면 언제든지 확인하실 수 있습니다." → `리서치 완료` 카드.
- **진행 패널이 18개 항목**이다. 하위주제 6개 × 검색 단계 3개 안팎. 각 항목이 "…를 찾기 위해 검색 중입니다"로 의도를 서술한다. 잔이벤트가 아니라 **의미 있는 단계만** 남긴다.
- **보고서 뼈대**: 서론 → 섹션별(`도입 문단` → `대표 핵심 논문 요약` → `향후 연구 방향 및 개방 문제`). 논문 요약은 불릿 하나가 논문 하나이고 `이름 (연도):` + 2~3문장 + 인용칩 형태다.
- **인용칩 호버 팝업**: 논문 제목 + `원문 보기↗` + 초록 인용 + `1/2` 페이지네이션.
- AI 생성 다이어그램이 본문에 들어가고 "AI가 생성한 이미지로 실제와 다를 수 있습니다" 고지가 붙는다.

**규모로는 못 이긴다** — 디비피아는 국내 400만 + 해외 2.7억을 내세운다. 우리는 7만이다. 경쟁축은 규모가 아니라 **국내 학술자원에 대해 근거를 끝까지 추적해 보여주는 깊이**여야 한다.

인덱싱 잡 `kci-full-236k`(236,450건, 2026-08-07 시작)가 **오래된 것부터** 처리 중이다. 2026-09-21 기준 완료 75,055 / 대기 163,816, 최근 처리 속도 **143건/h**.

- 잔여 163,816건 ÷ 143건/h = **47.7일** → 완주 11월 초
- 대회(10월 초 추정)까지 약 55,000건 추가 → **2013~2014년까지 도달**
- **2020년대는 대회 때까지 한 편도 안 들어온다**

*(143건/h은 재시작 후 첫 한 시간 값이라 램프업이 섞였을 수 있다. 잡 평균은 69건/h였다.)*

**결론: 전체 코퍼스로는 "최근 동향" 질문이 성립하지 않는다.** 시연 분야만 우선 인덱싱해 해결한다(§8).

## 2. 결정 사항과 근거

### 2-1. 실행 모델 — 비동기 Celery + SSE 중계 + 영속

동기 SSE(2~3분 상한, 탭 닫으면 소실), 순수 비동기(시연에서 기다리는 그림이 안 남), 둘의 결합 중 **결합**을 택했다. 작업은 Celery로 돌리고 진행은 SSE로 중계하며 결과는 DB에 남는다. 시연에선 실시간으로 보고, 평소엔 닫아도 되고, 나중에 다시 연다.

디비피아도 같은 모델이다.

### 2-2. LangGraph 미도입

루프가 `계획 → 검색 → 평가 → 재검색 → 종합`이고 분기는 "한 번 더 돌까"와 "사용자 승인 대기" 둘뿐이다. 이 정도는 **상태 dataclass + 명시적 async 함수**로 충분히 표현된다. 계획 승인도 새 런타임이 필요한 게 아니라 **작업 상태가 `awaiting_approval` 로 멈췄다 재개되는 것**이고, `ingest_jobs` 의 `stage`/`status` 분리가 이미 그 모양이다.

LangGraph를 넣으면 상태 스키마·노드 등록·체크포인터라는 새 개념이 붙고, **시연 3주 전에 디버깅할 표면이 하나 늘어난다.** dev 스택이 registry pull 방식이라 반영 사이클도 느리다.

값을 하는 지점(분기 5개 이상, 복잡한 중단·재개)이 생기면 그때 갈아끼운다. 그래서 오케스트레이터를 **순수 단계 함수 + 상태 객체**로 짠다 — 그 함수들을 LangGraph 노드에 그대로 꽂을 수 있다.

### 2-3. 진행 기록은 2계층

한 테이블로 진행 패널과 보고서를 겸하면 **입자 크기가 충돌한다.** 패널은 잘고 빈번한 걸(카운터, "리랭킹 중") 원하고 보고서는 굵고 적은 걸 원한다. 잘게 쓰면 보고서가 지저분해지고, 굵게 쓰면 화면이 멈춰 보인다. 게다가 진행은 `pending→running→done` 으로 UPDATE되고 로그는 append-only여서, 섞으면 감사 기록으로 못 쓴다.

| 계층 | 저장소 | 입자 | 수명 |
|---|---|---|---|
| 의미 있는 단계 | `research_steps` (Postgres) | 굵게 — 18개 안팎 | 영구 |
| 실시간 진행 이벤트 | Redis pub/sub만 | 잘게 — 카운터, 부분 토큰 | 휘발 |

재접속하면 Postgres에서 뼈대를 복원하고 Redis에서 그 이후를 이어받는다. 놓친 잔이벤트는 볼 필요가 없다.

`research_steps` 는 그대로 **보고서의 탐색 경로 섹션**이 된다. 진행 UI를 만드는 일이 곧 보고서 한 섹션을 만드는 일이다.

별도 이벤트 로그 테이블은 만들지 않는다. 유일한 값인 "에이전트가 왜 그렇게 판단했나"는 **자기점검 단계의 판단 근거를 그 step의 `result` JSONB에 남기면** 대부분 해결된다.

### 2-4. 산출물 구조

디비피아 뼈대를 따르되 한 섹션을 더한다.

| 섹션 | 근거 데이터 |
|---|---|
| 서론 — 질문 해석과 이번 탐색 범위 | 입력 + 실행 시점 수록 범위 |
| 섹션별 `도입 문단` | 종합 |
| 섹션별 `대표 논문 요약` + 인용칩 | 초록·본문 청크·리랭킹·피인용 |
| 섹션별 `향후 연구 방향` | 종합 |
| 탐색 경로 | `research_steps` |
| **한계와 미확인 영역** | 자기점검 결과를 그대로 노출 |

**한계 섹션이 차별점이다.** 자기점검을 내부 로직으로만 쓰지 않고 사용자에게 보여준다. "3번 하위질문은 2015년 이후 자료가 없어 결론이 약하다" 같은 문장이 들어간다. 우리 코퍼스는 구멍이 많은데, **숨기면 들키고 드러내면 강점이 된다.** 사서가 심사위원이라면 모른다고 말하는 시스템이 아는 척하는 시스템보다 신뢰를 얻는다.

수록 범위는 **고정 문구로 박지 않는다.** 코퍼스가 계속 자라는 중이므로 실행 시점에 질의해서 넣는다.

## 3. 아키텍처

### 3-1. 코드 구조

새 패키지 `app/services/research/` — 기존 `search/` 를 소비하는 쪽이다.

| 파일 | 역할 |
|---|---|
| `state.py` | `ResearchState` dataclass — 질문·계획·하위질문별 근거·점검 이력·보고서 |
| `planner.py` | 질문 → 하위질문 5~6개 |
| `explorer.py` | 하위질문 1개 탐색 (`search()` + `reranker` + 피인용 가중) |
| `critic.py` | 근거 충분성 판정 + 재검색 쿼리 생성 |
| `synthesizer.py` | 섹션별 보고서 + 인용 바인딩 |
| `runner.py` | 단계 오케스트레이션 |

**각 단계는 `ResearchState` 를 받아 갱신해 돌려주는 함수다.** Celery·Redis·Milvus 없이 테스트되고, 나중에 다른 런타임으로 옮길 때도 그대로 쓴다. `scripts/recovery/rewrite_milvus_doc_type.py` 가 순수함수/IO를 갈라 Milvus 없이 테스트한 것과 같은 구조다.

재사용: `search()`, `reranker`, `context_expander`, `paper_citation`, `llm_client`, `prompts` 레지스트리, `sse_helpers`. 신규 프롬프트는 계획·점검·종합 3종.

### 3-2. 데이터 모델

`ingest_jobs` 패턴을 따른다.

```
research_jobs
  id            UUID PK
  question      Text
  status        created → planning → awaiting_approval
                → running → completed | failed | canceled
  params        JSONB   깊이 파라미터 (§3-4)
  plan          JSONB   하위질문 목록 (사용자 수정 반영본)
  report        JSONB   최종 산출물 (§4-4)
  created_by    String
  created_at · started_at · finished_at

research_steps
  id            BigInt PK
  job_id        FK → research_jobs
  seq           Int
  kind          plan | search | critique | synthesize
  subq_idx      Int NULL
  title         Text    하위질문 제목
  detail        Text    "…를 찾기 위해 검색 중입니다"
  status        pending | running | done | failed
  result        JSONB   찾은 건수, 판정 근거, 재검색 쿼리 등
  created_at · finished_at · updated_at
```

`updated_at` 기반 stale 감지로 워커 사망을 복구한다(`ingest_job_items` 와 동일).

### 3-3. API

```
POST /api/research                질문 제출 → job 생성, 계획 수립 착수
POST /api/research/{id}/approve   계획 승인 (수정된 계획 동봉 가능) → 실행 시작
GET  /api/research/{id}/stream    SSE 진행 중계
GET  /api/research/{id}           최종 보고서 조회
```

진행 중계 채널은 Redis pub/sub `research:{job_id}`. 워커가 publish, SSE 엔드포인트가 subscribe.

### 3-4. 파이프라인

1. **질문 접수** — 논문 검색창에서 `/deep-research <질문>`
2. **연구 계획 수립** — 하위질문 5~6개로 분해 (LLM)
3. **계획 승인 대기** — 사용자가 수정하거나 승인 (`awaiting_approval`)
4. **하위질문별 탐색** — 검색 · 리랭킹 · 피인용 가중
5. **자기점검** — 부족하면 쿼리 재구성 후 4로 복귀 (상한 있음)
6. **보고서 종합** — 섹션별 서술 + 인용칩
7. **저장 · 열람**

**실행 시간 예산은 중간(5~7분)** — 하위질문 5~6개, 재검색 2~3회, 근거 40~60편, 유망 논문은 본문까지 읽는다.

깊이는 하드코딩하지 않고 `research_jobs.params` 에 넣는다.

```json
{ "max_subquestions": 6, "max_recheck": 3, "max_evidence": 60,
  "citation_weight": 0.2, "deep_read_top_n": 5 }
```

**시연 직전에 값만 바꿔 짧게 돌릴 수 있어야 한다.** `ingest_jobs.params` 가 이미 그 패턴이다.

## 4. 근거·인용 구조

가장 어려운 건 **LLM이 인용을 지어내지 않게 하는 것**이다. 근거 표기가 틀린 리서치 도구는 안 쓰느니만 못하다. 인용을 두 종류로 나눈다.

### 4-1. 구조적 인용 — 틀릴 수 없는 쪽

`대표 논문 요약`은 **불릿 하나가 논문 하나**다. 불릿을 그 논문의 근거만 넣고 생성하면 **인용이 추론이 아니라 구조로 정해진다.** 모델이 인용을 고를 일이 없다.

여기에 하나 더 건다 — **논문 제목·저자·연도는 모델 출력에서 가져오지 않고 DB 레코드에서 직접 렌더한다.** 모델은 요약 본문만 쓴다. 라벨을 모델이 쓰게 두면 언젠가 없는 논문을 만들어낸다.

### 4-2. 마커 인용 — 검증하는 쪽

`도입 문단`과 `향후 연구 방향`은 여러 논문을 가로지르므로 구조로 못 정한다. 프롬프트에 근거를 `E1`…`En` 으로 주고 모델이 `[E3]` 로 달게 한 뒤 **후처리에서 전수 검증한다.**

- 해석 안 되는 마커 → 칩을 제거한다 (조용히 통과시키지 않는다)
- 마커 없는 문장 → 남기되 개수를 센다
- 임계 초과 시 **한계 섹션에 "근거 표기가 없는 서술 N건"으로 기록**

### 4-3. 근거 단위

```
Evidence {
  id        "E12"                      보고서 안에서만 유효한 지역 ID
  cnts_id   "KCI_FI000850832"
  meta      제목 · 저자 · 학술지 · 권호 · 연월 · 피인용 · 등재구분
  chunks[]  { chunk_id, text, page_start, page_end, score }   최대 2~3개
}
```

**칩 호버에 초록이 아니라 `chunks[].text` 를 띄운다.** 디비피아는 초록을 보여주지만 우리는 `book_sections` 에 본문이 있으므로 **그 문장의 실제 출처 대목**을 쪽수와 함께 보여준다. 근거가 여럿이면 `1/2` 페이지네이션.

`원문 보기` 는 UCI·DOI가 없으므로 **자체 상세 페이지 `/papers/{cnts_id}`** 로 보낸다.

### 4-4. 랭킹 — 피인용 정규화 (함정)

피인용을 그대로 쓰면 **오래된 논문이 무조건 이긴다.** 2002년 논문은 24년간 쌓았고 2024년 논문은 2년이다. 최댓값 879회도 십중팔구 초기 연도 논문이다. 그대로 쓰면 "최근 동향"을 물었는데 2003년 논문만 올라온다.

**연간 피인용(`kci_citations / 경과연수`)으로 정규화한다.** 최종 점수는 리랭킹 점수를 주로 하고 정규화된 영향력을 보조 가중으로 얹는다. 가중치는 `params.citation_weight`.

**화면에는 원본 값(`피인용 41회`)을 그대로 보여준다.** 정규화는 순위에만 쓴다 — 사용자가 검증할 수 있어야 한다.

`grade`(KCI 등재 구분)도 보조 신호로 쓸 수 있다.

### 4-5. 저장 형식

`research_jobs.report` JSONB 한 덩어리. 프론트는 이것만 받아 칩을 렌더하고 호버도 같은 데이터로 띄운다 — 추가 요청이 없다.

```json
{ "range": { "from": "2002", "to": "2026", "n_papers": 72054 },
  "sections": [
    { "heading": "...", "intro": "...",
      "papers": [ { "cnts_id": "...", "summary": "...", "evidence": ["E12"] } ],
      "future": [ { "text": "...", "evidence": ["E3", "E7"] } ] } ],
  "evidence": { "E12": { "cnts_id": "...", "meta": {}, "chunks": [] } },
  "limitations": [ "..." ] }
```

## 5. 화면

- **진입**: 논문 검색창에서 `/deep-research <질문>`. 진입장벽이 낮고 "같은 검색창인데 더 깊은 모드"라는 서사가 산다.
- **계획 승인**: 하위질문 목록 + `수정` / `승인 및 진행`
- **진행 패널**: 단계 타임라인 + 실시간 카운터(검토한 논문 · 채택 근거 · 재검색). **자기점검이 근거 부족을 판정하고 검색어를 바꾸는 순간을 명시적으로 강조한다** — 이게 "검색 도구"와 "판단하는 에이전트"를 가르는 장면이다.
- **보고서**: 섹션별 렌더 + 인용칩 + 호버 팝업

## 6. 실패 처리

**부분 실패는 전체 실패가 아니다.** 하위질문 6개 중 5개만 답해도 쓸모 있는 보고서다.

| 상황 | 처리 |
|---|---|
| 계획 수립 LLM 실패 | job `failed`. 근거가 없으니 재시도가 깨끗하다 |
| 하위질문 검색 0편 | 실패 아님. `근거 없음`으로 남기고 진행, 한계에 기록 |
| 재검색 상한까지 부족 | 진행. 한계에 "근거 3편으로 결론이 약함" 기록 |
| 종합 LLM 실패 | 1회 재시도. 실패 시 job `failed` 이되 **steps·근거는 보존** → 종합 단계부터 재개 |
| 워커 사망 | `updated_at` stale 감지 후 status 되돌려 재개 |
| Milvus·DB 오류 | 해당 step만 `failed`, 나머지 하위질문은 계속 |

종합만 재실행할 수 있는 것이 `stage`/`status` 분리의 값이다. 5분 탐색을 다시 돌리지 않는다.

## 7. 테스트 전략

LLM과 Milvus는 mock하고 순수 함수를 촘촘히 덮는다.

- 계획 파싱 — 모델이 번호 매김을 흐트러뜨려도 하위질문이 떨어지는지
- **마커 검증 회귀 — 없는 `[E99]` 를 뱉었을 때 칩이 만들어지지 않는지.** 인용 무결성의 마지막 방어선이라 가장 중요하다
- 피인용 정규화 — 2002년 879회와 2024년 40회의 순위가 뒤집히는지
- 재검색 루프 상한 — 항상 "부족"을 반환하는 critic을 물려도 멈추는지
- 근거 조립 — 청크 여러 개가 한 evidence로 묶이고 쪽수가 맞는지

**mock 입력의 타입을 실제와 맞춘다.** round03에서 임베딩을 `list[float]` 로 mock해 테스트가 통과했는데 운영에서 `numpy.float32` 로 터진 일이 있다(`docs/ops/recurring-gotchas.md`).

## 8. 병행 운영 작업 — 시연 분야 우선 인덱싱

딥리서치 코드와 독립적이며 병렬로 진행한다.

시연 분야는 **문헌정보학 + 교육·심리**다. 문헌정보학은 도서관 대회 주제와 정확히 맞고 심사위원이 결과를 즉석에서 검증할 수 있다.

| 학술지 | 인덱싱됨 | 카탈로그 | 미적재 |
|---|---|---|---|
| 한국도서관·정보학회지 | 384 | 808 | 424 |
| 한국기록관리학회지 | 35 | 314 | 279 |
| 기록학연구 | 52 | 193 | 141 |
| 정보관리학회지 | 113 | 124 | 11 |
| 한국문헌정보학회지 | 44 | 51 | 7 |
| 기록과 정보·문화 연구 | 0 | 31 | 31 |
| **문헌정보학 합계** | **628** | **1,521** | **893** |

문헌정보학만이면 143건/h로 약 6시간. 교육·심리 물량은 **미측정**(§10).

절차: `kci-full-236k` 를 `paused` 로 세우고 → 해당 분야 매니페스트로 잡 생성·실행 → 재개. 대량 잡은 어차피 11월까지 가므로 반나절 지연은 손실이 아니다.

이러면 시연이 이렇게 된다 — 해당 분야 질문에는 최신까지 답하고, 범위 밖 질문에는 자기점검이 "이 주제는 2009년까지만 수록됐다"고 스스로 밝힌다. **코퍼스가 성장 중이라는 사실이 약점이 아니라 정직하게 드러나는 시스템 특성이 된다.**

## 10. 구현 계획 분할 권고

이 spec 하나가 계획 하나로는 크다. 백엔드(패키지 6모듈 · 테이블 2 · API 4 · Celery · Redis 중계)와 프론트(슬래시 진입 · 계획 승인 · 진행 패널 · 보고서 렌더 · 인용칩 호버)가 각각 독립적으로 완결된다.

**백엔드를 먼저 세우고 프론트를 그 위에 얹는 2단계**를 권한다. 백엔드가 서면 `curl` 로 SSE와 보고서 JSON을 확인할 수 있어 프론트 작업의 기준이 생긴다. 시연 일정이 빠듯하면 프론트 단계에서 진행 패널과 인용칩을 우선하고 계획 승인 UI를 뒤로 미룰 수 있다 — API는 이미 있으니 자동 승인으로 돌리면 된다.
