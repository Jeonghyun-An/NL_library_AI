## 0. 사용자 프롬프트 (paraphrase)

> 이 적재 파이프라인을 nanet 에 옮겨 운영하다가 세 가지를 고쳤다 — 병렬화가 제대로 안 됐고, 섹션 요약에서 뒤가 버려졌고, 섹션이 너무 크게 잘렸다. SKOVIX 도 같은 이유로 느린지 보고 고칠 것을 찾자.

2026-10-01 운영에 GET 만 보내(잡 조회 API, gemma·VLM `/metrics`, 섹션 조회) 쟀다. nanet 의 첫째(섹션 요약 순차)는 SKOVIX 에 해당하지 않았다. 대신 다른 병목 두 곳이 번갈아 막고 있었고, 데이터를 잃거나 버리는 결함이 여럿 있었다(§1-1). 사용자는 그 18개를 한 라운드에 모두 고치기로 했다.

> 일단 pause 해둘테니깐 전수 바꾸자.

본 잡 `kci-full-236k` 는 그날 pause 했다(in-flight 0, 08:11 UTC). `dev` `9798f46` 에서 `feat/round07-ingest-pipeline-fix` 를 따 계획의 Task 0~12 를 구현하고, 태스크마다 리뷰했다.

2026-10-02 에 이어서 마무리했다. 리뷰를 반영하던 중 운영 `nl-lib-celery-cpu` 의 `pip show` 로 운영 opendataloader-pdf 가 개발 PC 의 2.5.0 이 아니라 2.5.9 라는 것을 알았다(`fe1be0c`). 2.5.9 의 markdown 은 `& < >` 를 HTML 엔티티로 낸다. 사용자는 이스케이프를 되돌리기로 했고, java 힙 상한은 서버 메모리(`free -g` — RAM 251GB, 가용 131GB)를 보고 3g 로 정했다. 그 뒤로는 사용자 승인을 받아 차례로 했다.

1. `dev` 머지("응 머지해").
2. 이미지 빌드·Docker Hub push 와 `dev` push("응 이미지 올리고 push도 해").
3. 운영 스택 정의를 받아 round07 변경만 얹어 돌려줬다("원래 스택인데 바꿀 부분 고쳐서 줘").
4. 사용자가 런북 §9 로 배포·카나리·재처리·재개를 했다.

같은 날 round05a 의 `/round-finish` 가 `dev→main` 을 올리면서 round07 도 `main` 에 들어갔다. 그 뒤 사용자 요청("main으로 round5 작업하면서 승격했어. 문서 작성해")으로 이 교본과 완료노트를 썼다. 함께 낸 작은 덩어리 round07b(초기 SKOVIX 화면 `/search-classic` 되살리기)는 06 챕터다.

즉 **운영 진단 → 설계(18개) → 태스크별 구현·리뷰 → 영역별 최종 리뷰 → 운영 판 맞춤(2.5.9) → 재리뷰 → `dev` 머지 → 운영 배포·카나리 → 실패분·빈 본문 재처리·본 잡 재개** 순서로 이어진 라운드다. DB 칼럼과 화면(round07b 밖)은 건드리지 않았다.

### 1-3. 아이템 하나가 지나는 길 (round07 뒤)

```text
[celery-beat] 30초 틱 (expires 25초)
   └→ [celery-control ×1] dispatch_job_items — stale 복구(실행 중/대기 분리) → id 순으로 pending·백오프 지난 failed
        └→ chain(run_token=T) ─────────────────────────────────────────────────────────────
           extract      q_cpu   celery-cpu ×4    ODL(자식 프로세스·-Xmx3g·상한) → 쪽 판정(문서 단위 스캔본)
                                                 → OCR 2쪽씩 동시(VLM 8석) → 섹션. 0개면 강제 재추출 → no_text|vlm_error
           summarize    q_llm   celery-llm ×4    섹션 요약 ∥ [논문] 보강 — 세마포어 하나 → 보강 아티팩트(T)
           embed_index  q_embed celery-embed ×1  청킹 + 보강 아티팩트(T 와 같을 때) → BGE-M3 → Milvus
                                                 (PDF 가 있던 논문인데 추출 아티팩트가 없으면 artifact_missing)
           finalize     q_llm   celery-llm ×4    계층 요약 입력 1회(시간 예산) → 요약·소개글 동시, 논문 표지 없음
        단계마다: FOR UPDATE 로 읽어 토큰·done·체크포인트 대조 → 아니면 Ignore(체인 정지)
                  BookLock 실패 → Ignore(락 경합) · 시작/성공/실패 기록마다 토큰 재대조
```

### 1-4. 새 설정 (03 챕터 §2.29 에 전체)

`x-common-env` 에 새로 선언한 12개와 기본값이 바뀐 1개다. 모두 `${이름:-기본값}` 이라 스택 env 로 바꿀 수 있다(선언이 없으면 Portainer 가 무시한다).

## 4. 면접식 Q&A

**Q1. nanet 에서 고친 세 가지가 SKOVIX 에도 그대로 해당했나?**
A. 셋 다 다른 모양으로 있었다. ① 병렬화 — nanet 이 고친 섹션 요약 순차는 해당하지 않았다(SKOVIX 는 이미 세마포어로 동시에 보냈다). 대신 스캔본 쪽을 하나씩 OCR 하는 순차가 있었고, 사용자는 nanet 에서 겪은 문제라며 꼭 고치게 했다("vlm 병렬처리도 꼭 진행하고", spec 2). ② 뒤가 버려지는 문제는 다른 모양으로 있었다 — 문서 요약 입력이 14,000자를 넘으면 균등 샘플링으로 마지막 섹션이 빠졌다(계층 요약, spec 13). ③ 섹션 과대 분할도 있었다 — 문장 5개 이하 분기에 크기 상한이 없어 표·통계 문서가 섹션 하나가 될 수 있었다(spec 12). 그리고 nanet 목록에 없던 병목(embed 칸 안의 보강 LLM 대기)과 데이터를 잃는 결함이 나왔다. 이식이 아니라 같은 질문으로 다시 잰 것이 맞았다. (§1-1)

**Q2. 18개를 왜 한 라운드에, 한 번에 배포했나? 위험이 커지지 않나?**
A. 배포 비용이 항목 수가 아니라 배포 횟수에 비례하기 때문이다. 앱 서비스는 모두 같은 `:latest` 이미지라 스택 업데이트 한 번이 적재 워커 전부를 재생성한다(함정 16). 그래서 배포마다 본 잡 pause → in-flight 0 → 재생성 → 카나리 → 재개가 든다. 위험은 세 가지로 줄였다. 태스크마다 리뷰하고 영역별 최종 리뷰·재리뷰를 했다. 카나리를 문제 유형별로 골라 18개가 각각 드러나게 했다. 카나리 지표마다 멈춤 기준을 미리 적어(런북 9-7) 하나라도 걸리면 본 잡을 재개하지 않게 했다. 되돌리기도 in-flight 0 에서 이미지 태그와 옛 스택 정의로 하도록 런북에 적었다. (§1-2, 04 챕터)

**Q3. 병목이 둘인데 진행 상한 32 를 올려 둘을 겹쳐 돌리지 않은 이유는?**
A. 두 병목이 같은 GPU 를 쓰기 때문이다. VLM·gemma·임베딩이 GPU 0 을 함께 쓰므로 겹쳐 돌리면 서로 느려진다 — VLM 동시 추출이 3 이상이면 ODL 문서의 embed 평균이 11.6 → 19.6초로 늘었다. 얻는 것은 6~9%(추정)인데, 대기열이 길어지면 stale 오판이 커져 중복 체인 위험이 늘었다. 그래서 상한은 그대로 두고 각 병목 안의 낭비(embed 칸의 LLM 대기, 쪽 순차 OCR)를 없앴다. gemma 자리(16)를 늘리지 않은 것도 같은 까닭이다 — 자리를 다 채운 구간에서 처리량이 오히려 1.89 → 1.71건/초로 줄었다. (spec 6)

**Q4. 운영 판(2.5.9)을 라운드 막바지에 알았다. 무엇을 다시 했고 교훈은?**
A. 판정의 근거를 다시 쟀다. 같은 45건을 두 판으로 돌려 쪽 수·표 충전율·OCR 판정이 같은지 봤고(같았다), 다른 점(markdown 이스케이프)을 되돌리기로 맞췄다. jar 상수와 원본 출력으로 이스케이프 범위가 셋뿐임을 확인했고, 운영 이미지(리눅스) 안에서도 쪽 본문·충전율·OCR 판정이 같았다(1차 코드 기준). 버전은 `==2.5.9` 로 고정하고, 되돌리기가 그 판을 전제로 한다는 것을 테스트가 본다. 교훈은 "관찰은 운영과 같은 판으로" 다 — 함정 22번으로 남겼고, 런북 9-2 는 ODL 판을 바꾸는 배포라면 같은 비교를 다시 하라고 적는다. (05 챕터, 01 챕터 §2.4)

**Q5. 실패분 재처리를 왜 `reset_stage: "pending"`(추출부터)으로 했나? 그냥 retry 하면 안 되나?**
A. 실패의 대부분이 추출 결과 자체가 틀린 것이었다. '섹션 없음' 545건은 스탬프만 남은 스캔본이라 옛 추출이 섹션 0개를 냈고, `extract_empty` 275건도 추출이 비었다. 체크포인트에서 이어 하면 같은 빈 추출 결과로 다시 실패한다. 새 라우팅(문서 단위 스캔본 판정)으로 다시 추출해야 본문이 생긴다. `llm_error` 264건도 같은 규칙으로 추출부터 보냈다(spec §4 — 실패분은 그룹마다 `reset_stage: "pending"`). '카탈로그 row 없음' 15건은 카탈로그 문제라 다시 돌려도 같아 보내지 않았다. (04 챕터 §1-1)

**Q6. 빈 본문 완료분을 왜 따로 골라 다시 돌렸나? 새 코드로 끝난 문서는?**
A. 옛 코드가 '완료'로 끝낸 문서 가운데 본문이 거의 없는 것이 있었다(추정 약 907건) — 09-03 일시 코드 구간·VLM 실패 뒤 ODL 폴백·빈 표 격자·부분 본문 등이다. 실패가 아니라 완료라 retry 대상에 들지 않으므로, 쪽당 본문 글자 수로 따로 골랐다(832건). 배포 시각 뒤에 끝난 문서는 새 코드가 처리한 것이라 다시 돌려도 같으므로 `--finished-before` 로 뺐다. 다음 날 다시 끝난 문서의 쪽당 글자 수를 보는 질의를 런북 9-10 에 적었다. (04 챕터 §2.38)

**Q7. 이 라운드에서 DB 칼럼을 하나도 더하지 않은 까닭은?**
A. 새 상태를 모두 아이템 `meta` JSON 에 둔 것은 기존 테이블 무변경 원칙 때문이다(spec 18). 그러면 되돌리기가 이미지 태그와 스택 정의만으로 끝난다 — 마이그레이션을 되돌릴 일이 없다. 대가는 질의 쪽이다. JSON 숫자인지 확인하고(`jsonb_typeof`) 키 존재와 값을 가려야 한다(`->>` 와 `IS NOT NULL` — 함정 10번). 카나리·재처리 SQL 이 모두 그 규칙을 따른다. 배포 전에 `meta` 칼럼이 jsonb 인지 런북 9-1 이 본다 — 수동 retry 가 jsonb 연산(`||`)으로 토큰을 덮기 때문이다. (03 챕터)

**Q8. 재개 뒤 잡 조회에서 `running` 이 4건뿐이고 `dispatched` 가 28건이다. 정상인가?**
A. 정상이다. 잡 하나가 동시에 들고 있는 아이템은 32건까지이고(`INGEST_HIGH_WATER`), `running` 은 첫 단계를 시작한 아이템, `dispatched` 는 보냈지만 아직 추출 칸을 못 잡은 아이템이다. 추출은 `celery-cpu` 4칸이 한다. 재개 직후에는 다시 보낸 1,916건(실패분 1,084 + 빈 본문 832)이 앞 id 라 먼저 나가는데, 대부분 스캔본이라 문서마다 모든 쪽을 OCR 하느라 몇 분씩 걸린다. 4칸이 그 문서를 붙잡고 나머지는 큐에서 기다린다. 실제 천장은 VLM 이다 — 4칸 × 문서 안 2쪽 = 8 = VLM `max-num-seqs`. 상한 32 를 올려도 큐만 길어진다. 재처리분이 빠지면 추출이 몇 초인 ODL 문서가 와서 요약·embed 쪽이 차고 처리량이 오른다(추정 340~390건/h). (§3-5)

**Q9. 임베딩 512토큰 절단을 알고도 고치지 않은 이유는?**
A. 영향은 크다 — `[핵심 테마]`·`[섹션 요약]` 머리가 약 270토큰을 먹어 본문 자리는 약 440자이고, 본문 청크의 50~60% 가 잘려 본문 글자의 35~45% 가 벡터에 들어가지 않는다. 그런데 바꾸면 새 벡터가 기존 약 620만 청크와 섞인다. 효과를 보려면 전부 다시 임베딩해야 하는데, `run_embed_index` 를 다시 돌리는 방식은 쓸 수 없다 — 마무리가 추출 아티팩트를 지워 논문이 초록으로 대체되고 기존 청크가 지워진다(이제는 `artifact_missing` 이 막는다). Milvus 본문과 섹션 요약·테마로 다시 임베딩하는 전용 경로가 필요해, 적재가 끝난 뒤 별도 라운드로 정했다. (spec §3)
