# round04a 교본 (3) — 계획·자기점검·탐색

> 이 교본 하나로 round04a 전체를 클론코딩할 수 있어야 한다. 코드는 저장소 파일을 그대로 수록했다(`GIT_WORKFLOW.md` §개발 가이드 문서).

전체 개요·검증·Q&A 는 [00-개요.md](00-개요.md) 참조.

## 이 챕터의 자리

하위질문 루프를 이루는 세 단계(계획·탐색·자기점검)와, 탐색이 올라타는 기존 검색 경로(`pipeline.py`·`reranker.py`)의 변경을 다룬다.

```text
계획 태스크   make_plan(question) → research_plan.yaml → parse_plan → ["하위질문", …]
                                                        │ 사용자가 고치거나 승인
실행 태스크   하위질문마다 runner.explore_subquestion
               ├ explore(query)       → pipeline.search(청크·논문, 검색만) → 서지 조회 → rank_hits
               ├ critique(subq, 근거) → research_critique.yaml → parse_verdict → Verdict
               └ insufficient 이고 상한 전이면 new_queries 중 안 써 본 검색어로 다시 explore
```

루프를 돌리는 `runner.py` 는 [04-오케스트레이션-워커-API.md](04-오케스트레이션-워커-API.md), 여기서 쓰는 상태 객체·점수·근거 조립·JSON 추출은 [01-데이터모델과-상태.md](01-데이터모델과-상태.md)에 있다. 이 챕터의 세 모듈(`planner`·`explorer`·`critic`)은 전부 **한 번의 호출**만 책임진다 — 계획 한 번, 검색 한 번, 판정 한 번. 반복·상한·근거 번호 매기기·트랜잭션 경계는 러너 몫이다.

이 챕터를 관통하는 원칙은 둘이다.

- **모델 출력은 흐트러진다는 전제로 받는다.** 계획은 번호 목록을 관용적으로 읽고, 판정은 못 읽으면 루프를 끝내되 "못 읽었다"는 사실을 따로 들고 간다. 파싱은 LLM 호출과 떼어 네트워크 없이 테스트한다.
- **공용 검색 경로의 기본 동작은 바꾸지 않는다.** `pipeline.py` 에 넣은 인자는 전부 기본값이 기존 동작이고 딥리서치만 다른 값을 넘긴다. 예외가 하나 있다 — 리랭크 폴백의 예외 좁힘은 모든 호출자에게 적용된다(§2.18).

머지 전 리뷰에서 들어온 이 챕터의 변경(`query_key` 공용화·점검 전송 오류의 판정 불가 처리·날짜 필터 끔·리랭크 전 필터·보강 청크 제외·폴백 예외 좁힘·CPU float32)은 **라이브 검증 이후**다. 라이브 검증은 `b6360b8` 코드로 했고, 반영분은 아직 운영에 배포하지 않았다(완료노트 §2·§8).

## 2. 구현 (클론코딩)

### 2.14 `research_plan.yaml` — 계획 프롬프트

질문 하나를 하위질문 번호 목록으로 나누게 하는 프롬프트다. 변수는 `question` 과 `limit`(= `params["max_subquestions"]`, 기본 6) 둘이다. `parser: plain`(후처리 없음 — 이 필드를 읽는 것은 적재 요약기뿐이다)이고, 응답 문자열은 `make_plan` 이 그대로 `parse_plan` 에 넘긴다.

**JSON 이 아니라 번호 목록을 받는다.** 계획의 출력은 문자열 목록 하나뿐이다. 필드가 셋인 판정(§2.16)과 달리 구조가 필요 없으므로 번호 목록으로 받고, 모델이 번호 매김을 흐트러뜨리는 것은 파서가 흡수한다(`planner.py` 모듈 docstring — "모델이 번호 매김을 흐트러뜨리는 것은 흔한 일").

**규칙 문장마다 코드 쪽 짝이 있다.** 프롬프트는 부탁이고, 강제는 코드가 한다.

| 프롬프트 규칙 | 실제로 보장하는 코드 |
|---|---|
| 하위질문은 최대 `{{ limit }}`개 | `parse_plan` 의 `items[:limit]`. 승인 때 사용자가 고친 계획은 `api/research.py` `_validated_plan` 이 422 |
| 서로 겹치지 않게 | `parse_plan` 이 `query_key` 로 중복 제거. 승인 계획도 같은 키로 422 |
| 번호 목록으로만, 서론·맺음말 금지 | 항목 모양이 아닌 줄은 `parse_plan` 이 버린다(`test_preamble_is_dropped`) |

**"그 자체로 논문 검색어가 될 만큼 구체적이어야"가 가장 무거운 줄이다.** 탐색은 쿼리 재작성을 끄고(`use_rewrite=False`, §2.20) 하위질문 문장을 그대로 임베딩해 Milvus 에 보낸다. 검색어를 만드는 일을 계획 단계가 떠맡는다는 계약이 이 한 줄이다.

**템플릿 변수명은 런타임에서야 터진다.** 프롬프트 로더(`services/prompts.py`)는 Jinja `StrictUndefined` 라, 호출부 kwargs 와 변수명이 어긋나면 워커에서 `UndefinedError` 가 난다. `test_prompts.py` 의 렌더 회귀([03-보고서-종합과-인용.md](03-보고서-종합과-인용.md))와 `TestMakePlan`(§2.21)이 실제 템플릿을 통과시켜 이걸 로컬에서 잡는다.

**라이브에서 본 것 — planner 는 결정적이지 않다.** 같은 질문에서 세 번째 하위질문이 한 번은 `공공도서관 서비스 품질 평가 모델`, 한 번은 `서비스 품질 평가 모델 (SERVQUAL 등) 적용 사례 - 공공도서관` 으로 나왔다(완료노트 §2). 그래서 시연은 미리 돌려둔 보고서를 여는 방식을 권한다(완료노트 §8). 이 파일은 첫 커밋(`61ea7ea`) 이후 바뀌지 않았다.

### 2.15 `planner.py` — 계획 파싱과 검색어 중복 키

`make_plan()` 은 템플릿을 렌더해 `chat()` 을 한 번 부르고 결과를 `parse_plan()` 에 넘긴다. 이 파일의 실질은 파서다.

**관용도가 중요한 이유 — 실패가 전부 아니면 전무다.** 항목으로 읽힌 줄이 하나도 없으면 `parse_plan` 이 `ValueError` 를 던지고, 계획 태스크(`research_tasks._plan_deep_research`)는 plan step 과 잡을 `failed` 로 둔다. 계획이 없는 잡은 `POST /retry` 가 409 라 사용자는 새 잡을 만들어야 한다(spec §6 구현 시 변경). 원인은 모델이 마크다운을 조금 다르게 쓴 것뿐인데 잡이 죽는다. 그래서 모델의 실제 출력 습관만큼은 받아내야 한다.

**강조를 벗기는 순서와 범위가 요점이다.**

1. **줄 전체를 감싼 강조를 항목 매칭보다 먼저 벗긴다**(`_unwrap_line`). 모델이 `**1. 가**` 처럼 항목 전체를 굵게 쓸 때 `_ITEM` 매칭을 먼저 하면 앞의 `*` 가 불릿으로 먹혀 매칭이 깨진다. 모든 줄이 이 모양이면 위의 전멸이다.
2. **줄 전체 강조와 내용 안 강조를 나눈다.** `_WRAP` 은 여는 표식 바로 뒤가 공백이 아닐 것(`(?=\S)`)을 요구한다. 불릿 뒤에는 공백이 오므로 `* **가**` 의 앞 `*` 는 강조로 오인되지 않고 불릿으로 남는다. 두 처리를 한 정규식으로 합치면 불릿 `*` 와 뒤쪽 강조 `*` 가 짝지어져 내용이 사라진다.
3. **쌍으로 감싼 강조만 벗긴다**(`_PAIRED_EMPH`). 초안은 `` [*_`]+ `` 를 위치와 무관하게 전부 지워 `TF_IDF 가중치` 를 `TFIDF 가중치` 로 훼손했다. 논문 검색어에는 밑줄이 든 식별자가 실제로 온다. 중첩된 강조는 `_strip_emphasis` 가 더 바뀌는 것이 없을 때까지 반복해 벗긴다.

**중복은 원문이 아니라 정규화 키로 가린다 — `query_key`.** 공백을 한 칸으로 접고 `casefold()` 한다. `AI 윤리` 와 `ai  윤리` 는 같은 검색을 두 번 돌린다. 하위질문 하나가 중복되면 탐색(Milvus 검색)과 점검(LLM 호출)이 최대 4라운드(첫 검색 1 + `max_recheck` 기본 3) 헛돈다. 비교만 키로 하고 **저장하는 것은 먼저 나온 원문 그대로**다. 중복 제거가 `limit` 자르기보다 먼저라 중복이 자리를 먹지 않는다.

`query_key` 는 처음엔 `parse_plan` 안의 한 줄이었다. 머지 전 리뷰(`2bac7ee`)에서 같은 규칙이 세 곳에 필요해져 공개 함수로 뺐다.

| 쓰는 곳 | 막는 것 |
|---|---|
| `planner.parse_plan` | 모델이 낸 계획의 중복 |
| `api/research.py` `_validated_plan` | 사용자가 승인 때 고친 계획의 중복(422) |
| `runner._next_query` | critic 이 제안한 검색어 중 이미 시도한 것의 재검색 |

세 곳이 각자 비교하면 "계획에서는 중복이 아닌데 재검색에서는 중복"인 식으로 규칙이 갈라진다.

**해석하지 못한 줄은 `debug` 로 남긴다.** 전멸이면 `ValueError` 메시지에 모델 응답 앞 120자가 실리고, 워커가 그 문자열을 plan step 의 `error` 로 기록한다.

**리뷰에서 바뀐 것.**

- Task 5 리뷰(`a29c9a7`) — 위 1·2·3 과 정규화 중복 키. 초안(`61ea7ea`)은 `_ITEM` 매칭 뒤 전역 문자 제거, 원문 그대로의 중복 비교였다.
- 머지 전 리뷰(`2bac7ee`) — `query_key` 추출.

**알면서 남긴 것**(low, 리뷰 98 · 완료노트 §8). 아래는 현재 코드로 직접 돌려 확인한 동작이다.

- 번호가 든 **부분** 굵게(`**1. 소득 격차:** 설명`)는 `_WRAP` 에도 `_ITEM` 에도 맞지 않아 줄째 탈락한다. `(1) 가`·`① 가` 도 탈락한다.
- 들여쓴 하위 불릿(`   - 소득`)이 독립 하위질문으로 올라오고, `limit` 에서 뒤쪽 최상위 항목을 밀어낼 수 있다.
- 밑줄이 **둘**이면 짝으로 벗겨진다 — `1. TF_IDF와 BM_25 비교` 는 `TFIDF와 BM25 비교` 가 된다. 하나일 때만 막혀 있다.

셋 다 계획 실패로 드러나거나, 승인 단계(`POST /api/research/{id}/approve` 의 계획 수정)에서 사용자가 고칠 수 있는 모양이다. 데이터를 해치지 않는 실패라 이번에는 두었다(완료노트 §4 고치지 않은 것).

**파일**: `app/services/research/planner.py` — 전체 81줄

```python
"""planner.py — 질문을 하위질문으로 분해

파싱을 LLM 호출에서 분리한 이유: 모델이 번호 매김을 흐트러뜨리는 것은
흔한 일이고, 그 처리를 네트워크 없이 테스트할 수 있어야 한다.
"""
import logging
import re

from services.llm_client import chat
from services.prompts import get_prompt

log = logging.getLogger(__name__)

_ITEM = re.compile(r"^\s*(?:\d+[.)]|[-*•])\s+(.+?)\s*$")
# 줄 전체를 감싼 강조. 여는 표식 뒤가 공백이 아닐 것을 요구해야 불릿과 구분된다 —
# "* **가**" 의 앞 "*" 는 불릿이지 강조가 아니다.
_WRAP = re.compile(r"^\s*(\*\*|__|\*|_)(?=\S)(.*?)\1\s*$", re.S)
# 쌍으로 감싼 강조만 벗긴다. 전역으로 [*_`] 를 지우면 TF_IDF → TFIDF 처럼
# 본문 중간 문자까지 훼손된다.
_PAIRED_EMPH = re.compile(r"(\*\*|__|\*|_|`)(?=\S)(.+?)\1")
_WS = re.compile(r"\s+")


def _unwrap_line(line: str) -> str:
    """`**1. 가**` 처럼 항목 전체를 감싼 강조를 벗긴다.

    이걸 항목 매칭보다 먼저 해야 한다. 안 그러면 앞의 `*` 가 불릿으로 먹혀
    매칭이 깨지고, 모든 줄이 탈락해 계획 수립이 통째로 실패한다.
    """
    m = _WRAP.match(line)
    return m.group(2) if m else line


def query_key(text: str) -> str:
    """검색어 중복 판정 키. "AI 윤리" 와 "ai  윤리" 는 같은 검색을 두 번 돌린다."""
    return _WS.sub(" ", text.strip()).casefold()


def _strip_emphasis(text: str) -> str:
    prev = None
    while prev != text:
        prev = text
        text = _PAIRED_EMPH.sub(r"\2", text)
    return text


def parse_plan(raw: str, *, limit: int) -> list[str]:
    """번호/불릿 목록에서 하위질문을 뽑는다. 중복·공백 제거, limit 개까지.

    강조를 항목 매칭보다 먼저 벗기는 이유: 모델이 `**1. 주제**` 처럼 항목
    전체를 굵게 쓰면 앞의 `*` 가 불릿으로 먹혀 매칭이 깨진다. 그러면 모든
    줄이 탈락해 계획 수립이 통째로 실패하고 job 이 죽는다.
    """
    items: list[str] = []
    seen: set[str] = set()
    for line in (raw or "").splitlines():
        m = _ITEM.match(_unwrap_line(line))
        if not m:
            if line.strip():
                log.debug("[planner] 항목으로 해석되지 않은 줄 — %r", line.strip()[:80])
            continue
        text = _strip_emphasis(m.group(1)).strip()
        key = query_key(text)
        if text and key not in seen:
            seen.add(key)
            items.append(text)
    if not items:
        raise ValueError(f"계획을 해석하지 못했다: {(raw or '')[:120]!r}")
    return items[:limit]


async def make_plan(question: str, *, params: dict) -> list[str]:
    limit = params["max_subquestions"]
    system, user, llm_params = get_prompt("research_plan").render(
        question=question, limit=limit,
    )
    raw = await chat(
        [{"role": "system", "content": system}, {"role": "user", "content": user}],
        params=llm_params,
    )
    return parse_plan(raw, limit=limit)
```
따라 친 뒤 관용도를 눈으로 확인한다. 굵게 감싼 항목·굵게 쓴 불릿·밑줄 하나가 살아남고, 공백·대소문자만 다른 중복은 먼저 나온 원문으로 남는다.

```bash
$ cd app && python -c "from services.research.planner import parse_plan; print(parse_plan('**1. 가**\n* **나**\n1. TF_IDF 연구\n2. ai  윤리\n3. AI 윤리', limit=6))"
['가', '나', 'TF_IDF 연구', 'ai  윤리']
```

### 2.16 `research_critique.yaml` — 자기점검 프롬프트

하위질문 하나와 거기 모인 근거 목록을 주고 충분한지 판정하게 하는 프롬프트다. 변수는 `subquestion`·`tried_queries`·`evidence_count`·`evidence_list`·`min_evidence` 다섯이고, 응답은 `verdict`·`note`·`new_queries` 세 필드의 JSON 이다.

**판단 기준의 순서가 곧 우선순위다.** 첫 줄이 "본문 발췌를 보고, 제목만으로 짐작하지 말고"이고 편수는 맨 끝에 "부족할 가능성이 높습니다"로만 둔다. 그리고 따로 한 문단을 들여 **편수는 필요조건이 아니라 신호 중 하나**라고 못 박는다. 코퍼스가 2002–2009 년에 쏠려 있어 `min_evidence`(기본 5)를 못 채우는 하위질문이 정상적으로 나오는데, 그걸 전부 부족으로 판정하면 재검색이 상한까지 헛돈다(plan Task 6). 코드도 같은 입장이다 — `critic.py` 는 편수로 판정을 뒤집지 않고, `min_evidence` 는 프롬프트에만 들어간다.

**JSON 예시는 유효한 JSON 골격이어야 한다.** 초안의 예시는 한 줄짜리 `{"verdict": "sufficient" 또는 "insufficient", …}` 였다 — 값 자리에 "또는"이 들어간, JSON 이 아닌 설명문이다. 모델이 이 모양을 흉내 내면 곧장 파싱 실패다. 이 코드베이스의 `curation.yaml` 관례대로 **유효한 JSON 골격**으로 바꾸고 값 자리는 꺾쇠 플레이스홀더(`<…>`)로 두었으며, 허용값은 아래에 문장으로 따로 적었다(`a29c9a7`).

**프롬프트의 규칙마다 코드가 한 번 더 막는다.** 계획 프롬프트(§2.14)와 같은 구조다.

| 프롬프트 규칙 | 코드 쪽 방어 |
|---|---|
| verdict 는 sufficient/insufficient 만 | 다른 값이면 `parse_verdict` 가 판정 불가(`parse_failed`)로 |
| new_queries 는 항상 배열 | 문자열이 오면 `parse_verdict` 가 빈 목록으로(글자 단위 쪼개짐 방지) |
| 이미 시도한 검색어와 다르게 | `runner._next_query` 가 `query_key` 로 시도한 검색어를 건너뛴다 |

**note 는 사용자에게 그대로 보인다.** 탐색 경로와 진행 패널에 실리고, 하위질문이 부족하거나 근거가 0편이면 보고서 "한계와 미확인 영역"의 사유(`— {note}`)가 된다. 그래서 "한국어로 구체적으로"를 요구한다.

함정 15번(모델은 프롬프트 JSON 예시의 **개수**를 베낀다)에 이 프롬프트를 대 보면, `new_queries` 예시는 원소 2개로 허용 상한("최대 2개")과 같다. 러너는 그중 안 써 본 첫 검색어 하나만 쓴다 — 개수를 베껴도 구성이 틀어지지 않는 자리다.

**리뷰에서 바뀐 것.** 초안(`20f81bc`)은 편수 기준이 첫 줄이었고 발췌 이야기가 없었다. `a801099` 에서 발췌 기준 한 줄을 더했고, Task 5·6 리뷰(`a29c9a7`)에서 기준 순서를 바꾸고 편수를 신호로 낮추고 JSON 골격을 고쳤다.

**라이브에서 본 것.** 리허설(하위질문 3·재검색 1)에서 세 하위질문 모두 재탐색 후에도 `insufficient` 였다. 사유는 "평가 지표 자체의 심층 분석 부족", "시기 편중(2004~2006)", "공공도서관 특화 모델 부족" — 코퍼스 빈틈으로 보이며, 한계 섹션이 이를 그대로 드러냈다(완료노트 §2). 모른다고 말하는 것이 이 기능의 값이라는 spec §2-4 의 의도대로다.

### 2.17 `critic.py` — 판정 파싱·근거 목록·판정 불가

`critique()` 가 근거 목록을 문자열로 만들어(`format_evidence_list`) 프롬프트를 렌더하고, LLM 응답을 `parse_verdict()` 로 `Verdict` 로 바꾼다. `should_recheck()` 는 "한 번 더 돌까"의 순수 판정이고, 루프 자체는 러너가 돈다.

**근거마다 본문 발췌를 붙인다.** 제목·연도만으로는 "이 논문이 하위질문을 실제로 다루는가"를 모델이 판단할 수 없어 판정이 사실상 편수 세기가 된다. 그래서 그 하위질문 검색에서 실제로 매칭된 청크(`chunks[0]`)의 앞 200자를 붙인다. 한 논문이 여러 하위질문의 근거가 될 수 있으므로, 러너가 청크를 **그 하위질문 몫**으로 추려서 넘긴다(`runner._as_seen_by` → `citations.chunks_for`). 청크가 없는 근거는 제목+연도만 남긴다 — 인덱스 문제 하나로 점검 전체가 죽으면 안 된다.

**발췌는 자르기 전에 공백을 접는다.** 표 청크는 `[표]\n…\n{table_md}` 로 저장되고 본문 청크도 단락 개행을 보존한다. 그대로 쓰면 한 항목이 여러 줄로 퍼져 어느 발췌가 어느 논문 것인지 흐려진다. 말줄임표(`…`)는 실제로 잘렸을 때만 붙인다.

**빈 메타는 `get` 의 기본값이 아니라 `or` 로 받는다.** 이 코드베이스는 빈 서지를 `None` 이 아니라 `""` 로 표현하므로 `e.meta.get("title", "(제목 없음)")` 은 빈 문자열을 그대로 돌려준다(`test_empty_meta_values_fall_back`).

**근거 목록은 20편에서 끊는다(`_MAX_LISTED`).** 재검색 라운드마다 근거가 누적되는데 상한이 없으면 프롬프트가 컨텍스트를 넘고, 앞쪽부터 잘려 system 의 JSON 출력 지시가 사라진다. 그러면 산문 응답이 와서 판정이 또 실패하는 악순환이 된다. 잘린 수는 `- …외 N편` 한 줄로 알리고, `evidence_count` 는 전체 편수를 그대로 준다.

잘리는 쪽이 어느 근거인지가 중요하다. 머지 전 리뷰(리뷰 18)가 짚은 것이 이것이다 — 당시 `evidence_ids` 는 **채택 순서**(1라운드 전체 → 재검색 라운드)라, 20편을 넘으면 방금 재검색으로 보탠 근거가 `…외 N편` 으로 숨었다. critic 은 보완하려고 모은 근거를 못 보고 다시 판정했다. 고친 곳은 이 파일이 아니라 러너다 — 하위질문 안 순위(라운드별 1위 앞자리 보장 + `rank_score` 순, `runner._rank_order`)로 정렬해 넘긴다. 이 파일은 docstring 에 "잘리는 쪽이 순위 낮은 근거"라는 전제를 적어 두었다.

**판정을 못 읽었을 때 — 세 선택지 중 셋째를 골랐다.**

| 선택지 | 결과 |
|---|---|
| `insufficient` 로 떨어뜨린다 | 파싱이 깨질 때마다 재검색이 상한까지 돌아 시간을 태운다. 실패가 루프가 된다 |
| 그냥 `sufficient` 로 떨어뜨린다 | "모델이 충분하다고 판단한 것"과 구분되지 않는다. 자기점검이 전부 꺼져도 보고서가 "한계 없음"으로 보인다 |
| **`sufficient` + `parse_failed=True`** | 루프는 끝내고, 못 읽었다는 사실은 따로 센다 |

`parse_failed` 는 이렇게 흘러간다. 러너가 `subq.parse_failed` 로 옮기고(마지막 라운드 값으로 덮어써도 된다 — 판정 불가는 `sufficient` 라 루프가 거기서 끝나므로 늘 마지막 라운드다), `synthesizer.build_limitations` 가 "자동 점검을 완료하지 못한 하위질문 N건"으로 센다. `critique` 이벤트와 `report.trail` 에도 플래그로 실린다.

**모델 원문은 로그에만, note 는 중립 문장으로.** 초안은 실패를 `note="판정 해석 실패 — {원문 앞 80자}"` 로만 표시했다. 그 note 는 탐색 경로·진행 패널에 그대로 실리므로 모델 원문이 사용자 화면에 샜고, 반대로 한계 섹션은 `insufficient` 만 세서 실패를 못 봤다 — 노출이 정확히 뒤집혀 있었다. 지금은 원문을 `_failed` 의 `log.warning` 에만 남기고 note 는 `"자동 점검을 완료하지 못했다"` 로 고정한다. 한계 섹션은 판정 불가일 때 이 note 를 사유로 붙이지 않는다(같은 실패의 반복이라 집계 문장이 따로 센다). 모델 원문이 남는 곳은 로그뿐이므로 반드시 남긴다 — 원문 없이는 프롬프트를 고칠 수 없다.

**`parse_verdict` 의 나머지 방어.**

- JSON 추출은 `llm_json.extract_json` 에 맡긴다. 코드펜스를 벗기고 `raw_decode` 로 첫 유효 JSON 에서 멈춘다 — JSON 뒤 산문의 `}` 까지 먹지 않는다(종합도 같은 함수를 쓴다).
- `verdict` 는 `state.LLM_VERDICTS` 로 검사한다. 이 튜플은 `VERDICTS[1:]` 가 아니라 값 기준(`pending` 제외)으로 만든다 — 위치로 자르면 `VERDICTS` 순서만 바뀌어도 `sufficient` 가 빠져 모든 정상 판정이 "알 수 없는 verdict"가 된다.
- `new_queries` 가 문자열이면 빈 목록으로 둔다. 그대로 순회하면 `"진로상담 앱 효과"` 가 글자 단위로 쪼개져 `"진"` 한 글자로 재검색한다. 문자열이 아니거나 공백뿐인 원소도 버린다.

**판정 호출의 전송 오류도 판정 불가로 낮춘다 — 머지 전 리뷰에서 고친 것(리뷰 20).** 전에는 `critique()` 가 `chat()` 예외를 잡지 않았다. 타임아웃·5xx 가 러너를 빠져나가면 워커가 그 하위질문을 `failed` 로 두는데, 이때 탐색은 이미 끝나 근거가 모여 있다. 그런데 종합은 `failed` 하위질문을 "탐색 중 오류"로 보고해 앞 라운드에서 모은 근거까지 절에서 빠졌고, 그 근거는 `max_evidence` 예산만 차지한 채 남았다. 파싱 실패면 절을 유지하는데 전송 실패면 버리는 비대칭이었다. 판정을 받지 못한 것이지 탐색이 실패한 것이 아니므로 둘을 같은 `_unchecked()` 로 모았다.

잡는 것은 `Exception` 이 아니라 `httpx.HTTPError` 다. 타임아웃(`httpx.TimeoutException`)과 `llm_client.chat` 이 로그를 남기고 다시 던지는 `HTTPStatusError` 가 둘 다 여기 속한다. 같은 라운드의 규칙(함정 19번 재발 방지 — "폴백은 실제로 나는 실패 타입만 잡는다")과도 맞는다. 응답 모양이 깨진 경우(`KeyError` 등)는 여전히 올라가 그 하위질문이 `failed` 가 된다. 호출 타임아웃은 `chat()` 기본값 120초 그대로다.

**리뷰에서 바뀐 것.** `a801099` — 발췌 추가, 판정 실패 로깅. `a29c9a7`(Task 5·6 리뷰) — `parse_failed`, `new_queries` 타입 확인, 발췌 공백 접기, 20편 상한, JSON 추출 공용화. `2bac7ee`(머지 전 리뷰) — 전송 오류를 판정 불가로, 근거 순서 전제를 docstring 에.

    """판정 JSON 을 읽는다. 못 읽으면 sufficient 로 떨어뜨려 루프를 끝낸다.

    해석 실패를 insufficient 로 두면 파싱이 깨질 때마다 재검색이 상한까지
    돌아 시간을 태운다. 실패가 루프가 되면 안 된다.
    """
    data = extract_json(raw)
    if data is None:
        return _failed("판정 JSON 파싱 실패", raw)

    verdict = data.get("verdict")
    if verdict not in LLM_VERDICTS:
        return _failed(f"알 수 없는 verdict 값 {verdict!r}", raw)

    raw_queries = data.get("new_queries")
    if not isinstance(raw_queries, list):
        # 문자열이 오면 순회 시 글자 단위로 쪼개져 "진" 한 글자로 재검색한다
        raw_queries = []
    queries = [q for q in raw_queries if isinstance(q, str) and q.strip()]
    return Verdict(verdict, note=str(data.get("note") or ""), new_queries=queries)


def should_recheck(subq: SubQuestion, *, recheck_count: int, max_recheck: int) -> bool:
    return subq.verdict == "insufficient" and recheck_count < max_recheck


def format_evidence_list(evidence: list[Evidence]) -> str:
    """근거를 critic 프롬프트용 목록 문자열로 만든다.

    제목·연도만으로는 "이 논문이 하위질문을 실제로 다루는가"를 모델이
    판단하기 어렵다 — 그 하위질문 검색에서 실제로 매칭된 본문(chunks[0])의
    앞부분을 붙여 직접적인 근거로 준다. runner 가 청크를 그 하위질문 몫으로
    추려서 넘긴다(citations.chunks_for). 청크가 없는 근거는 제목+연도만
    남긴다 — 인덱스 오류로 이 계층 전체가 죽으면 안 된다.

    evidence 는 하위질문 안 순위순이다 — 상한에서 잘리는 쪽이 순위 낮은 근거다.

    발췌는 자르기 전에 공백을 접는다. 표 청크는 `[표]\\n…\\n{table_md}` 로
    저장되고 본문 청크도 단락 개행을 보존하므로, 그대로 쓰면 한 항목이
    여러 줄로 퍼져 어느 발췌가 어느 논문 것인지 흐려진다.
    """
    lines: list[str] = []
    for e in evidence[:_MAX_LISTED]:
        title = e.meta.get("title") or "(제목 없음)"
        year = e.meta.get("pub_date") or "연도미상"
        if not e.chunks:
            lines.append(f"- {title} ({year})")
            continue
        flat = " ".join(e.chunks[0].text.split())
        excerpt = flat[:_EXCERPT_LEN]
        if len(flat) > _EXCERPT_LEN:
            excerpt += "…"
        lines.append(f"- {title} ({year}) — {excerpt}")

    hidden = len(evidence) - _MAX_LISTED
    if hidden > 0:
        lines.append(f"- …외 {hidden}편")
    return "\n".join(lines) or "(없음)"


async def critique(
    subq: SubQuestion, evidence: list[Evidence], *, params: dict,
) -> Verdict:
    system, user, llm_params = get_prompt("research_critique").render(
        subquestion=subq.text,
        evidence_count=len(evidence),
        evidence_list=format_evidence_list(evidence),
        min_evidence=params["min_evidence_per_subq"],
        tried_queries=", ".join(subq.queries) or "(없음)",
    )
    try:
        raw = await chat(
            [{"role": "system", "content": system}, {"role": "user", "content": user}],
            params=llm_params,
        )
    except httpx.HTTPError as e:
        # 올려 보내면 워커가 하위질문을 failed 로 두고, 이미 모은 근거가 절에서
        # 빠진 채 "탐색 중 오류"로 보고된다. 파싱 실패와 같은 '판정 불가'로 낮춘다.
        log.warning("[critic] 판정 호출 실패 subq=%s — %s: %s", subq.idx, type(e).__name__, e)
        return _unchecked()
    return parse_verdict(raw)

### 2.18 `pipeline.py` — 검색만 하는 스위치 셋과 리랭크 폴백 좁힘

`main` 대비 변경은 셋이다. `search()` 에 인자 셋(`generate_answer`·`use_metadata_filter`·`chunk_filter`)을 더했고, 청크 모드가 그중 둘을 받아 확장·생성을 건너뛰거나 리랭크 전에 거른다. 그리고 두 모드의 리랭크 폴백 예외를 허용 목록(`_RERANK_FAILURES`)으로 좁혔다.

**왜 파이프라인을 복제하지 않고 스위치를 달았나.** 탐색은 논문 검색 화면과 같은 검색(질의 임베딩 → Milvus 하이브리드 검색 → 리랭크)이 필요하다. 필요 없는 것은 그 화면에 붙은 도서 검색용 전처리와 답변 생성이다. 그래서 `explorer.py` 는 "기존 검색 파이프라인을 그대로 쓰고"(모듈 docstring) 필요 없는 것만 끈다.

**기존 호출자의 기본 동작은 그대로다.** 새 인자를 넘기는 곳은 `explorer.py` 하나뿐이다(`app/api/book.py`·`app/api/paper.py`·`app/api/scenario.py`·`app/scripts/eval_*.py` 는 셋 다 넘기지 않는다 — `grep` 확인). 기본값이 옛 분기를 그대로 재현한다.

| 인자 | 기본값 | 기본값일 때 |
|---|---|---|
| `generate_answer` | `True` | db 있으면 확장+생성, 없으면 청크로 생성 — 옛 분기 그대로 |
| `use_metadata_filter` | `True` | `if db and True` 는 옛 `if db:` 와 같다 |
| `chunk_filter` | `None` | 거르지 않는다 |

테스트가 기본값 쪽을 고정한다 — `test_default_generates_with_expanded_context`(§2.24), `test_default_still_runs_the_filter_when_db_is_given`·`test_no_filter_keeps_the_live_behavior`(§2.25).

**`generate_answer=False` 는 생성뿐 아니라 컨텍스트 확장도 건너뛴다.** 확장이 먼저 컨텍스트 예산(`CONTEXT_BUDGET_TOKENS`, 기본 10만 토큰)만큼 원문을 끌어오므로, 답변을 버릴 호출자에게는 둘 다 낭비다. `explore` 는 `resp.chunks` 만 읽는다. 기본 파라미터면 한 잡에 탐색이 6~24회(하위질문 6 × (첫 검색 1 + 재검색 최대 3)) 도는데, 그 횟수만큼 공유 GPU 로 확장+생성을 하고 전부 버리고 있었다. Task 7 리뷰(`a168e1d`)에서 들어왔다.

**`use_metadata_filter` — db 유무가 날짜 필터 스위치를 겸하고 있었다.** 원래 코드는 `if db:` 면 `extract_metadata_filter`(LLM)로 날짜 조건을 뽑아 Milvus `pub_date` 식을 붙였다. 이 프롬프트(`metadata_filter.yaml`)는 도서관 검색어용이라 "YYYY년 단독 언급 → 그 해만" 규칙이 있다. `explore` 는 서지 조회에 쓰는 워커 세션을 `db` 로 넘기므로 하위질문마다 이 필터가 조용히 돌았다(리뷰 29·47). "2006년 도서관법 전부개정이 공공도서관 운영에 미친 영향"이 `pub_date >= "2006" && pub_date < "2007"` 이 되어 그 뒤 연구가 전부 빠지고, "1994년 …"이면 코퍼스(2002년~)에서 0건이 된다. 그 조건은 탐색 경로 어디에도 남지 않아 한계 섹션에는 "근거를 찾지 못했다"만 적힌다. 탐색 1회마다 LLM 호출도 하나씩 붙었다. 리뷰 제안대로 기본값 `True` 인 명시 인자로 떼어냈다(`2bac7ee`).

**`chunk_filter` — 자르기 전에, 리랭크 전에 거른다.** 탐색은 메타청크(`chunk_idx=-1`)와 원문 대목이 아닌 보강 청크를 근거에서 빼야 한다(§2.20). Task 7 리뷰 때는 `explore` 가 파이프라인 결과에서 메타청크를 사후에 걸렀다. 그런데 파이프라인은 리랭크 뒤 `chunks[:top_k]` 로 잘라서 돌려주고, 메타청크는 제목·초록을 품어 주제형 질의에서 리랭크 점수가 잘 나와 상위 슬롯을 차지한다. 사후에 거르면 걸러진 수만큼 `per_subq_top_k` 가 조용히 줄었다(리뷰 28·108) — 기본값 12개를 요청했는데 메타청크 5개가 섞이면 본문은 7개다. 근거 수가 `min_evidence` 에 못 미치면 critic 이 부족으로 판정하기 쉬워 재검색이 늘 수 있다.

리뷰가 낸 대안은 둘이었다 — Milvus 식에 `chunk_idx >= 0` 을 붙이는 옵트인 플래그, 또는 `explore` 가 `top_k` 를 넉넉히 받아 거른 뒤 자르기. 구현은 둘 다 아니고 **리랭크 전 필터 콜백**이다. 그 결과로 성립하는 것:

- Milvus 후보는 `top_k × CHUNK_MODE_FETCH_MULTIPLIER`(기본 4)개다. 그 안에서 거른 뒤 리랭크하고 `top_k` 로 자르므로, 후보가 꽉 찼다면 4분의 3 을 넘게 걸러지는 극단이 아닌 한 `top_k` 가 채워진다. `explore` 가 배수를 추측할 필요가 없다.
- 버릴 청크에 cross-encoder 연산을 쓰지 않는다.
- **무엇을** 거를지는 `explorer.is_source_passage` 가, **언제** 거를지는 파이프라인이 정한다. 메타청크와 보강 청크(라벨+쪽수 0) 판정이 한 함수에 모이고, 그 함수는 Milvus 없이 테스트된다(§2.23).

논문 검색 화면은 `chunk_filter` 를 넘기지 않으므로 여전히 메타청크가 결과에 섞인다. 라이브 경로라 기본값을 그대로 두었다 — 그 화면에서도 거를지는 별건이다.

**리랭크 폴백 예외를 허용 목록으로 — 함정 19번.** 폴백은 원래 `except Exception` 이었다. Celery 의 `SoftTimeLimitExceeded` 는 `Exception` 의 하위이고, 소프트 리밋 시그널 핸들러는 메인 스레드에서 바이트코드 사이에 예외를 올린다. 동기 코드인 리랭크(torch forward) 도중에 리밋이 걸리면 예외가 이 `except` 에 잡혀 "리랭킹 실패, 벡터 점수 유지" 경고 한 줄로 삼켜지고 탐색이 계속된다(리뷰 79, 스크래치 재현). 리뷰 당시 코드(데드라인 도입 전)에서는 이 경로로 워커의 소프트 리밋 정리가 돌지 않고, 하드 리밋(35분)에 프로세스째 죽어 잡과 step 이 `running` 에 남았다(함정 19번 증상). 리뷰는 CPU 로 리랭크하는 과도기 구성(§2.19)이면 이 구간에서 가장 걸리기 쉽다고 봤다.

지금 워커의 1차 방어는 잡 본문의 asyncio 데드라인(`JOB_DEADLINE`, 25분)이다. 그런데 `asyncio.timeout` 은 await 지점에서만 끊으므로 await 가 없는 동기 리랭크 도중에는 끊지 못한다 — 그 구간의 백스톱이 소프트 리밋(30분)이고, 이 좁힘은 백스톱이 삼켜지지 않게 한다. 같은 삼킴이 남은 `relay.publish` 를 완료노트 §8 이 low 로 둔 이유도 여기 있다 — 데드라인이 소프트 리밋보다 먼저 만료되므로, 삼켜져도 다음 await 에서 밀려 있던 데드라인 취소가 걸린다. 목록(`RuntimeError`·`OSError`·`ValueError`·`ImportError`)은 리랭커가 실제로 내는 실패다 — 모델 로드, 설정·토크나이저, torch 연산(CUDA OOM 포함). 허용 목록으로 좁히면 `services` 계층이 `celery` 를 import 하지 않아도 된다. 도서 모드의 도서 내 리랭크도 같은 목록으로 좁혔다.

**이 좁힘만은 모든 호출자에게 적용된다.** 이 diff 에서 기존 동작을 바꾸는 유일한 변경이다 — 리랭커가 목록 밖 예외를 내면 도서·논문 검색 API 에서도 폴백 대신 예외가 올라간다. `search()` 경로에 남은 넓은 예외 처리는 둘이고(답변 생성 함수 안의 `except Exception` 은 생성과 함께 건너뛴다), 둘 다 딥리서치 경로에서는 돌지 않는다.

- 컨텍스트 확장 실패의 `except Exception` — `generate_answer=False` 라 `explore` 는 그 분기에 들어가지 않는다. Celery 안에서 `pipeline` 을 부르는 것은 딥리서치뿐이다(리뷰 79 — `app/workers` 검색 결과).
- 전처리의 `asyncio.gather(..., return_exceptions=True)` — 재작성과 날짜 필터를 둘 다 끄면 `coros` 가 비어 `gather` 자체를 부르지 않는다.

### 2.19 `reranker.py` — GPU 가 없으면 float32

`_load_model()` 이 장치를 먼저 정하고, 그 장치에 맞는 dtype 으로 모델을 올린다. GPU 면 `float16`, 아니면 `float32`. 장치 판정(`torch.cuda.is_available()`)을 `from_pretrained` 앞으로 옮긴 것은 dtype 을 로드 시점에 정해야 하기 때문이다.

**왜 — 딥리서치가 GPU 없는 워커에서 리랭커를 부른다(함정 17번).** 딥리서치 큐의 기본값은 아직 `q_llm` 이라, 전용 워커로 넘기기 전(과도기)에는 탐색이 `celery-llm` 에서 돈다. `celery-llm` 은 외부 vLLM 을 HTTP 로 부르는 적재 요약 전용이라 GPU 예약도 모델 캐시 마운트도 없다. 그런데 `pipeline.search()` 는 BGE-M3 와 리랭커를 **워커 프로세스 안에서** 올린다. 기존 코드(`main`)는 `torch_dtype=torch.float16` 고정이라 여기서 CPU 반정밀도로 올라갔다. CPU 반정밀도는 빨라지지도 않고 연산에 따라 정밀도·지원이 흔들린다(코드 주석).

리뷰(118)는 두 갈래 위험을 적었다. (a) 반정밀도 미지원 연산이 예외를 내면 탐색 전부가 리랭크 없이 RRF 점수로 조용히 끝나고 보고서는 `completed` 로 저장된다. (b) 연산이 돌면 탐색 1회마다 수십 쌍을 CPU 반정밀도로 계산해 잡이 길어지고, 소프트 리밋에 닿으면 §2.18 의 삼킴으로 이어진다. 검증 단계는 둘 다 입증하지 못해 PLAUSIBLE 로 남겼다 — 검증자는 운영 이미지의 torch 2.4.1 이 CPU 반정밀도 주요 연산을 지원하는 버전대라 (a) 의 개연성은 낮고, (b) 는 라이브 실측(`cdb44716` 실행 34초)과 맞지 않는다고 봤다. 그래도 고친 것은 확실한 쪽 때문이다 — GPU 가 없는 프로세스에서 반정밀도는 얻는 것 없이 정밀도·지원만 흔든다.

GPU 가 있는 프로세스는 바뀌지 않는다. FastAPI 와 전용 워커 `celery-research`(GPU 예약·모델 캐시·`--concurrency=1`)는 `cuda` 경로라 여전히 `float16` 이다. `float32` 경로는 과도기 구성을 위한 것이다.

**docstring 도 사실에 맞췄다.** FastAPI 는 lifespan 에서 `warmup()` 으로 올리지만 딥리서치 워커는 첫 호출 때 올린다.

**알면서 남긴 것**(low, 완료노트 §8). 과도기 `celery-llm` 은 prefork 자식 4개가 torch 스레드 제한(`torch.set_num_threads`·`OMP_NUM_THREADS`) 없이 CPU 리랭크를 나눠 쓰고, 워커 기동 때 리랭커를 올려 보는 검증(`worker_process_init` 워밍업)도 없다. 리랭커가 깨져 있어도 첫 탐색에서야 드러난다. 전용 워커로 넘기면 해당하지 않는 과도기 문제라 두었다.

이 파일은 모듈 최상단에서 `import torch` 한다. `pipeline.py` 가 이 파일을 최상단에서 import 하므로, `pipeline` 을 최상단에서 import 하는 모듈은 전부 torch 가 필요해진다 — §2.20 의 함정 13번 이 여기서 시작된다.

### 2.20 `explorer.py` — 하위질문 1회 탐색

`explore(query, params, db)` 가 검색 → 서지 조회 → 피인용 가중 재정렬을 하고 `(정렬된 hit 목록, cnts_id → 서지 메타)` 를 돌려준다. 원문 대목 판정(`is_source_passage`)과 순위 계산(`rank_hits`)은 순수 함수로 떼어 Milvus 없이 테스트한다.

**`pipeline` 은 함수 본문 안에서 import 한다 — 함정 13번.** `pipeline.py` → `reranker.py` → `import torch` 인데, torch 는 로컬 venv 에 의도적으로 없다(`requirements.txt` 에 없고 Dockerfile 에서 CUDA 버전으로 따로 설치). 최상단에서 import 하면 `pytest` 가 collection 단계에서 `ModuleNotFoundError` 로 죽고 **세션 전체가 0건**이 된다. `rank_hits` 만 쓰는 테스트도 같이 죽는다. 코드베이스의 관례이기도 하다(`app/api/book.py:619`·`app/main.py:54`·`app/services/ingestion/stages.py:87`). 덤으로, 지연 import 덕에 테스트가 `sys.modules` 에 가짜 `pipeline` 모듈을 꽂아 `explore()` 를 통째로 돌릴 수 있다(§2.23).

**`search()` 에 넘기는 네 스위치 — 탐색은 검색만 시킨다.**

| 인자 | 이유 |
|---|---|
| `generate_answer=False` | 답변은 전부 버려진다. 보고서는 탐색이 끝난 뒤 synthesizer 가 하위질문별로 쓴다. 잡당 6~24회의 확장+생성 낭비 |
| `use_rewrite=False` | 쿼리 재작성은 도서 추천 전용이다(아래) |
| `use_metadata_filter=False` | 하위질문의 사건 연도가 발행연도 필터가 된다(§2.18) |
| `chunk_filter=is_source_passage` | 원문 대목만 남긴다. 리랭크·절단 전에 걸러야 `per_subq_top_k` 가 줄지 않는다(§2.18) |

**`use_rewrite=False` 의 이유는 둘이다.** 첫째, 프롬프트가 맞지 않는다. `query_rewrite.yaml` 의 유사도 규칙이 "제목·저자명은 쿼리에 절대 포함하지 마세요"이고 예시가 채식주의자·카프카·하루키다. 하위질문("부르디외 문화자본론을 적용한 국내 독서격차 연구")을 통과시키면 고유명사가 떨어져 분위기 키워드가 되고, "X 같은 책" 패턴에 걸리면 `_enrich_from_db` 가 쿼리를 그 책의 `themes` 로 통째로 갈아버린다. 계획 단계가 이미 검색어로 쓸 수 있는 문장을 낸다(§2.14). 둘째, 기록이 맞아야 진단된다. 러너는 검색 직전 문자열을 `subq.queries` 에 남기므로, 재작성이 켜져 있으면 탐색 경로와 `research_steps.result["queries"]` 가 **실제로 보낸 적 없는 쿼리**를 기록해 0건 하위질문을 사후에 진단할 수 없다. 날짜 필터를 끈 이유의 절반도 같다 — 걸린 조건이 기록에 남지 않는다.

**원문 대목 판정 — `is_source_passage`.** 인용칩은 "그 문장의 실제 출처 대목"을 쪽수와 함께 띄운다(spec §4-3). 그러니 근거가 될 수 있는 청크는 논문 원문에서 떼어 낸 대목뿐이다. 빼는 것은 둘이다.

- **메타청크(`chunk_idx == -1`).** 카탈로그 서지 덩어리("제목: … | 기관: … | 초록: …")다. `doc_type` 스칼라가 같아 `doc_scope="paper"` 를 통과하고, 제목·초록을 품어 주제형 하위질문에서 점수가 오히려 잘 나온다. 그대로 두면 보고서가 서지 덩어리를 "p.0-0" 발췌로 인용하고 critic 에게도 발췌로 들어간다. 도서 모드는 원래부터 메타청크를 뺐고, 청크 모드(논문 검색 화면)는 빼지 않는다.
- **쪽수 0 인 보강 청크 `[초록]`·`[키워드]`·`[표 설명]`·`[그림 설명]`.** 적재가 논문마다 본문 청크 뒤에 붙이는 청크로, 쪽수를 주지 않아 인덱싱 때 `page_start` 가 0 이 된다(`indexer.index_chunks` 의 `or 0`). 라벨별 출처는 `paper_enricher.py` 로 확인했다. `[표 설명]`(`interpret_table`)·`[그림 설명]`(`describe_figure`)은 LLM·VLM 이 쓴 서술로 논문에 없는 문장이다. `[키워드]` 는 헤더 추출이 실패하면 LLM(`generate_keywords`)이 만들고, 청크만 봐서는 어느 쪽인지 알 수 없으며, 목록이라 대목도 아니다. `[초록]` 은 원문이지만 같은 문장이 쪽수 달린 본문 청크에 이미 있고, 메타청크처럼 상위를 차지해 본문 대목을 밀어낸다. 이것들이 근거에 들면 칩이 모델이 쓴 문장을 원문 대목처럼 "p.0" 으로 띄운다(리뷰 68).

`[표]` 는 **남긴다.** `_extract_tables` 가 추출 본문의 표 마크다운과 그 앞 200자를 그대로 담은 원문이고, 적재가 수치 질문용으로 따로 둔 청크라 수치 근거가 된다. 라벨 문자열은 적재가 쓰는 모양(`stages.py` 의 `f"[초록] {…}"` 등, 뒤에 공백 하나)을 그대로 따른다.

**라벨과 쪽수 0 을 함께 요구한다.** 어느 하나만으로는 가를 수 없다.

- 라벨만 보면 — 쪽수가 있는 본문 청크가 우연히 `[표 설명]` 같은 글자로 시작해도 빠진다. 보강 청크는 쪽수가 **늘** 0 이므로, 쪽수가 있으면 본문이다(`test_label_lookalike_in_paged_body_is_kept`).
- 쪽수 0 만 보면 — PyMuPDF 쪽 번호(`page.number`)가 0 부터라 첫 쪽 본문도 0 이고, PDF 없이 초록을 본문으로 적재한 논문의 본문도 0 이다(`test_page_zero_body_is_kept`).

**점수 — `rerank_score` 가 `None` 일 때만 벡터 점수로.** `c.rerank_score if c.rerank_score is not None else c.score` 다. `0.0` 은 "리랭커가 이 청크를 버렸다"는 정보인데, falsy 로 판단(`c.rerank_score or c.score`)하면 버려진 청크가 벡터 점수(예: 0.7)로 되살아난다. `None` 은 리랭크가 폴백했을 때다(§2.18 의 허용 목록 예외).

**서지를 못 찾은 청크는 여기서 떨구고 로그를 남긴다.** `citations.build_evidence` 는 `meta_by_id` 에 없는 `book_id` 를 말없이 버린다. 그대로 넘기면 근거 수가 조용히 모자라 critic 이 `insufficient` 를 내고, 재검색이 상한까지 돌고도 로그에 흔적이 없다. Milvus 에는 있는데 `library_catalog` 행이 사라진 일이 실제로 있었다(함정 9번 — round03 카탈로그 전멸). 그래서 제외 건수와 `cnts_id`(최대 5개)를 `warning` 으로 남긴다. 서지 7개 필드는 `getattr(b, …, None)` 이 아니라 직접 속성 접근으로 읽는다 — `get_by_cnts_ids` 는 `dict[str, BookOut]` 을 돌려주고 `BookOut` 에 일곱 필드가 다 있다. `getattr` 기본값은 컬럼명이 바뀌어도 조용히 `None` 을 넣어 순위가 틀어지는 쪽으로 실패한다(plan Task 7). hit 이 없으면 서지 조회 자체를 하지 않는다.

"""explorer.py — 하위질문 1개를 탐색한다

기존 검색 파이프라인을 그대로 쓰고(논문 스코프) 원문 대목만 남긴 뒤, 그 위에
피인용 가중을 얹는다. 순위 계산은 rank_hits 로 빼서 Milvus 없이 테스트한다.
"""

from datetime import datetime

from sqlalchemy.ext.asyncio import AsyncSession

from schemas.book import ChunkHit

# 원문 대목이 아닌 논문 보강 청크의 라벨. 적재(services/ingestion/stages.py
# run_embed_index)는 논문마다 본문 청크 뒤에 보강 청크를 붙이는데, 쪽수를 주지 않아
# 인덱싱 때 page_start 가 0 이 된다(indexer.index_chunks 의 `or 0`). 라벨별 출처는
# services/ingestion/paper_enricher.py 에서 확인했다.
#   [표 설명]   interpret_table — LLM 이 쓴 서술이다. 논문에 없는 문장이다.
#   [그림 설명] describe_figure — VLM 이 쓴 서술이다. 역시 논문에 없다.
#   [키워드]   헤더 추출이 실패하면 generate_keywords(LLM)가 만든다. 청크만 보고는
#              어느 쪽인지 알 수 없고, 목록이라 대목도 아니다.
#   [초록]     extract_abstract 가 본문에서 그대로 떼어 낸 원문이다. 다만 같은 문장이
#              쪽수가 달린 본문 청크에 이미 있다. 또 메타청크처럼 주제형 질의에서 상위를
#              차지해 본문 대목을 밀어낸다.
# 이것들이 근거에 들면 인용칩이 모델이 쓴 문장이나 초록을 원문 대목처럼 "p.0-0" 으로 띄운다.
# [표] 는 남긴다 — _extract_tables 가 추출 본문의 표 마크다운과 그 앞 200자를 그대로
# 담은 원문이고, 적재가 수치 질문용으로 따로 둔 청크라 수치 근거가 된다.
_NON_SOURCE_LABELS = ("[초록] ", "[키워드] ", "[표 설명] ", "[그림 설명] ")


def is_source_passage(chunk: ChunkHit) -> bool:
    """근거로 인용할 수 있는 원문 대목인가. 메타청크와 생성·중복 보강 청크를 뺀다.

    라벨만 보지 않고 쪽수 0 을 함께 요구한다. 보강 청크는 쪽수가 늘 0 이라, 쪽수가
    있는 청크의 같은 글자는 본문에 우연히 나온 것이다. 반대로 쪽수 0 만으로는 가를 수
    없다 — PyMuPDF 쪽 번호(page.number)가 0 부터라 첫 쪽 본문도 0 이고, PDF 없이
    초록을 본문으로 적재한 논문의 본문도 0 이다.
    """
    # chunk_idx == -1 은 카탈로그 메타 청크다("제목: … | 기관: … | 초록: …").
    # doc_type 스칼라가 같아 doc_scope="paper" 를 통과하고, 제목·초록을 품어 주제형
    # 하위질문에서 점수가 오히려 잘 나온다. 그대로 두면 보고서가 서지 덩어리를
    # 발췌로 인용하고 critic 에게도 그게 발췌로 들어간다.
    if chunk.chunk_idx == -1:
        return False
    return not (chunk.page_start == 0 and chunk.text.startswith(_NON_SOURCE_LABELS))


def rank_hits(
    hits: list[HitRow], meta_by_id: dict[str, dict], *,
    citation_weight: float, now_year: int,
) -> list[HitRow]:
    """연간 피인용을 얹은 rank_score 로 다시 정렬한다. 입력은 건드리지 않는다.

    혼합값을 score 에 덮어쓰지 않는 이유: 혼합값은 1.0 을 넘는다. 리랭킹 0.92
    짜리 2024년 논문이 40회 인용됐으면 0.92 * (1 + 0.2*ln(14.33)) = 1.41 이다.
    score 를 유사도로 읽는 쪽은 그대로 "141%" 를 그리고, 생 리랭킹 점수는
    되찾을 길이 없어진다. 정렬은 rank_score 로, 표시는 score 로 한다.
    """
    ranked = []
    for hit in hits:
        meta = meta_by_id.get(hit["book_id"]) or {}
        impact = impact_per_year(
            meta.get("kci_citations"), parse_pub_year(meta.get("pub_date")),
            now_year=now_year,
        )
        row = dict(hit)
        row["rank_score"] = blend_score(hit["score"], impact=impact, weight=citation_weight)
        ranked.append(row)
    ranked.sort(key=lambda r: r["rank_score"], reverse=True)
    return ranked


async def explore(query: str, *, params: dict, db: AsyncSession) -> tuple[list[HitRow], dict[str, dict]]:
    """검색 → 서지 조회 → 피인용 가중 재정렬.

    returns (정렬된 hit 목록, cnts_id → 서지 메타)
    """
    # pipeline 은 reranker(torch) 를 물고 와 모듈 최상단에서 임포트하면 이 파일을
    # 단순히 열기만 해도(rank_hits 만 쓰는 테스트에서도) torch 가 있어야 한다.
    # 기존 코드베이스도 같은 이유로 지연 임포트한다(api/book.py·main.py 참고).
    from services.search.pipeline import search

    # generate_answer=False — 여기서 만든 답변은 전부 버려진다(resp.chunks 만 쓴다).
    # 보고서는 탐색이 끝난 뒤 synthesizer 가 하위질문별로 모은 근거만 받아 절마다 따로
    # 쓴다. 기본 파라미터로도 explore 는 한 잡에 6~24회 도는데, 여기서 생성하면 컨텍스트
    # 예산 10만 토큰짜리 확장+생성이 그 횟수만큼 공유 GPU 를 물고 아무것도 남기지 않는다.
    #
    # use_rewrite=False — 쿼리 재작성은 도서 추천 전용이다. query_rewrite.yaml 의
    # 유사도 규칙이 "제목·저자명은 쿼리에 절대 포함하지 마세요"이고 예시가
    # 채식주의자·카프카·하루키다. 하위질문("부르디외 문화자본론을 적용한 국내 독서격차
    # 연구")을 통과시키면 고유명사가 떨어져 분위기 키워드로 바뀌고, "X 같은 책" 패턴에
    # 걸리면 _enrich_from_db 가 쿼리를 그 책의 themes 로 통째로 갈아버린다. 계획
    # 단계가 이미 검색어로 쓸 수 있는 문장을 내놓는다(research_plan.yaml).
    # 기록도 이쪽이 맞다 — runner 는 검색 직전 문자열을 subq.queries 에 남기므로,
    # 재작성이 켜져 있으면 사용자에게 보이는 탐색 경로와 research_steps.result["queries"]
    # 가 둘 다 실제로 보낸 적 없는 쿼리를 기록해 0건 하위질문을 사후에 진단할 수 없다.
    #
    # use_metadata_filter=False — db 를 넘기면 파이프라인이 도서 검색어용 날짜 필터를
    # LLM 으로 뽑아 pub_date 조건을 건다(metadata_filter.yaml: "YYYY년 단독 → 그 해만").
    # 하위질문의 사건 연도("2006년 도서관법 전부개정의 영향")가 발행연도가 되어 그 뒤에
    # 나온 연구가 전부 빠지고, 그 조건은 탐색 경로 어디에도 남지 않는다. 재작성을 끈
    # 이유(보낸 검색을 그대로 기록해야 진단된다)가 여기에도 그대로 선다.
    #
    # chunk_filter — 원문 대목만 남긴다(is_source_passage). 파이프라인이 top_k 로 자르기
    # 전에 걸러야 걸러진 수만큼 per_subq_top_k 가 줄지 않는다. 논문 검색 화면이 쓰는
    # 라이브 경로라 기본값은 그대로 두고 여기서만 넘긴다.
    resp = await search(
        query, mode="chunk", top_k=params["per_subq_top_k"],
        doc_scope="paper", generate_answer=False, use_rewrite=False,
        use_metadata_filter=False, chunk_filter=is_source_passage, db=db,
    )
    hits: list[HitRow] = [
        {
            "book_id": c.book_id, "chunk_id": c.chunk_id, "text": c.text,
            "page_start": c.page_start, "page_end": c.page_end,
            "score": c.rerank_score if c.rerank_score is not None else c.score,
        }
        for c in resp.chunks
    ]
    if not hits:
        return [], {}

    repo = BookRepository(db)
    books = await repo.get_by_cnts_ids(list({h["book_id"] for h in hits}))
    meta_by_id = {
        cnts_id: {
            "title": b.title, "personal_author": b.personal_author,
            "series_title": b.series_title, "vol_issue": b.vol_issue,
            "pub_date": b.pub_date, "kci_citations": b.kci_citations,
            "grade": b.grade,
        }
        for cnts_id, b in books.items()
    }
    # 서지를 못 찾은 청크는 여기서 떨군다. build_evidence 가 meta_by_id 에 없는
    # book_id 를 말없이 버리기 때문에, 그대로 넘기면 근거 수가 조용히 모자라고
    # critic 이 insufficient 를 내 재검색이 상한까지 돌고도 로그에 흔적이 없다.
    # Milvus 에는 있는데 library_catalog 행이 사라진 일이 실제로 있었다
    # (docs/ops/recurring-gotchas.md 9번).
    kept = [h for h in hits if h["book_id"] in meta_by_id]
    if len(kept) < len(hits):
        orphans = sorted({h["book_id"] for h in hits if h["book_id"] not in meta_by_id})
        log.warning(
            "[explore] 서지 없는 청크 %d/%d 건 제외 — cnts_id %s",
            len(hits) - len(kept), len(hits), orphans[:5],
        )
    ranked = rank_hits(
        kept, meta_by_id,
        citation_weight=params["citation_weight"], now_year=datetime.now().year,
    )
    return ranked, meta_by_id

def _pipeline_search_params() -> set[str]:
    """pipeline.search 의 인자 이름을 소스에서 읽는다.

### 2.24 `test_search_chunk_answer_flag.py` — 답변 생성 스위치와 로더 격리

6건. 로더 격리 2건 + 동작 4건.

**진짜 `pipeline` 을 import 하는 방법.** `pipeline` 은 `reranker`(torch·transformers)와 `embedder`·`indexer`(FlagEmbedding·pymilvus)를 물고 온다. `_HEAVY` 중 **설치되지 않은 것만** `MagicMock` 으로 꽂고 `pipeline` 을 새로 import 한다. 그 뒤 Milvus 검색·확장·생성 함수를 대역으로 바꿔 호출 기록만 남긴다.

**로더의 정리가 복잡한 이유 — 머지 전 리뷰에서 고친 격리 결함.** `monkeypatch.delitem(sys.modules, name, raising=False)` 은 키가 **원래 없으면 아무것도 기록하지 않는다.** 그래서 여기서 새로 import 한 모듈(더미 torch·pymilvus 에 묶인 것)이 teardown 뒤에도 `sys.modules` 에 남아 뒤 순서의 테스트가 물려받았다(리뷰 109, 완료노트 §4 테스트 격리). 지금은 원래 있던 항목은 `monkeypatch` 가 되돌리게 두고, 새로 생긴 항목은 `yield` 뒤에서 직접 뺀다. 부모 패키지 속성(`services.search` 모듈의 `pipeline` 속성 등)도 같은 규칙으로 다룬다 — 문자열 경로 `monkeypatch` 는 `sys.modules` 보다 부모 속성을 먼저 따라가고, 되살아난 `sys.modules` 항목은 다시 import 해도 부모 속성을 되달지 않기 때문이다. 로더 테스트 2건이 `sys.modules` 를 찾은 그대로 되돌리는지와, 이미 올라와 있던 모듈이면 부모 패키지 속성까지 되돌리는지를 고정한다.

**동작 4건.** 기본값 `True` 는 확장+생성(기존 호출자 불변), `False` 는 확장·생성 모두 건너뛰고 검색 결과는 그대로, db 없는 경로도 `False` 면 생성하지 않음. 마지막 `test_search_threads_the_flag_into_chunk_mode` 는 `search()` 가 플래그를 청크 모드까지 실제로 넘기는지 본다 — 안 넘기면 `explore` 의 `generate_answer=False` 가 조용히 무시된다.

이 마지막 테스트는 머지 전 리뷰 47 을 반영해 **`db=MagicMock()`** 으로 부른다. 전에는 `db=None` 이었는데, 그러면 확장 분기와 날짜 필터 분기를 둘 다 건너뛰어 운영 호출 형태(워커 세션을 넘긴다)를 가렸다. 날짜 필터 호출은 대역이 예외를 던지게 하지 않고 **기록**으로 잡는다. `search` 는 전처리를 `asyncio.gather(return_exceptions=True)` 로 돌려 예외를 경고 로그로 삼키므로, 대역의 `AssertionError` 로는 테스트가 실패하지 않는다.

        if module is not None and getattr(sys.modules.get(parent), child, None) is module:

### 2.26 `test_search_reranker_dtype.py` — 리랭커 정밀도는 장치를 따른다

3건. 로더 격리 1건 + CPU·GPU 각 1건.

**torch·transformers 는 늘 대역으로 꽂는다.** §2.24 의 로더와 달리 설치 여부를 보지 않는다. 확인할 것은 장치 분기 하나이고, 실물 torch 가 있는 환경(컨테이너)에서도 결과가 같아야 한다. 대역 torch 의 `cuda.is_available()` 반환값만 바꿔 리랭커 모듈을 새로 import 하고 `_load_model()` 을 직접 부른 뒤, `from_pretrained` 에 넘어간 `torch_dtype` 과 모듈 전역 `_device` 를 본다.

**`is` 비교가 성립하는 이유.** `MagicMock` 은 같은 속성 이름에 늘 같은 자식 객체를 돌려주고, 이름이 다르면 다른 객체다. 그래서 `torch.float32` 와 `torch.float16` 이 서로 구별되는 표식이 되어 `_loaded_dtype(reranker) is torch.float32` 로 분기를 단언할 수 있다.
