## 1. 왜 했나 — 기준 잡과 DBpia 비교

round04b 운영 검증 잡 "컴퓨팅 자원에 대한 연구가 궁금해"(2026-09-29 10:20)의 보고서를 같은 질문의 DBpia AI 답변과 비교했다. 화면은 우리가 낫지만 내용은 DBpia 가 나았다. 기준 잡의 결과는 이렇다.

- 6절 27편. 근거 60편 가운데 HPC 가 32편이고, 질문의 핵심인 자원 관리는 2편뿐이었다. 근거 상한(`max_evidence` 60)이 잡 전체 공용이라 먼저 탐색한 하위질문이 가져갔다(round04a 완료노트 §8 이월).
- 하위질문이 HPC·클라우드·분산·병렬·엣지·자원관리였다. "컴퓨팅" 전반의 기술 분야 목록이 됐다.
- 엣지 절에 의료영상 *Edge method* 같은, 같은 단어를 다른 뜻으로 쓴 논문이 실렸다. 검색에 걸린 논문을 관련성 확인 없이 전부 채택했기 때문이다.
- 절마다 문체("~합니다"·"~다")가 섞였고, 한계 문장의 조사가 `' 는` 으로 고정돼 있었다.

원인과 코드 위치는 spec §1 표에 있다. 사용자가 추천 순서를 정했다. 먼저 **A·B·C·G** 를 하고(이 라운드), D(핵심 요약·주제 종합)·E(이어서 물어보기)·F(화면 참고문헌)는 다음 묶음으로 미뤘다(spec §0·§8).

- **reload 를 하는 이유**: round04b 배포 때 게이트웨이가 Recreate 전 IP 로 보내 502 가 났다. 그래서 fastapi·nuxt 를 Recreate 하면 마지막에 reload 한다(`recurring-gotchas.md` 20번 — round04b 에서 추가).
- DB 구조 변경이 없어 `alembic` 작업은 필요 없다(spec Q7). 적재 워커는 대상이 아니다(spec §9).

### 4-3. 남은 질 문제 3가지

1. **계획이 여전히 일반 틀이다 — C 미달.** 하위질문이 정의·방법론·적용 분야·성과·한계·동향으로 나왔다. 6개 하위질문이 모두 재검색을 거듭하고도 끝까지 "근거 부족"이었다.
2. **과잉 제외.** 「프록시기반 모바일 그리드 자원관리」·「웹기반 대용량 계산환경」처럼 원 질문 주제에 맞는 논문을 하위질문의 측면에 맞지 않는다는 이유로 뺐다. 지금 프롬프트의 제외 기준은 "발췌가 **하위질문의** 핵심 개념을 다루지 않는 근거"다.
3. **반대로 무관한 논문이 남았다.** 방법론 절에 「DI 한글읽기프로그램」·「발명교육」이 근거로 들어갔다. 원인은 아직 조사하지 않았다.

spec §7 의 운영 전후 비교 항목 가운데 ④ 문체가 "~다"로 통일됐는지는 이 노트에 확인 기록이 없다.

## 5. 결정

- **하위질문별 근거 예산 = `max_evidence // 하위질문 수`(최소 `min_evidence_per_subq` 5, 1 미만 금지).** 새 파라미터 없이 기존 두 값으로 정한다. 계획에서 하위질문을 지우면 남은 하위질문의 몫이 커진다(spec Q1). 하위질문 사이 재배분은 하지 않는다(spec §8).
- **`max_evidence` 90.** 60이면 6개 기준 10편씩이다. 첫 검색이 보통 8~10편을 채우므로 재검색이 보탤 자리가 없다(spec Q2). 검증 범위 상한 200 은 그대로다.
- **보고서 `evidence` 에는 절이 인용한 근거만 싣는다.** 상한을 올려도 보고서 JSON 이 붇지 않는다. 화면·문서는 칩으로만 근거를 조회한다(spec Q3).
- **무관 판정은 발췌를 읽는 critic 이 번호로 하고, 빼는 일은 러너가 한다.** 점수 하한은 데이터 없이 정하면 추측이다. 리랭커 점수 분포를 모은 뒤로 미뤘다(spec Q4·§8).
- **근거 없는 "충분"은 없다.** 보인 근거를 모두 빼면서 충분이라고 하면 부족으로 읽는다. 단 끈 잡(`exclude_off_topic=0`)은 뒤집지 않는다. 근거가 그대로 남아 판정이 본 근거가 있고, 뒤집으면 끈 잡만 재검색이 늘어 비교가 흐려진다(`43e66cc`).
- **걸러낸 것은 버리지 않고 보인다(§11-1).** critic 은 논문마다 이유를 쓰지 않는다(출력 토큰·파싱 위험). 그래서 펼친 목록 위에는 고정 문구 하나만 두고, 판단 근거(note)는 바로 아래 판정 줄이 보인다.
- **제외 수의 단위는 "건".** 하위질문별 판단의 수라 서로 다른 논문 수가 아니다(`83101cd`).
- **무관 제외는 잡 파라미터로 재배포 없이 끈다.** 화면 입력은 두지 않았다. 운영자가 API `params` 로 `{"exclude_off_topic": 0}` 을 넘긴다(spec §11-3).
- **프롬프트에 예시를 넣지 않는다(C).** gemma 는 예시의 개수·분야를 베낀다(함정 15번). 모델이 섞어 쓴 문체를 코드로 고치지도 않는다. 뜻이 바뀔 수 있다(spec §6).
- **새 잡 파라미터를 들이는 배포는 워커가 먼저다(§4-1).**
- **넓은 화면의 기본 보기는 보고서 전 B, 보고서가 나오면 A.** 손으로 고른 보기는 그 방문의 지금 단계에서만 따른다. 좁은 화면(1200px 미만)은 늘 B 다(round04b spec §7-5, 사용자 결정 2026-09-30). 기획자 시연에서 배치 A 가 덜 인터랙티브해 보인다는 평(round04b spec §7-4)을 받아, 과정은 크게 보이는 B 로 보여 준다.

## 7. 배운 점

1. **수치 합격 기준은 관련성을 재지 못한다.** "실린 논문 27편 이상"은 절 상한(6 × 5 = 30)에 가까워 거의 늘 채워진다. 첫 잡도 모든 절이 5편까지 찼지만, 그 안에 「발명교육」이 있었다. §11-4 기준은 "결과가 줄어 보이면 안 된다"는 우려에서 나와 양만 쟀다. 다음 비교 기준에는 절마다 실린 논문이 원 질문 주제에 맞는지 읽어 보는 항목을 넣는다.
2. **무관 판정을 하위질문에 걸면 계획의 질에 묶인다.** 계획이 "성과"·"동향" 같은 측면 틀로 나오면, 하위질문의 핵심 개념은 원 질문의 주제가 아니라 그 측면이 된다. 그 기준으로 critic 이 주제에 맞는 논문(모바일 그리드 자원관리)을 뺐다. critic 은 원 질문을 아예 받지 않는다(§10 ①). 제외 기준은 원 질문 주제에 걸어야 한다.
3. **LLM 필터는 양쪽으로 틀린다.** 한 잡에서 과잉 제외(②)와 누락(③)이 같이 나왔다. 제외 수만 보면 어느 쪽인지 모른다. §11 에서 뺀 논문을 버리지 않고 남겨 둔 덕에 무엇을 뺐는지 제목으로 짚을 수 있었다. 결과를 줄이는 자동 판단은 판단 대상을 남겨 보여 줘야 고칠 수 있다.
4. **(가설) 예시를 빼도 규칙 속 나열이 틀이 될 수 있다.** 계획 프롬프트는 측면을 "개념·정의, 방법·기법, 적용 분야, 성과·평가, 한계·과제 중 맞는 것"으로 나열했다. 첫 잡의 계획(정의·방법론·적용 분야·성과·한계·동향)은 그 나열과 거의 같다. 함정 15번(예시의 개수를 베낀다)과 같은 계열로 보이지만 한 잡뿐이라 확인하지 않았다. 계획 프롬프트를 다시 볼 때 이 나열부터 의심한다(§10 ②).
5. **약한 입력의 테스트는 경계를 가르지 못한다.** 근거 1편, "모두 뺀 경우" 하나 같은 입력으로는 "목록 밖 번호"와 "근거 없는 번호", "한 편이라도 빼면 재검색"과 "빼고 0편이면 재검색"이 갈리지 않았다. 품질 검토가 변이를 넣어 테스트가 실제로 실패하는지 확인하고 나서야 드러났다(§3).
6. **수의 단위는 무엇을 셌는지에 맞춘다.** `excluded` 는 하위질문별 판단의 수다. "편"으로 쓰면 검토·채택 수와 더해 맞아야 할 논문 수로 읽힌다. 첫 잡에서 제외 91건이 검토 121편에 견줘 크게 보이는 것도 이 셈 때문이다(`83101cd`).
7. **잡 파라미터를 API 가 합쳐 저장하는 구조에서는 새 키가 배포 순서를 정한다.** 소비하는 쪽(워커)이 먼저 새 키를 알아야 한다(§4-1).
