## 0. 사용자 프롬프트 (paraphrase)

> round04a 로 만든 딥리서치 백엔드에 화면을 붙이자. 기존 논문 검색창에서 들어가고, 진행은 별도 화면에서 보게 하자. 최종 목표는 입력창 앞의 `+` 버튼으로 딥리서치 같은 모드를 골라 함께 쓰는 것이다. 사이드바의 세션(검색 기록) 탭이 엉켜 있으니 이번에 같이 손보고, 나중에 DB id 기반 세션이 들어올 자리까지 설계해서 구현하자. **기존 데이터가 날아가는 일은 절대 없어야 하고 운영에 부담을 주지 않아야 한다.**

사용자는 이 프로그램의 개발자이자 설계자이며 총괄이다. 화면에 무엇이 나와야 하는지와 큰 구도는 사용자가 정하고, 시각 디자인과 세부 배치는 화면 기획자와 함께 다듬는다(spec §0). 그래서 spec 은 배치를 하나로 정하지 않고 **A(2단)·B(쌓이는 문서) 둘 다 되는 구조**로 짰고(D4), 기획자에게는 Figma 와이어프레임으로 넘겼다(spec §8).

§1~13 을 구현해 운영에 올린 뒤(2026-09-28) 두 번째 요청이 왔다.

> 보고서를 쓰는 동안(화면에 "보고서 작성 중 2/5" 만 뜨는 구간) 보여 주는 게 부족해서 기다리기 지루하다. 그리고 보고서를 문서로 내려받는 기능이 있었으면 좋겠다. 내려받기는 최종본이 완성된 뒤에 하는 게 깔끔하지만, 중간에도 저장할 수 있으면 그렇게 해 달라. (spec §14-0)

같은 시기 기획자 시연에서 배치 A(우측 패널에 탐색 과정)가 **"덜 인터랙티브해 보인다"**는 평을 받았고, 사용자는 **인터랙티브함이 매우 중요하다**는 방침을 세웠다(spec §7-4). §14 의 화면(현황 카드·초안)은 이 방침 아래 만들었다.

즉 **설계(2026-09-26 확정) → 계획 38개 태스크(백엔드 두 영역·프론트 두 영역) → 태스크마다 품질 검토 → 최종 리뷰 → 운영 배포 → §14 추가 설계·계획 11개 태스크 → 다듬기 → §14 운영 배포 → 운영 확인** 순서로 이어진 라운드다. 사용자 기록으로 구현 기간은 2026-09-23~28, 브랜치 커밋 시각은 2026-09-26 18:40(spec)부터 2026-09-29 00:14(§14 다듬기 마지막)까지다. dev 머지는 2026-10-01(`9b776d2`)이다.

### 1-2. 전체 흐름

```text
[논문 입력창] + 메뉴 / "/deep-research 질문"
   │ SearchPlusMenu: 캡처 단계로 엔터 가로채기
   ▼
POST /api/research (x-session-id → created_by) ─▶ PUT /api/history/{job_id} (kind=research)
   ▼
/research/<job_id>  ── useResearchJob ── GET /api/research/{id} → initialResearchView
   │                     EventSource /stream ─ snapshot → status·step·search·counters·critique·synth → 종료
   │                     applyResearchEvent (순수 리듀서) — 하트비트 snapshot·GET 재동기화도 같은 규칙
   ▼
 planning → awaiting(계획 카드·승인) → queued → exploring(진행 패널) → synthesizing(현황 카드 + 초안)
   → completed(보고서·인용칩·[다운로드]) | failed(재시도·멈춘 초안) | canceled(다시 시작·멈춘 초안)

[사이드바] useHistory ─ HybridStore(서버 → 실패 시 편지함) ─ 클릭 → routeFor(entry) → /?h=&q= · /papers?h=&q= · /research/<id>
[도서·논문 페이지] 주소(?h=)를 지켜봐 복원 · 검색 성공 시 router.replace({h, q})
```

### 1-4. round04a 가 남긴 백엔드 보강 목록은 어떻게 됐나

## 4. 면접식 Q&A

**Q1. 기록을 왜 서버로 옮겼고, 왜 새 테이블 하나만 더했나?**
A. 브라우저 저장만으로는 spec §1-2 의 증상 대부분을 못 푼다 — 쿼터에 걸리면 말없이 버리고(M3), 탭 둘이 서로 덮고(M4), 로컬 id 와 서버 id 를 이을 수 없다(M8). 나중에 DB id 기반 세션이 들어올 자리도 필요했다. 사용자 조건은 "기존 데이터 무손실·운영 부담 없음"이었다. 그래서 기존 `search_history`·`search_sessions` 는 읽지도 쓰지도 바꾸지도 않고 새 테이블 `history_items` 하나만 더했다. 이 저장소의 운영 스키마는 lifespan 의 `create_all` 이 만든다(함정 14번) — 새 테이블은 이미지가 뜰 때 생기고, 기존 테이블에 `ALTER` 가 없으니 잠금 문제(함정 18번)도 없다. 배포 뒤 `alembic stamp 0006_history_items` 로 버전만 맞췄다. 사용자가 지워도 행은 남는 소프트 삭제이고, 새 테이블은 기존 Postgres 정기 백업에 자동으로 포함된다. (본문 §2.1·§2.2)

**Q2. 로그인 없이 기록의 주인을 어떻게 가르나? 보안상 한계는?**
A. 브라우저 localStorage 의 UUID v4(`sid`)가 소유 단위다. 모든 `/api` 요청에 `x-session-id` 헤더로 싣고, URL 에는 싣지 않는다 — nginx access log 에 남지 않게. 서버는 행의 `session_id` 가 헤더와 다르면 **없는 기록과 똑같이 404** 를 준다. 구분하면 id 만으로 남의 기록이 있는지 떠볼 수 있다. 딥리서치 잡 생성은 브라우저 ID 를 `created_by` 에 넣지만 `GET /api/research/{id}` 에는 싣지 않는다 — 그 조회는 링크만 알면 누구나 여는데, 남의 브라우저 ID 가 나가면 그걸 헤더에 넣어 그 사람의 기록을 읽을 수 있다. 한계는 분명하다 — 브라우저 ID 를 아는 사람은 그 기록을 읽는다. 인증이 아니라 식별이다. 로그인은 비밀번호·세션 만료·탈취 대응이 따르는 보안 작업이라 대회 일정에 어설프게 넣으면 더 위험하다고 보고 `user_id` 컬럼 자리만 뒀다. 최종 형태는 도서관 회원 인증(SSO 등) 연결일 가능성이 크다. 브라우저를 바꾸거나 저장소를 지우면 새 ID 가 생겨 이전 기록이 사이드바에서 안 보인다(서버에서 지워지지는 않는다). (본문 §2.3·§2.6·§2.27)

**Q3. 기록의 PK 를 왜 브라우저가 만드나? 같은 요청이 두 번 와도 안전한가?**
A. 서버 응답을 기다리지 않고 주소(`?h=`)에 넣어야 하고, 실패한 뒤 다시 보내도 같은 행이 돼야 해서다. `PUT /api/history/{id}` 는 `INSERT … ON CONFLICT (id) DO UPDATE … WHERE session_id = excluded.session_id` 다. 같은 브라우저가 다시 보내면 목록 맨 위로 올라오고(`created_at = now()`) 지운 기록이면 되살아나며, 요청에 빠진 `snapshot`·`ai`·`ref_id` 는 `COALESCE` 로 기존 값을 지킨다 — 재전송이나 10분 중복 병합이 이미 받은 결과·AI 요약을 지우지 않게. 다른 브라우저의 행이면 `WHERE` 가 막아 0행이고 404 다. 이게 동작하려면 JSONB 칸이 파이썬 `None` 을 SQL NULL 로 써야 한다(`JSONB(none_as_null=True)`) — JSON `null` 이면 `COALESCE` 가 그것을 값으로 본다. 딥리서치 기록은 id 가 곧 `job_id` 다. 삭제도 멱등이다 — 이미 지운 내 행에도 204 를 준다. (본문 §2.1·§2.5)

**Q4. 보낼 편지함(outbox)은 무엇을 줄 세우고, 순서는 어떻게 지키나?**
A. 서버가 네트워크 단절·408·429·5xx 로 실패한 변경만 줄 세운다. 4xx 는 다시 보내도 같은 거절이라 버린다. 순서 규칙이 셋이다. ① 편지가 남아 있으면 새 변경을 서버로 바로 보내지 않는다 — 먼저 편지함을 비우고, 그래도 남으면 새 변경도 줄 선다. 순서가 뒤집히면 아직 서버에 없는 기록에 수정이 먼저 닿는다. ② 편지함은 앞에서부터 하나씩 보내고, 다시 보낼 만한 실패가 나면 거기서 멈춘다. ③ 이 탭의 동작은 부른 순서대로 끝낸다 — 변경은 앞의 모든 동작이 끝난 뒤 혼자 돌고, 읽기는 앞의 변경만 기다리며 읽기끼리는 나란히 돈다(프로미스 두 개로 만든 읽기-쓰기 잠금). 이게 없으면 저장이 끝나기 전에 누른 삭제가 서버에 먼저 닿아(404 → 성공) 늦게 끝난 저장이 기록을 되살린다. 덧붙여 축약 결과가 커서 413 이 나면 결과 없이 한 번 더 보낸다 — 4xx 라 편지함도 다시 안 보내니 그대로 두면 기록이 통째로 사라진다. (본문 §2.11 ①~④)

**Q5. 지운 기록이 되살아나는 경로가 몇 개였고 각각 어떻게 막았나?**
A. 리뷰에서 다섯 갈래가 나왔다. (1) 늦게 도착한 목록 응답 — 응답은 요청이 출발한 때의 서버 상태다. 삭제마다 순번을 올려 남기고, 요청이 출발한 뒤 지운 기록은 응답에서 버린다(`historyState`). (2) 늦게 도착한 저장 응답 — 같은 순번으로 막는다. (3) 저장이 끝나기 전에 누른 삭제 — 변경을 호출 순서로 직렬화한다(Q4 ③). (4) 다른 탭이 보낸 같은 편지 — 편지함은 모든 탭이 나눠 쓴다. 한 탭의 put 응답이 늦는 사이 다른 탭이 같은 편지를 보내 빼고, 사용자가 지우면, 늦게 닿은 첫 탭의 put 을 upsert 가 받아 되살린다. 그래서 편지함 보내기를 탭 사이에서 한 번에 하나만 돌린다 — Web Locks, 없으면(운영 게이트웨이는 http 라 없다) localStorage 한 키에 `기한|주인` 을 두는 잠금. 잠금을 쥔 **뒤에** 편지함을 읽어 앞 탭이 보낸 편지는 다시 보내지 않는다. (5) 메모리 모드로 넘어간 탭이 보낸 편지 — 저장소 사본에 남으면 다음 새로고침에 한 번 더 나간다. 보낸 편지는 저장소에서도 빼고, 다른 탭이 먼저 보내 빠진 편지는 보내지 않는다. 공통된 교훈은 "응답은 출발 시점의 사실이다"이다. (본문 §2.11 ④⑥⑦·§2.12)

**Q6. localStorage 쿼터는 어떻게 다루나?**
A. `QuotaExceededError`(브라우저마다 이름·코드가 달라 넷을 본다)만 덜어 내기로 처리하고, 다른 오류면 그 수명 동안 메모리 모드로 넘어간다. 캐시가 넘치면 가장 오래된 항목의 `snapshot` → `ai` 순으로 하나씩 비운다 — 목록은 남긴다(v1 은 5개씩 말없이 버렸다). 편지함이 넘치면 **캐시부터** 던다. 편지는 아직 서버에 없는 사용자 변경이고 캐시는 사본이다. 쿼터 대부분은 캐시가 쓰고 있으니, 편지함 때문에 메모리 모드로 넘어가면 새로고침 한 번에 편지가 사라진다. 메모리 모드로 넘어갈 때는 저장소의 두 키를 먼저 읽어 둔다 — 빈 메모리로 넘어가면 저장소에 남은 편지가 안 보이고 새 변경이 그 편지를 앞질러 서버로 간다. 테스트는 용량 상한을 흉내 내는 `MemoryStorage(capacity)` 대역으로 한다. (본문 §2.11 ⑥·§2.15)

**Q7. 브라우저에 있던 옛 기록(v1)은 어떻게 잃지 않고 옮겼나?**
A. 처음 로드 때 `skx_search_history` 를 v2 로 바꿔 100건씩 `POST /api/history/import` 로 올린다. 규칙은 넷이다. ① 서버가 받기 전에는 v1 을 건드리지 않는다 — 실패하면 다음 로드에 다시 시도한다. ② 성공해도 지우지 않고 `skx_search_history_backup_v1` 로 옮겨 둔다. ③ v1 id(13자리 숫자)는 서버가 `uuid5(NAMESPACE_URL, "nl-lib-history-v1:" + v1id)` 로 **결정론적으로** 바꾼다 — 몇 번 이전해도 같은 id 라 `ON CONFLICT DO NOTHING` 이 중복을 막고, 브라우저에 uuid5 구현을 두지 않아도 된다. 응답의 `{v1id: 새 id}` 대응표를 저장해 옛 `?restore=<v1id>` 주소가 새 id 를 찾는다. ④ 탭 경합 — 요청이 오가는 사이 구버전 탭이 v1 을 다시 썼으면 v1 을 남겨 다음에 다시 올리고, 두 탭이 함께 올려도 백업 사본은 하나만 남긴다. 리뷰에서 하나가 더 나왔다 — 업그레이드 뒤 첫 로드에서 옛 주소를 열면 대응표가 생기기 전에 복원이 돌아 랜딩으로 빠졌다. 페이지가 이전 완료를 기다리게 했다(`awaitsV1Map`·`migrated()`). import 는 상한을 넘은 칸만 비우고 413 을 내지 않는다 — 한 건 때문에 묶음 전체가 매번 실패하면 영영 옮겨지지 않는다. (본문 §2.5·§2.6·§2.11 ⑨·§2.16)

**Q8. "주소가 복원의 정본"이란 무엇이고 H2(뒤로가기·새로고침에 결과가 사라짐)를 어떻게 풀었나?**
A. 검색이 성공하면 `router.replace` 로 `?h=<기록 id>&q=<검색어>` 를 주소에 넣고, 페이지는 주소를 지켜봐 복원한다. 사이드바 클릭·뒤로가기·새로고침·공유 링크가 모두 이 한 길로 들어온다. 같은 경로에서 쿼리만 바뀌면 페이지가 다시 마운트되지 않으므로 `watch` 로 `h`(또는 별칭 `restore`)와 `q` 를 함께 본다 — `q` 도 보는 이유는 `h` 가 없는 주소(검색 중·실패 뒤)에서 랜딩으로 돌아오면 `h` 는 그대로 없어 변화를 놓치기 때문이다. 첫 복원은 `onMounted` 에서 한다 — 서버가 그린 랜딩과 하이드레이션이 어긋나지 않게. `h` 로 읽은 기록에 축약 결과가 있으면 재검색 없이 그리고, 없거나 남의 기록이면 `q` 로 새로 검색한다(공유 링크의 대체 동작). 검색을 시작할 때는 주소의 이전 `h` 를 먼저 내린다 — 남겨 두면 검색이 도는 동안 사이드바가 이전 기록을 강조하고, 그 기록을 누르면 지금 주소와 같아 이동이 무시된다. (본문 §2.16·§2.17)

**Q9. AI 요약이 다른 기록에 섞이던 문제(H1)는 어떻게 고쳤나? 큐레이션은 왜 예외인가?**
A. 원인은 스트림이 끝난 시점의 `currentHistoryId` 로 저장한 것이다. 도는 중에 다른 기록을 복원하면 그 기록을 덮었다. 지금은 검색 응답을 받으면 기록 id 를 먼저 확정해 스트림에 넘기고(붙잡은 id), 끝나면 그 id 로만 저장한다. 검색·복원·요약은 한 묶음(`AbortController`)이라 새 검색·복원·언마운트 때 이전 묶음을 끊는다 — 페이지를 떠나도 GPU 생성이 끝까지 돌던 문제도 함께 풀렸다. 도서 큐레이션은 예외다 — 스트림이 아니라 단발 POST 라 연결을 끊어도 서버의 LLM 생성은 끝까지 돌고 결과만 버려진다. 돌아온 화면은 요약이 빈 기록을 보고 처음부터 다시 만든다. 그래서 요청은 끊지 않고 끝까지 받아 붙잡은 id 로 저장하고, 같은 기록의 요청이 도는 중이면 이어받는다(앱 단일 인스턴스). 끊는 것은 타이핑 연출뿐이다. "끊는다"가 언제 실제로 서버 일을 멈추는지는 프로토콜(스트림 vs 단발)에 달렸다는 것이 교훈이다. (본문 §2.14·§2.17·§2.18)

**Q10. 이벤트로 흘린 것을 왜 전부 DB 에도 저장하나?**
A. 라이브로 볼 때와 끝난 뒤 다시 열 때 같은 장면이 나와야 해서다(D8). round04a 는 중간 회차의 판정을 저장하지 않아 끝난 잡에서 자기점검 장면을 재생할 수 없었다. 시연을 "미리 돌려둔 보고서 열기"로 할 때(계획이 결정적이지 않아 round04a 가 권했다) 그 장면이 빠지면 차별점이 사라진다. 그래서 회차 이력을 search 단계 result 의 `rounds` 에, 종합 진행을 synthesize 단계 result 에 남기고, 탐색·종합 **도중에도** 회차·절마다 덮어쓴다 — 처음 계획은 닫을 때만 썼는데, 그러면 탐색 중 새로고침한 화면이 앞 회차·카운터를 잃는다(계획 통합 때 Task 12 를 신설했다). 기존 JSONB 칸이라 DB 변경이 없다. 옛 잡(보강 전)은 `rounds` 가 없어 화면이 `report.trail` → 단계 `queries` 순으로 대신 그리고, 그 사실을 패널에 밝힌다. (본문 §2.24·§2.26·§2.29 ②)

**Q11. 스트림의 "스냅샷과 구독 사이의 틈"은 무엇이고 어떻게 메웠나?**
A. 스트림은 DB 스냅샷을 읽은 **뒤에** Redis 구독을 붙인다. 그 사이에 나간 이벤트는 다시 오지 않는다. 계획은 1초 안팎이라 plan 단계 `done`(계획 원안)과 `awaiting_approval` 이 이 틈에 빠지기 쉽다. 처음 구현은 15초 하트비트마다 DB 상태를 읽어 놓친 `status` 만 되살렸는데, 그러면 화면은 승인 대기로 가도 승인할 계획이 없어 막힌다(품질 검토에서 찾았다). 그래서 하트비트가 DB 의 `(status, stage)` 가 화면이 아는 값과 다르거나 계획이 생겼는데 준 적이 없으면 **스냅샷을 통째로** 다시 보낸다. 다시 읽는 조회는 어긋났을 때만 하고, 두 조회 사이에 끝났으면 종료 프레임으로만 알린다. 같은 틈이 종합에서도 나왔다 — 놓친 `synth(done)` 의 절 내용은 뒤따르는 가벼운 `step` 이 싣지 않아 현황 카드는 완료인데 초안에서 그 절이 빠졌다. 이건 API 를 고치지 않고 화면이 "끝났다는데 내용이 없는 절"을 보면 GET 으로 한 번 맞추게 했다. (면접에서 이어 물을 만한 대안 — 구독을 먼저 붙이고 스냅샷을 읽으면 틈은 없어지지만, 스냅샷보다 오래된 이벤트가 뒤따라 올 수 있어 리듀서가 그것을 걸러야 한다. 이 라운드의 spec·계획에는 이 대안을 검토한 기록이 없다.) (본문 §2.27·§2.37)

**Q12. 승인 응답과 워커의 `running` 이 경합하면 화면은 어떻게 되나?**
A. 두 겹으로 막았다. 서버는 승인을 **큐에 넣기 전에** `approved` 로 알린다 — 넣은 뒤에 알리면 워커가 곧바로 집어 낸 `running` 뒤에 `approved` 가 도착해 화면이 한 단계 뒤로 간다. 화면은 승인 HTTP 응답을 반영할 때 status 를 **아직 승인 대기일 때만** 바꾼다(`applyApproval`). 서버는 알린 뒤 큐에 넣고 나서야 응답하므로, `running`(또는 재접속 스냅샷)이 응답보다 먼저 올 수 있다. 응답의 `approved` 로 덮으면 화면이 대기열로 돌아가고, `step`·`search` 는 status 를 바꾸지 않으니 탐색이 끝날 때까지 복구되지 않는다. 같은 계열로 워커는 단계 행을 **커밋한 뒤에** `step` 을 알리고(먼저 알리면 재접속 스냅샷에 없는 단계가 이벤트로만 온다), 상태는 **조건부 전이가 성공한 뒤에만** 알린다(취소에 진 전이를 알리면 취소된 잡이 진행 중으로 그려진다). (본문 §2.26·§2.27·§2.29 ⑤)

**Q13. 진행 카운터가 거꾸로 가지 않게 어떻게 했나?**
A. 카운터의 출처가 둘이다 — 라이브 `counters` 이벤트(검색 직후)와 저장본(자기점검이 끝나야 쓰인다, 스냅샷·GET 으로 온다). 점검을 기다리는 동안 저장본은 한 회차 뒤처지고, 스트림이 끊긴 사이에는 저장본이 앞선다. 한 시도 안에서 카운터는 줄지 않으므로(검토한 논문 집합·근거·검색어는 늘기만 한다) 필드별로 큰 값을 남긴다. 예외가 하나 있다 — 탐색부터 다시 도는 재시도는 0 부터 새로 센다. 화면이 모르는 뒤 단계에서 나온 저장본이면 그대로 쓴다. 안 그러면 이전 시도의 큰 숫자가 버틴다. 끝난 잡은 보고서 `stats` 가 확정값이다. 서버 스냅샷의 카운터 선택 순서(`_live_counters` — 보고서 stats → 가장 큰 seq 의 단계 counters)와 화면의 `countersFromJob` 을 같게 맞췄다 — 갈리면 라이브로 볼 때와 다시 열 때 숫자가 다르다. 진행 카운터와 보고서 서론은 같은 함수(`research_stats`)를 본다. (본문 §2.23·§2.27·§2.29 ④)

**Q14. 재시도가 끼면 같은 하위질문의 단계 행이 여러 벌 남는다. 화면은 어떻게 "이번 시도"를 고르나?**
A. round04a 의 `research_steps` 에는 시도를 구분하는 컬럼이 없다. 컬럼을 더하지 않고 seq 로 가렸다. ① 하위질문마다 seq 가 가장 큰 search 행이 현재 시도다. ② 멈춘 지점은 하위질문 0 의 가장 늦은 search 행을 이번 시도의 시작으로 보고 그 뒤 행만 본다 — 이번 시도가 아직 닿지 않은 하위질문에는 이전 시도의 `done`·`failed` 행과 오류가 남아 있다. 부분 실패(하위질문 하나의 오류)를 멈춘 곳으로 짚지도 않는다 — 워커는 그다음 하위질문과 종합으로 넘어가므로 뒤 단계부터 본다. ③ 종합에서 재시도하면 워커가 `running` 을 알린 뒤 새 종합 단계를 열기 전까지 이전 시도의 닫힌 단계가 보여, 멈춘 초안·진행률이 '작성 중'으로 잠깐 되살아났다. 재시도를 알아보면 그 시도의 마지막 종합 단계 seq 를 기억해(`retiredSeq`) 더 큰 seq 가 열릴 때까지 읽지 않는다. 서버 쪽은 재시도가 완료되면 이전 시도 종합 단계의 멈춘 초안을 걷는다(수백 KB). (본문 §2.29 ①⑥·§2.36·§2.37)

**Q15. `EventSource` 의 수명주기에서 조심한 것은?**
A. 셋이다. ① **종료 이벤트를 받으면 반드시 닫는다.** 닫지 않으면 브라우저가 스스로 다시 붙고 서버는 끝난 잡에 스냅샷·종료를 다시 보내 무한히 반복한다. 닫은 뒤 GET 으로 보고서를 받는다(종료 프레임에는 보고서가 없다). ② **`onerror` 는 두 갈래다.** `CONNECTING` 이면 브라우저가 다시 붙고 서버가 스냅샷부터 보내니 할 일이 없다. `CLOSED` 는 브라우저가 포기한 경우라 GET 으로 맞추고 2·4·8·16·30초 백오프로 직접 다시 붙인다. ③ **늦게 도착한 응답을 버린다.** 주소의 잡이 바뀌거나 페이지를 떠난 뒤 온 응답이 `connect()` 를 부르면 닫을 주체가 없는 연결이 잡이 끝날 때까지 남는다 — 세대 번호(`generation`)로 버린다. GET 끼리도 뒤에 보낸 것이 있으면 앞의 응답을 버린다 — 도는 동안 보낸 GET 이 종료 뒤에 도착하면 끝난 화면을 도는 잡으로 되돌린다. 덧붙여 취소 응답이 스트림보다 먼저 오면 종료 이벤트를 못 받으므로 응답 쪽에서도 마무리한다. (본문 §2.31)

**Q16. 작성 중 초안을 왜 토큰 스트리밍이 아니라 절 단위로 했고, 초안과 최종본이 같다는 것을 어떻게 보장하나?**
A. 종합은 하위질문마다 LLM 을 한 번 부르고 JSON 으로 받는다(round04a 의 구성 버그 이후 "채울 칸이 정해진 출력"이다). 토큰을 흘리면 중간 글이 JSON 조각이라 풀기 어렵고, 인용 마커 검증(`bind_markers`) 전의 글이 보였다가 바뀐다 — 지어낸 인용이 잠깐이라도 화면에 뜬다. 절 단위면 검증을 마친 글만 보인다. 같음은 코드 하나로 보장한다 — `assemble_report` 의 절 루프 본문을 `finalize_section` 으로 떼어 초안(워커가 절마다)과 최종본이 같은 함수를 쓴다. 분리 뒤에도 `assemble_report` 의 출력은 한 글자도 바뀌지 않았고(기존 테스트 무변경 통과), 새 테스트가 같은 입력에서 둘의 절이 같음을 묶는다. 근거 모양도 `_evidence_entry` 하나가 만든다. 화면도 같은 부품(`ReportSectionBody`)으로 그린다. (본문 §2.35·§2.44)

**Q17. 절 미리보기 데이터가 커질 텐데 전송·저장 비용은?**
A. 절 하나에 수 KB~수십 KB(대목 원문이 대부분)다. 네 가지로 줄였다. ① 절 내용은 `synth` 이벤트가 절마다 **한 번만** 나른다. 진행 저장 뒤 알리는 `step` 이벤트에는 미리보기를 뺀 가벼운 result 를 싣는다 — 안 그러면 절이 쌓일수록 이미 보낸 절을 매번 다시 보낸다. 화면은 가벼운 값이 받은 내용을 지우지 않게 합친다. ② 근거는 그 절이 인용한 것·그 절의 대목만(`section_evidence`). ③ 완료로 닫으면 미리보기를 지운다 — 최종 보고서와 같은 내용이다. 실패·취소로 닫으면 멈춘 초안의 원천이라 남긴다. ④ 재시도가 완료되면 이전 시도의 멈춘 초안을 걷는다. 테스트가 절 6개·논문 30편에서 최종 보고서의 `evidence` 와 같은 규모임을 본다. DB 구조는 그대로다(기존 JSONB). (본문 §2.36)

**Q18. 남은 시간과 진행 막대는 어떻게 계산하나?**
A. 남은 시간 = 끝난 절들의 걸린 시간 평균 × 대기 절 수 + 쓰는 중인 절의 (평균 − 경과, 0 미만이면 0). 걸린 시간은 워커가 단조 시계로 잰 값이라 브라우저 시계와 무관하다. 경과만 서버의 `started_at` 과 화면 시계를 견주므로 시계가 어긋나 미래로 보이면 0 으로 자른다. 끝난 절이 없으면 "첫 절을 쓰는 중", 걸린 시간을 주지 않는 옛 워커면 칸을 비운다("계산 중"은 끝까지 틀린 말이 된다). 막대는 끝난 절 + 쓰는 중인 절의 몫이다 — 절 하나가 수십 초라 끝날 때만 늘면 서 있는 것처럼 보인다. 몫은 경과 ÷ 예상 소요이고 90% 아래에 둔다(끝나기 전에 다 차 보이면 멈춘 것처럼 읽힌다). 첫 절은 평균이 없어 30초마다 남은 거리의 절반씩 다가간다. 시계는 보고서를 쓰는 동안만 1초마다 돈다 — 늘 돌리면 화면 전체가 매초 다시 그려진다. (본문 §2.38·§2.40)

**Q19. 초안이 최종본으로 바뀌는 순간 읽던 자리·초점·열린 팝오버는 어떻게 지키나?**
A. 처음엔 초안 `ReportView` 와 최종본 `ReportView` 를 `v-if` 두 갈래로 그려, 최종본이 오면 vnode 종류·key 가 달라 초안 쪽을 언마운트하고 새로 마운트했다. 초안 안의 초점이 body 로 떨어지고, 고정해 둔 인용 팝오버가 닫히며, 스크롤 기준 노드가 사라져 읽던 자리가 튀었다. 그래서 한 갈래의 같은 `ReportView` 에 최종본이 오면 넘기고(`shownReport`), 버튼은 슬롯 안에서 가른다 — 절 idx 로 묶인 절·인용칩 인스턴스가 이어진다. 두 가지가 더 따라왔다. 절의 `tabindex="-1"` 을 최종본에도 둔다 — 초점이 있는 절의 `tabindex` 가 빠지면 Chrome 이 초점을 body 로 떨어뜨린다. 인용칩은 대목 목록을 배열 동일성이 아니라 대목 id 열쇠로 지켜본다 — 다시 그릴 때마다 새 배열이 와 열어 둔 팝오버가 첫 대목으로 돌아갔다. 완료 직후 최종본을 받는 동안에도 초안을 치우지 않고 배지를 '작성을 마친 초안'으로 바꾼다. (본문 §2.39·§2.42·§2.45·§2.46)

**Q20. "인터랙티브함 최우선"과 접근성은 어떻게 같이 챙겼나?**
A. 움직임은 넣되 강제하지 않는다. 이어 늘어나는 막대·1초마다 가는 경과·완성된 절의 체크가 튀어 오르는 효과·절이 제자리에 나타나는 효과·쓰는 중인 절의 회색 줄은 모두 `prefers-reduced-motion` 이면 끈다. **자동 스크롤은 하지 않는다** — 절이 완성될 때마다 끌고 가면 초안을 읽던 자리를 잃는다. 옮겨 가는 것은 사용자가 현황 카드 항목을 누를 때만이고, 그때 초점도 그 절로 옮겨 키보드 사용자가 이어 읽는다. 절 완성은 `aria-live="polite"` 로 한 번 읽힌다(처음 그릴 때는 몰아 읽지 않는다). 강조는 포인터와 초점을 따로 들어 한쪽이 다른 쪽을 지우지 않게 했고, 터치는 강조하지 않는다(iOS Safari 는 떠날 신호를 다음 탭까지 안 보낸다). 버튼은 `disabled` 대신 `aria-disabled` 를 쓴다 — 누른 직후 비활성이 되면 초점이 body 로 떨어진다. 강제 색 모드에서 투명 outline 이 테두리 상자로 칠해지는 회귀도 막았다. 입력창 쪽은 `+` 메뉴가 WAI-ARIA 메뉴 버튼, 슬래시 명령 목록이 콤보박스 관례를 따르고 한글 조합 중의 엔터를 고르기로 쓰지 않는다. (본문 §2.20·§2.21·§2.40·§2.41·§2.45)

**Q21. Word·PDF 를 문서 모델 하나에서 만든 이유와, 인용 번호·참고문헌 규칙은?**
A. 두 형식을 따로 만들면 인용 번호·참고문헌·부록이 어긋난다. 문서 모델(`buildReportDocument`)은 순수 함수라 Vitest 로 검증하고, Word(`docx`)와 PDF(인쇄 화면)는 그 블록을 그리기만 한다. 인용 번호는 문서에 처음 나온 순서(절 → 도입 → 대표 논문 → 향후 과제)로 `[1]`, `[2]` … 를 매기고 같은 근거는 같은 번호다. 참고문헌에는 인용된 근거만, `저자 (연도). 제목. 학술지, 권(호). 인용 쪽: …` 으로 적는다. 인용 쪽은 그 근거를 인용한 절들이 쓴 대목을 칩 팝오버와 같은 규칙으로 모아 0-based + 1 로 적고, 0 쪽(쪽 정보 없음)은 뺀다. 초안 문서는 제목·파일 이름에 초안임을 밝히고 한계 대신 안내를 싣는다. 부록 "탐색 경로"에 하위질문마다 검색어 흐름(→ 재검색)·판정·근거 수를 싣는다 — 자기점검이 차별점이다. 운영에서 하나가 터질 뻔했다 — LLM 이 쓴 LaTeX(`\frac`)가 JSON 이스케이프로 풀려 제어문자가 되고, `docx` 는 그것을 그대로 써서 Word 가 파일을 열지 못한다. 모델이 모든 글에서 XML 금지 문자를 빼고 Word 구성이 한 번 더 막는다. (본문 §2.48·§2.50)

**Q22. `docx` 번들과 PDF 인쇄에서 걸린 함정은?**
A. `docx` 는 1MB 가 넘어 다운로드를 누를 때 동적 import 한다 — 구성 함수가 그때 받은 모듈을 인자로 받는다. 값으로 import 하면 정적 번들에 들어간다. 계획 드라이런에서 별도 청크 1개(436K)를 딥리서치 페이지 청크만 부르는 것을 확인했다. 배포 뒤 옛 화면에서 누르면 조각 파일이 사라져 import 가 실패하니 "새로고침 뒤 다시"로 안내한다. PDF 는 두 가지가 걸렸다. ① 인쇄 뒤 되돌리기를 `afterprint` 에 맡겼더니, 인쇄를 정책으로 막았거나 인앱 브라우저처럼 `print()` 가 창 없이 돌아오고 `afterprint` 를 안 쏘는 곳에서 모든 내려받기 버튼이 '만드는 중…'에 멈췄다 — `print()` 가 돌아온 뒤 `finally` 에서 되돌린다. ② A4·여백을 이름 없는 `@page` 로 뒀더니 `research.css` 는 모든 페이지에 실려 논문 검색 등 **다른 화면의 인쇄**까지 바꾸고 인쇄 창의 가로/세로 선택을 숨겼다 — 이름 붙은 `@page rs-report` 를 인쇄 문서·딥리서치 화면에만 준다. "PDF로 저장"의 기본 파일 이름은 문서 제목이라 인쇄하는 동안 `document.title` 을 파일 이름으로 바꾼다. (본문 §2.50·§2.51·§2.53)

**Q23. 모델이 쓴 글을 왜 `v-html` 로 넣지 않았고, 대신 어떻게 그리나?**
A. 기존 화면은 `marked` + `v-html` 에 sanitize 가 없다. LLM 출력은 검색된 논문 원문의 영향을 받는 입력이라 신뢰할 수 없다 — HTML 로 해석시키면 스크립트 주입 표면이 된다(D9). 보고서는 서버가 인식한 인용 표기를 전부 `[E3]` 표준형으로 다시 써서 보내므로, 화면은 그 정규식 하나로 글을 `{text}`·`{cite}` 조각 배열로 나누고 글은 텍스트 보간으로, 인용은 `CitationChip` 컴포넌트로 그린다. 표준형이 아닌 것은 글자 그대로 둔다. 인쇄 화면·Word 도 같은 조각을 쓴다. 대가는 보고서 안에 굵게·목록 같은 서식을 모델이 넣을 수 없다는 것이다 — 서식은 구조(절·대표 논문·향후 과제)로 코드가 정한다. (본문 §2.42·§2.52)

**Q24. 운영 배포 직후 502 가 났다. 원인과 처방은?**
A. 함정 20번이다. 인덱싱 워커를 끊지 않으려고(함정 16번) 스택 업데이트 대신 바뀐 컨테이너 넷만 개별 Recreate 했다. 도커 네트워크는 컨테이너를 만들 때마다 빈 IP 를 배정하므로 Recreate 한 fastapi·nuxt 가 다른 IP 를 받을 수 있는데, nginx 는 `upstream` 블록의 호스트 이름을 **설정을 읽을 때 한 번만** IP 로 바꿔 쥐고 다시 묻지 않는다. 게이트웨이는 Recreate 대상이 아니어서 옛 IP(`172.21.0.14`)로 보냈다. `docker exec nl-lib-gateway nginx -s reload` 로 이름을 새로 풀게 해 해결했다 — 재시작 없이 새 워커 프로세스로 넘어간다. 이후 배포 절차는 fastapi·nuxt 를 Recreate 했으면 마지막에 reload 한다 — §14 계획의 배포 순서(spec §14-7)에 넣었고, round04c 배포(2026-09-30)는 워커 → fastapi → nuxt → reload 순서로 했다. round04a 처럼 컨테이너 안에서 앱에 직접 붙는 확인은 이 함정을 못 잡는다 — 배포 확인은 게이트웨이를 거쳐 한다. 근본 해결(실행 중 재해석 — nginx 의 `resolve`)은 검토 항목이다. (본문 §3-4, `docs/ops/recurring-gotchas.md` 20번)

**Q25. 이 라운드에서 범위 밖으로 남긴 것은?**
A. 크게 다섯 갈래다. (1) **설계상 범위 밖**(spec §11) — 로그인·사용자 계정(`user_id` 자리만), 채팅 대화 기록의 서버 저장(`kind` 하나를 더하면 되는 구조만), 기존 `search_history` 정리와 `GET /api/books/history/{session_id}` 폐기, 도서 입력창의 `+`, 인용 그래프·AI 다이어그램, Markdown·HWPX·서버 생성 PDF, 절 서술의 토큰 스트리밍. (2) **의도적으로 만들지 않은 것** — 딥리서치 잡 목록 API(사이드바 기록이 그 역할), 사이드바 "더 보기"(종류마다 최근 30건만 읽는다). (3) **정리 후보** — `components/SearchInput.vue`·`TopResult.vue`·`CategoryAccordion.vue`(셋 다 `search-classic.vue` 만 쓰던 부품이라 그 삭제 뒤 호출부 0 이지만 spec §4-9 삭제 목록에 없어 남김 — 계획은 `SearchInput.vue` 만 적었다), `BookChat.vue` 의 쪽수 표시(0부터 센 원시값을 `p.N` 으로 보여 한 쪽 어긋남 — 불일치로만 기록), `pages/index.vue` 의 죽은 코드. (4) **알려진 경계**(계획 "알려진 미확정") — 10분 중복 병합은 서버 `updated_at` 과 브라우저 시계를 비교해 시계가 10분 넘게 어긋나면 병합만 안 된다. `legacy_history_id` 는 v1 id 만으로 만들어 서로 다른 브라우저가 같은 밀리초에 만든 v1 기록이면 나중 쪽이 건너뛰어진다(원본은 백업 키에 남는다). (5) **다음 라운드로 간 것** — 기획자 피드백에 따른 기본 배치 변경과 운영 검증 잡이 드러낸 보고서 품질(쏠림·같은 단어 다른 뜻)은 round04c 로 갔다(§1-5·§3-5). 보안 이월(Redis 무인증 호스트 노출·`app/api/admin.py` Milvus expression injection)은 round04a 이월 그대로다. 전체 목록은 완료노트다.
