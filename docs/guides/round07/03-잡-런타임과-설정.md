## 1. 설계

### 1-1. 무엇이 문제였나

spec §1 의 진단 가운데 잡 런타임에 걸린 것이다.

| 문제 | 근거 | 결과 |
|---|---|---|
| 디스패처 둘이 in-flight 를 같이 읽는다 | `q_control` 을 추출 워커 `celery-cpu`(동시 4)가 받았다. 추출 4칸이 차면 디스패치 틱이 뒤에 쌓였다가 칸이 비면 여럿이 한꺼번에 돈다 | 둘 다 커밋 전의 in-flight 를 세 진행 상한(32)을 넘겨 보낸다 |
| stale 복구가 큐 대기를 실행 시간으로 잰다 | `_recover_stale` 이 단계가 끝난 시각(`updated_at`)부터 다음 단계의 실행 타임아웃(embed 1200·마무리 900초)을 쟀다 | 바쁜 `q_llm` 뒤에서 마무리를 기다리는 아이템이 stale 로 오판돼 새 체인이 열린다. spec 1번(보강을 요약 단계로)이 `q_llm` 을 더 바쁘게 만든다 |
| 옛 체인이 멈추지 않는다 | 단계 래퍼가 `canceled` 만 보고 `done`·체크포인트는 보지 않았다. stale 복구는 옛 태스크를 끊지 않았다. 락 경합이면 `pending` 으로 되돌리고 dict 를 돌려줘 체인이 다음 단계로 갔다 | 함정 16번 — 재전달된 옛 체인의 `embed_index` 가 아티팩트 없이 돌아 논문 본문 청크를 초록 청크로 덮는다 |
| 재시도가 같은 실패를 되풀이한다 | 섹션 0개를 추출 성공으로 넘기고 재시도는 요약부터 했다. 백오프가 없었다 | 같은 실패 3번으로 1~2분 만에 시도를 다 쓴다. 장애 때 `llm_error` 264건이 영구 실패로 남았다 |

### 1-2. 결정과 버린 대안

| 결정 | 버린 대안 | 이유 |
|---|---|---|
| 디스패처가 체인마다 새 실행 토큰(`uuid4().hex`)을 아이템 `meta.run_token` 에 적고 모든 단계 인자로 넘긴다. 단계 래퍼가 대조해 다르면 멈춘다 | DB 칼럼 추가 · stale 복구 때 Celery `revoke` | 기존 테이블을 바꾸지 않는다(meta JSON, spec 18). `revoke` 는 워커가 메모리의 id 목록으로 거르는 방식이라 워커가 모두 재시작하면 목록이 사라지고(함정 16 의 재전달은 바로 재배포 뒤에 온다), 이미 도는 태스크는 프로세스를 죽이지 않고는 멈추지 않는다. 토큰은 상태를 쓰는 바로 그 행에서 대조해 큐 대기·재전달·배포 전 메시지·늦게 끝난 시도를 한 규칙으로 막는다. (`revoke` 와 견준 것은 이 교본의 설명이다 — spec·계획에는 이 대안을 검토한 기록이 없다) |
| 실행하지 않는 단계는 `celery.exceptions.Ignore` 로 체인을 멈춘다 | dict 반환(옛 동작) · 예외로 실패 기록 | dict 는 성공이라 Celery 가 다음 단계를 보낸다. 실패로 기록하면 attempt 가 오르고 카탈로그에 거짓 `failed` 가 찍힌다. `Ignore` 는 상태를 남기지 않고 메시지를 ack 하며 다음 단계를 보내지 않는다 |
| 락 경합이면 아이템을 그대로 두고 이 체인만 멈춘다 | `pending` 으로 되돌림(옛 동작) | 되돌리면 디스패처가 30초 안에 새 토큰으로 다시 보내, 락을 쥐고 일하는 체인의 다음 단계를 토큰 불일치로 끊고 경합을 되풀이한다. 대가: 멈춘 아이템이 진행 상한 한 칸을 쥔 채 4시간 뒤 stale 복구를 기다린다 |
| 시작·성공·실패 기록마다 FOR UPDATE 로 토큰을 다시 대조한다 | 첫 읽기에서 한 번만 대조 | 단계가 도는 동안 stale 복구·재디스패치가 토큰을 바꿀 수 있다. 늦게 끝난 옛 시도가 새 체인의 상태를 덮으면 함정 16 이 다른 모양으로 남는다(a099356) |
| stale 판정을 '실행 중'(`meta.stage_running`)과 '대기 중'으로 나눈다 | 단계 끝 시각부터 다음 단계 실행 타임아웃으로(옛 동작) · 단계 타임아웃을 크게 | 큐 대기는 실행이 아니다. 타임아웃을 키우면 진짜 죽은 워커의 회수까지 늦어진다 |
| 수동 retry 는 토큰을 `retry` 로 덮는다 | 토큰 유지 · 토큰 삭제(7871cb7 의 첫 구현) | 유지하면 옛 체인 메시지가 같은 토큰으로 통과한다. 지우면 배포 전에 보낸 토큰 없는 메시지가 통과한다(259b823) |
| `no_text` 는 실패를 기록할 때 attempt 를 한도로 올린다 | 다른 오류처럼 자동 재시도 | 같은 코드로 다시 해도 결과가 같다 — 시도와 VLM 시간만 쓴다 |
| 자동 재시도 백오프(120·600초)를 후보 조회의 SQL 조건으로 넣는다 | `limit` 뒤 파이썬에서 거르기 | id 가 앞선 백오프 중 실패가 `limit` 을 채워 뒤의 `pending` 을 막는다 |
| `q_control` 을 새 워커 `celery-control`(동시 1, GPU 없음)이 받고 beat 틱에 `expires` 를 둔다 | `celery-cpu`(동시 4)에 그대로 · 진행 상한 32 를 올리거나 둘로 나누기 | 한 칸이면 디스패처가 한 번에 하나만 돈다. 상한을 올려도 VLM·gemma·embed 가 GPU 0 을 같이 써 얻는 것은 6~9%(추정)이고, 대기열이 길어져 stale 오판이 커진다(spec 6) |
| 추출 stale 판정 3600초, 데드라인과의 관계를 설정을 읽을 때 검사한다 | 14400초 유지 · 관계를 주석으로만 적기 | 3600 은 추출이 스스로 끝나는 시각(기본 2830초) 위, `visibility_timeout` 7200 아래다. 스택 env 가 관계를 깨면 추출이 끝나기 전에 토큰이 바뀌어 결과가 버려진다 — 조용히 틀리는 대신 앱이 뜨지 않게 한다 |
| ETA 는 24시간 처리량으로, running 잡만 낸다 | 1시간 창(옛 동작) | 1시간 창은 스캔본이 몰리면 48시간 기준의 0.73~5.7배로 출렁였다. 멈춘 잡의 ETA 는 뜻이 없다 |
| 실패 그룹 대표 메시지는 `mode()` 다 | `max(last_error)`(옛 동작) | 사전순 최댓값은 드문 메시지를 대표로 고른다 |

### 1-3. 아이템 하나의 체인 — 실행 토큰과 stale 판정

```text
[celery-beat] 30초마다 디스패치 틱 (expires 25초 — 늦게 받은 옛 틱은 버린다)
     │
[celery-control, 동시 1] dispatch_job_items (소프트 60·하드 90초) — running 잡마다
     │ ① _recover_stale : dispatched·running 을 FOR UPDATE SKIP LOCKED 로 훑는다
     │     running + stage_running=X   → INGEST_STAGE_TIMEOUT_X 를 stage_started_at 부터  ("X 실행 중")
     │     running + stage_running 없음 → DISPATCH_STALE_SECONDS 를 updated_at 부터     ("다음 단계 대기")
     │     dispatched                  → DISPATCH_STALE_SECONDS 를 updated_at 부터     ("디스패치 대기")
     │     넘으면 failed(stale)·attempt+1·run_token=새 값(어느 체인도 싣지 않은 값)
     │ ② _dispatch_for_job : pending + 백오프 지난 failed(attempt < 한도)를 id 순, FOR UPDATE SKIP LOCKED
     │     vlm_error·'섹션 없음' 실패면 체크포인트 → pending (추출부터)
     │     run_token=T 를 meta 에 적고 chain(extract.si(id,T) → summarize → embed_index → finalize) 보냄
     │     status=dispatched … 루프 끝에서 COMMIT
     │ ③ _maybe_complete
     ▼
[celery-cpu · celery-llm · celery-embed] stage_X(id, T)
   1. 아이템을 FOR UPDATE 로 읽는다 (디스패처의 COMMIT 을 기다린다)
      _skip_reason: 없음·취소·토큰≠T·토큰 없는 옛 메시지·done·지난 단계 → Ignore (체인 정지, 아무것도 안 씀)
   2. BookLock(TTL = 단계 타임아웃) 실패 → Ignore (락 경합 — 상태 그대로, 대기 상한 뒤 stale 복구)
   3. 시작 기록: running · stage_running=X · stage_started_at   [토큰 대조 — 다르면 락 풀고 Ignore]
   4. STAGE_FUNCS[X](StageContext(item_meta=…))
   5. 성공 기록: 체크포인트 · stage_running=null                 [다르면 늦은 성공 버림 → Ignore]
      실패 기록: failed · attempt+1 (no_text 면 한도까지)        [다르면 늦은 실패 버림, 예외만 올림]
   6. 예외 없이 끝나면 Celery 가 체인의 다음 단계(같은 T)를 보낸다
```

## 2. 구현 (클론코딩)

### 2.24 `app/workers/job_runtime.py` — 실행 토큰·단계 래퍼·디스패처·stale 복구·백오프

**파일**: `app/workers/job_runtime.py` (라운드 시작 `9798f46` 대비 diff)

이 라운드의 중심 파일이다. 커밋은 3179f39(실행 토큰)·1390055(재시도 정책)·b834d66(stale 판정 분리)·a099356·49f62ef(기록마다 토큰 대조)·7871cb7(백오프 파서)·2881e22·0263d8a(제어 큐 태스크의 시간 제한)·34e7295(타입 힌트)다.

**머리말·상수.** 독스트링에 두 규칙을 더했다 — 자동 재시도 백오프와 실행 토큰. `DISPATCH_STALE_SECONDS` 의 값(14400초)은 그대로이고 주석만 고쳤다(spec 16 의 `job_runtime.py:55`). "visibility_timeout 의 2배"라는 숫자는 맞았다. 바뀐 것은 쓰임이다 — 디스패치 대기뿐 아니라 단계 사이 대기에도 쓴다. 까닭도 적었다. 받은 채 죽은 워커의 메시지가 7200초 뒤 재전달돼 다시 집힐 때까지 기다리는 값이다. `NO_RETRY_GROUPS` 는 자동 재시도하지 않는 그룹이다(`no_text` 하나). import 는 토큰(`uuid`)·`Ignore`·백오프 SQL 조건(`and_`·`or_`·`true`)·파서 캐시(`functools`)·타입 힌트(`ColumnElement`·`Session`)·제어 큐 시간 제한(§2.27) 몫이다.

**`_skip_reason` — 실행하지 않을 이유.** 위에서부터 처음 걸리는 이유를 돌려준다. 없으면 `None` 이다.

| 순서 | 조건 | 이유 문구 | 옛 동작 |
|---|---|---|---|
| 1 | 아이템 없음 | `아이템 없음` | dict 반환 → 다음 단계로 |
| 2 | 아이템이나 잡이 `canceled` | `취소됨` | dict 반환 → 다음 단계로 |
| 3 | 메시지에 토큰이 있고 아이템 토큰과 다르다 | `실행 토큰 불일치(메시지 …, 아이템 …) — 옛 체인` | (토큰 없음) 실행 |
| 4 | 메시지에 토큰이 없는데(배포 전 메시지) 아이템에는 있다 | `토큰 없는 옛 메시지인데 아이템에는 실행 토큰이 있다 — 새 체인이 떴다` | 실행 |
| 5 | `status == "done"` | `이미 완료(done)` | 실행 |
| 6 | 체크포인트가 이 단계를 이미 지났다(`CHECKPOINT_TO_REMAINING`) | `이미 지난 단계(체크포인트 …)` | 실행 |

토큰은 앞 8자만 로그에 남긴다. 토큰 없는 메시지가 토큰 없는 아이템(배포 전 아이템)에 오면 3·4 를 지나 예전처럼 돈다 — 옛 메시지 호환이다. 함정 16 ② 의 재전달된 요약·`embed_index` 는 5·6 에서 멈춘다.

**`_run_stage` — 단계 래퍼.** 다섯 마디다.

1. 첫 읽기는 `with_for_update()` 다. 디스패처는 메시지를 보낸 뒤 루프 끝에서 토큰을 커밋한다. 큐가 비어 있으면 워커가 그 커밋보다 먼저 메시지를 받는다. 그냥 읽으면 커밋 전 값(옛 토큰)을 보고 새 체인을 토큰 불일치(위 표의 3)로 멈춘다 — 아이템은 `dispatched` 로 4시간 묶인다. FOR UPDATE 는 디스패처의 행 잠금(커밋까지 유지)이 풀리기를 기다린 뒤 커밋된 새 토큰을 읽는다(READ COMMITTED). 읽은 뒤 세션을 바로 닫아 잠금을 놓는다.
2. 이유가 있으면 WARNING `[book] item=N <단계> 실행 안 함 — <이유> → 체인 정지` 를 남기고 `Ignore` 를 던진다. 아이템·카탈로그는 바꾸지 않는다.
3. 문서 락(`BookLock`, TTL = 그 단계 타임아웃)을 못 얻으면 `Ignore("락 경합")` 이다. 옛 코드는 `pending` 으로 되돌리고 `skipped` 를 돌려줘 체인이 다음 단계로 갔다. 이제 상태는 그대로이고, 멈춘 아이템은 대기 상한(`DISPATCH_STALE_SECONDS`) 뒤 stale 복구가 회수한다(§1-2).
4. 시작 기록은 `status=running` 과 함께 `meta.stage_running`(단계 이름)·`stage_started_at`(UTC ISO)을 적는다 — stale 판정이 실행 시간을 이 시각부터 잰다. 이 기록이 토큰 대조에서 막히면 쥔 락을 풀고(새 체인의 같은 단계가 락 경합에 막히지 않게) `Ignore` 다.
5. 단계 함수에는 아이템 meta 사본(`item_meta`)을 넘긴다(§2.25). 성공 기록은 결과와 `stage_running: None` 을 함께 쓴다. 실패 기록은 `no_text` 면 `min_attempt` 로 attempt 를 한도까지 올린다. 한도는 잡 params 의 `max_attempts`, 없으면 `INGEST_MAX_ATTEMPTS` 다.

기록이 토큰 대조에서 막히면(단계가 도는 동안 새 체인이 떴다) 셋 중 하나다.

| 기록 | 하는 일 | 로그 |
|---|---|---|
| 시작 | 락을 풀고 `Ignore` — 단계 함수를 부르지 않는다 | `실행 안 함 — 실행 토큰 불일치(시작 기록) → 체인 정지` |
| 성공 | 결과를 쓰지 않고 `Ignore` — 다음 단계를 보내지 않는다. finalize 도 카탈로그를 `embedded` 로 바꾸지 않는다 | `늦은 성공 기록 버림 — 새 체인이 있다 → 체인 정지` |
| 실패 | 아이템·카탈로그에 실패를 찍지 않고 원래 예외만 올린다 | `늦은 실패 기록 버림 — 새 체인이 있다` |

늦은 성공의 `Ignore` 는 `try` 밖(마지막 `if not recorded`)에서 던진다. `Ignore` 는 `Exception` 의 하위라 `try` 안에서 던지면 `except Exception` 이 실패로 기록한다. 그래서 `return` 도 `try` 뒤로 옮겼다. `Ignore` 가 체인을 멈추는 근거는 Celery 5.4.0 의 동작이다 — 체인의 다음 단계는 태스크가 예외 없이 끝났을 때만 보내고(`celery/app/trace.py` 의 `else:` 분기), `Ignore` 는 상태를 남기지 않고 메시지를 ack 한다(`celery/worker/request.py`, `acks_late` 여도 재전달 안 함). 출처는 계획 Task 2 설계 메모 ① 에 있다.

**`_update_item` — 기록해도 되는지를 돌려준다.** 반환이 `None` 에서 `bool` 이 됐다. `expect_token` 은 이 체인 메시지의 토큰이다. FOR UPDATE 로 읽은 아이템의 `meta.run_token`(빈 값은 `None` 으로 본다)과 같을 때만 쓰고, 다르면 읽기만 하고 `False` 다. `None` 이면 아이템에도 토큰이 없을 때만 쓴다(49f62ef — 처음에는 대조 없이 써서, 재전달된 배포 전 메시지가 도는 사이 stale 복구가 토큰을 적어도 그 늦은 기록이 새 체인을 덮을 수 있었다). `False` 는 아이템이 없거나 토큰이 다를 때뿐이다. DB 오류는 예전처럼 삼키고 경고만 남긴 채 `True` 다 — 토큰 때문에 안 쓴 것이 아니라서 단계 흐름은 그대로 간다. `meta_update` 는 `None` 값도 쓴다(`stage_running` 을 지울 때). `min_attempt` 는 attempt 를 그 값 이상으로 올린다.

**단계 태스크·체인.** 네 단계 태스크가 `run_token` 인자를 받는다. 기본값 `None` 이라 배포 전에 보낸 메시지(인자 `item_id` 하나)도 받는다. `acks_late=True` 는 그대로다 — 받은 채 죽은 워커의 메시지 재전달을 stale 복구·토큰이 전제로 한다(34e7295 가 테스트로 고정). `build_item_chain` 은 모든 단계 서명에 같은 토큰을 싣는다(`.si(item_id, run_token)`).

- 후보 조회: `pending` 이거나, `failed` 이면서 백오프가 지난 것(`_retry_ready`)을 id 순으로. 조건을 SQL 에 넣었다(1390055).

**재시도 백오프.** `_parse_retry_backoff` 가 `"120,600"` 을 `(120, 600)` 으로 푼다. 정수가 아닌 칸은 건너뛰고 경고하며, 빈 칸(끝 쉼표·빈 설정)은 조용히 건너뛴다. 디스패처가 30초마다 읽으므로 `lru_cache` 로 같은 설정 문자열은 한 번만 풀고 한 번만 경고한다(7871cb7 — `llm_client` 의 백오프 파서와 같은 방식). 잘못된 칸 하나로 디스패처가 죽으면 적재 전체가 멈추므로 예외를 내지 않는다. `_retry_ready(now)` 는 아래 SQL 조건을 만든다.

| attempt | 다시 집는 조건(기본 `120,600`) |
|---|---|
| 0 | 바로 |
| 1 | `updated_at` 에서 120초가 지났다 |
| 2 이상 | `updated_at` 에서 600초가 지났다(값이 모자라면 마지막 값을 되풀이) |

`updated_at` 은 실패를 기록한 시각이다. stale 복구도 attempt 를 올리고 `updated_at` 을 찍으므로 같은 백오프를 탄다. 설정이 비면 조건은 `true()` — 기다리지 않는다. 잡 완료 판정(`_maybe_complete`)은 그대로다. 백오프 중인 실패도 `attempt < 한도` 라 남은 일로 세므로 그동안 잡이 완료로 넘어가지 않고, attempt 가 한도에 오른 `no_text` 는 남은 일에서 빠진다.

수동 retry(`POST /api/admin/ingest-jobs/{id}/retry` → `retry_items`)는 아이템을 `pending`·attempt 0 으로 되돌리고 `error_group`·`last_error` 를 지운다. `reset_stage` 를 주면 체크포인트도 그 값으로 바꾼다. round07 의 실패분 재처리는 `reset_stage: "pending"` 으로 추출부터 다시 한다(spec §4). 여기까지는 원래 있던 동작이다. round07 이 바꾼 것은 둘이다.

**실행 토큰을 `retry` 로 덮는다(`RETRY_RUN_TOKEN`).** pending 으로 되돌린 아이템에는 디스패처가 새 토큰을 적기 전까지 틈이 있다. 그 틈에 옛 체인의 남은 메시지(큐 대기·재전달)가 오면 이렇게 된다.

| 토큰 처리 | 토큰 있는 옛 메시지 | 토큰 없는 배포 전 메시지 |
|---|---|---|
| 그대로 두기 | 같은 토큰이라 통과 — pending 아이템을 돌린다 | 멈춤 |

**설정을 읽을 때 막는 값 셋.** 모두 오타 하나가 모든 문서를 조용히 망치는 설정이다. 앱 컨테이너가 뜨지 않는 편이 낫다(런북 9-3 — 업데이트 뒤 재시작을 되풀이하면 `docker logs` 부터 본다).

① `ODL_IMAGE_OUTPUT` — `Literal["off", "embedded", "external"]`(1a56e93). opendataloader-pdf CLI 가 받는 값만이다. 모르는 값이면 java 가 문서마다 exit 2 로 끝나고, 추출은 그것을 ODL 실패로 받아 모든 문서를 fitz 텍스트로 대신했다. 대소문자도 가린다(`OFF`·빈 값은 거절).

② `ODL_JAVA_MAX_HEAP` — 두 겹이다(8608473·b1543bc·52ac6ad).

- 형식: `Field` 의 `pattern`(`^([1-9][0-9]*[mMgG])?$`) — `-Xmx` 뒤에 붙는 크기만 받는다. `2gb`·`-Xmx2g`·`0g`·`3`·`1.5g`·`3k` 와 공백이 든 값은 거절하고, 빈 값은 통과한다(상한 없음). `2gb` 면 java 가 뜨지 않는다.
- 하한: `_odl_heap_floor` 가 형식 검사 뒤에 크기를 MB 로 바꿔 1024 아래를 거절한다. 형식은 맞는 `3m`(`3g` 오타)이면 java 는 떠도 변환이 JNI 오류로 모두 실패한다. 1g 아래로는 무거운 문서부터 메모리 부족이 는다 — 운영 이미지 실측(`research/round07-odl-heap`)에서 가장 무거운 12건 중 768m·512m 에서 2건, 384m 에서 3건이 실패했다. 1g 는 무거운 문서 61건에서 상한 없을 때보다 1건 더 실패했다. 오류 문구도 이 실측대로 고쳤다(52ac6ad).
- 기본 3g 의 근거: 무거운 문서 61건은 2·3g 에서 상한 없을 때와 추출 결과가 같았고, 일반 688건은 2g 에서 3건만 메모리 부족이었다(3g 로 살아나는 건 그중 1건). java RSS 는 상한 + 0.2~0.3GB 라 `celery-cpu` 4칸 최악 합계가 약 13GB 다(운영 가용 131GB, 사용자 결정 2026-10-02). 상한이 없으면 JVM 기본 힙이 메모리의 1/4 이라, 운영 서버(RAM 251GB)에서 문서 하나가 약 63GB 까지 갈 수 있다(함정 23).
- 빈 값 = 상한 없음은 앱 설정에서만 된다. compose 의 `${ODL_JAVA_MAX_HEAP:-3g}` 는 빈 스택 env 도 3g 로 채운다. 운영에서 상한을 풀려면 `64g` 같은 큰 값을 준다.
- 끝 줄바꿈(`3g\n`)도 거절되는 것을 테스트가 고정한다. 파이썬 `re` 의 `$` 는 끝 줄바꿈 앞에서도 맞지만 pydantic 의 기본 정규식 엔진은 그렇지 않다 — 엔진이 바뀌면 새어 들 수 있는 자리다.

③ 추출 시간 관계 — `_extract_deadline_fits_inside_stale_timeout`(`model_validator(mode="after")`, 396a20c·70c1e87). 추출 단계가 스스로 끝나는 가장 늦은 시각이 `INGEST_STAGE_TIMEOUT_EXTRACT` 보다 짧아야 한다. 기본값으로 2700 + 60 + 60 + 10 = 2830 < 3600 이다.

### 2.32 `app/api/ingest_jobs.py` — ETA 24시간·남은 수·실패 대표 메시지

**파일**: `app/api/ingest_jobs.py` (라운드 시작 `9798f46` 대비 diff)

잡 상세(`GET /api/admin/ingest-jobs/{id}`)와 실패 그룹(`GET …/failures`)을 고친다(spec 17, 51f9c9d·528f12f). 응답은 키를 더하기만 한다 — 대시보드(`frontend/pages/admin/jobs.vue`)는 그대로다.

**`compute_eta(remaining, done_last_24h, status)`.** 남은 수 ÷ 최근 24시간의 시간당 처리량이다.

| 잡 상태 | ETA |
|---|---|
| `completed`·`completed_with_errors` | `0.0` |
| `running` 이 아님(`created`·`validating`·`ready`·`paused`·`canceled`) | `None` — 처리되지 않는다 |
| `running`, 남은 것 0 이하 | `0.0` |
| `running`, 24시간 처리 0 | `None` |
| `running` | `remaining × 24 ÷ done_last_24h` 시간(소수 한 자리) |

처음(51f9c9d)에는 paused 만 `None` 이었다. 리뷰(528f12f)가 숫자를 내는 상태를 running 하나로 좁혔다 — 취소한 잡·시작 전 잡도 처리되지 않는다.

**처리량 두 칸.** `_done_counts` 는 done 행을 한 번만 훑는 한 문장이다 — `count(*) FILTER (WHERE finished_at >= 1시간 전)` 과 같은 꼴의 24시간 칸(528f12f 가 두 문장을 합쳤다). `rate_per_hour` 는 1시간 그대로 두고 `rate_per_hour_24h`(24시간 ÷ 24)를 더한다. 1시간 칸은 재개 직후 처리량을 잴 때 쓴다(런북 9-9).

**남은 수.** `total_items − done − 영구 실패 − canceled` 다. 영구 실패(`_permanently_failed`)는 `failed` 이고 attempt 가 한도(잡 params 의 `max_attempts`, 없으면 `INGEST_MAX_ATTEMPTS`) 이상인 것 — 디스패처가 다시 집지 않는 조건과 같다. `no_text` 도 attempt 를 한도로 올리므로(§2.24) 여기 든다. 그 수를 `permanently_failed` 로 같이 낸다 — 그래야 `done_total + remaining` 이 `total_items` 와 맞지 않는 까닭이 보인다.

**실패 그룹 대표 메시지.** `_failure_groups` 가 `max(last_error)` 대신 `mode() WITHIN GROUP (ORDER BY last_error)` 로 그룹 안에서 가장 흔한 메시지를 낸다(NULL 은 세지 않는다). 사전순 최댓값이라 `not_found` 545건('섹션 없음')이 15건뿐인 '카탈로그 row 없음'으로 보였다.

세 문장(`_done_counts`·`_permanently_failed`·`_failure_groups`)을 함수로 뗀 것은 테스트가 PostgreSQL 로 컴파일해 조건과 바인드 값을 고정하려는 것이다(§2.36).

class _Ignore(Exception):
    """celery.exceptions.Ignore 대역 — 진짜처럼 Exception 의 하위다(그래서 except Exception 밖에서 던져야 한다)."""


class _Sig:
    def __init__(self, task_name: str, args: tuple):
        self.task_name = task_name

class _Chain:
    """celery.chain 대역 — 받은 서명을 남기고 apply_async 는 태스크 id 만 돌려준다."""

    def __init__(self, *sigs):
        self.sigs = list(sigs)

        return types.SimpleNamespace(id=f"celery-{uuid.uuid4().hex[:8]}")


class _Task:
    def __init__(self, fn, name: str, options: dict | None = None):
        self.fn = fn
        self.name = name
        self.options = dict(options or {})   # 데코레이터 인자(name·soft_time_limit·time_limit …)

    def __call__(self, *a, **kw):
        return self.fn(*a, **kw)

    def si(self, *args):
        return _Sig(self.name, args)


class _Conf:
    def update(self, **kw):
        for key, value in kw.items():
            setattr(self, key, value)


class _Celery:
    def __init__(self, *a, **kw):
        self.conf = _Conf()

    def task(self, *a, **kw):
        def _decorator(fn):
            return _Task(fn, kw.get("name"), kw)
        return _decorator


def _stub_missing(monkeypatch, name: str) -> None:
    try:
        importlib.import_module(name)
    except ModuleNotFoundError:
        monkeypatch.setitem(sys.modules, name, MagicMock())


def _forget_on_teardown(monkeypatch, names: tuple[str, ...]) -> None:
    """names 를 sys.modules 와 부모 패키지 속성에서 빼고, 테스트가 끝나면 import 전 그대로 되돌린다
    (test_research_tasks.py 의 같은 이름 함수 주석 참고)."""
    for name in names:
        parent, _, child = name.rpartition(".")
        monkeypatch.setattr(importlib.import_module(parent), child, None, raising=False)
        monkeypatch.setitem(sys.modules, name, None)
        del sys.modules[name]


def _load_runtime(monkeypatch, ingest_states: list):
    celery_mod = types.ModuleType("celery")
    celery_mod.Celery = _Celery
    celery_mod.chain = _Chain
    celery_exc = types.ModuleType("celery.exceptions")
    celery_exc.Ignore = _Ignore
    celery_exc.SoftTimeLimitExceeded = type("SoftTimeLimitExceeded", (Exception,), {})
    monkeypatch.setitem(sys.modules, "celery", celery_mod)
    monkeypatch.setitem(sys.modules, "celery.exceptions", celery_exc)
    _stub_missing(monkeypatch, "redis")
    # _run_stage 가 함수 안에서 import 하는 workers.tasks — 진짜는 적재 태스크 전부를 끌고 온다
    tasks_mod = types.ModuleType("workers.tasks")
    tasks_mod._set_ingest_state = lambda book_id, state, **kw: ingest_states.append((book_id, state))
    monkeypatch.setitem(sys.modules, "workers.tasks", tasks_mod)
    _forget_on_teardown(monkeypatch, _CACHED)
    return importlib.import_module("workers.job_runtime")

def _make_engine() -> sa.Engine:
    engine = sa.create_engine(
        "sqlite://", poolclass=StaticPool, connect_args={"check_same_thread": False},
    )
    metadata = sa.MetaData()
    for table in (IngestJob.__table__, IngestJobItem.__table__):
        copy = table.to_metadata(metadata)
        for col in copy.columns:
            default = col.server_default
            if default is not None and "::" in str(getattr(default, "arg", "")):
                col.server_default = None
    metadata.create_all(engine)
    return engine

def _record_selects(env) -> list[str]:
    """env.Session 으로 나가는 SELECT 를 PostgreSQL 문장으로 컴파일해 모은다. SQLite 는 FOR UPDATE 같은
    잠금을 그리지 않으므로, 잠금이 있는지는 같은 문장을 Postgres 로 컴파일해 본다."""
    selects: list[str] = []

    @event.listens_for(env.Session, "do_orm_execute")
    def _record(state):
        if state.is_select:
            selects.append(str(state.statement.compile(dialect=postgresql.dialect())))

    return selects

# ── 늦은 기록: 단계가 도는 동안 새 체인이 토큰을 바꾼 경우 ─────────────────
class TestLateRecords:
    """첫 읽기의 토큰 대조는 그 순간의 판단일 뿐이다. 단계가 도는 동안 디스패처의 재디스패치나 stale
    복구가 토큰을 바꾸면 이 체인은 옛 체인이 되는데, 그 뒤의 시작·성공·실패 기록이 새 체인의 상태를
    덮으면 안 된다(함정 16 — 늦게 끝난 옛 체인의 성공이 failed·재디스패치 상태를 덮던 경로).
    _update_item 이 FOR UPDATE 로 읽은 토큰과 대조해 다르면 아무것도 쓰지 않는다."""

    def _swap(self, env, item_id=1):
        return lambda: env.set_token(item_id, "new")

    def test_start_record_is_dropped_and_the_lock_released(self, env, caplog):
        # 첫 읽기(토큰 일치)와 시작 기록 사이에 새 체인이 토큰을 바꿨다
        env.add_item(1, stage="pending", status="dispatched", meta={"run_token": "t"})
        env.on_acquire = self._swap(env)

        with caplog.at_level(logging.WARNING, logger=env.rt.log.name):
            with pytest.raises(env.rt.Ignore):
                env.rt._run_stage("extract", 1, "celery-1", "t")

        row = env.item(1)
        assert env.calls == [], "단계 함수가 돌면 안 된다"
        assert row.status == "dispatched" and row.meta == {"run_token": "new"}, "시작 기록을 쓰면 안 된다"
        assert env.ingest_states == [], "카탈로그를 processing 으로 바꾸면 안 된다"
        assert env.locks[0].released, "쥔 락은 풀어야 새 체인이 락 경합으로 막히지 않는다"
        assert "[KCI_0001] item=1 extract 실행 안 함 — 실행 토큰 불일치(시작 기록) → 체인 정지" in caplog.text

    def test_late_success_is_dropped_and_the_chain_stops(self, env, caplog):
        env.add_item(1, stage="extracted", status="dispatched", meta={"run_token": "t"})
        env.results["summarize"] = {"sections_total": 3}
        env.during["summarize"] = self._swap(env)   # 단계가 도는 동안 새 체인이 토큰을 바꿨다

        with caplog.at_level(logging.WARNING, logger=env.rt.log.name):
            with pytest.raises(env.rt.Ignore):   # 체인 정지 — 다음 단계(embed_index)로 가지 않는다
                env.rt._run_stage("summarize", 1, "celery-1", "t")

        row = env.item(1)
        assert row.stage == "extracted", "체크포인트를 올리면 새 체인의 위치를 건너뛴다"
        assert "sections_total" not in row.meta
        assert row.meta["stage_running"] == "summarize", "성공 기록이 stage_running 을 지우면 안 된다"
        assert row.meta["run_token"] == "new"
        assert row.error_group is None and row.attempt == 0, "Ignore 는 Exception 의 하위라 실패로 기록되기 쉽다"
        assert env.locks[0].released
        assert "늦은 성공 기록 버림 — 새 체인이 있다" in caplog.text

    def test_late_finalize_is_not_marked_done_or_embedded(self, env):
        env.add_item(1, stage="indexed", status="running", meta={"run_token": "t"})

    def test_late_failure_is_dropped_but_the_error_still_propagates(self, env, caplog):

        env.during["summarize"] = self._swap(env)

        with caplog.at_level(logging.WARNING, logger=env.rt.log.name):
            with pytest.raises(StageError):   # Ignore 로 바꾸지 않는다 — 원래 예외가 그대로 올라간다
                env.rt._run_stage("summarize", 1, "celery-1", "t")

        row = env.item(1)
        assert row.status == "running" and row.attempt == 0, "새 체인의 아이템에 실패를 찍으면 안 된다"
        assert row.error_group is None and row.last_error is None
        assert row.meta["run_token"] == "new" and row.meta["stage_running"] == "summarize"
        assert env.ingest_states == [], "카탈로그를 failed 로 바꾸면 안 된다"
        assert env.locks[0].released
        assert "늦은 실패 기록 버림" in caplog.text

    def test_message_without_token_stops_writing_once_the_item_gets_one(self, env, caplog):

        # 적었으면 새 체인이 있다 — 재전달된 옛 메시지의 늦은 성공이 새 체인의 상태를 덮지 않는다

        row = env.item(1)
        assert row.stage == "extracted" and "sections_total" not in row.meta
        assert row.meta["run_token"] == "new"
        assert "늦은 성공 기록 버림" in caplog.text

    def test_message_without_token_still_writes_on_an_item_without_token(self, env):
        env.add_item(1, stage="extracted", status="dispatched", meta={})
        env.results["summarize"] = {"sections_total": 3}

        out = env.rt._run_stage("summarize", 1, "celery-legacy", None)

        assert out["stage"] == "summarize"
        assert row.stage == "summarized" and row.meta["sections_total"] == 3

# ── 수동 retry: 끝난 잡을 다시 running 으로 ────────────────────────────────
class TestRetryReopensJob:
    """retry 는 끝난 잡을 running 으로 되돌린다. 다른 잡이 이미 돌고 있으면(카나리 + 본 잡) 막지 않고 경고만 한다 —
    디스패처는 잡마다 high_water 까지 보내므로 함께 돌면 동시에 도는 아이템이 그만큼 는다."""

    def _add_job(self, env, name, status):
        job_id = uuid.uuid4()
        with env.Session() as s:
            s.add(IngestJob(id=job_id, name=name, status=status, params={}, total_items=0))
            s.commit()
        return job_id

    def _reopen(self, env, job_id):
        from services.ingestion.job_manager import _reopen_finished_job

        with env.Session() as s:
            _reopen_finished_job(s, job_id)
            s.commit()
        with env.Session() as s:
            return s.get(IngestJob, job_id)

    def test_reopening_while_another_job_runs_warns_with_both_names(self, env, caplog):
        canary = self._add_job(env, "kci-canary", "completed_with_errors")   # env 의 잡 'kci-test' 는 running

        with caplog.at_level(logging.WARNING, logger="services.ingestion.job_manager"):
            job = self._reopen(env, canary)

        assert job.status == "running" and job.finished_at is None
        warned = [r.getMessage() for r in caplog.records if r.levelno == logging.WARNING]
        assert len(warned) == 1 and "kci-canary" in warned[0] and "kci-test" in warned[0]

    def test_reopening_alone_does_not_warn(self, env, caplog):
        env.set_job(status="completed")
        with caplog.at_level(logging.WARNING, logger="services.ingestion.job_manager"):
            job = self._reopen(env, env.job_id)
        assert job.status == "running"
        assert [r for r in caplog.records if r.levelno == logging.WARNING] == []

    @pytest.mark.parametrize("status", ["running", "paused", "canceled"])
    def test_unfinished_job_keeps_its_status(self, env, status):
        job_id = self._add_job(env, "other", status)
        assert self._reopen(env, job_id).status == status

def _queues(command) -> set[str]:
    """compose command 가 celery 워커로 받는 큐 — 문자열·리스트(sh -c "…" 포함) 명령,
    -Q a,b · -Qa,b · --queues a,b · --queues=a,b."""
    if isinstance(command, str):
        args = command.split()
    elif isinstance(command, list):
        args = [token for part in command for token in str(part).split()]
    else:
        return set()
    names: list[str] = []
    for i, arg in enumerate(args):
        if arg in ("-Q", "--queues"):
            names += args[i + 1].split(",") if i + 1 < len(args) else []

            names += arg.split("=", 1)[1].split(",")
        elif arg.startswith("-Q"):
            names += arg[2:].split(",")
    return {name for name in names if name}

## 4. 면접식 Q&A

**Q1. 실행 토큰을 왜 아이템 `meta` 에 두었나 — DB 칼럼이나 Celery `revoke` 대신?**
A. 막아야 할 길이 넷이다. 큐에 남은 옛 체인 메시지, `visibility_timeout` 뒤 재전달된 메시지, 배포 전에 보낸 토큰 없는 메시지, 타임아웃을 넘겨 늦게 끝난 시도의 기록. 토큰은 단계 래퍼가 상태를 쓰는 바로 그 행을 FOR UPDATE 로 읽어 대조하므로 넷을 한 규칙으로 막는다. `revoke` 는 워커가 메모리의 id 목록으로 거르는 방식이라 워커가 모두 재시작하면(`--statedb` 없이) 목록이 사라진다 — 함정 16 의 재전달은 바로 재배포 뒤에 온다. 이미 도는 태스크는 `terminate` 로 프로세스를 죽이지 않으면 멈추지 않고, 죽이면 부분 결과가 남는다. 칼럼 대신 meta 를 쓴 것은 기존 테이블을 바꾸지 않는 원칙 때문이다(spec 18) — 마이그레이션 없이 배포하고 되돌린다. 토큰은 그 행을 읽을 때만 보므로 인덱스도 필요 없다. (`revoke` 의 한계는 Celery 의 일반 동작으로 덧붙인 설명이다 — spec·계획에는 이 대안을 검토한 기록이 없다.)

**Q2. 락 경합이면 왜 아이템을 pending 으로 되돌리지 않고 체인만 멈추나? 대가는?**
A. 락 경합은 같은 문서를 다른 체인이나 다른 잡이 쥐고 있다는 뜻이다. pending 으로 되돌리면 디스패처가 30초 안에 새 토큰으로 다시 보낸다. 새 토큰은 락을 쥐고 일하는 체인의 다음 단계를 토큰 불일치로 끊고, 새 체인은 또 락에 막힌다 — 쥔 쪽이 끝날 때까지 경합을 되풀이하며 일을 버린다. 그래서 아무것도 쓰지 않고 이 체인만 멈춘다. 대가는 느림이다. 아이템은 `dispatched`(단계 사이였으면 `running`)로 남아 잡의 진행 상한 한 칸을 쥔 채, 대기 상한(`DISPATCH_STALE_SECONDS`, 4시간) 뒤 stale 복구가 회수할 때까지 기다린다. 중복 실행은 없다. 이 대가가 운영 규칙이 됐다 — 같은 문서를 가진 두 잡(카나리와 본 잡)을 동시에 `running` 으로 두지 않고, 끝난 잡을 retry 로 되살릴 때 다른 잡이 돌고 있으면 경고한다(§2.26). 카나리의 락 경합은 0 이었다.

**Q3. stale 판정을 왜 '실행 중'과 '대기 중'으로 나눴나? 대기 상한은 왜 14400초인가?**
A. 옛 판정은 단계가 끝난 시각부터 다음 단계의 실행 타임아웃(embed 1200·마무리 900초)을 쟀다. 그 사이에는 큐 대기가 들어 있다. 보강을 요약 단계로 옮기면(spec 1) `q_llm` 이 바빠져, 마무리를 기다리는 아이템이 900초를 넘기 쉽다. 그러면 살아 있는 체인 옆에 새 체인이 열린다(함정 16). 그래서 단계 래퍼가 시작할 때 `stage_running`·`stage_started_at` 을 적고 끝날 때 지운다. 실행 중이면 그 단계 타임아웃을 단계 시작부터, 아니면 대기로 보고 `DISPATCH_STALE_SECONDS` 를 마지막 갱신부터 잰다. 대기 상한 14400초는 `visibility_timeout` 7200초의 2배다. 받은 채 죽은 워커의 메시지는 7200초 뒤 재전달돼 다시 집히므로, 그보다 넉넉히 기다린 뒤에야 메시지가 사라졌다고 본다. 짧게 잡으면 재전달을 기다리는 아이템에 새 체인을 연다. 테스트가 마무리 큐에서 2000초째 기다리는 아이템을 stale 로 보지 않는 것을 고정한다.

**Q4. 실행하지 않는 단계는 왜 `Ignore` 를 던지고, 왜 `except Exception` 밖에서 던지나?**
A. 단계 태스크의 끝은 셋이다. 값을 돌려주면 Celery 는 성공으로 보고 체인의 다음 단계를 보낸다 — 옛 코드의 `{"skipped": …}` 가 그래서 락 경합 뒤에도 다음 단계로 갔다. 예외를 던지면 실패다 — attempt 가 오르고 카탈로그에 거짓 `failed` 가 찍힌다. `Ignore` 는 상태를 남기지 않고 메시지를 ack 하며(`acks_late` 여도 재전달 안 함) 다음 단계를 보내지 않는다. Celery 5.4 의 `trace.py` 가 체인의 다음 서명을 예외 없는 `else:` 분기에서만 보내기 때문이다. 그런데 `Ignore` 는 `Exception` 의 하위라, 단계 함수를 감싼 `try … except Exception` 안에서 던지면 실패로 기록된다. 그래서 실행 판단(첫 읽기·락·시작 기록)은 `try` 앞에서, 늦은 성공 판단은 `try` 뒤에서 한다. 테스트 대역 `_Ignore` 도 일부러 `Exception` 하위로 만들어 이 실수를 잡는다.

**Q5. 첫 읽기에서 토큰을 봤는데 왜 기록마다 다시 보나? 그래도 남는 한계는?**
A. 첫 읽기는 그 순간의 판단이다. 추출은 데드라인(45분)까지 돈다. 그동안 stale 복구가 토큰을 바꾸거나, 수동 retry 가 `retry` 로 덮고 디스패처가 새 체인을 보낼 수 있다. 그 뒤 옛 시도가 성공을 쓰면 체크포인트를 올려 새 체인의 위치를 건너뛰고, 실패를 쓰면 새 체인의 아이템에 attempt 를 올린다. 그래서 `_update_item` 이 기록마다 FOR UPDATE 로 다시 읽어 대조하고, 다르면 아무것도 쓰지 않는다(a099356). 한계: 버리는 것은 아이템·카탈로그의 상태 기록뿐이다. 그 시도가 이미 쓴 `book_sections`·MinIO 아티팩트·Milvus 청크는 남는다. 그래서 단계 타임아웃이 시도별 하드 마감이 됐고(§2.29 의 검사가 추출이 그 안에 끝나게 한다), 카나리는 단계 꼬리(⑧)와 겹쳐 쓴 흔적(⑨)을 따로 본다.

**Q6. 제어 큐를 동시 1 의 별도 워커로 떼고 beat 에 `expires` 를 둔 까닭과 그 대가는?**
A. 디스패처는 in-flight 를 세고 `high_water − in_flight` 만큼 보낸다. 두 틱이 함께 돌면 둘 다 커밋 전의 in-flight 를 세 상한을 넘겨 보낸다 — `SKIP LOCKED` 는 같은 아이템을 두 번 집는 것만 막는다. `q_control` 을 추출 워커(동시 4)가 받으면 추출 4칸이 찰 때 틱이 뒤에 쌓였다가 칸이 비면 여럿이 함께 돌았다. 한 칸 워커는 틱을 하나씩 돌리고, 주기보다 짧은 `expires` 는 늦게 받은 옛 틱을 버려 밀린 틱이 연달아 돌지 않게 한다. 처리량 이득은 거의 없고 안정성 이득이다(spec 6). 대가는 한 칸이 붙잡히면 디스패치·stale 복구·정리·회수가 모두 멈춘다는 것이다. 그래서 제어 큐 태스크마다 시간 제한(디스패처·회수기 60/90초, 정리 120/150초)을 두고 Milvus flush 에 정수 타임아웃을 줬다. 디스패처는 도중에 끊겨도 커밋 전 토큰을 실은 메시지가 멈추고 다음 틱이 다시 보내므로 안전하다. 배포 확인에 `q_control` 소비자가 `celery-control` 하나인지를 넣었다.

**Q7. 추출 stale 판정 3600초는 왜 `visibility_timeout`(7200초) 아래여야 하고, 데드라인과의 관계는 왜 설정을 읽을 때 검사하나?**
A. 두 시계의 순서를 맞추는 일이다. 브로커는 ack 안 된 메시지를 받은 지 7200초 뒤 큐로 되돌린다(`acks_late`). stale 복구는 상한을 넘긴 아이템의 토큰을 바꾼다. 실행 중인 단계는 stale(3600) → 재전달(7200) 순서다. 워커가 죽은 시도는 stale 복구가 먼저 토큰을 바꾸고, 7200초에 재전달된 그 메시지는 토큰 불일치로 멈춘다. 정상으로 도는 추출은 2830초 안에 끝나 재전달 전에 ack 된다. 대기 중인 아이템은 반대로 재전달(7200) → stale(14400) 순서라, 받은 채 죽은 워커의 메시지가 재전달로 먼저 다시 집힌다. 옛 값 14400초는 실행 중인 추출에서 이 순서를 뒤집었다. 아래쪽 경계는 단계 타임아웃이 시도별 하드 마감이라 생긴다. 넘긴 시도는 결과가 버려지고 같은 일을 처음부터 되풀이하며, 문서 락 TTL 도 같은 값이라 다시 나간 체인이 옛 시도와 같은 문서를 함께 돌 수 있다. 그래서 추출이 스스로 끝나는 가장 늦은 시각(2700 + 60 + 60 + 10)이 3600 아래여야 한다. 이 관계는 스택 env 하나로 깨진다(stale 판정만 1800 으로 줄이는 식). 문서로만 두면 조용히 결과를 버리는 적재가 되므로, `ODL_IMAGE_OUTPUT` 오타처럼 기동 때 `ValidationError` 로 멈추게 했다. 위쪽 경계는 `celery_app.py` 의 상수라 테스트가 compose 기본값으로 본다. 카나리의 추출 최대는 383초였다.

**Q8. ETA 를 왜 24시간 처리량으로 내고, paused·영구 실패는 어떻게 다루나?**
A. 이 잡에는 처리량이 다른 두 구간(일반 PDF 시간당 약 300건, 스캔본 약 50건)이 섞여 있다. 1시간 창은 스캔본이 몰린 시간에 재면 처리량이 몇 분의 1로 떨어져, ETA 가 48시간 기준의 0.73~5.7배로 출렁였다(진단 때 856시간). 24시간 창은 두 구간이 섞여 덜 흔들린다. 대가는 느린 반응이다 — 재개 직후에는 멈춰 있던 시간이 창에 들어 ETA 가 길게 나온다(런북은 재개 하루 뒤부터 보라고 적는다). 그래서 1시간 처리량(`rate_per_hour`)은 그대로 남겨 재개 직후 처리량을 잰다. paused·canceled·시작 전 잡은 처리되지 않으니 ETA 가 `None` 이다(옛 코드는 paused 에도 554시간을 냈다). 남은 수에서는 영구 실패(시도 한도에 닿은 failed — `no_text` 포함)와 취소한 아이템을 뺀다. 더 처리되지 않는 것을 남은 수에 넣으면 ETA 가 0 에 닿지 않는다. 뺀 수는 `permanently_failed` 로 같이 낸다.
