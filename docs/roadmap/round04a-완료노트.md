## 3. 라이브에서 발견해 고친 버그 — 종합이 절 1개만 만들었다 (`b6360b8`)

**증상**: 하위질문 3개에 근거 10편을 모았는데 보고서는 절 1개, 논문 1편, 향후 과제 1개. Step 7 의 무결성 검사(미해석 마커)는 `set()` 으로 통과했다 — 검사가 **무결성만 보고 구성을 보지 않았다.**

**원인**: 전체를 한 번의 호출로 맡긴 종합 프롬프트의 JSON 예시가 "섹션 1 · 논문 1 · 과제 1" 모양이었고, gemma-3-12b 가 그 개수를 그대로 베꼈다. 동시에 spec §4-1 위반이었다 — "불릿을 그 논문의 근거만 넣고 생성하면 인용이 구조로 정해진다"인데, 어느 절·어느 논문을 실을지를 모델이 고르고 있었다.

**수정**:
- 하위질문마다 호출 1회. 소제목은 하위질문 그대로, 논문 목록은 그 하위질문의 근거 순서대로 최대 5편(`PAPERS_PER_SECTION`)을 코드가 정한다(`synthesizer.build_section`). 모델은 도입·요약·향후 과제 **문장만** 쓴다. 다만 요약은 절의 논문 5편 발췌를 한 호출에 넣고 번호별로 받는다 — 어느 논문이 실리고 칩이 어디를 가리키는지는 구조로 정해지지만, **요약 문장이 그 논문 내용인지는 모델의 번호 배정(추론)에 달려 있다.** 이 수정으로 §4-1 이 온전히 성립한 것은 아니다(spec §4-1 구현 시 변경).
- 모델이 빠뜨린 요약은 빈 요약으로 싣고 한계에 "요약을 생성하지 못한 논문 N편". 일부 절 실패는 "서술을 생성하지 못한 절 N개"로 보고하고 넘어가며, **전부 실패하면 예외** — 서술 0줄짜리 보고서를 completed 로 두면 `stage=explored` 재시도 기회가 사라진다.
- 수정본을 배포 전에 **같은 잡의 `state_snapshot` 으로 종합만 드라이런**(DB 쓰기 없음, 워킹트리 코드를 gzip+base64 로 stdin 스크립트에 박아 `nl-lib-fastapi` 에서 실행)해 절 3 · 논문 9/10 · 요약 12/12 를 확인한 뒤 배포했다. 탐색 비용 없이 같은 근거로 전후를 비교할 수 있어 유용했다. 요약이 **맞는 논문에 배정됐는지**는 이 드라이런에서 재지 않았다.
- 그 드라이런에서 모델이 **대표 논문 요약에도 `[E7]` 을 달았다.** 요약은 `bind_markers` 를 거치지 않으므로 지어낸 번호가 검증 없이 나갈 수 있다 → `citations.strip_markers` 로 전부 걷어낸다(인용은 칩이 구조로 이미 가짐). 프롬프트에도 금지를 명시.
- plan Task 11 Step 7 에 구성 검사(절 수·논문으로 실린 근거·요약 속 마커)를 추가.

2. **적대적 검증 워크플로** — 발견마다 별도 검증자가 반박을 시도하고, 가능하면 스크래치 대역으로 재현했다(SQLite 세션·시그널 흉내·가짜 LLM 응답·변이본으로 테스트가 회귀를 잡는지 확인). 영역 경계에서 아무도 안 본 공백 5개(워커 유휴 트랜잭션 잠금 · 소프트 리밋 삼킴 · `celery-llm` CPU fp16 리랭크 · step 이력의 시도 구분 · Redis 중계 신뢰)도 따로 찾아 같은 절차를 거쳤다.
3. **결과 — 발견 133 · CONFIRMED 118 · PLAUSIBLE 2 · REFUTED 13.** 남은 120건(high 5 · medium 77 · low 38)은 여러 영역이 같은 원인을 짚은 것이 많아, 중복을 병합하면 **원인은 약 18개**다. high 5건은 전부 한 원인(취소 덮어쓰기)이다.

- **대표 논문 요약의 논문별 호출** — 호출 수가 절당 최대 5배다. 차이와 이유는 spec §4-1 구현 시 변경.
- **탐색 중 시간 초과의 부분 체크포인트** — 하위질문 단위 스냅샷이 필요해 재개 설계가 바뀐다. 기본 파라미터 실측으로 상한 여유부터 본다.
- **근거 상한의 선착순 배분** — `max_evidence` 는 잡 전역이라 앞 하위질문이 채우면 뒤 하위질문이 굶는다. 이번에는 그 사실을 한계에 따로 쓰고 헛재검색을 멈추게만 했다. 하위질문별 예산(예: `max_evidence // 하위질문 수`)은 절당 5편 상한과 함께 정할 제품 결정이라 두었다(25·48).
- **전용 워커 전환 뒤의 동시 실행 상한·429 없음** — 전용 워커는 실행을 한 번에 한 잡씩 돌리고, 뒤 잡은 `approved` 로 앞 잡이 끝나길 기다린다(최대 25분, 계획은 별도 워커라 막히지 않는다). 적재 슬롯을 먹지 않으므로 대기 신호와 함께 화면에서 정한다. 전환 전 과도기(`RESEARCH_QUEUE` 가 적재 큐)에는 적재 데이터를 지키려고 상한 1·429 를 뒀다(75).
- **라우터의 ORM 직접 사용(표준 반례)** — 서비스·리포지토리·응답 스키마로 옮기는 구조 변경이라 대회 이후.
- **Redis 무인증 호스트 노출** — 기존 인프라(round03 이월). 대회 전 조치 여부는 사용자 결정.
- **low 몇 건** — JSON 추출 관용도, 계획 파싱의 형식 내성, 무근거 문장 과소 계수. 실패하면 판정 불가·계획 실패·한계 과소 보고로 드러나고 데이터를 해치지 않는다.

## 5. 결정

- **실행 모델은 비동기 Celery + SSE 중계 + DB 영속의 결합.** 동기 SSE 는 탭을 닫으면 소실되고, 순수 비동기는 시연에서 기다리는 그림이 안 남는다(spec §2-1).
- **LangGraph 미도입.** 분기가 "한 번 더 돌까"와 "승인 대기" 둘뿐이라 상태 dataclass + async 함수로 충분하다. 단계 함수는 나중에 노드로 그대로 꽂을 수 있게 짰다(spec §2-2).
- **진행 기록 2계층.** 굵은 단계는 `research_steps`(영구), 잔이벤트는 Redis pub/sub(휘발). 재접속 시 Postgres 로 뼈대를 복원하고 Redis 로 이어받는다(spec §2-3). 구현에서 step 은 하위질문당 1행(재검색 라운드는 합침)이다.
- **보고서의 탐색 경로 정본은 `report.trail`, 진행 패널은 `research_steps`.** `research_steps` 는 재시도마다 행이 쌓이는 실행 이력이고(시도 구분 없음), `report.trail` 은 그 보고서를 만든 시도의 탐색이다. 계획 목록은 `research_jobs.plan`(승인본) — plan step 의 result 는 LLM 원안이다(spec §2-3 구현 시 변경).
- **인용 2갈래.** 대표 논문 요약은 실리는 논문과 칩을 코드가 정하는 구조적 인용, 도입·향후 과제는 `[E#]` 마커 + **그 절에 준 번호로** 전수 검증. 지어낸 번호는 1건부터, 무근거 서술은 3건부터 한계에 보고. 요약 문장의 논문 배정은 모델 추론으로 남았다 — 논문별 호출은 호출 수 최대 5배라 이번에 하지 않았다(spec §4-1 구현 시 변경).
- **종합은 하위질문별 호출이고 절·논문 구성은 코드가 정한다** — §3. 모델에게 구조를 맡기면 예시의 개수를 베낀다. 절마다 1회 재시도하고, 그래도 실패한 절만 논문 목록으로 남긴다.
- **절당 대표 논문 5편 상한 유지.** "대표 핵심 논문"이 spec 의 뼈대이고, 이번 실측에서 근거 1편(6편 중 6번째)이 이 상한으로 빠졌다.
- **`status` 와 `stage` 분리, 복구는 `POST /retry` 하나.** 종합이 실패하면 `stage=explored` 와 `state_snapshot` 이 남아 retry 가 탐색을 건너뛰고 종합부터 다시 한다. spec §6 의 자동 재개(워커 사망 시 되돌려 재개)는 구현하지 않았다 — 워커가 죽은 잡은 회수기가 `failed` 로 떨어뜨릴 뿐이다. **round04b 에 재시도 UI 가 필요하다.**
- **상태 전이는 조건부 UPDATE 로만.** 워커도 API 도 job ORM 객체에 상태를 대입하지 않는다. 취소는 API 프로세스가, 진행은 워커가 찍으므로 조건 없이 쓰면 늦게 쓴 쪽이 이긴다.
- **딥리서치 전용 큐·워커(`q_research` / `celery-research`, 계획은 `q_research_plan` / `celery-research-plan`).** 적재 요약과 같은 `q_llm` FIFO 에 있으면 사용자의 계획 요청(0.6초짜리)이 적재 요약 수십 건 뒤에 서고, 반대로 리서치 실행(설계 5~7분, 상한 25분)이 적재 요약 슬롯 4개 중 하나를 쥔다 — 처리량만의 문제가 아니다. 여럿이 쥐면 슬롯을 기다리는 적재 아이템이 단계 타임아웃을 넘겨 stale 복구되고 중복 체인(함정 16번)이 열린다. `celery-llm` 은 GPU·모델 캐시가 없어 탐색의 BGE-M3·리랭커에 맞지 않는다(함정 17번). 전용 워커는 GPU·`/data/models/.hf-cache:/models`·`--concurrency=1`(모델을 자식마다 따로 올리지 않는다).
  - **concurrency 1 의 대가** — 실행은 한 번에 한 잡이다. 두 번째 잡은 계획 승인 뒤 `approved` 로 앞 잡이 끝나길 기다린다(최대 `JOB_DEADLINE` 25분, SSE 는 ping 만). 계획까지 같은 슬롯이면 새 질문이 `created` 로 멈춰 "계획 수립 중"조차 안 뜨므로, 계획은 GPU 가 필요 없는 경량 워커(`--concurrency=2`)가 따로 받는다(`RESEARCH_PLAN_QUEUE` — 비우면 `RESEARCH_QUEUE` 를 따라 지금처럼 `q_llm`). 전환 뒤에는 동시 실행 상한·429 가 없다(§8). 전환 전 과도기에는 approve·retry 가 실행 슬롯 1개(`approved`·`queued`·`running`)를 넘으면 429 다.
- **`RESEARCH_QUEUE` 기본값은 `q_llm` 으로 두고, 전용 워커 전환은 스택 업데이트 한 번으로 한다 — 인덱싱이 끝난 뒤, 또는 적재를 pause 해 in-flight 를 비운 뒤.** compose 는 `RESEARCH_QUEUE: q_research`·`RESEARCH_PLAN_QUEUE: q_research_plan` 을 `x-common-env` 가 아니라 fastapi·`celery-research`·`celery-research-plan` 서비스 env 에만 둔다.
  - **1단계(선택, 인덱싱 중에도 가능)** — 리뷰 반영 코드를 먼저 내보내야 하면, 서버에서 새 `:latest` 를 `docker pull` 해 두고 Portainer 에서 `nl-lib-fastapi`·`nl-lib-celery-llm` 컨테이너만 Recreate 한다. 컨테이너 Recreate 는 기존 설정을 그대로 써서 `RESEARCH_QUEUE` 가 없으므로 딥리서치는 지금처럼 `q_llm`·`celery-llm` 에서 돈다. 비용: `celery-llm` 은 적재의 요약·마무리 단계도 돌리므로 recreate 순간의 적재 태스크(최대 4개)가 끊기고, 끊긴 아이템은 약 2시간 뒤 옛 태스크가 재전달돼 다시 돈다(아래 이유) — **적재를 pause 하고 in-flight 가 0 이 된 뒤 Recreate 하면 끊기는 태스크가 없다**(런북 §8). fastapi Recreate 는 lifespan 의 `ALTER TABLE library_catalog` 가 잠금을 기다리는 동안 조회를 줄 세운다(함정 18번). **새 compose 로 `docker compose up -d fastapi celery-llm` 을 하면 안 된다** — fastapi 만 `q_research` 로 보내 잡이 소비자 없는 큐에 쌓인다. 1단계에서는 Portainer 스택 정의(compose)도 바꾸지 않는다 — 스택 정의를 고쳐 업데이트하는 것이 곧 2단계다. 스택이 git 저장소 자동 업데이트에 묶여 있다면 compose 변경을 push 하는 것만으로 2단계가 일어날 수 있으니 인덱싱 중에는 먼저 확인한다(설정은 저장소에 기록돼 있지 않다). **1단계 구성에서 적재가 `running` 인 동안에는 운영 딥리서치를 돌리지 않는다** — 적재를 pause 하고 in-flight 0 을 본 뒤 돌린다(런북 §8). API 의 상한 1 은 몰아서 승인하는 사고를 막는 안전장치다.
  - **2단계(인덱싱이 끝난 뒤, 또는 적재 pause 로 in-flight 를 비운 뒤)** — **2026-09-23 18:23 KST 완료(§2-1).** 스택 업데이트 한 번. fastapi 가 계획은 `q_research_plan`, 실행은 `q_research` 로 보내고 `celery-research`·`celery-research-plan` 이 생긴다. 띄우기 전에 `nvidia-smi` 로 GPU 여유(BGE-M3+리랭커 약 3~4GB)를 본다. 확인은 plan Task 11 Step 3. 끝나면 워밍업 잡 1회 뒤 resume(런북 §8).
  - **이유** — 스택 업데이트는 같은 `:latest` 를 쓰는 적재 워커 5개를 모두 재생성할 수 있다(함정 16번). Postgres·Milvus·MinIO 는 외부 볼륨이라 재생성으로 지워지지 않는다. 문제는 끊긴 아이템이다 — 디스패처의 stale 복구(약 20분 뒤 새 체인)와 브로커 재전달(`task_acks_late=True`·`visibility_timeout` 7200초 뒤 옛 체인)이 **둘 다** 돈다. 새 체인이 끝나며 추출 아티팩트를 지운 뒤 옛 체인이 같은 아이템의 `embed_index` 를 다시 돌면, 논문은 PDF 본문 청크가 초록 청크로 덮이고 도서는 멀쩡한 벡터에 `ingest_state='failed'` 가 찍힌다. 그래서 적재 워커는 in-flight 가 0 일 때만 재생성한다. 근본 수정은 적재 코드라 인덱싱이 끝난 뒤로 미룬다(§8).
- **시연 구간 운영.** (해소 — 2단계를 인덱싱 도중 pause 안에서 마쳐 시연은 전용 워커 구성으로 치른다. 아래는 그 전의 판단 기록.) 인덱싱 완주는 11월 초, 대회는 10월 초로 추정한다(spec §1). 2단계를 인덱싱 뒤로 미루면 시연은 과도기 구성(`q_llm`·`celery-llm`)으로 치르게 되고, 계획·실행이 적재 요약 FIFO 뒤에 서며 recreate 뒤 첫 탐색은 모델을 새로 받는다. 시연 전에 둘 중 하나를 정한다 — (a) 적재 pause → in-flight 0 → 2단계 스택 업데이트 → 워밍업 → resume, (b) 과도기 구성 그대로 두고 시연·리허설 구간만 적재 pause + 워커 기동 뒤 워밍업. (b)는 `celery-llm` 자식 4개가 모델을 따로 올려 워밍업 1회가 모두를 데우지 못한다. 어느 쪽이든 과도기 구성에서 딥리서치를 돌리는 구간(리허설·미리 돌리기·실측 포함)은 적재 pause·in-flight 0 안이어야 한다 — 적재가 돌 때 실행이 슬롯을 쥐면 적재 아이템이 stale 복구로 밀린다(함정 16번). 절차는 `bulk_ingest_runbook.md` §8, 미리 돌려둔 보고서를 여는 방식(§8 시연 질문)이면 둘 다 필요 없다.
- **원문 보기는 자체 PDF(`/api/books/{cnts_id}/pdf`).** `uci`·`url` 이 논문 236,513편 전부 0건이라 외부 링크 분기는 운영에서 죽은 코드다.
- **비동기 테스트는 `asyncio.run(...)` 관례.** `pytest-asyncio` 는 설치하지 않는다 — 플러그인 없이 `@pytest.mark.asyncio` 를 쓰면 코루틴 본문이 실행되지 않는다(로컬 pytest 9.1.1 은 `async def functions are not natively supported` 로 실패 처리한다 — 예전 판본은 경고만 남기고 통과시켰다).

## 6. 라이브에서만 드러난 함정

`docs/ops/recurring-gotchas.md` 에 반영(13~19번).

- **13** — `services.search.pipeline` 을 모듈 최상단에서 import 하면 torch 가 없는 로컬에서 pytest collection 이 통째로 죽는다. 함수 본문 안에서 import.
- **14** — 운영 스키마는 Alembic 이 아니라 FastAPI lifespan 이 만든다 — `create_all`(새 테이블)과 `ALTER TABLE … ADD COLUMN IF NOT EXISTS` 블록(`doc_type`·`extra`·인덱스). `alembic_version` 이 `0003` 인데 `0004` 객체가 전부 실재해 `upgrade head` 가 `DuplicateColumn` 으로 죽었다. 객체 확인 후 `stamp`. 현재 서버는 `0005_research_jobs`.
- **15** — LLM 은 프롬프트 JSON 예시의 **개수**를 베낀다. 예시에 항목이 하나면 출력도 하나다. 구성(몇 개·무엇을)은 코드가 정하고 모델에게는 채울 칸만 준다. 검증 스크립트도 무결성뿐 아니라 구성을 봐야 잡힌다.
- **16** — 앱 서비스가 전부 같은 `:latest` 라 스택 업데이트 한 번이 도는 적재 워커를 모두 재생성한다. `celery-llm` 하나만 recreate 해도 적재 요약이 끊긴다. 볼륨 데이터는 지워지지 않지만, 끊긴 아이템은 stale 복구와 브로커 재전달이 둘 다 돌아 약 2시간 뒤 옛 체인이 다시 돈다 — 논문은 본문 청크가 초록 청크로 덮일 수 있다. 재생성 전에 적재를 pause 해 in-flight 를 비운다.
- **17** — `celery-llm` 에는 GPU·모델 캐시 마운트가 없다. 거기서 검색을 돌리면 recreate 마다 모델을 새로 받고 CPU(그것도 fp16)로 리랭크한다.
- **18** (잠복) — lifespan 의 `ALTER TABLE library_catalog` 는 컬럼이 있어도 배타 잠금을 요구한다. 트랜잭션을 연 채 LLM 을 기다리는 세션 하나가 FastAPI 기동과 그 뒤 모든 조회를 멈출 수 있다.
- **19** (리뷰에서 재현) — Celery 소프트 리밋은 asyncio 코루틴 안에서 믿을 수 없다. await 중이면 `asyncio.run` 밖으로 튀고, 하위 계층의 `except Exception` 이 삼킨다. 코루틴 안의 데드라인으로 둔다.
- **취소 API 는 즉시 `canceled` 를 반환하지만 워커는 진행 중인 하위질문(탐색) 또는 절 호출(종합)을 마저 끝낸 뒤 멈춘다.** `status` 만 보고 "끝났다"고 판단하면 `running` 인 step 을 보게 된다. 취소 검증은 잠시 뒤 step 이 닫혔는지와 이후 step 이 없는지로 한다. (설계대로의 동작이라 함정 목록에는 넣지 않았다.)
