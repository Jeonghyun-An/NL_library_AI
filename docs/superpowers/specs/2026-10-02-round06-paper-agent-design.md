## 0. 사용자 요청 (paraphrase)

> 딥리서치에서 자연스럽게 이어져 논문 주제와 읽기 목록까지 만들고, 초안 작성까지 돕는 진짜 논문 에이전트 플랫폼으로 거듭나자. 태그라인은 "질문으로 시작해 연구 자동화까지". 지금 딥리서치 결과 화면이 논문 검색과 다른 스타일로 따로 열리는 것도 함께 정리하자. 10월 말 도서관 대회에서 연구 논문·도서 전문가들이 직접 써 본다 — 범위는 시연에 맞추되, 미리 돌린 가짜 화면이 아니라 실제로 동작하고 DBpia AI 아이디어와 견줄 차별점이 있는 제품 품질로. 보안은 뒤에 보강한다. (검토 때) 지금 딥리서치 기능은 있고, 그다음으로 연구 주제 만들기 등이 이어지는 것이다.

**한 줄 설계:** 딥리서치는 지금 그대로 두고, 보고서 끝 [이 연구 이어가기] 를 누른 딥리서치가 그 자리에서 연구 한 건으로 자란다 — 주제 → 읽기 목록 → 연구계획서. 이 이어가기 뒤의 흐름을 **연구 어시스턴트**라고 부른다. 단계마다 AI 가 후보를 내고 사용자가 골라 확정한다. 연구 공백 주장은 내세우기 전에 코퍼스 전체에서 스스로 반증 검사를 거친다.

> 10-08 회의: 단계 이름은 제목 고르기 → 참고문헌 선택하기 → 보고서(이름 미정), 마지막 단계는 [보고서 만들기] 한 번으로 자동 산출한다(D20·D23·D24). 공백 반증 검사(격자·확인 검색)는 대회 뒤다(D19) — §12.

**대회 한 줄:** "질문하면 답과 근거를 함께 주고, 필요하면 그 자리에서 더 깊게 조사해 연구계획서 초안까지 이어 준다."

**연구 어시스턴트 단계 공통(S2′~S7)**
- 단계는 주소 `?s=` 에 싣는다 — 새로고침·뒤로 가기·새 탭이 그대로 된다. `?s=` 가 없으면 탐색·보고서(S1·S2)를 연다(기존 링크 호환). 기존 `?at=&y=` 위치 복원은 그대로 동작한다. 사이드바에서 이어간 연구 줄을 누르면 그 연구의 현재 단계 `?s=` 로 간다.
- 끝난 단계는 진행 막대에서 눌러 언제든 다시 연다(① 탐색 = 보고서). 앞 단계를 바꿔도 뒤 단계는 지우지 않고 '다시 맞춤 필요' 배지만 붙인다.
- 자동 스크롤은 하지 않는다. 화면 밖이 바뀌면 "새 후보 3 ↓" 알약만 띄운다. `prefers-reduced-motion` 이면 즉시 전환한다. (딥리서치 진행 화면은 D22 로 지금 쓰는 절을 따라간다 — 이 규칙은 어시스턴트 단계에만 남는다.)
- **온보딩 모달:** [이 연구 이어가기] 를 브라우저에서 처음 누를 때 한 번 띄운다. "탐색은 끝났습니다. 주제 → 읽기 목록 → 계획서 3단계를 거쳐 연구계획서 초안까지 갑니다" + 단계마다 한 줄 설명과 사용자가 결정할 것. 진행 막대의 [?] 로 다시 본다.
- **4단계 진행 막대:** 이어간 연구에만 보인다. `① 탐색 ② 주제 ③ 읽기 목록 ④ 계획서` + "2/4 단계 · 주제 고르는 중". 끝난 단계는 누를 수 있다. 사이드바의 이어간 연구 줄에는 지금의 진행 표시 옆에 같은 막대를 작게 넣는다. 이어가지 않은 딥리서치의 화면·사이드바 줄은 지금과 같다. → 단계 이름(온보딩 포함)은 D23·D24, 마지막 이름은 Q2(§12-10). 06d 의 고정 진행 영역은 끝나지 않은 잡에만 서므로 이 막대와 한 화면에 함께 서지 않는다(§12-3).

LLM 을 쓰지 않는다.
- **열 = 방법 유형 8개(코드 열거형, 제안):** 실험·준실험 / 설문·조사 / 사례 연구 / 면담·관찰(질적) / 문헌 고찰·메타분석 / 내용·텍스트 분석 / 모델·시스템 개발 / 이론·개념 연구. 논문의 방법 유형은 특징 추출(§5-4) 결과로 정한다. 추출 전이거나 '미확인'인 논문은 칸에 세지 않고 "미분류 k편"으로 따로 보인다.
- **표본 수 n:** 채택 근거 중 그 칸에 드는 논문 수 — `GET .../grid`(동기, LLM 없음). 특징 추출이 끝날 때마다 워커가 저장된 개념 소속과 `paper_facets` 로 칸 숫자만 다시 세어 `grid` 이벤트를 보낸다(`concept_members` 가 비었으면 보내지 않는다).
- **확인 검색 m:** `POST .../grid/check`(동기, FastAPI — 하이브리드 검색과 리랭커가 있는 곳) — 질의 "개념 + 방법 유형"으로 코퍼스 전체를 하이브리드 검색해 상위 50편을 리랭커로 다시 매기고 임계값 이상을 센다. 결과·코퍼스 스냅숏을 `research_gap_checks` 에 저장하고 찾은 논문을 서랍에 펼친다. 확인은 사용자가 칸을 눌러 돌린다(와 장면 2) — 화면이 자동으로 돌리지 않는다.
- **확인 검색을 거치지 않은 칸은 주제 씨앗으로 쓰지 않는다.** 표본과 확인 검색은 문구·화면 모두에서 구분한다("채택 48편 중" ≠ "적재분 N편 검색 상위 50편").

### 5-4. 읽기 목록 (06b 기본, 06c 추출 열·넓히기·연관)

> 10-08: 화면 이름은 '참고문헌 선택하기', 논문을 누르면 오른쪽 딥리드(D24, §12-4 참고문헌 선택하기). [주제로 넓히기]·[연관 더 찾기]·특징 추출·추출 열은 대회 뒤(D19).

- **후보 갈래:**
  - ① 채택 근거 전체(최대 90편 — `state_snapshot.evidence`, 이어가기 때 가져온다).
  - ② 되살린 제외 논문 — 후보 서랍의 'critic 이 뺀 논문' 묶음(`trail[].excluded_papers`). 논문별 제외 사유는 저장된 곳이 없으므로(critic 출력은 번호 배열뿐이고 D16 으로 형식을 바꾸지 않는다) 어느 하위질문의 몇 회차에서 뺐는지와 그 회차의 critic note(`rounds[].note`)를 함께 보인다. [되살리기] 로 후보에 넣는다(origin `revived`, 보고서는 바꾸지 않는다).
  - ③ [주제로 넓히기] — 고른 주제 질의로 검색 1회(동기, LLM 없음).
  - ④ [연관 더 찾기] — 담은 논문마다 `find_related_papers`(한 편 씨앗 함수)를 부른다. 씨앗은 최대 5편, 결과를 합쳐 이미 후보·담음인 논문을 빼고 점수순으로 자른다(동기).
  - ⑤ 빠른검색 결과의 [담기](D17, origin `user`).
  - 보고서가 인용한 논문을 자동으로 '담음' 처리하지 않는다.
- **들어온 경로(`origin_ref` JSONB) — 저장된 값만 쓴다:** 하위질문(`subquestions[].evidence_ids` 소속), 그 하위질문 안 순위(`evidence_ids` 순서), 매칭 대목과 점수(`evidence_chunks`·`chunk_scores`), critic 판정(하위질문 verdict), 처음 채택된 회차(§5-1 의 `adopted_papers` — 06a 뒤 잡부터, 그 전 잡은 비운다), 되살림 여부. 넓히기·연관이면 질의·씨앗. 탐색 때만 있던 `rank_score` 는 저장되지 않으므로 쓰지 않는다. 행의 [경로] 팝오버로 3번 누르면 원문 쪽까지 간다(계획서 문장 → 칩 → 원문 쪽 → 들어온 경로).
- **사용자 동작:** 체크(담음/뺌), 행 메모, 묶음 이름, 순서. 담음 5편 이상이면 [목차 만들기].
- **논문 특징 추출(06c):** 논문 1편 = 생성 1건(Qwen). 목적·방법 유형(§5-3 열거형)·대상·결과 + 값마다 원문 인용구.
  - 입력은 DB 텍스트만 쓴다(워커가 읽는다): 초록 + 섹션 원문 앞부분(Qwen 16K 안에 들게 글자 예산은 계획에서 정한다). 섹션 원문이 없으면 섹션 요약 → 초록 순으로 물러나고, 요약을 입력으로 쓴 값은 '요약 기반(원문 미확인)'으로 표시한다.
  - 인용구는 공백을 정규화한 뒤 입력 원문의 부분 문자열인지 대조한다(`quote_ok`). 대조 실패·원문 미확인 값은 격자 집계에서 빼고 '미확인'으로 보낸다. 쪽 번호는 쪽 범위가 있는 원문에서 찾았을 때만 붙인다.
  - `paper_facets` 는 (`cnts_id`, `schema_ver`) 단위 공용 캐시 — 다른 연구도 같이 쓴다.
  - 순서: 읽기 목록 '담음' → 후보(하위질문 안 순위 순). 06c 부터 이어가기 때 배경으로 넣고, `POST .../extract` 는 06c 이전에 이어간 연구·새로 들어온 후보를 넣거나 특정 `cnts_id` 의 우선순위를 올린다.

### 5-5. 계획서 (06b 선행연구·연구 공백 2절, 06c 나머지 4절)

> 10-08: 06e 가 [보고서 만들기] 한 번으로 목차 확정과 절 작성을 자동으로 한다(D20, §12-4 보고서 자동 산출). 나머지 4절 생성은 지운다 — 연구 배경은 사용자가 쓰는 칸, 방법은 사용자(D19). 뒷받침 점수는 인용 근거 하이라이트가 대신한다(D24).

- **고정 6절:** 주제 · 연구 배경 · 선행연구 검토 · 연구 공백 · 연구 질문 · 방법 제안. 결과·논의 자리에는 "연구 후 직접 씁니다" 안내만 둔다. 진행 표시 'n/6절'은 내용이 채워진 절을 센다 — 06b 는 주제·연구 질문·방법 제안을 목차의 값(주제 제목·고른 연구 질문·적은 방법)으로 채우고 생성하지 않는다. 선행연구 검토는 묶음이 모두 써져야 1절(06b 정함 16).
- **목차 만들기(생성 1건, gemma):**
  - 선행연구 하위 묶음 수는 서버 코드가 정한다 — 담은 논문 4편당 1개, 최소 1·최대 4개이고, 논문들의 1순위 개념(개념이 없으면 하위질문) 가짓수를 넘지 않는다(06b 정함 7).
  - 묶음 배정도 서버 코드가 한다. 06c 는 개념 소속 → 방법 유형 순의 결정적 분할, 06b 는 개념 소속만(개념이 비면 하위질문 소속). 개념 소속은 목차 요청 때 FastAPI 가 계산해 생성 입력에 담는다(§6-3). → 방법 유형 분할은 특징 추출과 함께 대회 뒤(D19) — 06e 도 개념(키워드) 소속만.
  - 묶음이 둘 이상이면 묶음마다 2편 이상이다(`MIN_GROUP_PAPERS`, 10-14 — 미리 담은 8편이 운영 E2E 2/2 에서 7:1 로 나뉘어 1편짜리 선행연구 절이 그 논문 하나로 문장을 채우고 '선행연구들은'이라 썼다). 모자란 묶음은 여유 있는(2편을 넘는) 묶음에서 그 묶음 키 친밀도가 제 묶음 키보다 덜 뒤지는 논문을 데려오고, 데려올 논문이 없으면(하위질문 소속에서 흔하다) 풀어서 남은 묶음에 합친 뒤 키를 `prior.g1` 부터 다시 붙인다. 서버가 처음 배정할 때만의 규칙이다 — 저장된 목차와 [목차 고치기]에서 사용자가 만든 1편 묶음은 그대로 둔다.
  - LLM 은 묶음 이름, 연구 질문 후보 3개, 방법 선택지의 한 줄 설명만 쓴다. 방법 선택지는 읽기 목록 논문의 방법 유형 가운데서만 코드가 뽑는다(06b 는 특징이 없어 선택지 없이 사용자 입력 칸). → 대회 전에는 사용자 입력 칸 그대로(D19·D20).
  - 프론트는 서버가 준 묶음을 그대로 그리고, 사용자가 옮긴 결과만 저장한다.
- **목차 승인:** 사용자가 묶음 사이로 칩을 옮기고, 연구 질문 하나를 골라 다듬고, 방법을 고른 뒤 [목차 승인]. `research_proposals.version` 으로 동시 수정을 막는다(If-Match). → D20: 목차 생성이 끝나면 서버가 자동 승인하고, 이 편집·승인은 [목차 고치기]로 고른다.
- **절 쓰기(생성 1건, gemma, 스트리밍):** 절마다 사용자가 [이 절 쓰기] 를 누른다(원클릭 전체 생성은 없다). → D20: [보고서 만들기] 한 번에 화면이 남은 절을 문서 순서대로 넣는다.
  - 선행연구 검토는 하위 묶음마다 생성 1건(절 키 `prior.g1`~`prior.g4`)이다. 묶음당 6편을 넘으면 하위질문 안 순위 → 담은 순서로 6편만 넣고, 나머지는 참고문헌 후보로만 남긴다.
  - 입력은 배정 논문 6편 이하 × (특징 + 원문 대목 1,200자)를 로컬 [E#] 로, 수치는 코드가 센 [F#] 으로. 06b 는 특징 자리를 초록으로 대신한다. 원문 대목 고르기(리랭커)는 생성을 넣는 FastAPI 가 해서 입력에 담는다(§6-3). → 대회 전에는 초록 그대로(특징 추출은 대회 뒤 — D19).
  - **연구 공백 절의 입력:** 확인 검색을 통과한 칸(`research_gap_checks` — 찾은 논문·m·스냅숏)이 있으면 그것이고(06c), 없으면(06b, 격자를 잘랐을 때) 보고서 `future` 와 critic 이 insufficient 로 본 하위질문 note 로 한정한다. 후자는 "소장 코퍼스에서 확인하지 않은 공백 후보" 문구로 고정하고 금지 표현 후처리를 거친다. 배정 논문은 씨앗에 묶인 근거 논문이다. → 격자 보류로 보고서 재료 입력만 쓴다(D19).
    - 고른 카드면 그 카드의 씨앗 하나만 쓴다(10-14 — 씨앗이 들어 있던 절의 다른 향후 과제·그 하위질문 note 를 함께 넣자 운영 2/2 에서 고른 주제가 아닌 그 절 하위질문의 공백을 썼다). 공백 후보 줄에 하위질문 꼬리표를 붙이지 않고, insufficient note 는 원문(자기점검 말투) 대신 "'하위질문'에 답할 근거가 소장 코퍼스에서 충분히 확인되지 않았다." 한 줄로, 향후 과제는 보고서가 달았던 근거가 이 절 논문에 있으면 그 [E#] 를 붙여 넣는다. 직접 쓴 카드는 보고서 전체에서 씨앗 3개.
  - `chat_stream` 델타를 Redis 로 중계한다.
- **검증(서버, 생성 끝과 사용자 수정 뒤 `PUT` 때마다):**
  - 인용 번호: 로컬 [E#] 이 그 절의 입력 번호인지 확인한다. 문단 글에는 그 절의 로컬 [E#] 를 그대로 두고, 절에 {E#: cnts_id} 지도와 문단마다 인용한 cnts_id 목록(cites)을 함께 저장한다(06b 정함 9). 틀린 번호는 버리고 "인용 n개 버림"을 남긴다(`bind_markers` 와 같은 규칙).
  - 근거 표시 없는 문장 → 점선 밑줄.
  - [F#] 밖의 숫자가 문장에 있으면 '확인 필요'(06b 부터). [F#] 는 [E#] 와 같은 괄호 문법으로 읽어 입력에 있는 번호만 남기고, 괄호 안이 마커 문법으로만 된 것만 마커로 본다 — '[F1-score]'·'[F1 점수 0.92]' 같은 보통 괄호는 글로 남긴다(06b 리뷰 반영, `services/research_work/markers.py`).
  - 뒷받침 점수(06c): `POST .../sections/{key}/support`(동기, FastAPI 리랭커) — 문장과 그 문장이 인용한 대목의 점수가 임계값 아래면 '뒷받침 약함'. 모델에 준 대목은 문장 옆에서 펼쳐 볼 수 있다. → 점수는 대회 뒤, 모델에 준 대목은 인용 근거 탭에서 하이라이트해 보인다(D19·D24).
- **문단:** 상태 4가지를 저장한다. [다시] = 같은 입력으로 그 문단만 다시(생성 1건, `POST .../sections/{key}/paragraphs/{pid}/regenerate`). [고치기] = 직접 편집(상태 '사용자가 고침').
- **쓰지 않는 것:** 결과·논의, 예상 결과·가설 수치. 표본 규모 같은 수치는 사용자 입력 칸으로 둔다. 요청해도 만들지 않는다.

### 6-3. 작업 큐·LLM

- **큐:** 새 모듈 `app/workers/research_work_tasks.py` 를 `celery_app` 의 `include` 와 `task_routes` 둘 다에 등록한다. 큐는 설정값(`cfg.RESEARCH_PLAN_QUEUE`)이 아니라 **문자열 `"q_research_plan"` 으로 고정**한다(`task_routes` 와 `@celery_app.task(queue=…)` 둘 다). 회수기가 도는 celery-control·celery-beat 는 `RESEARCH_PLAN_QUEUE` env 를 받지 않아 설정값이면 `q_llm`(적재 워커)으로 떨어진다. `q_research_plan` 은 GPU 없음, 동시 2. compose 는 바꾸지 않는다.
- **생성 디스패처 — 전체에서 한 번에 1건:** 생성 1건 = Celery 메시지 1개. `q_research_plan` 의 두 자리 중 하나는 늘 딥리서치 계획(`tasks.plan_deep_research`)에 남긴다 — 생성이 두 자리를 채우면 새 딥리서치의 '계획 세우는 중'이 생성 1건 길이(최대 약 16~18분 — 호출 3회 × (300초 + 연결 10초) + 30초 = asyncio 데드라인 960초, Celery 하드 리밋 1080초)만큼 밀려 D15 를 깬다.
  - 생성을 넣는 API 는 늘 디스패치 태스크를 보낸다. 디스패치 태스크는 전역 advisory lock 안에서 running 생성 수를 세고, 1건 이상이면 아무것도 집지 않고 끝난다. 0건이면 모든 연구의 queued 생성 가운데 우선순위(사용자가 누른 생성 > 배경 특징 추출) → 오래된 순으로 1건을 `FOR UPDATE SKIP LOCKED` 로 집어 running 으로 바꾸고 실행한다. 부분 유니크 인덱스 `(work_id) WHERE status='running'` 은 이중 안전장치로 둔다.
  - 하나가 끝나면 queued 가 남았을 때(어느 연구든) 디스패치 태스크를 다시 보낸다. 생성 사이에 계획 요청은 남은 한 자리로 바로 돈다.
  - 처리량이 1건으로 묶이므로 동시에 여러 사람이 생성을 누르면 줄을 선다 — 대기 순번으로 보인다(아래).
- **재시도·넘김 공통 규칙:** 생성 1건 = `chat_full` 최대 3회. 주 모델 1회 → 해석 실패나 내용 검사 미달(예: 근거 칩 2개 미만)이면 주 모델 1회 더 → 전송 실패(`chat_full` 이 포기)면 곧바로, 해석·내용 미달이 두 번이면 다른 모델 1회 → 그래도 안 되면 kind 별 빈 결과(개념 비움, 카드 '근거 부족')로 done. `chat_full` 안의 일시적 실패 재시도는 이 횟수에 세지 않는다. `model` 에는 결과를 낸 모델을, `output.attempts` 에 시도 목록을 남긴다(공개 부록에 쓴다). → 저장은 그대로, 06e 부터 부록에는 싣지 않는다(D21).
- **시간 한도:** 비스트리밍 호출은 timeout 300초를 명시한다. kind 별 asyncio 데드라인 = 최대 호출 수 × (호출 timeout + 연결 10초) + 여유, Celery soft/hard limit 은 그보다 크게 둔다(함정 19). 기존 회수 태스크 `tasks.reap_stale_research`(q_control, 기존 beat 일정)를 넓혀, running 이 hard limit + 60초를 넘은 생성을 failed 로 두고, queued 가 남았는데 running 이 없으면 디스패치 태스크를 `"q_research_plan"` 으로 다시 보낸다.
- **입력 만드는 곳:** 임베딩·리랭커·Milvus 가 필요한 입력(개념 소속, 목차의 묶음 배정, 절의 원문 대목 고르기)은 생성을 넣는 FastAPI 가 만들어 `research_generations.input` 에 담는다. 워커는 DB 텍스트 조회와 LLM 호출만 한다.
- **동시 실행 제한(딥리서치):** 기준은 잡의 `created_by`(브라우저 ID)다 — 요청 헤더에 기대지 않고, NULL 이면 제한하지 않는다. approve 와 retry 가 함께 쓰는 `_to_run_queue` 안에서, `created_by` 해시로 `pg_advisory_xact_lock` 을 늘 잡은 뒤 같은 브라우저의 approved·queued·running 잡을 센다(승인 안 하고 둔 계획은 세지 않는다). 있으면 429 `{code: "browser_active", job_id}`.
- **대기 순번(딥리서치):** research_jobs 에 승인 시각 칼럼이 없으므로 Redis ZSET `research:run_queue`(member = job id, score = 넣은 시각)를 쓴다. approve·retry 가 큐에 넣을 때 더하고, 워커가 잡을 집을 때·취소·종료 때 뺀다. 순번 = running 잡 수 + ZSET 에서 내 점수보다 앞선 원소 가운데 DB 상태가 지금 approved·queued 인 잡 수(빼기가 Redis 실패를 삼켜 끝난 잡이 줄에 남아도 순번이 밀리지 않게 읽을 때 거른다 — 지우지는 않는다). 다시 줄에 선 잡은 넣은 시각을 새로 쓴다(NX 아님). ZSET 에 없으면(Redis 재기동) `created_at` 순으로 근사한다. 기다리는 잡의 스트림은 기존 15초 하트비트 때 순번을 다시 세어 바뀌었을 때만 `queue` 이벤트(ahead, eta_sec)를 보낸다. 예상 시간 = 최근 완료분 소요 시간 중앙값 × 순번.
- **대기 순번(생성):** 디스패처가 전역 한 줄이므로 DB 로 센다 — 내 앞의 queued 생성 수(우선순위 → 오래된 순) + running 1건. 예상 시간 = kind 별 최근 완료분 소요 시간 중앙값의 합. 다른 연구의 생성이 앞에 있으면 "다른 연구 작업 진행 중"을 함께 보인다.
- **모델 라우팅(코드 상수 `WORK_MODEL_ROUTES`):** 자식 카드·특징 추출 → Qwen(`VLM_BASE_URL`/`VLM_MODEL`, dev 의 config 에 이미 있다), 핵심 개념·주제 카드·목차·절·문단 → gemma(`LLM_BASE_URL`/`LLM_MODEL`). 핵심 개념은 06a Qwen 표본 확인(Qwen 이 하위질문 절 제목을 옮기고 되풀이했다)으로 06b 에서 gemma 로 옮겼고, 주제 카드는 06b 배포 뒤 정식 실행기로 다시 비교해 gemma 로 옮겼다 — 바꿀 때는 그 kind 의 값 한 칸만 바꾼다. 계획·critic·종합은 지금처럼 gemma. `llm_client` 의 `chat_full`(round07 — 재시도 포함)과 `chat_stream`(재시도 없음)에 호출별 `base_url`·`model` 을 더한다. 스트리밍 절의 연결 실패·5xx 넘김은 첫 델타 전에만 호출부가 한다.
- **Qwen 자리:** round07 로 OCR 이 8석을 다 쓰게 맞춰졌다(celery-cpu 4 × VLM 페이지 동시 2 = max-num-seqs 8). 스캔본이 몰리는 적재 구간에는 Qwen 생성이 vLLM 대기열에서 기다리고, 300초 timeout 뒤 gemma 로 넘어간다. round06 쪽 상한(생성 전역 1건)은 자리를 보장하지 않는다.

### 6-4. 실시간 이벤트

- `GET /api/research/{id}/work/stream` — 채널 `research:work:{id}`, 접속 직후 `snapshot`, 15초 `: ping`. 기존 `relay.py` 패턴을 따른다.
  - **06b 넘김(06a 최종 리뷰):** 06a 의 연구 SSE 는 하트비트 때 DB 를 다시 읽지 않고, 회수기가 오래 running 인 생성을 failed 로 바꿀 때 연구 채널에 알리지 않는다. 하드 리밋으로 디스패치 자식 프로세스가 죽거나 `celery-research-plan` 이 Recreate 되면 그 생성은 이벤트 없이 failed 가 되고, snapshot 을 읽은 뒤 구독이 붙기 전에 나간 done 이벤트도 다시 받을 길이 없다 — 화면은 새로고침 전까지 '진행 중'에 멈춘다. 06b 의 연구 화면 Task 가 하트비트 재동기화를 더한다: `stream_research` 처럼 하트비트마다 짧은 세션(`AsyncSessionLocal` — 요청 세션은 핸들러가 반환하면 닫힌다)을 열어 열린 생성(queued·running)의 (id, status) 집합을 읽고, 화면이 마지막으로 받은 값과 다르면 snapshot 을 다시 보낸다. 회수된 행이 열린 집합에서 빠져 15초 안에 드러나고 구독 전에 놓친 이벤트도 함께 풀린다. 회수기 publish(RETURNING 결과를 커밋 뒤 동기 Redis 로, 실패는 삼킴)는 지연만 줄이는 선택 사항이다.
- 이벤트: `generation`(kind·target·status·순번 — done 을 받으면 프론트가 해당 GET 을 다시 읽는다: concepts → `work`·`grid`, topic_card·refine → `topics`, facet → `reading`, outline·section·paragraph → `proposal`), `facet`(논문 특징 도착 — 06c), `grid`(칸 숫자 — 06c), `section_delta`(문장 조각), `work`(phase·progress). 카드 도착과 절의 검증 결과는 따로 보내지 않고 `generation` done 의 `result`(topic_card `{topic_id, state}`, section `{key, paragraphs, dropped}`)로 알린다 — 같은 사실을 두 이벤트로 보내면 순서·누락 처리가 두 벌이 된다(06b 결정, 처음 설계의 `topic`·`section_done` 을 갈음). 되살리기·넓히기·연관은 동기 응답으로 돌아오므로 SSE 가 필요 없다. → 10-08: `facet`·`grid` 이벤트는 대회 뒤(D19). concepts done 은 `work`·`topics` 를 다시 읽는다(§12-4 제목 고르기 — `grid` 는 대회 뒤).
- 프론트는 순수 리듀서 `utils/workEvents.ts` 로 상태를 만든다(Vitest 대상).
- 탐색 중 근거 장부는 기존 연구 SSE 의 `critique` 이벤트(`adopted_papers`·`excluded_papers`)와 재접속 때 `steps[].result.rounds` 로 그린다. 대기 순번은 기존 연구 SSE 의 새 `queue` 이벤트다.

## 7. 품질·윤리 장치

- **critic 새 기준은 합격해야 켠다(D11).** 미달이면 `critic_scope` 0(지금 기준)으로 둔 채 06b 이후를 그대로 진행하고, 계획 프롬프트 수정 여부를 사용자에게 묻는다. 오판은 읽기 목록의 [되살리기]·빼기로 고친다.
- **공백:** 표본과 확인 검색을 문구·화면 모두에서 나누고, 확인 검색을 거치지 않은 칸은 씨앗으로 쓰지 않으며, 확인하지 않은 공백은 "확인하지 않은 공백 후보"로만 쓰고, 금지 표현을 후처리하고, 편수 추이를 근거로 쓰지 않는다(§5-2·5-3·5-5).
- **인용이라는 말을 정확히 쓴다.** 인용 번호 검증은 번호가 맞는지까지다. 문장이 실제로 뒷받침되는지는 뒷받침 점수로 따로 보이고 모델에 준 대목을 펼쳐 볼 수 있게 한다. → 점수는 대회 뒤, 대목은 인용 근거 탭에서 하이라이트해 보인다(D24). 대회 자료에 "문장마다 검증"이라고 쓰지 않는다.
- **원문 인용구·숫자:** §5-4·5-5. 수치는 [F#] 로만 들어간다.
- **범위:** 고정 띠, 산출물마다 코퍼스 스냅숏, 적재 뒤 바뀌면 '다시 세기' 배지.
- **AI 표시:** 문단 상태 4가지, 기여 비율은 문단 상태로 센다, 공개 부록.
- **생성 범위:** 원클릭 전체 생성 없음, 결과·논의·가설 수치 없음. → [보고서 만들기] 한 번으로 자동 산출한다(D20). 결과·논의·가설 수치를 쓰지 않는 것은 그대로다.

### 12-2. 06c 질의 — 시작 질문 넓히기·검색어 합성 (D25)

**목적.** 개념 하나짜리 짧은 질문은 계획 프롬프트의 측면 목록(`research_plan.yaml:12` — 개념·정의, 방법·기법, 적용 분야, 성과·평가, 한계·과제)을 그대로 옮겨 일반 틀이 된다. 06b 계획 30개 중 약 25개다(원 질문 낱말은 빼고 셈 — computing·library·multicultural 은 6/6). 논문 상세 [이 논문으로 딥리서치] 질문(`frontend/utils/paperResearch.ts:17-27`)은 실제 제목(범위 고정)·키워드 3개(나눌 축)·측면 셋(전개·쟁점·과제)이 있어 잘 나뉜다 — 이 일을 계획 전에 자동으로 한다. 이 관찰은 회의에서 나왔고 잰 기록이 없어 대조군으로 잰다(§12-7). 남은 무관은 검색어가 데려오는 동음이의다(06b 이월 §7-10·11) — 검색어에 범위 용어를 합성한다.

**낱말 맞추기(공용 순수 함수)** — 넓히기 검사·검색어 합성·일반 틀 비율이 한국어 낱말을 같은 방식으로 나누고 맞춘다. 어절째 대조하면 '노인의'↔'노인' 같은 조사 차이로 넓히기가 거의 늘 원문으로 떨어진다.
- 내용어 `content_words(text)`: NFKC → casefold → 문장부호(`[^\w\s]`)를 공백으로 → 공백으로 어절 나누기 → 어절 끝 조사 하나 떼기(상수 `PARTICLES` 처음 값 `에서·에게·으로·로·의·은·는·이·가·을·를·와·과·에·도·만`, 긴 것부터, 떼고 남은 것이 2자 미만이면 떼지 않는다) → 2자 이상이고 질문 꼴 낱말(상수 `QUESTION_WORDS` 처음 값 `연구·관한·대한·관련·궁금해·궁금합니다·알려줘·찾아줘·무엇·어떻게` — 06c 구현은 그 활용 꼴 `관해·관하여·대해·대하여·궁금해요·알려주세요·찾아주세요·연구들` 을 더했다)도, 조사만 남은 어절(`PARTICLES` 자체 — 「…」에서 를 공백으로 나눈 뒤의 '에서')도 아닌 것을 처음 나온 순서로 중복 없이(06c 계획 정함 7).
- 들어 있음 `contains(text, word)`: §12-4 제목 고르기의 일치 규칙을 그대로 쓴다 — NFKC → casefold → 공백 제거 뒤 부분 문자열, 아니면 word 의 낱말이 모두 순서대로 들어 있음.
- 자리: 06c 가 `app/services/research/terms.py` 에 둔다. 06e 의 제목 일치 검사는 06c 머지 뒤 dev 를 받아 같은 함수를 쓴다(06c 가 먼저 머지한다 — §12-6). `scripts/research_eval/score.py` 는 app 을 import 하지 않으므로(HTTP 만 쓴다) 복사본을 두고 공용 고정 예제로 맞춘다(`frontend/tests/fixtures/marker_checks.json` 선례).

**넓히기 — 스위치 `broaden`**
- **자리:** 계획 태스크 `_plan_deep_research`(`app/workers/research_tasks.py:519-567`)의 `make_plan`(`:545`) 바로 앞, 같은 태스크 안에서 gemma 1회. 태스크를 나누지 않는다.
- **프롬프트(새 파일 `app/domains/nl_library/prompts/research_frame.yaml` — parser plain·max_tokens 600·temperature 0.2, 변수 `question` 하나. 넓히기 코드는 새 모듈 `app/services/research/framing.py` 이고 `planner.py` 는 고치지 않는다):** 출력 JSON `{question, terms}` — 한 문장으로 다시 쓴 질문 + 범위를 정하는 용어 2~4개.
  - 원 질문 낱말을 모두 그대로 둔다.

- **코드 검사:** 원 질문의 `content_words` 가 모두 넓힌 문장에 `contains` 여야 한다 — 하나라도 빠지면 원문. `terms` 는 코드가 문자열만 받아 NFKC 정규화·공백 정리 뒤 빈 것과 30자 넘는 것을 버리고 casefold 기준 중복을 지워 4개에서 자른다. 넓힌 문장이 비었거나 500자(`ResearchCreate.question` 상한)를 넘으면 원문. 넓힌 문장은 맨 앞 입력 이름표(`질문:`·`질문：`)를 뗀 뒤 검사한다 — 모델이 user 메시지를 이름표째 옮기면 낱말 검사를 통과해 계획 입력·`question_used` 에 이름표가 실리기 때문이다(함정 26). 넓히기 검사는 `content_words` 에 더해 원 질문의 한 글자 어절(조사·질문 꼴 낱말·잇는 말 `ONE_CHAR_FUNCTION_WORDS` 제외)도 넓힌 문장에 어절로 있어야 한다 — 같은 방식(NFKC·casefold·문장부호 공백 — `terms.tokens`)으로 나눈 넓힌 문장의 어절이 그 글자이거나 '그 글자 + 조사 하나'(암의·뇌를)일 때만 들어 있다고 본다. 한 글자 명사(암·뇌·법)는 `content_words` 의 2자 바닥에 걸려 '암 연구가 궁금해'에 지어낸 주제를 낸 답도 지나가고, `contains`(부분 문자열)로 보면 '방법'·'암호화'·'뇌물' 안의 글자에도 맞기 때문이다(`content_words`·`contains` 정의는 그대로). 원 질문에 대조할 낱말(내용어·한 글자 어절)이 하나도 없으면('연구가 궁금해'·'관련 연구 알려줘') 검사할 수 없으니 넓히지 않고 원 질문으로 계획한다 — 그대로 두면 지어낸 주제가 계획 입력·`question_used` 가 된다.
