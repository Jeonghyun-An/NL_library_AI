## 이 챕터의 자리

탐색이 끝나면 워커는 체크포인트(`stage=explored` · `state_snapshot`)를 남기고 `synthesize(state, should_stop=…)` 를 부른다. 이 챕터는 그 뒤를 다룬다 — 모은 근거로 보고서 JSON(spec §4-5 구현 시 변경의 모양)을 만들고, 모델이 쓴 인용을 검증하고, 탐색·종합에서 생긴 빈틈을 사용자에게 보일 한계 문장으로 바꾸는 부분이다.

인용은 두 갈래다(spec §4).

- **구조적 인용** — `대표 논문 요약`. 불릿 하나가 논문 하나라, 어느 논문이 실리고 칩이 어디를 가리키는지를 코드가 정한다.
- **마커 인용** — `도입 문단`·`향후 과제`. 여러 논문을 가로지르므로 구조로 못 정한다. 모델이 `[E3]` 을 달고 코드가 전수 검증한다. 검증 함수(`citations.bind_markers`·`strip_markers`)는 §2.7(01 챕터)에 수록했고, 여기서는 그 결과를 쓰는 쪽만 본다.

`synthesizer.py` 는 구현 뒤 설계가 두 번 바뀐 파일이다(plan 도 Task 8 을 "가장 크게 바뀐 절"이라 적었다). 모양이 세 번 있었다.

|---|---|---|
| Task 8 구현 | `d537183` | LLM 호출 1회로 보고서 전체(절 구성·논문 선택·서술)를 받는다 |
| 라이브 검증 중 수정 | `b6360b8` | 하위질문마다 호출 1회. 절 구성은 코드, 문장은 모델 |

## 2. 구현 (클론코딩)

### 2.27 `research_synthesize.yaml` — 절 하나의 문장만 받는 종합 프롬프트

**무엇을 책임지나.** 하위질문 하나의 절에 들어갈 문장 — 도입(`intro`), 논문별 요약(`summaries`), 향후 과제(`future`) — 을 JSON 으로 받는 프롬프트다. 변수는 넷이다: `question`(연구 질문), `subquestion`(이 절의 하위질문), `evidence_block`(이 절 논문들의 서지 머리 + 발췌), `paper_ids`(이 절 논문 번호를 쉼표로 이은 것, 예: `E1, E3`). `synthesizer._synthesize_section` 이 절마다 한 번 렌더한다.

**왜 이렇게 짰나 — 모델에게 고를 것을 주지 않는다.** 출력에 소제목도 논문 목록도 없다. 둘 다 코드가 정하기 때문이다(§2.28 ②). 요약은 배열이 아니라 **번호를 키로 하는 객체**이고, 채워야 할 키를 `{{ paper_ids }}` 로 못 박는다("다음 번호를 빠짐없이 하나씩 키로 넣으세요"). 모델이 하는 일은 이미 정해진 칸을 채우는 것뿐이다. 함정 15번의 재발 방지 규칙 — "불가피하면 프롬프트에 기대 개수와 키 목록을 명시한다" — 을 그대로 옮긴 모양이다.

첫 구현(`d537183`)의 출력 예시는 `{"sections": [{"heading", "intro", "papers": [{"cnts_id", "summary"}], "future": [{"text"}]}]}` 모양이었다. 절을 몇 개 쓸지, 절마다 어느 논문(`cnts_id`)을 실을지를 모델이 정하는 스키마였고, 배열마다 항목이 하나인 그 예시를 gemma-3-12b 가 **개수까지** 베꼈다(§2.28 ①). 지금 예시에도 `future` 는 항목 하나짜리 배열이지만, 과제 개수는 절·논문 구성을 좌우하지 않는다 — 개수 범위는 "future 는 1~3개입니다"로 따로 적었다.

**예시 속 `[E#]` 는 일부러 남긴 자리표시자다.** gemma 는 예시를 견본으로 베끼므로 "이 하위질문에 대한 연구 흐름을 설명하는 2~4문장. 문장마다 [E#] 를 답니다." 같은 지시문 원문이 도입으로 돌아올 수 있다. `[E#]` 에는 숫자가 없어 `bind_markers` 가 인용으로 보지 않으므로(지우지도 세지도 않는다), 그대로 두면 지시문이 본문에 실린다. 그래서 코드가 `[E#]` 가 남은 필드 — 도입 전체, 또는 과제·요약 항목 하나 — 를 통째로 버린다(`synthesizer._PLACEHOLDER`, §2.28 ⑥). 예시를 `[E1]` 같은 실제 번호로 썼다면, 그 절에 E1 이 있는 한 베낀 지시문이 유효한 인용을 단 문장으로 통과했을 것이다 — 자리표시자가 실제 문법과 다르다는 점이 복사본을 가려내는 단서가 된다.

**서지는 모델에게 주되 쓰게 하지 않는다.** `evidence_block` 의 항목은 `[E3] 제목 (발행연월, 학술지)` 머리에 발췌가 붙은 모양이다. 제목을 주는 것은 모델이 무슨 논문인지 파악하게 하려는 것이고, 본문에 제목·저자·연도를 쓰지 못하게 한 것은 화면이 서지를 DB 레코드(`evidence.meta`)에서 직접 렌더하기 때문이다(spec §4-1). 라벨을 모델이 쓰게 두면 언젠가 없는 논문을 만들어낸다.

발췌는 그 하위질문 검색에서 매칭된 첫 청크의 앞 400자다. 초록이 아니다(spec §2-4 구현 시 변경). 발췌가 짧아 "무엇을 했고 무엇을 주장하는지 2~3문장"을 모델이 채울 여지가 크다 — §2.28 ③ 의 한계가 여기서 시작된다.

"아래에 나온 번호만 쓰세요"는 절마다 그 절의 논문 번호만 주기 때문에 들어간 문구다. 전체 근거를 한 번에 주던 첫 구현은 "없는 번호를 쓰지 마세요"였다. 코드도 같은 기준 — 그 절에 준 번호 — 으로 검증한다(§2.28 ⑧).

**라이브·리뷰에서 바뀐 것.**

- `b6360b8` — 보고서 전체용 프롬프트를 절 하나용으로 다시 썼다. 출력이 절 하나로 줄어 `max_tokens` 를 8000 에서 4000 으로 낮췄다. 변수는 `question`·`evidence_blocks` 둘에서 지금의 넷으로 바뀌었다. 렌더가 `StrictUndefined` 라 옛 YAML 과 새 코드를 섞으면 렌더에서 바로 실패한다(§2.30).
- 같은 커밋, 드라이런 뒤 — "summaries 의 값에는 논문 제목도 [E#] 마커도 쓰지 마세요"의 **마커 금지**가 붙었다. 배포 전 드라이런에서 모델이 요약 끝에 `[E7]` 을 달았기 때문이다. 서버에서 실제로 돌린 드라이런 산출물(§2.31)에 박힌 프롬프트에는 이 문구가 없다 — 드라이런이 먼저였다는 증거다. 다만 프롬프트 금지는 확률을 낮출 뿐이다. 보장은 코드의 `strip_markers` 가 한다(§2.28 ④).
- 머지 전 리뷰(`2bac7ee`)는 YAML 을 바꾸지 않았다. 리뷰가 짚은 "예시를 그대로 베낀 응답"(`[E#]` 가 남은 지시문)은 프롬프트가 아니라 코드(`_PLACEHOLDER`)에서 막았다.

**파일**: `app/domains/nl_library/prompts/research_synthesize.yaml` — 전체 26줄

```yaml
parser: plain
params:
  max_tokens: 4000
  temperature: 0.3
system: |-
  당신은 국내 학술논문을 다루는 연구 사서입니다. 수집된 근거만으로 보고서의 한 절을 씁니다.

  절대 규칙:
  - 제공된 근거에 없는 내용을 쓰지 마세요. 추측·일반상식·외부지식 금지.
  - 논문 제목·저자·연도를 본문에 쓰지 마세요. 시스템이 서지에서 직접 렌더합니다.
  - 근거를 인용할 때는 [E3] 형태의 마커만 씁니다. 아래에 나온 번호만 쓰세요.
  - 한국어로 씁니다.

  JSON 하나만 출력하세요.
  {"intro": "이 하위질문에 대한 연구 흐름을 설명하는 2~4문장. 문장마다 [E#] 를 답니다.",
   "summaries": {"E#": "그 논문이 무엇을 했고 무엇을 주장하는지 2~3문장"},
   "future": [{"text": "남은 과제 한 문장 [E#]."}]}

  summaries 에는 다음 번호를 빠짐없이 하나씩 키로 넣으세요: {{ paper_ids }}
  summaries 의 값에는 논문 제목도 [E#] 마커도 쓰지 마세요. 내용만 씁니다.
  future 는 1~3개입니다.
user: |-
  연구 질문: {{ question }}
  하위질문: {{ subquestion }}

  {{ evidence_block }}
```
렌더 검사는 §2.30 이, 실제 호출부의 변수 이름은 §2.29 `TestSynthesize` 가 지킨다.

### 2.28 `synthesizer.py` — 절 구성·인용 검증·한계 문장으로 보고서를 조립한다

**무엇을 책임지나.** 탐색이 끝난 `ResearchState` 를 받아 보고서 dict 를 돌려준다. DB 에는 쓰지 않는다 — 저장은 워커가 한다. 함수는 아래에서 위로 읽으면 흐름이 보인다.

| 함수 | 하는 일 |
|---|---|
| `synthesize` | 근거가 있는 하위질문마다 `_synthesize_section`. 전부 실패면 예외 |
| `_synthesize_section` | 프롬프트 렌더 → `chat` → `extract_json` → `build_section`. 절마다 1회 재시도, 매 호출 직전 취소 확인 |
| `build_section` | 소제목·논문 목록은 코드가, 문장은 모델 출력에서 (순수 함수) |
| `_evidence_block` | 절의 논문마다 `[E#] 제목 (연월, 학술지)` + 그 하위질문에서 매칭된 청크 앞 400자 |
| `assemble_report` | 절마다 인용 검증·요약 정리·집계 → 보고서 dict |
| `build_limitations` | 집계와 하위질문 상태를 한계 문장으로 |
| `_serialize_evidence` | 보고서의 근거 목록(지금 어느 하위질문이든 가리키는 청크만, 점수순) |

코드를 읽기 전에 설계의 핵심 열 가지를 본다. ①②④ 는 라이브 검증(`b6360b8`)에서, ③ 과 ⑤~⑩ 은 머지 전 리뷰(`2bac7ee`)에서 나왔다(①②④ 도 리뷰에서 일부 다듬었다).

**① 사건 — 하위질문 3개인데 절이 1개 나왔다 (함정 15번, 00 Q6).** 라이브 검증(완료노트 §2·§3, 잡 `24997861`, gemma-3-12b)에서 하위질문 3개로 근거 10편을 모았는데, 보고서는 절 1개 · 논문 1편 · 향후 과제 1개였다. 원인은 §2.27 의 옛 출력 예시다. 배열마다 항목이 하나였고, 모델은 그것을 형식이 아니라 **개수까지 포함한 견본**으로 따랐다.

더 배울 것은 **검증이 이걸 못 잡았다**는 점이다. plan Task 11 Step 7 의 검사는 "도입·과제의 `[E#]` 가 전부 근거 목록 안에 있는가"였고, 결과는 `미해석 set()` — 통과였다. 무결성만 보고 구성을 보지 않았기 때문이다. 인용이 적을수록 무결성 검사는 더 잘 통과한다. 절 1개 · 논문 1편짜리 보고서는 인용이 틀릴 기회 자체가 적었다. 단위 테스트도 잡을 수 없었다 — 가짜 LLM 응답은 우리가 쓴 모양 그대로 돌아오므로, 모델이 예시의 개수를 베끼는 성질은 라이브 모델에서만 드러난다. 그래서 Step 7 에 구성 검사(절 수 = 근거가 있는 하위질문 수, 논문으로 실린 근거 수, 요약 속 마커)를 더했고, 드라이런 도구(§2.31)도 결과를 구성 숫자부터 찍는다.

설계로 보면 spec §4-1 위반이었다. "불릿을 그 논문의 근거만 넣고 생성하면 인용이 구조로 정해진다"가 원칙인데, 어느 절·어느 논문을 실을지를 모델이 고르고 있었다. 그 순간 인용은 구조가 아니라 추론이다.

**② 고친 방향 — 구성은 코드, 문장은 모델 (`build_section`).** 종합을 하위질문 하나당 LLM 호출 하나로 바꿨다. `build_section` 은 순수 함수이고, 모델 출력에 무엇이 있든 없든 바뀌지 않는 부분이 둘이다.

- 소제목 = 하위질문 원문(`sq.text`).
- 논문 목록 = `section_paper_ids` — 그 하위질문 근거의 앞 5편(`PAPERS_PER_SECTION`).

모델 출력에서는 문장만 꺼낸다. 요약을 빠뜨린 논문도 빈 요약(`""`)으로 목록에 남고, 몇 편이 비었는지는 `assemble_report` 가 세어 한계에 올린다. 서술을 끝내 받지 못한 절(`data is None`)도 논문 목록은 남긴다 — 서술이 없어도 어떤 논문이 근거인지는 보여줄 수 있다.

앞 5편을 자르는 순서는 runner 가 정한다. 리뷰에서 `evidence_ids` 가 "검색 라운드 순 → 라운드 안에서만 순위순"이라 자기점검이 요청한 재검색 결과가 5편 상한에 먼저 잘린다는 지적이 여러 영역에서 나왔고, runner 가 하위질문 안 순위(라운드별 1위 앞자리 보장)로 정렬하게 고쳤다. 이 파일은 그 순서를 믿고 앞에서 자르기만 한다 — 주석도 "탐색 순위순"(사실과 달랐다)에서 지금 문구로 고쳤다.

버린 대안 둘.

- **한 번의 호출을 유지하고 프롬프트에 개수를 명시한다** — "절 3개, 절마다 논문 N편"을 적어도 지키느냐는 여전히 모델의 추론이다. 구조가 정확해야 하는 곳에 확률을 두지 않는다.
- **논문마다 따로 호출한다** — spec §4-1 을 온전히 지키는 길이지만 호출 수가 절당 최대 5배다(기본 파라미터 하위질문 6개면 6회 → 최대 30회). 종합 LLM 은 대량 인덱싱의 요약 단계와 같은 서버를 나눠 쓰고, 절 3개짜리 종합이 이미 약 17초였다(완료노트 §2). 이번에는 하지 않았다 — 그 대가가 ③ 이다.

근거가 없는 하위질문은 절을 만들지 않는다(LLM 도 부르지 않는다). 한계 문장이 그 사실을 적는다. 반대로 **탐색이 도중에 오류로 끊긴 하위질문이라도 그 전에 모은 근거가 있으면 절을 만든다.** `b6360b8` 은 `failed` 하위질문을 대상에서 뺐는데, 그러면 실재하는 근거가 `report.evidence` 에만 고아로 남고 한계에는 사실과 다른 "확인하지 못했다"만 실렸다. 모든 하위질문이 근거 없이 오류로 끝난 전멸은 이 파일이 아니라 워커가 막는다(`research_tasks._wiped_out` — 체크포인트를 남기지 않고 잡을 `failed` 로).

**③ 남은 한계 — 요약의 배정은 여전히 추론이다 (spec §4-1 구현 시 변경).** 이 수정으로 §4-1 이 온전히 성립한 것은 아니다. 구조로 정해지는 것은 **절 구성과 칩**이다. 불릿의 칩(`evidence: ["E12"]`)은 `cnts_id` 로 코드가 붙이고, 서지도 코드가 렌더한다. 그러나 요약은 절의 논문 최대 5편 발췌를 한 프롬프트에 넣고 `{"summaries": {"E1": …, "E3": …}}` 로 번호별로 받는다. **어느 요약 문장을 어느 번호에 쓸지는 모델이 발췌 머리의 `[E#]` 를 보고 정한다.** 모델이 E1 요약에 E2 내용을 섞어 써도 잡는 검사가 없다 — 마커 검증은 도입·향후 과제에만 걸린다. 발췌 형식이 혼선을 키울 수 있다. `_evidence_block` 은 공백을 접지 않아, 표 청크처럼 본문 안에 빈 줄이 있는 발췌는 항목 사이의 빈 줄과 구분되지 않는다(자기점검 쪽 발췌는 접는다).

드라이런에서 요약은 12/12 채워졌지만 **맞는 논문에 배정됐는지는 재지 않았다.** 그래서 모듈 docstring·spec·완료노트 어디에도 "요약도 구조로 정해진다"고 쓰지 않는다. 논문별 호출(병렬), 또는 최소한 발췌 경계 표시·공백 접기와 오배정 비율 실측이 이월이다(spec §4-1 구현 시 변경, 완료노트 §8).

**④ `strip_markers` — 검증을 거치지 않는 필드도 정리한다.** 배포 전 드라이런에서 모델이 대표 논문 요약에도 `[E7]` 을 달았다. 시키지 않은 일이다. 요약은 `bind_markers` 를 거치지 않는 자리라, 남겨 두면 지어낸 번호가 검증 없이 화면에 나간다. 그래서 `assemble_report` 가 요약의 인용 표기를 **전부** 걷어낸다 — 유효한 번호도 지운다. 그 자리의 인용은 불릿의 칩이 이미 구조로 갖고 있어 중복일 뿐이다. 걷어낸 뒤 마침표 하나만 남으면(`"[E1]."` → `"."`) 요약이 아니므로 빈 요약으로 두고 "요약을 생성하지 못한 논문"으로 센다(`_prose` — 이 처리는 리뷰에서 더했다). 함정 15번의 마지막 문장이 이 경우다 — 검증을 거치지 않는 필드에 모델 출력이 들어가면 그 필드도 정리한다. 수정 후 라이브 잡(`620579ac`)에서 요약 속 마커는 0 이었다.

**⑤ 절 단위 1회 재시도와 성공 판정.** `b6360b8` 의 절 호출은 JSON 해석 실패만 흡수했다. 리뷰가 세 구멍을 짚었다.

- **전송 오류 하나가 다른 절까지 버렸다.** `chat()` 의 타임아웃·5xx 가 `synthesize` 밖으로 전파돼, N번째 절의 일시적 오류 하나로 앞서 받은 절이 모두 버려지고 잡이 `failed` 가 됐다. spec §6 은 "종합 LLM 실패 — 1회 재시도"였는데 재시도 코드가 없었다. 종합 LLM 은 공유 GPU 라 대기로 300초를 넘기는 일이 있다.
- **성공 판정이 "파싱됐는가"뿐이었다.** `{}` 나 옛 스키마(`{"sections": [...]}`)도 dict 로 파싱되므로 성공으로 셌다. 모든 절이 이렇게 오면 "전부 실패면 예외" 가드를 빠져나가 **서술 0줄짜리 보고서가 `completed`** 가 된다. `completed` 는 retry 대상이 아니라(409) 복구할 길이 없다.
- **필드 타입 하나가 보고서 전체를 잃게 했다** — ⑥.

그래서 `_synthesize_section` 은 전송 오류(`httpx.HTTPError`)·해석 실패·서술 없는 응답을 모두 같은 실패로 보고, 같은 프롬프트를 한 번 더 보낸다(`_SECTION_ATTEMPTS = 2`, temperature 0.3). 그래도 안 되면 논문 목록만 남긴 절(`failed: True`)을 돌려주고 다음 절로 넘어간다. `synthesize` 는 **모든 절이 실패했을 때만** 예외를 던진다. 그러면 워커가 잡을 `failed` 로 두고 `stage=explored` · 스냅샷이 남아, `POST /retry` 가 탐색을 건너뛰고 종합부터 다시 한다.

잡는 예외를 `except Exception` 이 아니라 `httpx.HTTPError` 로 좁힌 것은 함정 19번의 교훈이다. 하위 계층의 넓은 `except` 는 Celery 의 `SoftTimeLimitExceeded`(역시 `Exception` 의 하위) 같은 태스크 제어 예외까지 삼킨다.

성공은 **서술 유무**로 판정한다(`_has_narrative`). 도입·과제·요약 중 하나라도 문장이 있어야 한다. 여기서 "문장"은 인용 표기를 걷어낸 뒤의 텍스트다(`_prose`). 판정은 검증 전 출력으로 하므로 이렇게 봐야 한다 — 마커만 있는 도입(`"[E7]"`)을 서술로 세면, `assemble_report` 에서 지워진 뒤 서술 0줄이 되는데도 재시도와 전부 실패 가드를 모두 건너뛴다.

재시도의 비용도 짚어 둔다. 호출 타임아웃이 300초라, 타임아웃으로 두 번 실패하는 절 하나에 10분이 든다. 하위질문이 많으면 그 합이 잡 본문 상한 25분(`JOB_DEADLINE`, 탐색 시간 포함)을 넘을 수 있고, 그때는 데드라인이 끊어 잡이 `failed`(시간 상한 초과)가 된다. `stage` 는 `explored` 로 남으므로 retry 는 역시 종합부터다.

**⑥ 모델 출력 필드 정리 (`_text`·`_eid_key`).** 코딩 표준은 외부 서비스 응답을 경계에서 검증하라고 한다. LLM 출력이 그 경계다. 리뷰 전 `build_section` 은 필드마다 검사가 제각각이었고, 리뷰가 짚은 결과는 이랬다.

- `future` 항목의 `text` 가 `null` 이면 `bind_markers` 안에서 `TypeError`. 이 예외는 **모든 절 호출이 끝난 뒤** `assemble_report` 에서 나므로, 받아 둔 절 전부를 잃고 잡이 `failed` 가 된다. 부분 실패를 넘기겠다는 설계와 정반대다.
- `summaries` 값이 문장 배열이면 `str()` 이 `"['문장1', '문장2']"` 를 요약으로 화면에 내보낸다.
- `future` 가 문자열 목록(`["과제 [E1]."]`)이면 조용히 전부 버려졌다.

지금은 `_text` 가 문장 필드 하나를 문자열로 만든다. 문자열은 그대로, 문자열 배열은 잇고, 그 밖의 모양(`null`·숫자·dict)은 버린다. §2.27 의 자리표시자 `[E#]` 가 든 문장도 버린다 — 지시문 원문이기 때문이다. `future` 는 `{"text": …}` 항목과 문자열 항목을 모두 받는다. `_eid_key` 는 `summaries` 의 키를 정규화한다(`"[E1]"`·`"e01"`·`" E 1 "` → `"E1"`). 키 표기가 어긋났다는 이유로 멀쩡한 요약을 잃지 않게 한다.

**⑦ 취소 — `should_stop` 과 `SynthesisCanceled`.** 리뷰의 high 5건은 전부 한 원인, 취소 덮어쓰기였다. 워커는 탐색 루프에서만 취소를 확인했고, 종합이 끝나면 조건 없이 `completed` 를 대입해 API 가 찍어 둔 `canceled` 를 덮었다. `b6360b8` 이후 종합이 절 수만큼 LLM 을 차례로 부르므로, 취소가 무시되는 구간이 호출 1회에서 N회로 늘어나 있었다. 취소 API 와 SSE 는 `canceled` 를 알렸는데 DB 는 나중에 `completed` 가 되고, 그동안 공유 GPU 는 계속 돈다.

상태 전이를 조건부 UPDATE 로 바꾼 것은 워커 쪽 수정이고(§2.36), 종합 쪽 수정이 이 두 이름이다. `synthesize` 는 `should_stop` 콜백을 받아 **LLM 을 부르기 직전마다** 확인한다 — 절마다, 그리고 재시도 직전에도. True 면 `SynthesisCanceled` 를 던진다.

설계 결정 둘.

- **콜백으로 주입한다.** `synthesize` 가 DB 세션을 받아 직접 상태를 읽으면 종합 모듈이 DB 를 알게 된다. 콜백(`lambda: _is_cancelled(db, jid)`)으로 받으면 종합은 여전히 "상태 + LLM"만 아는 함수로 남고, 테스트는 가짜 async 함수 하나로 취소 시점을 조절한다. 드라이런(§2.31)이 기댄 것도 이 성질이다 — 드라이런은 `should_stop` 이 생기기 전 코드로 돌았지만, 콜백이 선택 인자라 지금 코드도 `synthesize(state)` 한 줄로 DB 없이 부를 수 있다.
- **반환값이 아니라 전용 예외로 알린다.** 워커는 취소와 실패를 다르게 처리해야 한다 — 실패는 잡을 `failed` 로(retry 가능), 취소는 결과를 버리고 멈춘다. 워커는 `except SynthesisCanceled` 를 `except Exception` 보다 먼저 둔다.

```python
            try:
                report = await synthesize(state, should_stop=lambda: _is_cancelled(db, jid))
            except SynthesisCanceled:
                await _finish(db, step_id, "failed", {"error": "취소됨"})
                return await _stopped(db, jid)
```

`SynthesisCanceled` 도 `Exception` 의 하위라 순서가 바뀌면 취소가 종합 실패로 기록된다. 진행 중인 LLM 호출은 끊지 않는다 — 취소는 다음 호출 직전에 걸린다(spec §6 구현 시 변경). 마지막 절의 호출 도중에 들어온 취소는 워커의 조건부 전이가 받는다. `status='running'` 을 조건으로 건 `completed` 전이가 0행이 되어, 보고서를 버리고 멈춘다.

**⑧ 검증 집합을 그 절에 준 번호로 한정한 이유.** `b6360b8` 의 `assemble_report` 는 모든 절의 도입·과제를 전역 집합 `set(state.evidence.keys())` 로 검증했다. 그런데 모델이 절마다 받는 근거는 그 절의 논문 최대 5편뿐이다. **근거 번호는 E1…En 으로 연속 발급되므로**(`max_evidence` 기본 60) 모델이 지어낸 작은 번호는 거의 다 전역 집합 안에 있다. 결국 검증은 전체 근거 수보다 큰 번호에만 반응했다. E6~E10 만 받은 절이 도입에 `[E3]` 을 쓰면, 모델이 본 적도 없는 논문을 가리키는 칩이 생기고 호버에는 문장과 무관한 대목이 뜨는데 한계는 아무 말도 하지 않는다. 당시 테스트 하나도 E2·E3 만 받은 절의 도입에 `[E1]` 을 넣은 채 아무 지적 없이 통과하고 있었다.

지금은 절마다 검증 집합을 그 절의 논문에서 다시 계산한다.

```python
        valid = {by_cnts[p["cnts_id"]] for p in sec.get("papers", []) if p["cnts_id"] in by_cnts}
```

절의 논문 목록이 곧 `section_paper_ids` 이고, 그것이 곧 모델이 프롬프트에서 받은 번호다. 그래서 절 dict 에 번호 목록을 따로 싣지 않고 `papers` 의 `cnts_id` 에서 되돌려 구한다. 묶음·범위·전각 표기(`[E1, E2]`·`[E3-E5]`·`［E1］`)의 해석도 같은 리뷰에서 `bind_markers` 에 들어갔다 — 이 파일은 결과(`dropped`·`unparsed`·`used`·`unmarked`)만 쓴다.

한계 문구도 함께 바뀌었다. 전역 검증 때는 "존재하지 않는 근거 번호를 가리킨 인용 표기"였지만, 이제 지워지는 번호는 보고서 어딘가에는 존재할 수 있다. 그래서 "그 절의 근거에 없는 번호를 가리킨 인용 표기"로 고쳤다 — 한계 섹션에 사실과 다른 문장을 쓰지 않는다.

**⑨ 한계 문장 규칙 (`build_limitations`).** 한계 섹션은 spec §2-4 가 꼽은 차별점이다 — 모른다고 말하는 시스템이 아는 척하는 시스템보다 신뢰를 얻는다. 규칙의 뼈대는 **종류가 다른 사건을 한 문장으로 합치지 않는다**는 것이다.

| 사건 | 문구(요지) | 보고 기준 |
|---|---|---|
| 탐색 오류(`failed`), 근거 있음 | "…는 탐색이 오류로 중단돼 끝까지 확인하지 못했다(중단 전까지 모은 근거 N편으로만 썼다)" | 하위질문마다 |
| 탐색 오류, 근거 0편 | "…는 탐색 중 오류로 확인하지 못했다" | 하위질문마다 |
| 상한(`capped`)으로 근거 0편 | "…는 근거 상한(N편)에 닿아 검색된 논문 M편을 싣지 못했다" (critic 사유 안 붙임) | 하위질문마다 |
| 근거 0편 | "…에 대해서는 근거를 찾지 못했다 — {critic 사유}" | 하위질문마다 |
| 자기점검 `insufficient` | "…는 근거 N편으로 결론이 약하다" (+ 상한에 닿았으면 그 사실) | 하위질문마다 |
| 판정 불가(`parse_failed`) | "자동 점검을 완료하지 못한 하위질문이 N건 있다" | 1건부터 |
| 서술을 끝내 못 받은 절 | "서술을 생성하지 못한 절이 N개 있다 — 그 절은 근거 논문 목록만 싣는다" | 1개부터 |
| 도입이 빈 절(실패 절 제외) | "도입 문단을 생성하지 못한 절이 N개 있다" | 1개부터 |
| 요약이 빈 논문(실패 절 제외) | "요약을 생성하지 못한 논문 N편이 있다" | 1편부터 |
| 절 밖 번호(`dropped`) | "그 절의 근거에 없는 번호를 가리킨 인용 표기 N건을 본문에서 제거했다" | **1건부터** |
| 해석 불가 표기(`unparsed`) | "해석할 수 없는 인용 표기 N건을 본문에서 제거했다" | 1건부터 |
| 무근거 문장(`unmarked`) | "근거 표기가 없는 서술 N건이 있다" | **3건부터**(`UNMARKED_THRESHOLD`) |

각 규칙의 이유.

- **dropped 는 1건부터, unmarked 는 3건부터.** 마커 없는 문장은 "이 절에서는 …을 다룬다" 같은 연결 문장일 때가 많아 몇 건은 넘긴다. 절 밖 번호는 모델이 근거를 지어낸 것이라 1건이면 알릴 일이다. 초안은 둘을 `UNMARKED_THRESHOLD` 하나로 묶었는데, 그러면 흔한 쪽을 과하게 알리면서 정작 심각한 쪽을 임계값에 묻는다 — 초안의 자기 테스트(`[E99]` 하나로 한계 문장을 기대)가 `1 >= 3` 에 걸려 모순이 드러났다(plan Task 8). 같은 이유로 `unmarked_total`·`dropped_total` 은 기본값 없는 키워드 인자다 — 무결성 수치가 조용히 0 으로 기본값을 갖는 것이 막으려는 실패 그 자체다(plan Task 8). 뒤에 더한 `unparsed_total`·`failed_sections` 등은 기본값 0 이지만, 부르는 곳이 `assemble_report` 하나이고 거기서 전부 넘긴다.
- **unparsed 를 dropped 와 나눈다.** `[E1 참조]` 처럼 읽을 수 없는 표기는 번호를 지어낸 것이 아니라 형식을 어긴 것이다. 원인이 다르면 고칠 곳도 다르다(프롬프트 쪽).
- **세는 단위는 본문의 표기 수다.** 같은 `[E99]` 가 두 번 나오면 2건이다 — 사용자가 보는 단위가 그것이다. 그리고 `bind_markers` 는 절마다 도입 한 번, 과제 개수만큼 불리므로 반환값을 호출마다 누적한다. 한 번의 반환값만 읽으면 나머지 호출에서 지운 표기가 조용히 사라진다.
- **failed·capped 를 "근거 없음"보다 먼저 본다.** 시스템 장애나 우리 쪽 상한을 "근거를 찾지 못했다"로 쓰면 코퍼스 빈틈이라는 연구 결과로 둔갑한다. 상한 때문에 0편인 하위질문에는 critic 의 사유를 붙이지 않는다 — critic 은 근거 목록 "(없음)"을 보고 판정했으므로 "관련 논문이 없다" 같은 사유는 오보다.
- **판정 불가는 따로 센다.** 판정을 받지 못한 하위질문은 `verdict="sufficient"` 로 떨어져 insufficient 분기에 걸리지 않는다. 따로 세지 않으면 자기점검이 전부 꺼져도 보고서가 "한계 없음"으로 보인다. 근거 0편(따질 대상이 없다)과 탐색 오류(위에서 이미 알렸다)는 이 집계에서 뺀다. 판정 불가 하위질문에는 critic 의 사유도 붙이지 않는다 — 그 사유는 '왜'가 아니라 같은 실패의 반복이다.
- **이중 계수를 없앴다.** 서술이 통째로 실패한 절의 논문은 "요약을 생성하지 못한 논문"에 세지 않는다. "서술을 생성하지 못한 절 1개"와 "요약을 생성하지 못한 논문 5편"이 나란히 뜨면 실패가 두 건처럼 읽힌다. 도입 없음도 실패 절에서는 세지 않는다.
- **critic 사유는 여러 분기에 붙인다.** 근거 0편인 하위질문은 insufficient 분기에 닿지 못하는데, "왜 못 찾았는지"가 가장 필요한 경우가 바로 그때다.

남은 것(완료노트 §8). 한계는 "근거 6편"인데 절에는 상한 5편만 실려, 사용자가 세어 보면 어긋난다. 도입의 "문장마다 [E#]" 지시가 연결 문장에도 인용을 붙인다(실측: `본 절에서는 … 분석한다 [E1]`). 마침표에 바로 붙은 마커(`했다.[E1]`)나 구두점 없이 개행으로 끝나는 문장에서 무근거 문장을 적게 센다(low).

**⑩ 보고서의 근거 청크 (`_serialize_evidence`)와 절별 청크.** `Evidence.chunks` 는 매칭된 적 있는 청크의 저장소라 재검색이 갈아끼운 대목도 남아 있다. 보고서에는 지금 어느 하위질문이든 가리키는 청크만 점수순으로 싣는다 — 삽입 순서대로 실으면 어느 절도 쓰지 않은 약한 대목이 `chunks[0]` 에 와서 호버 첫 장에 뜬다. 매핑이 없는 옛 스냅샷에서 재개한 보고서는 전부 싣는다. 청크에는 `score` 를 넣는다 — 리뷰 전에는 빠져 있어, 프론트가 보고서 JSON 만 받는 구조(spec §4-5)에서 호버가 유사도를 그릴 경로가 없었다. 절마다 `evidence_chunks`(그 절에서 매칭된 청크 ID)와 `chunk_scores`(그 절 하위질문의 점수)를 싣는 것은, 한 논문이 여러 절에 실릴 때 호버가 그 절의 대목과 점수를 고르게 하려는 것이다. `trail` 에 `parse_failed`·`failed`·`capped` 를 싣는 것도 같은 리뷰에서다 — 플래그가 없으면 탐색 경로 화면이 판정 불가를 '충분'으로, 탐색 오류를 '대기 중'으로 그린다. 청크 매핑 자체(`citations.chunks_for`·`link_chunks`)는 §2.7 에 있다.

def build_limitations(
    state: ResearchState, *, unmarked_total: int, dropped_total: int,
    failed_sections: int = 0, unsummarized_total: int = 0,
    unparsed_total: int = 0, introless_sections: int = 0,
) -> list[str]:
    """자기점검 결과를 사용자에게 보이는 문장으로 바꾼다.

    판정을 받지 못한 하위질문(parse_failed)을 반드시 별도로 센다. 판정 불가는
    verdict="sufficient" 로 떨어지므로 아래 insufficient 분기에 걸리지 않고,
    그대로 두면 자기점검이 전부 꺼져도 보고서가 "한계 없음"으로 보인다.

    절에 주지 않은 근거 번호(dropped)와 무근거 서술(unmarked)도 한 문장으로
    합치지 않는다. 종류가 다른 사건이다 — 마커 없는 문장은 "이 절에서는 …을
    다룬다" 같은 연결 문장일 때가 많아 몇 건은 넘긴다. 반면 주지 않은 번호를
    가리킨 표기는 모델이 근거를 지어낸 것이니 1건부터 보고한다. 합치면 흔한 쪽을
    과하게 알리면서 정작 심각한 쪽을 임계값에 묻는다.
    """
    out: list[str] = []
    max_evidence = state.params["max_evidence"]
    for sq in state.subquestions:
        # note 를 여러 분기에 붙인다. 근거가 0편인 하위질문은 아래 insufficient
        # 분기에 닿지 못하는데, 정작 "왜 못 찾았는지"가 가장 필요한 경우다.
        # 판정을 못 받았을 때의 note 는 '왜'가 아니라 같은 실패의 반복이라 뺀다 —
        # 아래 집계 문장이 따로 센다.
        note = f" — {sq.note}" if sq.note and not sq.parse_failed else ""
        n = len(sq.evidence_ids)
        # failed·capped 를 "근거 없음"보다 먼저 본다. 시스템 장애나 우리 쪽 상한을
        # "근거를 찾지 못했다"로 쓰면 연구 결과(코퍼스 빈틈)로 둔갑한다.
        if sq.failed and n:
            out.append(
                f"'{sq.text}' 는 탐색이 오류로 중단돼 끝까지 확인하지 못했다"
                f"(중단 전까지 모은 근거 {n}편으로만 썼다){note}"
            )
        elif sq.failed:
            out.append(f"'{sq.text}' 는 탐색 중 오류로 확인하지 못했다{note}")
        elif not n and sq.capped:
            # 상한 때문에 0편이면 critic 은 "(없음)"을 보고 판정한다 — 그 note 는 오보다
            out.append(
                f"'{sq.text}' 는 근거 상한({max_evidence}편)에 닿아 "
                f"검색된 논문 {sq.capped}편을 싣지 못했다"
            )
        elif not n:
            out.append(f"'{sq.text}' 에 대해서는 근거를 찾지 못했다{note}")
        elif sq.verdict == "insufficient":
            cap = (f"(근거 상한({max_evidence}편)에 닿아 후보 {sq.capped}편을 더 싣지 못했다)"
                   if sq.capped else "")
            out.append(f"'{sq.text}' 는 근거 {n}편으로 결론이 약하다{cap}{note}")

    # 근거가 0편이면 충분성을 따질 대상이 없고, failed 는 위에서 이미 알렸다
    unchecked = sum(1 for sq in state.subquestions
                    if sq.parse_failed and sq.evidence_ids and not sq.failed)
    if unchecked:
        out.append(
            f"자동 점검을 완료하지 못한 하위질문이 {unchecked}건 있다 — "
            f"그 부분의 근거 충분성은 확인되지 않았다."
        )

    if failed_sections:
        out.append(
            f"서술을 생성하지 못한 절이 {failed_sections}개 있다 — "
            f"그 절은 근거 논문 목록만 싣는다."
        )

    if introless_sections:
        out.append(f"도입 문단을 생성하지 못한 절이 {introless_sections}개 있다.")

    if unsummarized_total:
        out.append(f"요약을 생성하지 못한 논문 {unsummarized_total}편이 있다.")

    if dropped_total:
        out.append(
            f"그 절의 근거에 없는 번호를 가리킨 인용 표기 "
            f"{dropped_total}건을 본문에서 제거했다."
        )

    if unparsed_total:
        out.append(f"해석할 수 없는 인용 표기 {unparsed_total}건을 본문에서 제거했다.")

    if unmarked_total >= UNMARKED_THRESHOLD:
        out.append(f"근거 표기가 없는 서술 {unmarked_total}건이 있다.")
    return out


def _serialize_evidence(state: ResearchState) -> dict:
    """보고서의 근거 목록. 청크는 지금 어느 하위질문이든 가리키는 것만, 점수순으로 싣는다.

    Evidence.chunks 는 매칭된 적 있는 청크의 저장소라 재검색이 갈아끼운 대목도 남아 있다.
    그대로 실으면 어느 절도 그 대목으로 쓰지 않았는데 삽입 순서대로 chunks[0] 에 나간다.
    매핑 없이 이 근거를 보는 하위질문이 있으면(옛 스냅샷) chunks_for 처럼 전부 싣는다.
    """
    mapped: dict[str, set[str]] = {}
    unmapped: set[str] = set()
    for sq in state.subquestions:
        for eid, ids in sq.evidence_chunks.items():
            mapped.setdefault(eid, set()).update(ids)
        unmapped.update(e for e in sq.evidence_ids if not sq.evidence_chunks.get(e))

    def _shown(eid: str, ev: Evidence) -> list[Chunk]:
        keep = ev.chunks if eid in unmapped or eid not in mapped else [
            c for c in ev.chunks if c.chunk_id in mapped[eid]]
        return sorted(keep, key=lambda c: c.score, reverse=True)

    return {
        eid: {
            "cnts_id": ev.cnts_id,
            "meta": ev.meta,
            "chunks": [asdict(c) for c in _shown(eid, ev)],
        }
        for eid, ev in state.evidence.items()
    }


def assemble_report(
    state: ResearchState, sections: list[dict], *, unmarked_total: int,
) -> dict:
    by_cnts = {ev.cnts_id: eid for eid, ev in state.evidence.items()}
    unmarked = unmarked_total
    # 마커 검증 결과는 bind_markers 호출마다 누적한다. 섹션마다 도입·향후
    # 과제로 여러 번 부르므로 한 번의 반환값만 읽으면 나머지 호출에서 지운
    # 표기가 조용히 사라진다. dropped 는 번호 종류가 아니라 본문에 박힌
    # 표기 수로 센다 — 사용자가 보는 단위가 그것이다.
    dropped = unparsed = 0
    unsummarized = failed_sections = introless = 0
    out_sections = []

    for sec in sections:
        failed = bool(sec.get("failed"))
        # 모델은 절마다 그 절의 논문만 받는다 — 검증도 그 번호로 한정한다. 근거
        # 번호가 E1..En 으로 연속 발급되므로 전역 집합으로 검증하면 모델이 지어낸
        # 작은 번호는 거의 다 통과하고, 본 적 없는 논문을 가리키는 칩이 생긴다.
        valid = {by_cnts[p["cnts_id"]] for p in sec.get("papers", []) if p["cnts_id"] in by_cnts}
        intro = bind_markers(sec.get("intro", ""), valid)
        unmarked += intro.unmarked
        dropped += len(intro.dropped)
        unparsed += len(intro.unparsed)
        # 칩만 남은 도입("[E1]")은 문장이 아니다 — 도입 없음으로 센다
        intro_text = intro.text if _prose(intro.text) else ""
        if failed:
            failed_sections += 1
        elif not intro_text:
            introless += 1

        papers = []
        for p in sec.get("papers", []):
            eid = by_cnts.get(p["cnts_id"])
            if eid is None:
                continue                      # 근거에 없는 논문은 싣지 않는다
            summary = strip_markers(p.get("summary", ""))
            if not _prose(summary):
                summary = ""                  # "[E1]." 에서 번호만 걷으면 마침표 하나가 남는다
            # 서술이 통째로 실패한 절은 위의 failed_sections 로 이미 보고한다 —
            # 그 절의 논문을 요약 누락으로 또 세면 실패가 두 건처럼 보인다.
            if not summary and not failed:
                unsummarized += 1
            papers.append({
                "cnts_id": p["cnts_id"],
                "summary": summary,
                "evidence": [eid],            # 구조적 인용 — 모델이 고르지 않는다
            })

        future = []
        for f in sec.get("future", []):
            res = bind_markers(f.get("text", ""), valid)
            unmarked += res.unmarked
            dropped += len(res.dropped)
            unparsed += len(res.unparsed)
            # 지운 번호는 위에서 이미 셌다. 마커만 있던 항목은 빈 불릿이나 칩 하나짜리
            # 불릿이 되므로 싣지 않는다.
            if not _prose(res.text):
                continue
            # used 를 bind_markers 가 돌려준다 — 여기서 정규식을 다시 쓰면
            # 마커 문법이 두 곳으로 갈라진다.
            future.append({"text": res.text, "evidence": res.used})

        out_sections.append({
            "heading": sec.get("heading", ""),
            "intro": intro_text, "papers": papers, "future": future,
            # 근거 ID → 이 절에서 매칭된 청크 ID. 한 논문이 여러 절에 실리면
            # evidence.chunks 는 그 합집합이라, 호버는 이걸로 그 절의 대목을 고른다.
            "evidence_chunks": sec.get("evidence_chunks", {}),
            # 청크 ID → 이 절의 하위질문 검색어로 받은 점수. 두 절이 한 청크를 쓰면
            # evidence.chunks[].score(최고값) 하나로는 한쪽 절에 남의 점수가 뜬다.
            "chunk_scores": sec.get("chunk_scores", {}),
        })

    return {
        "question": state.question,
        "range": state.corpus_range,
        "sections": out_sections,
        "evidence": _serialize_evidence(state),
        "trail": [
            {"subquestion": sq.text, "queries": sq.queries,
             "evidence_count": len(sq.evidence_ids),
             "verdict": sq.verdict, "note": sq.note,
             "parse_failed": sq.parse_failed, "failed": sq.failed, "capped": sq.capped}
            for sq in state.subquestions
        ],
        "limitations": build_limitations(
            state, unmarked_total=unmarked, dropped_total=dropped,
            failed_sections=failed_sections, unsummarized_total=unsummarized,
            unparsed_total=unparsed, introless_sections=introless,
        ),
    }


def section_paper_ids(state: ResearchState, sq: SubQuestion) -> list[str]:
    return sq.evidence_ids[:PAPERS_PER_SECTION]


def _text(value: object) -> str:
    """모델 출력의 문장 필드 하나를 문자열로 만든다.

    문장 배열은 잇는다 — str() 로 바꾸면 "['문장1', '문장2']" 가 화면에 나간다.
    그 밖의 모양(null·숫자·dict)은 버린다. null 이 bind_markers 까지 가면 모든 절
    호출이 끝난 뒤 TypeError 로 보고서 전체를 잃는다.
    """
    if isinstance(value, str):
        text = value.strip()
    elif isinstance(value, list) and all(isinstance(v, str) for v in value):
        text = " ".join(v.strip() for v in value if v.strip())
    else:
        return ""
    return "" if _PLACEHOLDER in text else text


def _eid_key(key: str) -> str:
    m = _EID_KEY.fullmatch(key)
    return f"E{int(m.group(1))}" if m else key


def build_section(state: ResearchState, sq: SubQuestion, data: dict | None) -> dict:
    """하위질문 하나와 모델 출력으로 절을 만든다 (순수 함수).

    소제목은 하위질문 그대로, 논문 목록은 section_paper_ids 그대로다 — 모델
    출력에 무엇이 있든 없든 바뀌지 않는다. 모델이 요약을 빠뜨린 논문도 빈
    요약으로 싣고 assemble_report 가 개수를 한계에 올린다. data 가 None(서술을
    끝내 받지 못함)이면 논문 목록만 남기고 failed 로 표시한다.
    """
    raw = data or {}
    summaries = raw.get("summaries")
    summaries = ({_eid_key(str(k)): _text(v) for k, v in summaries.items()}
                 if isinstance(summaries, dict) else {})
    future = raw.get("future")
    future_texts = []
    for f in future if isinstance(future, list) else []:
        text = _text(f.get("text") if isinstance(f, dict) else f)
        if text:
            future_texts.append(text)
    eids = section_paper_ids(state, sq)
    chunks = {eid: chunks_for(state.evidence[eid], sq) for eid in eids}
    return {
        "heading": sq.text,
        "intro": _text(raw.get("intro")),
        "papers": [
            {"cnts_id": state.evidence[eid].cnts_id, "summary": summaries.get(eid, "")}
            for eid in eids
        ],
        "future": [{"text": t} for t in future_texts],
        "evidence_chunks": {eid: [c.chunk_id for c in cs] for eid, cs in chunks.items()},
        "chunk_scores": {c.chunk_id: c.score for cs in chunks.values() for c in cs},
        "failed": data is None,
    }


def _prose(text: str) -> str:
    """인용 표기를 걷어낸 문장. 마커만 있는 필드는 빈 문자열이다."""
    return strip_markers(text).strip(" \t\n.,;:")


def _has_narrative(section: dict) -> bool:
    """검증 전 출력으로 판정하므로 문장 기준으로 본다. 마커만 있는 도입·과제를
    서술로 세면 assemble_report 에서 지워진 뒤 서술 0줄이 되는데도, 재시도와
    '전부 실패' 가드를 건너뛰어 completed 로 남는다."""
    return bool(
        _prose(section["intro"])
        or any(_prose(f["text"]) for f in section["future"])
        or any(_prose(p["summary"]) for p in section["papers"])
    )


def _evidence_block(state: ResearchState, sq: SubQuestion) -> str:
    lines = []
    for eid in section_paper_ids(state, sq):
        ev = state.evidence[eid]
        # 그 하위질문 검색에서 매칭된 대목을 준다 — 재사용 근거의 첫 청크는
        # 다른 하위질문의 검색어로 뽑힌 것일 수 있다.
        chunks = chunks_for(ev, sq)
        excerpt = chunks[0].text[:400] if chunks else ""
        lines.append(
            f"[{eid}] {ev.meta.get('title')} "
            f"({ev.meta.get('pub_date')}, {ev.meta.get('series_title')})\n{excerpt}"
        )
    return "\n\n".join(lines)


async def _synthesize_section(
    state: ResearchState, sq: SubQuestion,
    *, should_stop: Callable[[], Awaitable[bool]] | None,
) -> dict:
    """절 하나를 만든다.

    전송 오류·해석 실패·서술 없는 응답은 한 번 다시 부르고, 그래도 안 되면
    논문 목록만 남긴 절(failed)을 돌려준다 — 한 절의 실패가 이미 받은 다른
    절을 버리게 두지 않는다.
    """
    system, user, llm_params = get_prompt("research_synthesize").render(
        question=state.question, subquestion=sq.text,
        evidence_block=_evidence_block(state, sq),
        paper_ids=", ".join(section_paper_ids(state, sq)),
    )
    for attempt in range(1, _SECTION_ATTEMPTS + 1):
        if should_stop is not None and await should_stop():
            raise SynthesisCanceled
        try:
            raw = await chat(
                [{"role": "system", "content": system}, {"role": "user", "content": user}],
                params=llm_params, timeout=300.0,
            )
        except httpx.HTTPError as e:
            log.warning("[research] 절 종합 호출 실패 job=%s idx=%s 시도=%d — %s: %s",
                        state.job_id, sq.idx, attempt, type(e).__name__, e)
            continue
        # 공용 추출기를 쓴다. 여기서 다시 구현하지 마라 —
        # body[index("{"):rindex("}")+1] 은 JSON 뒤에 } 를 포함한 산문이 붙으면
        # 그 끝까지 먹어 파싱이 깨진다.
        data = extract_json(raw)
        if data is None:
            log.error("[research] 절 종합 JSON 파싱 실패 job=%s idx=%s 시도=%d: %s",
                      state.job_id, sq.idx, attempt, (raw or "")[:300])
            continue
        section = build_section(state, sq, data)
        # 파싱만으로 성공을 판정하면 키가 다른 dict·빈 dict 가 성공으로 세어져,
        # 모든 절이 그렇게 와도 아래 '전부 실패' 가드를 빠져나간다.
        if _has_narrative(section):
            return section
        log.error("[research] 절 종합 응답에 서술이 없다 job=%s idx=%s 시도=%d: %s",
                  state.job_id, sq.idx, attempt, (raw or "")[:300])
    return build_section(state, sq, None)


async def synthesize(
    state: ResearchState, *, should_stop: Callable[[], Awaitable[bool]] | None = None,
) -> dict:
    """하위질문마다 절을 하나씩 만든다.

    근거가 없는 하위질문은 절을 만들지 않는다 — 한계 섹션이 그 사실을 적는다.
    탐색이 도중에 실패한 하위질문이라도 그 전에 모은 근거가 있으면 절을 만든다.
    빼면 실재하는 근거가 report.evidence 에만 고아로 남고, 한계에는 사실과 다른
    "확인하지 못했다"만 실린다.

    일부 절의 실패는 한계로 보고하고 넘어가지만, 전부 실패하면 예외를 던진다.
    서술이 한 줄도 없는 보고서를 completed 로 두면 재시도(stage=explored 에서
    재개) 기회가 사라진다.

    should_stop 은 LLM 을 부르기 직전마다 확인하고, True 면 SynthesisCanceled 를
    던진다 — 취소 뒤에도 남은 절을 다 부르면 GPU 를 비운다는 취소의 약속이 거짓이 된다.
    """
    targets = [sq for sq in state.subquestions if sq.evidence_ids]
    sections = []
    for sq in targets:
        section = await _synthesize_section(state, sq, should_stop=should_stop)
        sections.append(section)
        log.info("[research] 절 종합 job=%s idx=%s 논문=%d ok=%s",
                 state.job_id, sq.idx, len(section["papers"]), not section["failed"])

    if targets and all(s["failed"] for s in sections):
        raise ValueError("보고서의 어느 절도 서술을 받지 못했다")

    return assemble_report(state, sections, unmarked_total=0)

class TestBuildSection:
    def test_heading_and_papers_are_structural(self):
        """모델이 논문을 하나만 요약해도 절의 논문 목록은 하위질문의 근거 그대로다."""
        st = _state_three()
        sec = build_section(st, st.subquestions[0],
                            {"intro": "도입 [E1].", "summaries": {"E1": "요약"}, "future": []})
        assert sec["heading"] == "하위1"
        assert [p["cnts_id"] for p in sec["papers"]] == ["A", "B"]
        assert sec["papers"][1]["summary"] == ""

    def test_parse_failure_keeps_paper_list(self):
        st = _state_three()
        sec = build_section(st, st.subquestions[0], None)
        assert sec["intro"] == "" and sec["future"] == []
        assert [p["cnts_id"] for p in sec["papers"]] == ["A", "B"]

    def test_malformed_fields_are_ignored(self):
        st = _state_three()
        sec = build_section(st, st.subquestions[0],
                            {"intro": 3, "summaries": ["x"], "future": "x"})
        assert sec["intro"] == "" and sec["future"] == []
        assert all(p["summary"] == "" for p in sec["papers"])

    def test_papers_are_capped(self):
        st = _state_three()
        ids = [f"E{i}" for i in range(1, 10)]
        for eid in ids:
            st.evidence.setdefault(eid, Evidence(id=eid, cnts_id=eid, meta={}))
        st.subquestions[0].evidence_ids = ids
        assert len(build_section(st, st.subquestions[0], {})["papers"]) == PAPERS_PER_SECTION

    def test_papers_follow_evidence_order(self):
        # runner 가 evidence_ids 를 하위질문 안 순위로 정렬해 둔다 — 절은 그 앞을 자른다
        st = _state_three()
        st.subquestions[0].evidence_ids = ["E2", "E1"]
        sec = build_section(st, st.subquestions[0], {})
        assert [p["cnts_id"] for p in sec["papers"]] == ["B", "A"]

    def test_future_item_with_non_string_text_is_dropped(self):
        """text 가 null 이면 bind_markers 에서 TypeError — 모든 절 호출이 끝난 뒤라 보고서 전체를 잃는다."""
        st = _state_three()
        sec = build_section(st, st.subquestions[0], {"intro": "도입.", "future": [
            {"text": None}, {"text": {"a": 1}}, {"no_text": 1}, {"text": "  "}, 7,

        assert sec["future"] == [{"text": "과제 [E1]."}]

        assert sec["future"] == [{"text": "과제 [E1]."}]

### 2.31 `research/round04a-synth-dryrun/` — 스냅샷으로 종합만 다시 돌린 드라이런

**무엇을 책임지나.** 운영 잡의 `state_snapshot`(탐색이 끝난 체크포인트)으로 **보고서 종합만** 다시 돌려, 같은 근거에서 종합 코드의 전후를 비교한 1회성 실험이다. DB 에 쓰지 않는다. `b6360b8` 의 수정을 배포하기 전에 라이브 모델로 확인하는 데 썼다. 다시 돌릴 일이 없는 실험이라 `scripts/` 가 아니라 `research/` 에 실행 산출물과 함께 둔다(`CLAUDE.md` §1, `d435ff3`).

**왜 이런 도구가 필요했나.** 절 1개 버그의 수정은 단위 테스트로 확인할 수 없다 — 버그 자체가 라이브 모델에서만 나기 때문이다(§2.29 "못 잡는 것"). 그렇다고 잡을 새로 돌리면 두 가지가 걸린다.

- **같은 근거로 비교할 수 없다.** planner 가 결정적이지 않아 같은 질문에서도 하위질문이 달라진다(완료노트 §2). 탐색 비용도 다시 든다.
- **배포부터 해야 한다.** 새 코드를 서버에서 돌리려면 이미지를 바꿔 컨테이너를 재생성해야 하는데, 대량 인덱싱이 도는 중이라 적재 워커를 끊을 수 있다(함정 16번).

스냅샷이 답이었다. 종합의 입력은 `stage=explored` 체크포인트에 정확히 들어 있고, `synthesize(state)` 는 DB 를 모르는 함수다(§2.28 ⑦). 스냅샷을 읽어 `restore_state` 로 되살리고, 새 종합만 부른 뒤, 결과를 찍기만 하면 된다.

**어떻게 돌렸나 — 코드를 명령에 박는다.**

1. `gen_dryrun.py` 가 워킹트리의 `synthesizer.py` 와 `research_synthesize.yaml` 을 gzip → base64 로 만들어 파이썬 스크립트 템플릿에 박는다. 그 스크립트를 `docker exec -i … nl-lib-fastapi python - <<'PY' … PY` 로 감싼 셸 명령(`synth_dryrun.sh`)과, 감싸지 않은 본문(`synth_dryrun_body.py`)을 이 폴더에 쓴다.
2. 스크립트는 컨테이너 안에서 base64 를 풀고, YAML 로 `PromptTemplate` 을 직접 만들고, synthesizer 소스를 빈 모듈(`synth_new`)에 `exec` 한 뒤, 그 모듈의 `get_prompt` 를 "종합 프롬프트면 박아 넣은 템플릿을 돌려주는" 함수로 바꾼다. `_synthesize_section` 은 `get_prompt` 를 모듈 전역에서 **호출 시점에** 찾으므로 이 교체가 먹는다 — 테스트의 `monkeypatch` 와 같은 원리다. 이미지에 든 옛 YAML 은 쓰이지 않는다.
3. `JOB` 의 `state_snapshot` 을 읽어 `mod.synthesize(st)` 를 부르고, **구성 숫자부터** 찍는다(`절 N | 근거 N | 논문으로 실린 근거 N`, 절마다 논문 수·요약 수·향후 과제 수). 함정 15번의 교훈 그대로 — 무결성보다 구성을 먼저 본다.

왜 이 방식인가.

- **서버에 코드를 들이지 않는다.** stdin 으로 흘려 넣으므로 이미지도 컨테이너의 앱 코드도 그대로이고, 파일 전송(scp·`docker cp`) 없이 `JOB=<job_id>` 를 잡은 셸에 붙여넣기 한 번이면 된다. `nl-lib-fastapi` 에서 돌리는 것은 거기에 DB 접속(`AsyncSessionLocal`)과 LLM 설정이 있고, `-w /app`·`PYTHONPATH=/app` 로 앱 모듈을 앱과 같은 경로로 임포트할 수 있어서다.
- **gzip + base64.** 박는 자리가 템플릿 속 파이썬 문자열 리터럴(`un("…")`)이라, 한글·따옴표·백슬래시·개행이 섞인 소스를 그대로 넣으면 리터럴이 깨진다. base64 는 영숫자와 `+/=` 뿐이라 리터럴에도 붙여넣기 경로에도 걸리는 문자가 없다. 셸 쪽은 here-doc 구분자를 `'PY'` 로 따옴표 쳐 `$`·백틱 확장을 막았다. gzip 은 명령 길이를 줄인다.

**제약 — 박는 것은 두 파일뿐이다.** `citations`·`state`·`llm_json`·`llm_client`·`prompts` 는 **서버 이미지의 것**을 쓴다. 종합이 새로 의존하는 함수가 이미지에 없으면 임포트에서 실패한다. 예를 들어 지금 HEAD 의 synthesizer 는 `2bac7ee` 에서 생긴 `citations.chunks_for` 를 임포트하므로, 그보다 오래된 이미지에서는 돌지 않는다. 완료노트 §2·§8 기준 운영에는 리뷰 반영분(`2bac7ee`)이 아직 배포되지 않았으므로, 지금 HEAD 로 만든 명령을 운영에 붙이면 임포트에서 실패한다. 그때는 의존 모듈도 함께 박도록 `gen_dryrun.py` 를 고쳐야 한다. 스냅샷을 되살리는 `restore_state` 도 이미지 쪽 것이다. 그리고 드라이런은 **진짜 LLM 을 부른다** — 공유 GPU 를 쓰고, temperature 0.3 이라 돌릴 때마다 문장이 다르다. 한 번의 결과는 표본 하나다.

**결과.** 절 1개가 나왔던 그 잡의 스냅샷으로 수정본을 돌려 **절 3 · 논문으로 실린 근거 9/10 · 요약 12/12** 를 확인한 뒤 배포했다. 10번째 근거는 6편짜리 하위질문의 6번째라 `PAPERS_PER_SECTION = 5` 상한에 걸렸다. 탐색 비용 없이 같은 근거로 전후를 비교할 수 있었다. 같은 드라이런에서 모델이 요약에 `[E7]` 을 단 것이 `strip_markers` 와 프롬프트의 마커 금지 문구로 이어졌다(§2.28 ④, §2.27). 요약이 맞는 논문에 배정됐는지는 이 드라이런에서 재지 않았다.

#### `gen_dryrun.py`

인자는 저장소 루트 하나다. 템플릿은 원시 문자열이고, `@@SYN@@`·`@@PRM@@` 자리를 `str.replace` 로 채운다 — f-string 이나 `format` 을 쓰면 템플릿 속 파이썬 코드의 중괄호(`cited = {e for s in …}`)를 일일이 `{{ }}` 로 이스케이프해야 한다. 두 파일을 `newline="\n"` 으로 쓰는 것은 Windows 개발 PC 에서 만들어도 LF 로 남기려는 것이다. CRLF 가 섞이면 서버 셸에서 here-doc 종료 줄이 `PY\r` 이 되어 `PY` 와 일치하지 않는다. 마지막에 셸 명령의 길이(문자 수)를 찍는다.

**파일**: `research/round04a-synth-dryrun/gen_dryrun.py` — 전체 78줄

```python
"""드라이런 명령 생성기 — 워킹트리의 synthesizer.py·프롬프트를 gzip+base64 로 박아 넣는다."""
import base64
import gzip
import pathlib
import sys

repo = pathlib.Path(sys.argv[1])
out = pathlib.Path(__file__).parent


def pack(rel):
    return base64.b64encode(gzip.compress((repo / rel).read_bytes())).decode()


TEMPLATE = r'''import asyncio, base64, gzip, logging, os, types, uuid
import yaml
from sqlalchemy import select
from db.postgres import AsyncSessionLocal
from models.research import ResearchJob
from services.prompts import PromptTemplate
from services.research.state import restore_state

logging.basicConfig(level=logging.INFO, format="%(message)s")
for noisy in ("httpx", "httpcore", "sqlalchemy"):
    logging.getLogger(noisy).setLevel(logging.WARNING)

un = lambda s: gzip.decompress(base64.b64decode(s)).decode("utf-8")
SYN, PRM = un("@@SYN@@"), un("@@PRM@@")

d = yaml.safe_load(PRM)
tpl = PromptTemplate(name="research_synthesize", system=str(d["system"]).rstrip("\n"),
                     user=str(d["user"]).rstrip("\n"), parser=d.get("parser", "plain"),
                     params=d.get("params") or {})
mod = types.ModuleType("synth_new")
exec(compile(SYN, "synthesizer_new.py", "exec"), mod.__dict__)
_orig = mod.get_prompt
mod.get_prompt = lambda name, *a, **k: tpl if name == "research_synthesize" else _orig(name, *a, **k)


async def main():
    jid = os.environ["JOB"]
    async with AsyncSessionLocal() as db:
        job = (await db.execute(
            select(ResearchJob).where(ResearchJob.id == uuid.UUID(jid)))).scalar_one()
        snap = job.state_snapshot
    if not snap:
        print("state_snapshot 없음 — 이 잡으로는 드라이런 불가")
        return
    st = restore_state(jid, snap)
    r = await mod.synthesize(st)          # DB 에 쓰지 않는다
    cited = {e for s in r["sections"] for p in s["papers"] for e in p["evidence"]}
    print()
    print("절", len(r["sections"]), "| 근거", len(r["evidence"]), "| 논문으로 실린 근거", len(cited))
    for s in r["sections"]:
        filled = sum(1 for p in s["papers"] if p["summary"])
        print()
        print("===", s["heading"], "| 논문", len(s["papers"]), "(요약", filled, ") | 향후", len(s["future"]))
        print("도입:", s["intro"])
        for p in s["papers"]:
            print("  -", p["evidence"][0], (p["summary"] or "(요약 없음)")[:120])
        for f in s["future"]:
            print("  >", f["text"])
    print()
    for line in r["limitations"]:
        print("한계:", line)


asyncio.run(main())
'''

body = (TEMPLATE
        .replace("@@SYN@@", pack("app/services/research/synthesizer.py"))
        .replace("@@PRM@@", pack("app/domains/nl_library/prompts/research_synthesize.yaml")))
sh = ("docker exec -i -e JOB=\"$JOB\" -e PYTHONPATH=/app -w /app nl-lib-fastapi python - <<'PY'\n"
      + body + "PY\n")
(out / "synth_dryrun_body.py").write_text(body, encoding="utf-8", newline="\n")
(out / "synth_dryrun.sh").write_text(sh, encoding="utf-8", newline="\n")
print(len(sh))
```
#### `smoke_dryrun.py`

만든 본문을 서버에 붙여넣기 전에 로컬에서 DB 없이 먼저 돌려 본다. 본문을 `async def main():` 앞에서 잘라 그 앞부분(디코딩·템플릿 조립·모듈 `exec`·`get_prompt` 교체)만 실행하고, `mod.chat` 을 가짜로 바꾼 뒤 손으로 쓴 스냅샷에 `synthesize` 를 돌린다. 마지막 두 줄이 **박아 넣은 새 템플릿이 실제로 쓰였는지**(시스템 프롬프트에 `"summaries"` 와 `paper_ids` 가 렌더됐는지)와 LLM 파라미터를 확인한다. base64·gzip 오류, 템플릿과 코드의 변수 어긋남을 서버 시간과 GPU 를 쓰기 전에 잡는다.

단, 이 스모크는 `sys.argv[1]`(로컬 `app/`)의 모듈로 돈다. 위 **제약** — 서버 이미지에 새 의존 함수가 있는가 — 은 확인하지 못한다.

r = asyncio.run(mod.synthesize(restore_state("j", snap)))
print("sections", [s["heading"] for s in r["sections"]])
