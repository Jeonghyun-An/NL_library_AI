## 종합 프롬프트 yaml 갈아 끼우기 (variant_attrib 작성 때 적음)

- `base.yaml` = fix-live worktree(fix/round06-live-check)의 `app/domains/nl_library/prompts/research_synthesize.yaml` 현행 사본(마지막 변경 커밋 4e5ea63).
- synthesizer 는 `from services.prompts import get_prompt` 로 **이름을 가져온다** → `services.prompts.get_prompt` 를 덮어도 소용없고
  `services.research.synthesizer.get_prompt` 를 덮어야 한다. 로더는 `services.prompts._load_template(경로, 이름)` 을 바로 쓴다
  (`PromptLibrary(dir).get()` 은 파일 이름이 `research_synthesize.yaml` 이어야 해서 변형 파일명엔 안 맞는다).

  ```python
  from services.prompts import _load_template
  import services.research.synthesizer as syn
  syn.get_prompt = lambda name, doc_type=None: _load_template(r"<절대경로>/variant_attrib.yaml", name)
  ```
  `_load_template` 은 경로 키 lru_cache 다 — 같은 파일을 고쳐 다시 돌릴 땐 새 프로세스로 돌린다.
- 이 폴더의 `run_prompt.py` 가 위 방식으로 갈아 끼우고 절마다 원문·형식 문제를 남긴다(같은 폴더 rebuild.py 의 state_of 사용, 코드는 SYNTH_AB_APP — README 재현 절).
  `PYTHONIOENCODING=utf-8 python run_prompt.py variant_attrib.yaml 630e <회수> <출력.json>`
  — 동시 요청 = 그 프로세스에서 동시에 도는 잡 수(회수×태그). 세마포어가 프로세스마다 따로라 **여러 프로세스를 같이 돌리면 합이 4 이하**가 되게 회수를 나눈다.
- yaml 계약(어기면 파싱 실패·렌더 실패): 변수는 `question`·`subquestion`·`evidence_block`·`paper_ids` 만(StrictUndefined — 없는 변수를 쓰면 렌더에서 죽고, 안 쓰는 건 괜찮다),
  출력은 JSON 하나 `{"intro": str, "summaries": {"E#": str}, "future": [{"text": str}]}`. 출력에 글자 그대로 `[E#]` 가 남은 필드는 코드가 버린다(_PLACEHOLDER).
  summaries 의 마커는 strip_markers 가 지운다. 운영 반영은 이 yaml 을 `research_synthesize.yaml` 로 바꿔 넣기만 하면 된다(코드 변경 없음).

## variant_attrib.yaml — 방향 B: 출처 정확성

현행 대비 바꾼 지시(출력 형식·변수·params·user 템플릿은 그대로, 예시 문장 없음):
1. **재인용 규칙 신설** — 괄호 속 저자·연도, 각주 번호, '선행연구'·'~에 따르면' 으로 다른 연구의 결과를 전하는 문장은 재인용. 그 근거 논문의
   발견·주장으로 쓰지 말고, 쓸 때는 원 연구의 결과임을 밝히고(저자·연도는 대목에 적힌 그대로) 그것을 전한 근거 논문 번호를 단다. 근거 논문 자신의 결과를 앞세운다.
2. "논문 제목·저자·연도를 쓰지 마라" → "**근거 논문의** 제목·저자·연도" 로 좁힘(재인용 원 연구는 이름을 밝혀야 하므로).
3. intro·future **모든 문장에 대목 번호**, 번호를 달 수 없는 문장(하위질문 되풀이·절 소개·대목에 없는 총론·평가)은 쓰지 않는다.
4. 연구의 양·시기·추세 판단은 대목이 직접 밝힌 것만, 한 논문 결과를 연구 전체 경향으로 넓히지 않는다.
5. summaries = 그 논문 **자신의** 연구 대상·방법·결과만. 대목이 재인용뿐이면 그 논문이 어떤 선행연구를 들어 무엇을 논의하는지로 쓰고 선행연구 결과임을 밝힌다.
6. future 는 대목이 밝힌 한계·제언에서만, 개수 1~3 → **0~3**(없으면 빈 배열).
7. JSON 골격의 설명 글: intro "연구 흐름을 설명하는" → "하위질문에 대목의 사실로 답하는", summaries "무엇을 했고 무엇을 주장하는지" → "그 논문 자신의 연구 대상·방법·결과",
   future "남은 과제" → "대목이 밝힌 남은 과제". 키·자료형·`[E#]` 자리표시자 꼴은 그대로.
- system 길이 591 → 1,143자(근거 블록 포함 전체 프롬프트로는 약 +15%).

형식 확인(630e, gemma-3-12b, 3회 = 18호출 — gen_attrib_630e_a.json(1회)·gen_attrib_630e_b.json(2회)):

한계 줄에 인용 표기 제거/무근거 서술 없음. future 는 모델이 매 호출 1개를 냈고(0개 낸 적 없음), 절별 0개는 drop_repeats 가 앞 절과 같은 과제를 지운 것.

## variant_concise.yaml — 방향 C: 간결한 학술 요약체

갈아 끼우기는 위 절과 같다(`syn.get_prompt` 를 덮는다 — `run_prompt.py` 그대로 쓴다):
`PYTHONIOENCODING=utf-8 python run_prompt.py variant_concise.yaml 630e 1 gen_concise_630e_r0.json`
`_concise_driver.sh` 는 돌고 있는 다른 `run_prompt.py` 들의 잡 수(회수 인자 합, both 는 2배)가 3 이하일 때만 1회씩 3번 띄운다 — 프로세스마다
세마포어가 따로라 여럿이 같이 돌 때 gemma 동시 요청 합을 4 이하로 지키려고. 상한·길이 지표는 `concise_stats.py [--tag 630e] <gen json>…`

현행 대비 바꾼 지시(출력 JSON 키·`[E#]` 자리표시자 꼴·변수 4개·params 그대로, 예시 문장 없음):
1. **문장 수 상한을 근거 편수 n 에 비례** — system 맨 앞에서 Jinja 로 계산한다(코드 변경 없음):
   `n = paper_ids.split(', ')|length`, 도입 `n//2+1` 문장 이내(1편 1 · 2~3편 2 · 4~5편 3, 현행 '2~4문장'), 요약 논문마다 1~2문장(현행 2~3),
   향후 과제 `0~(n<3 ? 1 : 2)`개(현행 1~3). ⚠ `paper_ids` 가 synthesizer 의 `", ".join(...)` 꼴이라는 데 기댄다 — 구분자가 바뀌면 n=1 로 조용히 줄어든다.
2. 이 절은 같은 논문을 다른 하위질문으로 다루는 여러 절 중 하나 → **이 하위질문이 묻는 것만** 쓴다(옆길 ②).
3. **한 문장 = 주장 하나**, intro·future 는 문장마다 **마침표 바로 앞**에 그 문장의 마커, 문단 끝에 몰아 달기 금지(④).
   마커를 달 수 없는 문장 — 분야·연구 흐름 소개, 하위질문 문구 되풀이, 절 내용 예고, 대상을 특정하지 않은 일반론 — 금지(①·② 군말).
4. 재인용: 대목이 저자(연도)로 소개한 다른 연구의 내용은 그 논문의 결과가 아니다, 쓰려면 선행연구로 검토한 것이라고 밝힌다(③).
5. 같은 내용 두 번 금지 — 논문 하나의 세부는 summaries 에만. 단 future 가 요약에 나온 한계를 '다음 연구가 할 일'로 바꾸는 것은 되풀이가 아니다
   (이 단서가 없으면 gemma 가 future 를 거의 늘 [] 로 냈다 — draft1).
6. future 는 대목이 밝힌 한계·제언·상반된 결과에서만, 그런 대목이 하나도 없을 때만 빈 배열. summaries 는 하위질문에 닿는 내용을 앞세우되,
   없어도 비우지 말고 대목 핵심 한 문장(이 문장이 없던 draft1 에서 summaries 번호 하나를 빠뜨린 회차가 나왔다).
7. JSON 골격 설명: intro '연구 흐름을 설명하는 2~4문장' → '하위질문에 대한 답 N문장 이내, 첫 문장부터 근거의 구체적 결과'(현행 문구 '연구 흐름'이 ① 도입 문장을 부른다고 봤다).
8. **user 끝에 할 일 한 줄**(26번 함정의 처방) — 하위질문을 주어로 되풀이하지 말고 첫 문장부터 결과로 답, 문장마다 마침표 앞 마커, 모든 문장 '~다'.
   이 줄은 **해라체로 써야 한다**: '~답니다' 로 쓴 draft2 는 gemma 가 절 통째로 합니다체로 옮겨 써 한 회에 9~27문장이 '~습니다'였다.

## variant_focus.yaml — 방향 A: 절의 하위질문에 곧장 답하기

갈아 끼우는 법은 위 절과 같다(`run_prompt.py` 는 이 변형을 만들며 쓴 스크립트다).
`PYTHONIOENCODING=utf-8 python run_prompt.py variant_focus.yaml 630e <회수> <출력.json>` — 출력 JSON 은 synth_impl/analyze.py 가 읽는
`tag·run·variant·sections·limitations` 에 `calls`(절마다 gemma 원문·형식 문제)를 더한 모양이다.

현행 대비 바꾼 지시(JSON 키·자료형·`[E#]` 자리표시자 꼴·변수 4개·params 그대로, 예시 문장 없음):
1. 첫 줄에 "이 절은 하위질문 하나에 답하는 자리" 를 더하고, **"intro 는 도입부가 아니라 하위질문에 대한 답 문단"** 이라고 못박는다(키 이름 intro 를 바꿀 수 없어서).
2. 하위질문이 묻는 것(개념·방법·대상·결과·한계·시기별 변화 등)을 정하고 **그것만** 쓴다 — 근거에 있어도 다른 차원은 intro 에 쓰지 않는다.
3. **첫 문장이 곧 답**: 근거가 보여 주는 가장 구체적인 발견(수치·대상·방법·결과)을 [E#] 와 함께. 하위질문이 연구 자체를 물으면 근거 논문들이 직접 쓴 방법·대상도 답이다.
4. 문장의 [E#] 는 그 문장 내용이 실린 대목의 번호 — 앞 번호를 습관적으로 달지 않는다(아래 '초안 경과' ②).
5. 금지 문장을 서술로 적는다(예문 없이): 구체적 내용 없는 분야·동향 일반론, 하위질문 문구를 되받은 문장, 절·보고서·본 연구의 예고, 중요성만 강조하는 맺음.
6. intro 는 [E#] 를 달 수 없는 문장을 쓰지 않고, 분량을 다른 내용으로 채우지 않고, 4문장을 넘기지 않는다. 모든 논문을 intro 에 넣을 필요는 없다(논문별 내용은 summaries).
7. summaries 는 논문마다 2~3문장, 그 논문 대목에서 하위질문이 묻는 것을 먼저, 이어서 한 일·주장.
8. JSON 골격 설명: intro "연구 흐름을 설명하는 2~4문장" → "하위질문에 대한 답 2~4문장. 첫 문장부터 문장마다 [E#]", future "남은 과제" → "이 하위질문에 대해 남은 과제". summaries 설명은 현행 그대로.
9. user 템플릿 끝에 한 줄: `위 근거로 하위질문 "{{ subquestion }}" 에 답하세요.` (같은 변수를 한 번 더 쓸 뿐, 변수 추가 없음).
