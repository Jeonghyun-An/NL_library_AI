# 브로셔용 검색 품질 수치 실험 — 키워드 통합검색(BM25) vs SKOVIX

기획 메모의 요구("검색 품질·의도에 맞춘 검색 수준을 정량 표기", "기존 통합검색 vs 자연어 검색이 얼마나 차이 나는지")를
**표기 한계까지 함께** 답하는 실험이다. 하니스: `app/scripts/eval_brochure_search.py` (테스트 `app/tests/test_eval_brochure_search.py`).

> ⚠️ 이 문서의 어떤 수치도 아직 **측정 결과가 아니다.** 실험은 운영 서버에서 돌려야 하고, 돌리기 전까지 브로셔에 들어갈 숫자는 없다.

## 왜 기존 평가 스크립트로는 안 되나

`eval_search.py` 의 질의는 **논문 제목·초록 앞부분**이고, `build_golden_queries.py` 는 **주제어 3개 나열·기관+연도 템플릿·초록 첫 문장**이다.
전부 문서 필드에서 기계적으로 뽑은 질의라 사람이 쓰는 자연어 질문이 아니다 — 이 수치로 "자연어 검색 정확도"라고 쓰면 안 된다.
또 초록 첫 문장을 초록 색인에 던지면 어휘가 그대로 겹쳐서 BM25 도 거의 100% 가 나와(천장 효과) 비교가 무의미하다.

## 비교 방식

| arm | 내용 |
|---|---|
| `bm25_meta` | 키워드 통합검색 기준선. **제목·주제어·초록(없으면 소개)**을 음절 bigram 으로 색인한 BM25. SKOVIX 가 만든 요약(summary)은 색인하지 않는다 |
| `skovix_hybrid` | BGE-M3 dense+sparse RRF. 질의 재작성·리랭커 없음 |
| `skovix_rerank` | 위 + 리랭커 |
| `skovix_rewrite` | 위 + LLM 질의 재작성(메타데이터 필터 없음) |
| `skovix_norewrite` | 운영 기본에서 질의 재작성만 끈 구성(리랭커 + 메타데이터 필터) — 2026-10-14 에 논문 검색 기본값이 이 구성으로 바뀜 |
| `skovix_full` | `pipeline.search` 의 기본 플래그 그대로(질의 재작성 + 메타데이터 필터 + 리랭커) |
| `prod_api` | **배포된 `POST /api/papers/search` 를 그대로 호출**(논문 화면과 같은 top_k=20·리랭커). `pipeline.search` 바깥의 제목 일치율 재정렬까지 포함한, 사용자가 실제로 받는 결과. 요청에는 재작성 켬을 보내 서버가 무시하는지 확인하는 카나리로 쓴다(`run` 끝에 '배포본이 재작성을 적용하지 않았다/적용했다'를 출력) |

BM25 → hybrid → +리랭커 → +재작성 → 전체(+메타필터)로 올라가는 사다리가 "백엔드 알고리즘 기술력"의 구성요소별 기여를 보여준다(메모 1-1).
리포트는 기준선 대비 차이와 **단계별(직전 단계 대비) 기여**를 함께 낸다 — 어떤 단계가 보탬이 되는지, 어떤 단계가 해치는지는 이 줄로 가린다.
**해치는 단계가 있으면 "기술력 강조" 문구에 그 단계를 넣으면 안 된다.**

## 지표

| 지표 | 의미 | 한계 |
|---|---|---|
| Recall@1/5/10, MRR@10, nDCG@10 | 질의의 원문서가 몇 위에 나오나 | 정답 1건 가정 — 같은 주제의 다른 문서는 오답 처리되므로 **하한** |
| **OTR@10** (On-Topic Rate) | 상위 10건 중 질의 주제에 '주로' 맞는 문서 비율 | LLM 판정. 사람 검증 필요 |

모든 값에 질의 단위 부트스트랩 95% 신뢰구간, 방식 간 차이는 쌍대 부트스트랩 + 부호검정.

**OTR 출처** — *Semantic Search Evaluation* ([arXiv:2410.21549](https://arxiv.org/abs/2410.21549), LinkedIn). (질의, 문서) 쌍을 이진 판정(관련 1/0)하고
`OTR@K = 상위 K건 중 관련 쌍의 합 / K`(논문은 K=10). 프롬프트에 정의·판정 지침·**근거 포함 예시**를 넣었고(예시가 없으면 사람 판단과 어긋났다고 보고),
키워드 일치만으로 판정하지 말라는 지침과 "primarily about" 표현을 썼다. 최종 규칙은 이진 판정이 1 이고 점수가 임계값(0.5) 이상.
논문의 사람 검증은 평가자 10명 기준 81.72% 일치(별도 검증 세트 600쌍에서 94.5% 정확도).
→ 하니스도 같은 구조(근거 포함 few-shot, 키워드 일치 금지, 이진+점수 0.5)로 만들었다.

**순환 주의** — LLM 판정자가 검색 파이프라인에도 쓰이면 순환이 된다([arXiv:2510.04633](https://arxiv.org/abs/2510.04633) 의 비판).
질의 재작성은 gemma 이므로 **판정 기본값은 Qwen3-VL(`--judge vlm`)** 이다. gemma 로도 한 번 판정해 일치도를 보고하는 것을 권한다.

## 실행 (운영 서버 `nl-lib-fastapi`, 읽기 전용)

색인·DB 에 쓰지 않는다. 다만 아래는 서버 자원을 쓴다 — **먼저 확인**:
- 새 프로세스가 BGE-M3+리랭커를 올린다(GPU 약 3~4GB 추가, gotchas #17). `nvidia-smi` 로 여유 확인.
- gemma(질문 합성·질의 재작성·메타필터)와 Qwen3-VL(판정)을 호출한다. 대량 적재가 돌고 있으면 같이 느려지고 적재도 느려진다 → 적재가 한가한 시간에.
- 호출량(대략): 질문 합성 ~300회 · 재작성(`skovix_rewrite`·`skovix_full`) 400회 + 메타필터(`skovix_full`) 200회 · 판정 최대 약 10,000회(NL 200문항 × 5방식 × 10건, 중복 제외하면 더 적다).
- **스모크 실측(2026-10-13, 운영 서버)**: BM25 색인 — 논문 197,256건 42초, 도서 910건 0.2초. `run` 8문항 전체 1분 1초(BM25 색인·모델 로드 포함). `judge` 214쌍 34초(≈ 0.16초/쌍, docker exec 기동 포함) · 실패 0건. 외삽하면 본 실험 `judge` 는 10,000쌍 기준 20~30분.
  이 외삽은 스모크 크기(8문항)에서 나온 것이라 부하가 큰 시간대엔 더 걸릴 수 있다.
- 코퍼스(2026-10-13): 논문 197,256건 · 도서·보고서 910건 — 이 수치는 `queries.json` 에 자동 기록된다.

```bash
# 로컬 worktree → 서버 호스트 → 컨테이너 (재생성되면 사라지는 일회용 복사 — gotchas #3).
# 로컬 docker 에는 nl-lib-fastapi 가 없다. 서버는 원격이라 두 번 옮긴다.
# 주소: 사내망이면 192.168.12.57, 외부망이면 공인 IP 211.219.26.15 (사내에서 공인 IP 로는 타임아웃 — 2026-10-13 확인).
scp -P 8022 app/scripts/eval_brochure_search.py landsoft@192.168.12.57:/tmp/
#   (이하는 서버에 SSH 접속한 뒤)
docker cp /tmp/eval_brochure_search.py nl-lib-fastapi:/app/scripts/
E="docker exec -w /app nl-lib-fastapi python -m scripts.eval_brochure_search"

# 1) 스모크 테스트 — 작게, 별도 작업 폴더에서. 여기서 오류·건당 시간을 먼저 본다
$E --workdir /app/data/brochure_eval_smoke build --n-papers 5 --n-books 3
$E --workdir /app/data/brochure_eval_smoke run
$E --workdir /app/data/brochure_eval_smoke judge
$E --workdir /app/data/brochure_eval_smoke report

# 2) 본 실험 (기본 /app/data/brochure_eval) — 각 단계는 중단 후 재실행하면 이어 간다
$E build --n-papers 150 --n-books 50          # (선택) --golden /app/data/golden_queries.json
$E run
$E audit --only-differ skovix_rerank,skovix_full   # 두 방식의 순위가 갈린 질의 + 재작성·메타필터가 실제로 한 일
$E judge --judge vlm                           # 판정 모델명은 /v1/models 로 자동 확인해 기록(별칭만 보이면 --model-label 로 지정)
$E judge --judge llm                           # 판정자 간 일치도용(선택)
$E report --judges vlm --scopes paper          # 도서·보고서는 뺀 논문 전용 표(아래 '본 실험에서 확인한 것' 참고)

# 3) OTR 사람 검증 — 60쌍을 사람이 0/1 로 채운다(LLM 판정은 가려져 있음)
$E review-sheet --n 60 --scopes paper
docker cp nl-lib-fastapi:/app/data/brochure_eval/review_sheet.csv .   # 채운 뒤 다시 cp
$E agreement --sheet /app/data/brochure_eval/review_sheet.csv
$E report --judges vlm --scopes paper          # 사람 일치도가 표 하단에 들어간다

# 4) 결과 내려받기 → research/brochure-search-eval/results/
docker cp nl-lib-fastapi:/app/data/brochure_eval ./results
```

산출물: `queries.json`(질의·시드·코퍼스 크기) · `runs.json`(방식별 상위 10건) · `judgments_*.json` · `summary.json` · **`brochure_table.md`**.
질의 세트를 사람이 훑어 이상한 질문을 지울 수 있다 — 지우면 `run` 부터 다시 돌린다.

## 브로셔에 쓸 때

`brochure_table.md` 하단의 "표기 시 반드시 지킬 것"이 자동으로 붙는다. 요지:

| 써도 되는 표현 (결과가 뒷받침할 때) | 쓰면 안 되는 표현 |
|---|---|
| "합성 자연어 질문 N개 기준, 상위 10건 안에 원문서가 포함된 비율(Recall@10) — 키워드 통합검색 X% → SKOVIX Y%" | "자연어 검색 정확도 Y%" (합성·하한·기준선 정의가 빠짐) |
| "상위 10건 중 질의 주제에 맞는 문서 비율(OTR@10, LLM 판정·사람 검증 일치 Z%)" | 문서 필드 기반 질의(주제어·기관+연도·초록 첫 문장) 결과를 자연어 검색 정확도로 표기 |
| "키워드 통합검색(제목·주제어·초록 색인 BM25) 대비" | "기존 통합검색 대비"(실제 기관 사이트와 비교한 것이 아님) |

결과가 불리하게 나온 구간(예: 주제어 질의에서 BM25 와 비슷)도 그대로 둔다 — 자연어·의역 질문에서만 격차가 크다는 결과도 충분히 강한 메시지이고,
어휘 겹침이 낮은 절반(`nl_low_coverage`)이 그 증거 구간이다.

## 이 실험이 주지 못하는 것 (메모의 나머지 항목)

- **이용자 만족도** — 실험으로 만들 수 없다. 설문이 필요하다(5점 척도 3문항 + 응답자 수·대상 명시). 근거 없이 숫자를 쓰지 않는다.
- **"동일 자료를 찾는 시간 차이"** — 기계 시간(지연)은 이것과 다르다. 쓰려면 사람이 재야 한다: 정답 문서를 정해 두고 설명문만 주는 과제 10개, 참가자 2~3명이 키워드 사이트와 SKOVIX 를
  **순서를 교차해** 사용, 제한 3분(못 찾으면 3분+실패 표시), 중앙값 시간과 성공률을 보고하고 "N명·M과제 파일럿"이라고 적는다.
- **다른 모델과의 비교** — 외부 API 에 도서관 자료를 보내야 하므로 승인 없이 하지 않는다. 이 하니스의 사다리(BM25→하이브리드→리랭커→전체)가 내부 비교다.
- **딥리드·딥리서치 수치** — 딥리서치는 측정된 적이 없다. 답변 품질은 2026-08-03 재실험분만 유효하다(충실성 gemma 4.97/Qwen3-VL 4.80, 검색성공 93.3%, 출처 100%; 합성 질문 기반이라 상한).
  **`eval_results/` 의 07-31 파일은 무효 실행이니 인용하지 말 것.**

## 스모크 테스트 관찰 (2026-10-13, n=8 — 수치는 인용 금지, 원인 확인용)

파이프라인은 끝까지 돌았다(검색 오류 0, 판정 실패 0%). `audit` 로 "전체"가 "+리랭커"보다 낮게 나온 이유를 읽었다.

**처음 세운 가설은 틀렸다** — "17세기·19세기 같은 시대 표현을 발행연도 필터로 읽을 것"이라 봤지만 두 질문 모두 필터가 만들어지지 않았다(로그에 필터 줄 자체가 없음).
실제로 확인된 것:

| 현상 | 근거(audit) | 성격 |
|---|---|---|
| "**요즘** 독일어 교육은…" 이 `sort_by='recent'` 를 켜 날짜순으로 재정렬 → 정답(7위) 탈락 | `nl-p-0000` | **제품은 의도대로 동작.** 질문 세트의 문제 — 시간 표현이 든 질문은 정답 1건 평가와 안 맞는다 → 질문 합성에서 시간 표현(`요즘·최근·최신·올해·작년·지난해·연도·연대 범위`) 금지·거절(`time_expr`) |
| **재작성이 구체적 질문을 주제어 나열로 바꾼다**: "…**소설**이 어떤 사상적 배경…" → "17세기 말 가문 분쟁, 사회 질서, **봉건 제도, 윤리 도덕**, 사상사" (`소설` 탈락, 질문에 없던 주제어 추가) | `nl-p-0001`: 리랭커만 1위 → 재작성 10위 밖. `nl-b-0001` 1→5위, `nl-b-0002` 4→10위 밖. 8문항 중 3개 하락·상승 0 | 재작성 프롬프트가 "X 같은 책" 식 유사도 검색용으로 짜여 있어 생기는 것으로 **추정**. n=8 이라 확정 아님 → 본 실험의 **단계별 기여(리랭커→재작성)** 줄이 판정한다 |
| 도서 범위에서 BM25 가 SKOVIX 를 앞섬 (`nl-b-0000`: SKOVIX 전 방식 탈락, BM25 1위) | 질문이 카탈로그 초록에서 나왔고 BM25 는 바로 그 초록을 색인함 | **BM25 에 유리한 구조**(질문 출처 = BM25 색인 필드). 본문 위주로 색인된 SKOVIX 가 불리할 수 있다는 가설 — 미확인 |

**해석상 주의**
- 재작성이 정말 해친다면 그건 질문 세트 탓이 아니라 운영 기본값("전체")의 특성이다 — 브로셔 수치는 제품이 실제로 내놓는 "전체"로 써야 하고, 잘 나온 단계만 골라 쓰면 안 된다.
  다만 재작성은 모호한 질문·감성 질의에서 도움이 될 수 있어(OTR 은 도서에서 소폭 상승), "나쁘다"가 아니라 **구체적 질문에서 손해**일 수 있다는 말이다.
- **OTR@10 은 절대값이 낮게 나온다**(스모크: 논문 BM25 8% / SKOVIX 26~28%). 질문에 맞는 문서가 코퍼스에 소수뿐이면 상한 자체가 낮기 때문이다 → 상대 비교로만 쓴다.
- 도서·보고서 범위의 합성 질문은 모호하다("혼자 고립된 상황에서도 희망을 잃지 않는 사람의 이야기") — 정답이 여러 권이라 known-item 지표가 안 맞는다. 도서는 OTR 을 주지표로, 헤드라인은 논문 범위(197,256건)로 잡기를 권한다.
- 판정 모델명: 설정(`VLM_MODEL`)은 `qwen3-vl-8b` 이지만 실제 서빙은 Qwen3-VL-30B-A3B-FP8(별칭 유지). 하니스는 `/v1/models` 로 실제 모델을 적는다. Qwen 이 내려가 있으면 `--judge llm`(gemma) 으로 돌리고, 리포트에 순환 경고가 자동으로 붙는다.

### 세 세트 통합(논문 450문항, `results_pooled/brochure_table_pooled.md` · `pooled_analysis.py`)

"정확한/정확도" 표현은 여전히 금지.
- **재작성 켬(10-14 전 기본)**: Recall@10 71.3%, 키워드 대비 1.76배 [1.57–1.99].
- **질의 재작성이 해롭다 — 세 세트 모두 재현**: 리랭커 대비 재작성 단계 Recall@10 -18.0%p(A)·-16.0%p(B)·-15.3%p(C), 통합 **-17.6%p [-21.6, -13.8]**(85건 잃고 6건 얻음), 의역 위주 절반에서도 -17.5%p. 원인(코드·로그 확인)은 재작성 프롬프트가 도서 추천용이라 구체적 질문을 쉼표 나열 키워드로 바꾸며 구체어를 버리고 없던 주제어를 덧붙이는 것(`query_rewrite.yaml`; 재작성 150개 중 126개가 키워드 나열형).

### 세트 A 단독(2026-10-13)

- **논문(n=150, 색인 197,256건)**: 재작성 켬 구성(당시 운영 기본)이 BM25 보다 Recall@10 +29.3%p(CI +20.0~+39.3), OTR@10 약 2.0배. 날짜 필터가 걸린 9건을 뺀 층(`nl_unfiltered`, n=141)도 결론이 같다 — 시간 표현은 영향이 없었다.

- **OTR 판정 교차 확인 — 사람 검증은 하지 않았다(사람이 없어 대체).** 두 가지를 봤다.
  1. *Claude 채점 60쌍*(논문, Qwen 판정 1/0 각 30쌍; `agreement --rater Claude`, 라벨은 `results/review_labels_claude.json`): 일치율 81.7%, kappa 0.63. 갈린 11쌍은 Qwen 1/Claude 0 이 7쌍, 그 반대가 4쌍이라 한쪽으로 치우쳤다고 보기 어렵다(p≈0.55). 어긋남은 대부분 질의의 한 측면(온라인, 임시 충전재, 유물 전시 등)이 문서에 빠진 경계 사례다. Claude 판정을 정답으로 가정해 환산하면(두 오분류율이 방식과 무관하다는 가정, 표본이 작아 구간이 넓음) 전체/BM25 OTR 배수가 1.98배 → 약 1.45배(범위 1.15~1.72).
  2. *gemma 전체 판정 5,234쌍*(`results/brochure_table_gemma_judge_paper.md`): 절대값은 훨씬 낮지만(BM25 7.4%, 전체 13.9%) 배수는 비슷하다 — 전체/BM25 1.88배, +리랭커/BM25 2.17배(Qwen: 1.98·2.31배). 단 gemma 는 질문 합성·재작성 모델이라 재작성이 낀 방식에는 순환 소지가 있다. Qwen–gemma 판정자 간 일치율 81.9%, kappa 0.39(전체 분포 기준 — 대부분이 '아님'이라 kappa 가 낮게 나옴).

## 알려진 한계

1. 질문은 LLM 합성이다(실사용자 질의 아님). 어휘 겹침 정도를 `lex_coverage` 로 기록해 층화 보고한다.
2. 정답 1건 가정 → Recall·MRR·nDCG 는 하한. OTR 이 이를 보완하지만 LLM 판정이다.
3. BM25 기준선은 서지 필드만 색인한다. 본문 전체를 색인한 키워드 검색과의 비교는 하지 않았다.
4. 코퍼스는 측정 시점의 운영 색인이다(`queries.json` 에 크기 기록). 적재가 진행 중이면 재측정 값이 달라진다.
5. 판정 파싱 실패는 0 으로 세지 않고 결측으로 보고한다(`missing_pairs`). 결측률이 2% 를 넘으면 판정 프롬프트·모델을 점검한다.
6. **시간 표현이 든 질문**: 질문 합성에서 `요즘·최근·최신·올해·작년·지난해·세 자리 이상 연도("762년")·연대 범위("1960~70년대")` 를 정규식으로 거절하지만 정규식이 모든 표현을 잡지는 못한다.
   (본 실험 질문 목록에 `nl-p-0092` "762년에 세워진 비문…", `nl-p-0140` "1960~70년대 과학 잡지…", `nl-b-0016` "1920~30년대 문학가들…" 3건이 남았다 — 정규식을 넓히기 전에 만든 질문 세트라서다.)
   이런 질문은 운영 기본 설정이 발행연도 필터·날짜 정렬을 걸 수 있어 정답 1건 평가와 맞지 않는다. 그래서 리포트는 **필터가 실제로 걸린 질의를 뺀 층(`nl_unfiltered`)**을 따로 낸다.
   전체 "자연어 질문" 층과 이 층의 결론이 같으면 시간 표현은 영향이 없었다는 뜻이고, 다르면 헤드라인엔 `nl_unfiltered` 를 쓰되 "필터 걸린 N건 제외"를 같이 적는다.
   어떤 질의에 필터가 걸렸는지는 `audit` 으로 본다.
