## 0. 왜 하나

사용자는 이 적재 파이프라인을 nanet 에 이식해 운영하면서 세 가지를 발견해 고쳤다. ① 병렬화가 제대로 안 됨, ② 섹션 요약에서 뒤가 버려짐, ③ 섹션이 너무 크게 잘림. SKOVIX 도 같은 이유로 느린지 확인했다(2026-10-01, 운영에는 GET 만 보냄 — 잡 조회 API, gemma·VLM `/metrics`, 섹션 조회).

결론: nanet 의 ①(섹션 요약 순차)은 SKOVIX 에 해당하지 않는다. 대신 다른 병목 두 곳이 번갈아 막고, 데이터를 잃거나 버리는 결함이 여럿 있다. 아래 수치는 운영 실측이고 추정은 추정이라고 적는다.

## 2. 범위 — 고칠 것 18개

번호는 진단 순서다. 구현 순서는 계획서가 정한다.

### 2.1 처리량 (결과물은 같다)

1. **논문 보강을 embed 칸 밖으로.** `enrich_paper`(키워드·참고문헌 폴백·표 해석·그림 설명 LLM)를 요약 단계(`q_llm`, `celery-llm`)에서 섹션 요약 뒤에 돌린다. 결과는 이미 있는 `save_enrichment_artifact`(MinIO `artifacts/{id}/enrichment.json.gz`)와 DB(초록·키워드·`extra`)에 저장한다. embed 단계는 그 아티팩트를 읽어 보강 청크를 만들고 GPU 임베딩·Milvus 적재만 한다. 아티팩트가 없으면(배포 전 체크포인트에 머문 아이템) 예전처럼 embed 에서 보강을 돌린다 — 드문 경로다. `enrich_paper` 는 httpx 와 MinIO 만 쓰고 torch 를 쓰지 않으므로 GPU 없는 `celery-llm` 에서 돌아도 된다(함정 17 확인).
2. **VLM 페이지 병렬.** 페이지별 라우팅 판정(fitz 교차검증)은 지금처럼 순서대로 하고, OCR 이 필요한 페이지만 문서 안에서 동시에 `VLM_PAGE_CONCURRENCY`(기본 2)건씩 보낸다. fitz 렌더링은 스레드 안전하지 않으므로 렌더링은 잠금 안에서 하나씩, 요청만 동시에 보낸다. 결과는 페이지 순서로 조립한다. 문서당 VLM 상한(60쪽)과 실패 시 ODL 결과 폴백은 그대로 둔다. 추출 워커 4 × 2 = 8 = VLM `max-num-seqs`.
3. **마무리 병렬.** `run_finalize` 의 문서 요약과 소개글 LLM 호출을 동시에 보낸다(도서의 줄거리·독후 효과도 같은 묶음에서 동시에).
4. **논문 표지 생성 끄기(사용자 결정 2026-10-01 — "어차피 논문이니깐").** 잡 params 에 `skip_cover` 가 빠져 있어 논문마다 마무리 단계에서 표지 프롬프트 LLM + FLUX 를 부른다(`stages.py:758-770`). 측정 구간에서 표지 프롬프트 호출 수가 마무리를 마친 문서 수와 같았다(57/57, 98/98). FLUX 컨테이너는 꺼져 있어(`:18090` 연결 거부) 이미지 요청은 즉시 실패하고, 완료 논문 50건 모두 `cover_prompt` 만 저장되고 이미지 키는 0건이었다. 낭비는 문서당 LLM 1회(1.6~2.2초, gemma 요청의 약 4%)다. `doc_type == "paper"` 이면 params 와 상관없이 표지를 건너뛴다. 적재가 도는 동안 FLUX 를 켜면 논문마다 GPU 0 에서 표지를 렌더하므로, 이 수정 전에는 FLUX 를 켜지 않는다.
5. **LLM 동시성을 단계 하나로 묶기.** 1번으로 요약 단계 안에서 섹션 요약과 표 해석이 함께 돈다. 따로 두면 프로세스당 4 + 4 = 8, 합계 32 로 gemma 16석을 크게 넘는다. 그래서 요약 단계가 세마포어 하나(`LLM_SECTION_CONCURRENCY`)를 만들어 섹션 요약과 보강의 모든 LLM 호출이 나눠 쓴다(`enrich_paper` 에 세마포어 인자를 더한다). `celery-llm` 은 프로세스당 태스크 1개라 단계 세마포어 = 프로세스 세마포어다. 이벤트 루프가 단계마다 새로 생기므로(`stages.py:57-62`) 모듈 전역 세마포어는 쓰지 않는다.

**기대 처리량 (추정 — 카나리와 재개 뒤 실측으로 확인):**
- ODL 문서: 상한이 embed 칸(약 300건/h)에서 `q_llm` 4칸과 gemma 로 옮겨 약 340~390건/h. 보강을 옮기면 `q_llm` 문서당 시간이 약 6초 늘고, 3번(마무리 병렬)과 4번(표지 끄기)이 그만큼을 줄인다. gemma 지연이 길어지면 250건/h 쪽으로 내려갈 수 있다.
- 스캔본(VLM) 문서: 약 50건/h → 약 80~100건/h. GPU 공유로 페이지당 시간이 늘어 2배까지는 안 갈 수 있다.
- 남은 약 11.3만 건의 완료 예상은 10/19~24 에서 며칠 당겨지는 정도로 본다. 7번으로 VLM 비중이 오르고(+2~4%), 재처리(약 10시간 이상)가 더해진다.
6. **제어 큐 분리.** `q_control`(디스패치·stale 회수·정리)을 추출 워커(`celery-cpu`, 동시 4)에서 떼어 새 경량 워커 `celery-control`(동시 1, GPU 없음)이 받는다. 지금은 디스패처 둘이 동시에 in-flight 를 읽어 상한을 넘길 수 있다. beat 일정에는 `expires` 를 둔다. 처리량 이득은 거의 없고 안정성 이득이다. compose 변경.
   - **하지 않는 것 (검증 결과):**
     - 진행 상한 32 를 올리거나 둘로 나누지 않는다. 두 병목을 섞어 돌려도 VLM·gemma·embed 가 GPU 0 을 같이 써서 서로 느려진다. VLM 동시 추출이 3 이상이면 ODL embed 평균이 11.6 → 19.6초로 늘었다. 그래서 얻는 것은 6~9%(추정)이고, 대기열이 길어지면 아래 18번의 stale 오판이 커진다.
     - gemma 자리(16)와 `celery-llm` 동시성을 늘리지 않는다. 자리를 다 채운 구간에서 오히려 처리량이 1.89 → 1.71건/초로 줄었다(2.5분 표본). 한계는 GPU 공유다.

### 2.2 결함 (새로 처리하는 문서부터 결과가 좋아진다)

7. **스캔본 라우팅 — 문서 단위 표적 수정.** `:424` 분기를 통째로 VLM 으로 보내지 않는다. 50자 미만 트리거가 예전 VLM 호출의 90% 이상이었고 표지·간지까지 VLM 으로 보냈다 — d85df93 이 fitz 교차검증으로 그것을 고쳤다(`:413-415` 주석, 사용자 확인). 그 수정을 되돌리지 않는 것이 이 항목의 제약이다.
   - 쪽 하나만 보면 '스탬프만 남은 스캔 본문 쪽'과 '스탬프만 남은 이미지 표지'를 구분할 수 없다. 그래서 쪽 단위 규칙은 더하지 않는다(쪽 면적 이미지 규칙은 표지를 다시 VLM 으로 보내므로 쓰지 않는다).
   - 문서 단위로만 판정한다. 각 쪽의 짧음은 ODL 본문 길이와, fitz 텍스트에서 문서 쪽의 60% 이상에 되풀이되는 짧은 줄(머리말·꼬리말·스탬프)을 뺀 길이로 센다. ODL 은 json header/footer 로 그 줄을 이미 지우므로, fitz 쪽도 지워야 같은 것끼리 비교가 된다. 3쪽 이상 문서에서 짧은 쪽이 절반을 넘으면 스캔본으로 보고 짧은 쪽을 OCR 로 보낸다.
   - 스캔본이 아닌 문서는 지금과 똑같다. 표지·간지 같은 원래 짧은 쪽은 ODL 을 채택하고, CMap 손상 2배 판정·fitz 0자 → OCR·표 셀 충전율 판정도 그대로다.
   - 10-01 에 실패한 「한국문학연구」 블록은 모든 쪽이 짧은 쪽이라 이 판정으로 잡힌다. 그래도 섹션이 0개면 8번의 강제 OCR 재추출이 받친다.
   - 기대 영향(추정): VLM 문서 비중 약 4% → 4.5~5%, 총 처리 시간 +2~4%(약 0.4~0.7일). 놓치던 문서를 제대로 읽는 비용이다.
8. **섹션 0개 처리 — 결정적 실패와 일시적 실패를 나눈다.** 추출 결과 섹션이 0개면 그 자리에서 짧은 쪽 전부를 OCR 로 보내는 강제 모드로 한 번 더 추출한다.
   - 그래도 0개이고 OCR 오류가 없었으면 `StageError("no_text")` 다. 같은 코드로 다시 해도 결과가 같으므로 자동 재시도하지 않는다(attempt 를 한도로 올린다).
   - OCR 오류(VLM 장애 등)가 있었으면 `StageError("vlm_error")` 다. 추출부터 다시 하도록 체크포인트를 `pending` 으로 두고 자동 재시도한다.
   - 요약 단계에서 "섹션 없음"으로 실패한 옛 아이템도 재시도 때 체크포인트를 `pending` 으로 되돌린다.
   - 자동 재시도에는 백오프를 둔다(`attempt` 1 → 2분, 2 → 10분 뒤에 다시 집음).
9. **LLM 재시도와 잘림 감지.** `llm_client` 에 재시도 3회(첫 시도 포함, 백오프 2초 → 8초)를 넣는다.
   - 재시도 대상: 연결 계열 오류(`httpx.NetworkError` — 연결 실패·RST 로 끊긴 읽기·쓰기. gemma 재기동 때 처리 중 요청은 `ReadError` 로 들어온다), 타임아웃, 응답 도중 끊김, 429·5xx. 그 밖의 4xx 는 바로 올린다.
   - **재시도 전체를 호출자의 timeout 안에 묶는다(리뷰 반영).** 묶지 않으면 응답 없이 붙잡는 장애에서 호출 하나가 timeout 의 3배 넘게 늘어난다. 그러면 단계 타임아웃·BookLock TTL 을 넘겨 stale 복구가 중복 체인을 연다(18번이 막으려는 경로). 각 시도의 timeout 은 남은 시간으로 줄이고, 남은 시간이 다음 백오프보다 적으면 재시도하지 않는다. 그래서 빠른 실패(연결 리셋·429·503)만 재시도되고 최악 지연은 예전과 같다. gemma 재기동처럼 분 단위로 이어지는 장애는 잡 단위 백오프(8번)가 맡는다.
   - `chat()` 은 그대로 두고 `(content, finish_reason)` 을 돌려주는 `chat_full()` 을 더한다. 잘리면 경고 로그와 함께 호출부가 처리한다.
10. **표 해석 잘림.** 표 해석 호출의 약 51%(gemma length 종료 109,939건 ÷ 예산 500~1000 구간 요청 215,153건)가 600토큰에서 잘린 채 색인된다. 다만 임베딩 창(512토큰 ≈ 본문 약 940자)이 거의 같은 자리에서 이미 자르므로 벡터 영향은 작다. 손실은 저장 텍스트(답변 문맥·화면 표시)와 낭비된 생성이다.
    - 표 원본 마크다운 청크가 따로 색인되므로, 설명은 모든 행을 옮기지 않는다. "표가 보여 주는 핵심 비교·경향" 몇 문장으로 프롬프트를 바꾼다. 개수는 프롬프트 예시로 주지 않는다(함정 15).
    - **상한은 올리지 않는다(600 유지).** 올리면 생성 시간만 늘고 임베딩 창 때문에 검색 이득이 없다.
    - `finish_reason == "length"` 이면 마지막으로 끝난 문장까지만 남긴다.
11. **VLM 잘림.** 비추론 모드에서도 `finish_reason == "length"` 를 본다. 같은 줄·구절이 되풀이되는 꼬리를 걷어 내고, 걷어 낸 뒤에도 비정상(반복 비율 높음)이면 그 페이지는 ODL·fitz 텍스트로 대신한다. 아이템 meta 에 `vlm_truncated` 수를 남긴다.
12. **문장 5개 이하 분기 상한 + 줄바꿈 폴백.** nanet 7128e09(그 분기에도 `_split_oversized` 적용)와 493f760(줄바꿈 폴백·`_split_by_chars`·합친 텍스트로 크기 추정)을 이식한다. 다만 SKOVIX 는 `_normalize_linebreaks` 가 홑줄바꿈을 먼저 공백으로 바꾸므로, 줄바꿈 폴백은 정규화 **전에** 판단한다(마침표가 거의 없는 텍스트는 줄 단위로 나눈 뒤 줄 안만 정규화). kss 는 설치하지 않는다.
13. **계층 요약.** `_combine_sections` 가 상한을 넘으면 버리지 않는다. 섹션 요약을 순서대로 상한 안의 묶음으로 나눠 묶음마다 중간 요약을 만들고, 중간 요약을 합쳐 최종 입력으로 쓴다(nanet 746744e `reduce_section_summaries` 이식). 마무리 단계는 이 입력을 한 번 만들어 문서 요약·소개글이 같이 쓴다.
14. **`<br>` 껍데기.** 두 군데를 고친다.
    - 본문 길이를 셀 때 `<br>` 태그를 뺀다(지금은 4자로 셈, `extractor.py:71`·`82`). 그러면 빈 표 격자 쪽은 50자 미만이 되어 7번 판정(fitz 0자 → OCR)을 탄다.
    - 채택 텍스트를 다듬는 `_clean_text` 에서 3개 이상 이어진 `<br>` 를 줄바꿈 하나로 줄인다. 실제 쓰레기 섹션(예: KCI_FI001930485 — 섹션 196개 중 172개가 `<br>` 반복, 본문의 96%)은 실제 본문과 같은 쪽에 섞여 있어 길이 판정만으로는 막히지 않는다. 확인된 피해 문서는 1건이다.
15. **ODL.** `image_output` 을 끈다(그림 저장 0건 — 쓰이지 않는 인코딩). nanet 5f8fb80 처럼 ODL 에 쪽수 비례 타임아웃을 두고, 넘으면 fitz 로 재저장한 PDF 로 한 번 더, 그래도 안 되면 fitz 추출로 폴백한다.
16. **추출 시간 상한과 타임아웃 정합.**
   - 추출 전체에 asyncio 데드라인(`INGEST_EXTRACT_DEADLINE`, 기본 2,700초)을 둔다. 넘으면 남은 쪽은 ODL 결과로 채택하고 `meta.extract_deadline_hit` 를 남긴다. VLM 60쪽 상한과 같은 방식이다. Celery 소프트 리밋 대신 코루틴 안 데드라인을 쓴다(함정 19).
   - 그 위에서 `INGEST_STAGE_TIMEOUT_EXTRACT` 를 14,400 → 3,600초로 줄인다. 관측 최대 추출은 2,785초(표본 27,000건)이고 3,600초를 넘은 건은 없다. 이론 최악은 60쪽 × 120초 × 재시도 2 이다.
   - 3,600초는 Celery `visibility_timeout`(7,200초) 안쪽이라 실행 중인 추출 메시지가 재전달되지 않는다. `job_runtime.py:55` 의 "visibility 의 2배" 주석도 실제 값에 맞게 고친다.
17. **ETA·실패 표시.** 잡 조회가 최근 1시간과 24시간 처리량을 함께 내고, ETA 는 24시간 처리량으로 계산한다. paused 잡은 ETA 를 내지 않는다(지금은 paused 인데도 554시간을 낸다). 남은 수에서 영구 실패(attempt 가 한도에 닿은 failed)는 뺀다. 1시간 기준 ETA 는 48시간 기준의 0.73~5.7배로 출렁였다. `/failures` 의 그룹 대표 메시지는 `max(last_error)` 대신 그룹 안에서 가장 흔한 메시지로 바꾼다(지금은 `not_found` 545건이 '섹션 없음'인데 15건뿐인 '카탈로그 row 없음'으로 보인다, `ingest_jobs.py:249-266`).

### 2.3 안전 — 중복 체인 차단

18. **실행 토큰.** 디스패처가 체인을 보낼 때마다 새 `run_token` 을 만들어 아이템 `meta.run_token` 에 적고 단계 태스크 인자로 넘긴다(`.si(item_id, run_token)`). `_run_stage` 는 다음이면 실행하지 않고 체인을 멈춘다(`celery.exceptions.Ignore`).
    - 토큰이 아이템의 현재 토큰과 다르다(stale 복구로 새 체인이 떴거나 재전달된 옛 메시지).
    - 아이템 체크포인트가 이미 이 단계를 지났거나 `done` 이다.
    - 락 경합으로 pending 으로 되돌렸다(지금은 `skipped` 를 반환해 체인이 다음 단계로 간다).
    - 토큰 없이 온 옛 메시지는 아이템에 토큰이 없을 때만 실행한다(배포 전 메시지 호환).
    - 그리고 PDF 가 있던 논문(`meta.pages > 0`)인데 추출 아티팩트가 없으면 초록으로 색인하지 않고 `StageError("artifact_missing")` 로 멈춘다. 초록 폴백은 PDF 없는 메타데이터 전용 논문만 쓴다.
    - DB 칼럼을 더하지 않는다(meta JSON 사용 — 기존 테이블 무변경 원칙).
    - **stale 판정을 '실행 중'과 '다음 단계 대기 중'으로 나눈다.** 지금 `_recover_stale`(`job_runtime.py:282-299`)은 단계가 끝난 시각(`updated_at`)부터 다음 단계의 실행 타임아웃(embed 1,200초·finalize 900초)을 잰다. 그래서 큐에서 기다리는 시간도 실행 시간으로 센다. 1번으로 `q_llm` 이 바빠지면 마무리를 기다리다 stale 로 오판돼 중복 체인이 열린다. `_run_stage` 가 시작할 때 `meta.stage_running`(단계 이름)과 시작 시각을 적고 끝날 때 지운다. stale 판정은 실행 중이면 그 단계 타임아웃, 대기 중이면 대기 상한(`DISPATCH_STALE_SECONDS`)으로 잰다.

## 3. 하지 않는 것

- **임베딩 512토큰 절단** — 생각보다 크다. 다만 이번 라운드에서는 고치지 않는다.
  - 근거: `EMBEDDING_MAX_LENGTH`(`config.py:100`)가 compose 에 `"512"` 고정값이다(`docker-compose.yml:58`, env 로 못 바꿈). BGE-M3 토크나이저 실측으로 한국어 본문은 글자당 0.544토큰, 512토큰 ≈ 940자다. 그런데 앞에 붙는 `[핵심 테마]` + `[섹션 요약]` 이 약 270토큰을 먹어 본문 자리는 약 440자다. 본문 청크 평균은 630자다.
  - 영향: 본문 청크의 50~60%가 잘리고, 본문 글자의 35~45%가 dense·sparse 어느 벡터에도 들어가지 않는다. 청크 뒤쪽에만 있는 수치·고유명사 질의의 재현율이 떨어지고, 같은 섹션 청크끼리 벡터가 비슷해진다. 1024 로 올리면 잘리는 청크가 약 9%로 준다.
  - 바꾸지 않는 이유: 바꾸면 새 벡터가 기존 약 620만 청크와 섞인다. 효과를 보려면 전부 다시 임베딩해야 한다. **그런데 `run_embed_index` 를 다시 돌리는 방식은 쓸 수 없다** — 마무리가 추출 아티팩트를 지워(`stages.py:813`) 논문이 초록으로 대체되고 기존 청크가 전부 지워진다. Milvus 본문과 PG 섹션 요약·테마로 다시 임베딩하는 전용 경로가 필요하다. 적재가 끝난 뒤 별도 라운드로 정한다.
- **문장 임베딩 이중 계산**(`stages.py:109`·`566`): 같은 문장을 두 번 임베딩하고 경계도 똑같이 나온다. 하지만 embed 단계 시간의 3~5%뿐이다. 1번 뒤 embed 칸이 GPU 일만 하게 되므로 미룬다.
- **kss 설치**: 의존성이 무겁고 줄바꿈 폴백으로 표·통계 문제를 막는다.
- **표 설명·문서 요약 과거분 재처리**: 본 적재가 끝난 뒤 따로 정한다.
- **같은 통권 PDF 가 논문 여러 개로 적재된 문제**: 매니페스트 데이터 문제라 이번 코드 변경과 별개로 목록만 남긴다.
- **gemma `--max-num-batched-tokens`**: 큐 대기가 평균 0.18초라 지금은 필요 없다.
