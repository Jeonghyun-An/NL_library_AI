## 0. 사용자 프롬프트 (paraphrase)

> 논문 검색은 데이터도 많고 분석이라는 취지에도 맞으니 도서관 대회 시연의 '킥'으로 삼자. 디비피아 AI 의 딥리서치처럼, 질문 하나를 받아 여러 단계로 논문을 찾고, 근거가 충분한지 스스로 점검해 다시 찾고, 인용이 달린 보고서까지 만들어 내는 에이전트를 넣고 싶다. 시간이 좀 걸려도 "실제 논문 탐색에 쓸 수 있는 전문 에이전트가 있다"는 인상을 줘야 한다. 진입은 `/deep-research` 슬래시 명령이고, 시연에서는 과정이 역동적으로 보여야 하며 평소에 써도 지루하지 않아야 한다.

spec(§0)은 이 요청을 설계 지침으로 읽었다 — **"시간이 오래 걸린다"는 변명이 아니라 사양이다.** 기다림을 숨기면 느린 챗봇이 되고 드러내면 일하는 전문가가 된다. 그래서 spec 은 이 기능의 값이 최종 보고서 못지않게 과정을 보여주는 화면에 있다고 봤다. 백엔드로 옮기면 그 화면이 쓸 과정을 남기는 구조(계획 승인·진행 기록·자기점검·한계 보고)가 설계의 뼈대가 된다. spec §10 권고대로 백엔드(round04a)와 화면(round04b)을 나눴고, **이 교본은 백엔드다.**

구현(Task 1~10)을 마치고 운영 서버에 올린 뒤의 흐름은 이랬다.

> (2) 서버에서 돌린 보고서 검증 결과를 붙여넣으며 — 작업하던 것 이어서 보자.

인용 무결성 검사(미해석 마커 0)는 통과했는데 하위질문 3개에 근거 10편을 모아 놓고 **절 1개·논문 1편**만 실린 보고서였다. 원인은 종합 프롬프트의 JSON 예시를 모델이 개수까지 베낀 것이었다(§4 Q6).

> (3) 이 드라이런 스크립트는 서버에서 그대로 붙여넣으면 되나? 그럼 커밋하고 배포까지 가자.

같은 잡의 체크포인트로 종합만 다시 돌려 고친 코드를 확인하고(§3-4), 커밋(`b6360b8`) → 이미지 빌드·푸시 → 서버에서 컨테이너 Recreate → 새 잡으로 재검증했다.

> (4) 완료노트 정리하고 커밋해 줘. 그다음 머지 전 리뷰를 지금 모델 그대로 최대 강도로 돌려 줘.

영역별 정적 리뷰와 적대적 검증을 돌렸다. 살아남은 발견 120건은 원인 약 18개로 묶였고, 그중 **취소한 잡이 `completed` 로 되살아나는 결함**을 비롯해 고칠 것은 고치고 나머지는 이유와 함께 이월했다(`2bac7ee`, §3-5).

> (5) 남은 작업(교본 포함)을 다 끝낸 뒤 main 으로 가자.

즉 **백엔드 구현 → 운영 라이브 검증 → 라이브에서만 드러난 종합 버그 수정 → 머지 전 리뷰로 잠복 결함 수정** 순서로 이어진 라운드다. 적재(인덱싱) 코드는 이 라운드에서 건드리지 않았다 — 대량 인덱싱이 운영에서 도는 중이기 때문이다.

### 1-1. 핵심 결정

| 결정 | 버린 대안 | 이유 |
|---|---|---|
| **실행 모델 = Celery(실행) + SSE(중계) + DB(영속)의 결합** | 동기 SSE / 순수 비동기 | 동기 SSE 는 2~3분 상한에 탭을 닫으면 소실된다. 순수 비동기는 시연에서 "일하는 모습"이 안 남는다. 결합이면 시연에선 실시간으로 보고, 평소엔 닫았다가 다시 연다 |
| **LangGraph 미도입** — 상태 dataclass + 명시적 async 함수 | LangGraph 그래프·체크포인터 | 분기가 "한 번 더 돌까"와 "승인 대기" 둘뿐이다. 시연 3주 전에 디버깅할 표면을 늘리지 않는다. 단계 함수를 나중에 노드로 그대로 꽂을 수 있게 짰다(Q1) |
| **진행 기록 2계층** — `research_steps`(Postgres, 굵게·영구) + Redis pub/sub(잘게·휘발) | 한 테이블로 진행 패널과 보고서를 겸함 | 입자가 충돌한다. 진행은 UPDATE 되고 이력은 append-only 라 섞으면 감사 기록으로도 못 쓴다(Q4) |
| **인용 2갈래** — 대표 논문 요약은 구조적 인용, 도입·향후 과제는 `[E#]` 마커 + 전수 검증 | 모든 인용을 모델 마커로 | 모델이 고를 일이 없는 곳은 코드가 정한다. 다만 **요약 문장의 논문 배정은 여전히 모델 추론**이다(Q5) |
| **`status` 와 `stage` 분리 + 체크포인트(`state_snapshot`) + `POST /retry`** | `status` 하나로 관리 | `failed` 하나로는 어디서 죽었는지 모른다. 탐색이 끝났으면(`stage=explored`) 재시도가 탐색을 건너뛰고 종합부터 한다(Q3) |
| **상태 전이는 전부 조건부 UPDATE** | ORM 객체에 대입 후 커밋 | 취소는 API 프로세스가, 진행은 워커가 찍는다. 조건 없이 쓰면 늦게 쓴 쪽이 이긴다 — 리뷰에서 high 로 잡혔다(Q9) |
| **한계 섹션을 보고서에 노출** | 자기점검을 내부 제어로만 사용 | 코퍼스는 구멍이 많다. 숨기면 들키고 드러내면 강점이 된다(Q19) |
| **딥리서치 전용 큐·워커**, 단 `RESEARCH_QUEUE` 기본값은 `q_llm` | 적재 요약과 같은 `q_llm`·`celery-llm` 에 영구히 얹기 | 같은 FIFO 면 계획 요청이 요약 수십 건 뒤에 선다. 긴 실행이 적재 슬롯을 쥐면 슬롯을 기다리던 적재 아이템이 stale 복구돼 중복 체인이 열린다(함정 16번). 전환은 인덱싱 뒤(Q13) |

### 1-2. 파이프라인과 상태 전이

```text
POST /api/research ─────▶ tasks.plan_deep_research   (RESEARCH_PLAN_QUEUE)
  created → planning → awaiting_approval              stage=planned, plan=[하위질문…]

POST /api/research/{id}/approve {plan?} ─▶ tasks.run_deep_research   (RESEARCH_QUEUE)
  approved → running
    하위질문마다: 검색(리랭크+피인용 가중) → 자기점검 → insufficient 면 검색어 바꿔 재검색(≤ max_recheck)
    ── 체크포인트: stage=explored, state_snapshot 저장 ──
    절마다 LLM 1회(실패하면 그 절만 1회 재시도)로 종합 → 인용 검증 → report 저장
  → completed (stage=synthesized)

실패 → failed ──POST /retry──▶ queued → running   (stage=explored 면 종합부터)
created·planning·awaiting_approval·approved·queued·running ──POST /cancel──▶ canceled
```

워커가 선점할 수 있는 상태는 `approved`·`queued` 둘뿐이다(`RUNNABLE_STATUSES`). API 의 승인·재시도와 워커의 선점이 같은 상수를 보게 묶어 둔 이유는, 한쪽이 다른 값을 쓰면 워커가 그 잡을 영원히 `skipped` 로 건너뛰기 때문이다. 멈춘 잡은 되살리지 않고 **회수만** 한다 — beat 10분마다 `reap_stale_research` 가 45분(하드 리밋 35분보다 길게) 넘은 `planning`·`running` 잡을 `failed` 로 떨어뜨리고, 다시 돌리는 것은 사용자의 `POST /retry` 다(spec §6 의 자동 재개는 구현하지 않았다).

### 1-3. 인용 2갈래 — 설계와 구현 시 변경

| | 구조적 인용 | 마커 인용 |
|---|---|---|
| 자리 | 절의 `대표 논문 요약`(불릿 = 논문) | 절의 `도입 문단`·`향후 과제` |
| 코드가 정하는 것 | 절 구성(소제목 = 하위질문), 실을 논문(하위질문 안 순위 앞 5편), 칩(`evidence: ["E12"]`), 서지(제목·저자·연도는 DB 에서) | 없음 — 모델이 `[E3]` 를 단다 |
| 검증 | 요약 속 마커는 `strip_markers` 로 전부 걷어낸다(칩이 이미 인용을 가짐) | `bind_markers` 가 **그 절에 준 번호로만** 전수 검증. 없는 번호·해석 못 한 표기는 지우고 한계에 보고 |
| 남은 추론 | **요약 문장이 그 논문 내용인가** — 절의 논문 최대 5편 발췌를 한 호출에 넣고 번호별로 받는다 | 문장과 근거의 의미적 일치는 검사하지 않는다 |

spec 원안은 "불릿을 그 논문의 근거만 넣고 생성하면 인용이 구조로 정해진다"였다. 첫 구현은 절·논문 선택까지 모델에게 맡겨 그 전제가 깨졌고(§0 의 절 1개 버그), `b6360b8` 에서 구성을 코드로 옮긴 뒤에도 요약은 논문별 호출이 아니라서 **구조적 인용은 절반만 성립한다.** 논문별 호출은 호출 수가 절당 최대 5배라 이번에 하지 않았다(spec §4-1 구현 시 변경).

### 1-4. 진행 기록 2계층 — 실제로 흐르는 것

| 계층 | 저장소 | 실제 내용 | 수명 |
|---|---|---|---|
| 의미 있는 단계 | `research_steps` | `plan` 1행 + 하위질문마다 `search` 1행(재검색 라운드는 같은 행에 합침) + `synthesize` 1행. 기본 파라미터(하위질문 6)에서 8행 | 영구 |
| 실시간 이벤트 | Redis `research:{job_id}` | `search`(검색 라운드마다) · `critique`(자기점검 라운드마다) · 종료(`done`·`failed`·`canceled`) | 휘발 |

재접속하면 SSE 가 `snapshot`(steps 뼈대)을 먼저 보내고 그 뒤를 Redis 에서 이어받는다. 보고서 화면의 탐색 경로 정본은 `research_steps` 가 아니라 `report.trail` 이다 — `research_steps` 는 재시도마다 행이 쌓이는 실행 이력이고, `trail` 은 그 보고서를 만든 시도의 탐색이다.

### 1-5. 코퍼스 제약

spec 작성 시점(2026-09-21) 운영 실측으로 인덱싱 완료 논문 72,054건 중 **97%가 2002~2009년**이고, 인덱싱이 오래된 것부터 도는 속도로 추산하면 **2020년대는 대회(10월 초 추정) 때까지 한 편도 안 들어온다**(spec §1-2). 그래서 두 가지를 설계에 넣었다.

- **수록 범위는 고정 문구로 박지 않는다.** 실행마다 `library_catalog` 에서 재서(`_corpus_range`) 보고서 `range` 에 싣는다.
- **한계 섹션이 코퍼스 빈틈을 스스로 밝힌다.** 시연 분야(문헌정보학 등) 우선 인덱싱은 코드와 독립인 운영 작업이다(spec §8).

조건: 질문 `공공도서관 서비스 품질 평가는 어떻게 연구되어 왔는가`, 리허설용 축소 파라미터 `max_subquestions=3 · max_recheck=1 · per_subq_top_k=8`, 종합 모델 gemma-3-12b. 딥리서치가 `q_llm`·`celery-llm` 에서 돌던 구성이다. **이 실측은 머지 전 리뷰 반영 이전 코드(`b6360b8`)다** — 반영분은 아직 운영에 배포하지 않았다(§3-6). 명령은 사용자가 서버에서 실행했고, 게이트웨이 영향을 빼려고 fastapi 컨테이너 안에서 앱에 직접 붙었다.

```bash
docker exec nl-lib-fastapi curl -s -X POST http://localhost:8000/api/research/<job_id>/approve -H 'Content-Type: application/json' -d '{}'

# Step 6 — 진행 중계: snapshot → search/critique → 유휴 15초마다 ": ping" → done 후 닫힘
```

Step 7 은 인용 무결성(미해석 마커)에 더해 **구성**을 본다. 앞의 것만으로는 §0 의 절 1개 버그를 잡지 못했다.

```bash

docker exec nl-lib-fastapi curl -s http://localhost:8000/api/research/<job_id> | python -c "import json,sys,re; d=json.load(sys.stdin); r=d['report']; ids=set(r['evidence']); used=set(); [used.update(re.findall(r'\[(E\d+)\]', s['intro'])) for s in r['sections']]; [used.update(re.findall(r'\[(E\d+)\]', f['text'])) for s in r['sections'] for f in s['future']]; print('근거', len(ids), '사용된 마커', len(used), '미해석', used-ids); print('한계', r['limitations'])"

# Step 7 — 구성 검사. 절 수 = 근거가 있는 하위질문 수, 요약 속 마커 = [] 여야 한다

cited={e for s in r['sections'] for p in s['papers'] for e in p['evidence']}

# Step 8 — 같은 워커 프로세스에서 두 번째 잡: Step 4~7 반복. "attached to a different loop" 가 없어야 한다

# Step 9 — 취소(running 중에)
```

## 4. 면접식 Q&A

**Q1. 에이전트 루프인데 왜 LangGraph 를 쓰지 않았나?**
A. 루프가 `계획 → 검색 → 점검 → 재검색 → 종합` 이고 분기는 "한 번 더 돌까"와 "사용자 승인 대기" 둘뿐이다. 이 정도는 상태 dataclass(`ResearchState`)와 명시적 async 함수로 충분히 표현된다. 승인 대기도 새 런타임이 필요한 게 아니라 잡이 `awaiting_approval` 로 멈췄다가 승인 API 가 다시 큐에 넣는 것이고, LangGraph 체크포인터가 해 줄 "중간부터 재개"는 `stage` + `state_snapshot` 두 컬럼으로 DB 에 뒀다. 넣으면 상태 스키마·노드 등록·체크포인터라는 개념이 붙어 **시연 3주 전에 디버깅할 표면이 하나 는다.** 대신 갈아끼울 수 있게 짰다 — 각 단계는 상태를 받아 갱신하는 함수이고, `runner.explore_subquestion` 은 검색·점검·중계를 `explore_fn`·`critique_fn`·`emit` 인자로 주입받아 Celery·Redis·Milvus 없이 테스트된다. 분기가 다섯 개 이상이 되거나 중단·재개가 복잡해지면 그 함수들을 노드로 그대로 꽂는다(spec §2-2). (본문 §2.5·§2.35)

**Q2. 실행 모델을 왜 Celery + SSE + DB 의 결합으로 했나?**
A. 대안 둘이 각각 요구 하나씩을 못 채운다. 동기 SSE 는 요청 수명에 묶여 2~3분 상한이 있고 탭을 닫으면 작업이 사라진다. 순수 비동기(끝나면 알림)는 시연에서 "에이전트가 일하는 모습"이 안 남는다 — 요청이 과정을 보여 달라고 했다. 결합이면 작업은 Celery 워커가 끝까지 돌리고, 진행은 Redis pub/sub → SSE 로 실시간 중계하고, 결과·단계는 Postgres 에 남는다. 시연에선 실시간으로 보고, 평소엔 닫았다가 다시 열면 `research_steps` 로 뼈대를 복원한 뒤 이어받는다. 경쟁 제품(디비피아)도 같은 비동기 모델이다. (본문 04 챕터 머리·§2.37)

**Q3. `status` 와 `stage` 를 왜 나눴고, 재시도는 어떻게 동작하나?**
A. `status` 는 "지금 무슨 상태인가", `stage` 는 "어디까지 끝냈는가"다. 한 컬럼이면 `failed` 하나로 계획에서 죽었는지 종합에서 죽었는지 구분되지 않아 매번 탐색부터 다시 돈다. 워커는 탐색을 마치면 `stage=explored` 와 `state_snapshot`(탐색이 끝난 `ResearchState`)을 체크포인트로 남긴다. 종합이 실패하면 잡은 `failed` 가 되지만 둘은 그대로다. `POST /retry` 는 `failed` 를 `queued` 로 바꿔 다시 큐에 넣되 **`stage`·`state_snapshot` 을 건드리지 않는다** — 코드 docstring 의 표현으로 "이 엔드포인트의 전부"다. 워커는 `stage == "explored"` 면 스냅샷을 되살려 종합부터 한다. 워커가 선점하는 상태가 `approved`·`queued` 뿐이라, retry 가 없으면 `failed` 잡은 아무도 다시 집지 않고 체크포인트는 쓰기만 하는 컬럼이 된다. 계획 단계에서 실패한 잡(plan 없음)은 재시도해도 할 게 없어 409 로 "새 잡을 만든다"고 알린다. 한계도 있다 — 탐색 중 시간 초과는 하위질문 단위 체크포인트가 없어 retry 가 탐색을 처음부터 다시 돈다. 재개 경로는 단위 테스트로 세 구간을 덮었지만 **라이브에서는 한 번도 돌지 않았다.** (본문 §2.1·§2.36 ⑥·§2.37 ⑥)

**Q4. 진행 기록을 왜 두 계층으로 나눴나? 보고서의 탐색 경로는 어디서 오나?**
A. 한 테이블로 진행 패널과 보고서를 겸하면 입자가 충돌한다. 패널은 잘고 빈번한 것(카운터, "검색 중")을, 보고서는 굵고 적은 것을 원한다. 진행은 `running→done` 으로 UPDATE 되고 이력은 append-only 라 섞으면 감사 기록으로도 못 쓴다. 그래서 굵은 단계는 `research_steps`(영구), 잔이벤트는 Redis pub/sub(휘발)으로 나눴다. 구현에서 step 은 하위질문당 1행이고 재검색 라운드는 같은 행의 `result.queries` 에 누적된다. 자기점검은 행이 아니라 `search` 행의 `verdict`·`note` 와 SSE `critique` 이벤트로 나간다. 보고서의 탐색 경로는 `research_steps` 가 아니라 종합 시점에 만든 `report.trail` 이다 — `research_steps` 는 재시도마다 행이 쌓이는 실행 이력이라 탐색 도중 실패한 잡을 재시도하면 같은 하위질문의 `search` 행이 두 벌 남는다. 보고서에는 그 보고서를 만든 시도만 실려야 한다. 계획도 `plan` step 의 `result` 는 LLM 원안이고 사용자가 고친 승인본은 `research_jobs.plan` 에만 있다. (본문 §2.1, 04 챕터 머리 "진행 기록은 2계층이다")

**Q5. 구조적 인용과 마커 인용은 무엇이 다르고, 구조적 인용의 한계는 무엇인가?**
A. 구조적 인용은 모델이 인용을 고를 일이 없게 만든 것이다. `대표 논문 요약` 은 불릿 하나가 논문 하나이고, 어느 절에 어떤 논문이 실리는지(하위질문 근거의 순위 앞 5편), 불릿의 칩(`evidence: ["E12"]`), 제목·저자·연도(DB 서지)를 전부 코드가 정한다. 마커 인용은 여러 논문을 가로지르는 `도입`·`향후 과제` 에 쓴다 — 모델이 `[E3]` 를 달고 `bind_markers` 가 전수 검증한다. 한계는 **요약 문장의 배정이 여전히 추론**이라는 점이다. 요약은 논문별 호출이 아니라 절의 논문 최대 5편 발췌를 한 프롬프트에 넣고 `{"summaries": {"E1": …, "E3": …}}` 로 번호별로 받는다. 모델이 E1 요약에 E2 내용을 섞어 써도 잡는 검사가 없다. 칩이 가리키는 논문은 확실하지만 그 옆 문장이 그 논문 내용인지는 보장되지 않는다. 논문별 호출은 호출 수가 절당 최대 5배(기본 파라미터면 6회 → 최대 30회)이고 종합 LLM 은 대량 인덱싱의 요약 단계와 서버를 나눠 쓴다. 그래서 이번엔 하지 않고 오배정 비율 실측과 함께 이월했다. 그 전까지는 "요약도 구조로 정해진다"고 설명하지 않는다. (본문 §2.7·§2.28 ③)

**Q6. 라이브에서 보고서가 절 1개·논문 1편만 나왔다. 원인은? 왜 무결성 검사는 통과했나?**
A. 원인은 **모델이 프롬프트 JSON 예시의 개수를 베낀 것**이다(함정 15번). 첫 종합은 보고서 전체를 한 번의 호출로 맡겼고, 출력 예시(`d537183` 의 `research_synthesize.yaml`)는 배열마다 항목이 하나였다.

```text
  {"sections": [
     {"heading": "하위질문을 소제목으로 다듬은 문장",
      "intro": "이 주제의 흐름을 설명하는 2~4문장. 문장마다 [E#] 를 답니다.",
      "papers": [{"cnts_id": "근거의 cnts_id", "summary": "이 논문이 무엇을 했고 무엇을 주장하는지 2~3문장"}],
      "future": [{"text": "남은 과제 한 문장 [E#]."}]}
  ]}
```

gemma-3-12b 는 이것을 형식이 아니라 개수까지 포함한 견본으로 따랐다. 더 근본적으로는 어느 절·어느 논문을 실을지를 모델에게 맡긴 설계가 spec §4-1("인용이 구조로 정해진다")을 이미 어기고 있었다. Step 7 의 검사는 "본문의 마커가 전부 근거에 있는가"만 봤다 — 절 1개·논문 1편짜리 보고서도 미해석 마커는 0이다. **무결성만 보고 구성(입력 대비 출력 개수)을 보지 않았다.** 단위 테스트는 가짜 LLM 응답을 쓰므로 모델의 이런 습성을 원리상 못 본다. 고친 방식은 구성을 코드로 옮긴 것이다 — 하위질문마다 호출 1회, 소제목·논문 목록은 코드가 정하고, 모델에게는 채울 칸이 정해진 출력만 받는다(프롬프트: "summaries 에는 다음 번호를 빠짐없이 하나씩 키로 넣으세요: E1, E3"). 빠뜨린 칸은 코드가 세어 한계로 보고하고, Step 7 에 구성 검사를 추가했다. (본문 §2.27·§2.28 ①②)

**Q7. 모델이 없는 번호나 `[E1, E2]` 같은 묶음 표기를 내면 어떻게 검증하나?**
A. 모델은 "`[E3]` 형태만" 지시를 어긴다. 첫 구현은 `\[(E\d+)\]` 단일형만 인식해서 `[E2, E99]` 속의 없는 번호가 검증도 제거도 안 된 채 본문에 실렸다. 지금은 괄호 하나(전각 `［］`·`【】` 포함)를 통째로 잡아 안을 해석한다. 먼저 인용처럼 생겼는지 본다 — 영문자·숫자·소수점에 붙지 않은 `E` 뒤 숫자만 인용이라 `[ICE 2019]`·`[표 1]`·`[1.2e3]` 는 건드리지 않는다. 그다음 쉼표·세미콜론 목록과 범위(`[E3-E5]`)를 읽고 0패딩(`E01`→`E1`)·소문자를 정규화한다. 유효한 번호만 표준형 `[E#]` 로 다시 쓰고, 없는 번호는 지운 뒤 **1건부터** 한계에 "그 절의 근거에 없는 번호를 가리킨 인용 표기 N건을 본문에서 제거했다"로 적는다. 범위의 사이 번호는 준 것만 싣고 없는 것은 세지 않는다 — 모델이 쓴 건 끝점뿐이라 사이를 지어낸 것으로 보고하면 과장이다. 읽을 수 없는 표기(`[E1 참조]`)는 원인이 달라(프롬프트 형식 문제) 따로 센다. 가장 중요한 변경은 **검증 집합을 그 절에 준 번호로 한정**한 것이다. 번호가 E1…En 으로 연속 발급되므로 전역 집합으로 검증하면 모델이 지어낸 작은 번호는 거의 다 통과해, 본 적 없는 논문을 가리키는 칩이 생긴다. (본문 §2.7·§2.28 ⑧)

**Q8. 대표 논문 요약에 붙은 `[E7]` 은 왜 검증하지 않고 지우나?**
A. 드라이런에서 모델이 시키지 않았는데도 요약 끝에 `[E7]` 을 달았다. 요약 자리는 인용이 불릿의 논문으로 이미 정해져 있고 칩도 코드가 붙인다. 검증해서 유효한 번호를 남겨도 칩과 중복이고, 지어낸 번호는 `bind_markers` 를 거치지 않는 필드라 그대로 화면에 나간다. 그래서 `strip_markers` 로 묶음·전각을 포함해 전부 걷어내고 프롬프트에도 금지를 적었다. 일반 원칙은 "검증을 거치지 않는 필드에 모델 출력이 들어가면 그 필드도 정리한다"이다. 마커를 걷고 나서 문장이 남지 않으면(`"[E1]."`) 빈 요약으로 두고 "요약을 생성하지 못한 논문 N편"으로 센다. (본문 §2.7·§2.28 ④)

**Q9. 취소한 잡이 `completed` 로 되살아났다. 원인은? 라이브 검증은 왜 못 잡았나?**
A. 취소는 API 프로세스가 조건부 UPDATE 로 `canceled` 를 찍는데, 워커는 메모리의 ORM 객체에 상태를 대입해 커밋했다. 리뷰 반영 전(`2bac7ee^`) 워커의 종합 뒤 코드다.

```python
                report = await synthesize(state)
                job.report = report
                _set_stage(job, "synthesized")
                job.status = "completed"
```

ORM 은 바뀐 속성을 `UPDATE research_jobs SET status=… WHERE id=…` 로 내보낸다 — **상태 조건이 없어서** 그 사이 커밋된 `canceled` 를 덮는다. 계획 태스크의 `job.status = "awaiting_approval"` 도 같았다. 취소 확인도 하위질문 루프 맨 앞에만 있어서 마지막 하위질문·종합·계획 중에는 아예 보지 않았다. 라이브 Step 9 는 **하위질문 0 을 탐색하는 중에** 취소했다. 뒤에 하위질문이 남아 있었으니 다음 루프 머리의 확인에 걸려 잡 상태를 쓰지 않고 멈췄다 — 확인이 있는 유일한 구간을 밟아서 통과한 것이다. 고친 방식은 워커·API 의 모든 전이를 기대 상태를 `WHERE` 에 건 조건부 UPDATE(`_transition`)로 바꾼 것이다. 0행이면(누가 먼저 바꿨다) 결과를 버리고 멈춘다(`_stopped`). 종합은 절마다 LLM 호출 직전에 취소를 확인해 `SynthesisCanceled` 로 빠진다. 교훈은 "통과한 라이브 검증이 어느 경로를 밟았는지"를 적어야 한다는 것이다 — 완료노트에 "탐색 중 취소만 본 것"이라고 한정해 적었다. 종합·계획 중 취소는 단위 테스트로만 확인했고 재배포 뒤 라이브로 다시 본다. (본문 §2.36 ②③ — `_transition` 코드와 취소를 보는 네 곳, API 쪽 §2.37 ①, 종합 쪽 §2.28 ⑦)

**Q10. Celery 에 소프트 리밋(30분)이 있는데 왜 잡 안에 따로 데드라인을 뒀나?**
A. **소프트 리밋은 asyncio 코루틴 안에서 믿을 수 없다**(함정 19번, 리뷰에서 재현). 이유가 둘이다. (1) 소프트 리밋은 시그널 핸들러가 메인 스레드에서 `SoftTimeLimitExceeded` 를 던지는 방식인데, 메인 스레드가 LLM 응답을 await 하느라 이벤트 루프의 `select` 안에 있으면 예외가 코루틴이 아니라 `asyncio.run` 밖으로 튄다. 코루틴 안의 정리 코드가 하나도 돌지 않아 잡·step 이 `running` 에 남고 하드 리밋(35분)에 프로세스째 죽는다. (2) `SoftTimeLimitExceeded` 는 `Exception` 의 하위라, 동기 리랭크 도중 걸리면 `pipeline.py` 의 리랭크 폴백 `except Exception` 이 삼키고 경고 한 줄만 남긴 채 계속 돈다. 그래서 잡 본문을 `asyncio.timeout(JOB_DEADLINE)`(25분 = 소프트 리밋 − 300초)으로 감쌌다(`_within_deadline`). 데드라인은 await 지점에서 `CancelledError` 로 끊으므로 코루틴 안에서 확실히 잡힌다. `deadline.expired()` 로 우리 데드라인과 내부에서 올라온 다른 `TimeoutError` 를 가른다. 소프트 리밋은 데드라인이 못 끊는 동기 구간용 백스톱으로 남겨, `asyncio.run` 밖에서 잡히면 새 루프·새 엔진으로 같은 정리를 한다. 리랭크 폴백은 리랭커가 실제로 내는 실패(`RuntimeError`·`OSError`·`ValueError`·`ImportError`)만 잡게 좁혔다. 회수 임계도 30분 → 45분으로 올렸다 — 하드 리밋보다 짧으면 아직 살아서 쓰는 워커의 잡을 회수하고, 그 뒤 retry 한 새 실행과 옛 실행이 같은 잡에서 부딪힌다. (본문 §2.36 ⑦ — `_within_deadline` 코드와 네 겹의 시간 상한, 리랭크 폴백 §2.18)

**Q11. 워커의 트랜잭션 하나가 FastAPI 재시작을 멈출 수 있다는 건 무슨 경로인가?**
A. 함정 18번이다(잠복 — 리뷰에서 코드로 찾았다). FastAPI lifespan 은 기동마다 `ALTER TABLE library_catalog ADD COLUMN IF NOT EXISTS …` 를 돈다. 이 문장은 컬럼이 이미 있어도 먼저 ACCESS EXCLUSIVE 잠금을 잡으려 한다. 그런데 `explore()` 가 서지를 조회하면 SQLAlchemy 세션이 트랜잭션을 열고 `commit` 전까지 닫지 않는다. 워커는 그 상태로 critic LLM 응답을 수십 초 기다렸다. 그 사이 FastAPI 를 재시작하면 `ALTER` 가 워커의 공유 잠금을 기다리고, PostgreSQL 은 **대기 중인 배타 요청 뒤로 새 조회를 줄 세운다** — 검색·서지 조회·적재 쓰기가 전부 멈춘다. 고친 방식은 "LLM 을 기다리기 전에 커밋"이다. 러너는 `explore_fn` 직후 `db.commit()`, 취소 확인(`_current_status`)은 읽고 바로 커밋, 계획 태스크는 LLM 을 부르기 전에 커밋한다. 의심되면 `pg_stat_activity` 에서 `state = 'idle in transaction'` 을 찾는다. 근본 원인인 lifespan 의 ad-hoc `ALTER` 블록 제거는 스키마 경로 정리(함정 14번)와 같은 일이라 대회 이후다. (본문 §2.35 ①·§2.38)

**Q12. Celery 에서 async 코드를 돌릴 때 두 번째 잡에서만 터지는 버그는 무엇이고 어떻게 막았나?**
A. `db/postgres.py` 의 `AsyncSessionLocal` 은 FastAPI 의 장수 이벤트 루프 하나를 전제한 풀링 엔진이다. Celery 는 잡마다 `asyncio.run` 으로 루프를 새로 만들고 닫는데, 풀은 닫힌 루프에 묶인 asyncpg 커넥션을 들고 있다가 다음 잡에 건넨다 → `attached to a different loop`. **첫 잡은 성공하므로 리허설 한 번으로는 통과한다.** 그래서 잡 하나짜리 엔진(`_job_engine`, `pool_size=5`)을 만들어 쓰고 끝에서 `dispose()` 로 루프가 죽기 전에 정리한다. 잡 전체를 루프 하나로 돌리고 단계마다 `asyncio.run` 을 부르지 않는다. Redis 중계도 같은 이유로 클라이언트를 모듈 전역에 두지 않고 publish 마다 만든다(전역이면 두 번째 잡부터 `Event loop is closed`). 라이브 Step 8 이 이 회귀를 보는 단계다 — 같은 워커 프로세스(`ForkPoolWorker-2`)가 잡 2개(루프 4회)를 처리했고 오류가 없었다. (본문 §2.36 ①·§2.34 ②)

**Q13. 전용 워커를 만들어 놓고 왜 `RESEARCH_QUEUE` 기본값은 `q_llm` 인가? 전환 순서는?**
A. 전용 워커가 필요한 이유부터 보면, 딥리서치가 적재 요약과 같은 `q_llm` FIFO 에 있으면 0.6초짜리 계획 요청이 요약 수십 건 뒤에 선다. 게다가 `celery-llm` 은 GPU·모델 캐시가 없어 탐색의 BGE-M3·리랭커를 recreate 마다 새로 받고 CPU 로(그것도 fp16 으로) 돌렸다(함정 17번). 그래서 `celery-research`(GPU·`/data/models/.hf-cache:/models`·`--concurrency=1`·`-Q q_research`)와 계획 전용 경량 워커 `celery-research-plan`(`--concurrency=2`)을 compose 에 넣었다. 그런데도 기본값을 `q_llm` 으로 둔 것은 **배포 순서의 안전장치**다. 코드만 먼저 내보내면(기존 컨테이너 env 그대로 Recreate) `RESEARCH_QUEUE` 가 없으니 지금처럼 `celery-llm` 이 받는다. 기본값이 `q_research` 였다면 fastapi 만 새 이미지로 뜨는 순간 잡이 소비자 없는 큐에 쌓인다. 전환은 compose 의 fastapi·딥리서치 워커 서비스 env 에만 `RESEARCH_QUEUE: q_research` 를 둔다. `x-common-env` 에 두면 적재 워커 전부의 설정이 바뀌기 때문이다. 전환을 인덱싱 뒤로 미루는 이유는 함정 16번이다. 앱 서비스가 모두 같은 `:latest` 라 스택 업데이트 한 번이 도는 적재 워커를 전부 재생성하고, 끊긴 아이템은 stale 복구와 브로커 재전달이 **둘 다** 돌아 논문의 **PDF 본문 청크가 초록 청크로 덮일 수 있다.** 그래서 적재 워커는 in-flight 가 0 일 때만 재생성한다 — 인덱싱이 끝난 뒤, 또는 적재를 pause 해 비운 뒤다. concurrency 1 의 대가는 실행이 직렬이라는 것이다. 두 번째 잡은 `approved` 로 최대 25분 기다린다. 계획까지 같은 슬롯이면 새 질문이 `created` 로 멈춰 계획조차 안 뜨므로 계획 큐를 나눴다. (본문 §2.32·§2.39 — 복구 경로가 겹치는 과정과 두 단계 배포 순서)

**Q14. 과도기 구성에서 승인이 429 를 내는 이유와 구현은?**
A. 전환 전(`RESEARCH_QUEUE` 가 적재 큐)에는 딥리서치 실행이 `celery-llm` 슬롯 4개 중 하나를 잡마다 최대 25분 쥔다. 여럿이 쥐면 요약·마무리를 기다리는 적재 아이템이 단계 타임아웃을 넘겨 stale 복구되고, 컨테이너를 끊지 않아도 함정 16번의 덮어쓰기 경로가 열린다(리뷰에서 이산 사건 모델로 재현). 그래서 `_to_run_queue` 가 `RESEARCH_QUEUE` 가 적재 큐일 때만 실행 슬롯을 센다. `approved`·`queued`·`running` 잡이 1건이라도 있으면 승인·재시도를 429 로 돌려보내고 상태는 그대로 둔다. `running` 만 세면 몰아서 승인한 잡이 전부 통과하므로 대기 상태도 센다. 센 뒤 전이하는 사이의 경쟁은 `pg_advisory_xact_lock` 으로 줄 세운다. 이건 몰아서 승인하는 사고를 막는 안전장치일 뿐이고, 규칙은 **적재가 `running` 인 동안 운영 딥리서치를 돌리지 않는 것**이다(pause → in-flight 0 확인 뒤, 런북 §8). 전용 워커로 넘기면 적재 슬롯을 먹지 않으므로 상한이 없다. (본문 §2.37 ⑤)

**Q15. 피인용 수를 순위에 어떻게 반영했나? 왜 그대로 쓰지 않나?**
A. 생값으로 쓰면 오래된 논문이 무조건 이긴다. 2002년 논문은 20여 년을 쌓았고 2024년 논문은 몇 년뿐이라, "최근 동향"을 물어도 2000년대 초 논문만 올라온다. 그래서 **연간 피인용** `kci_citations / (올해 − 발행연도 + 1)` 로 정규화하고, 리랭킹 점수를 주로 해 `rerank × (1 + weight × log1p(연간 피인용))` 으로 얹는다(`citation_weight` 기본 0.2). `log1p` 로 감쇠하는 이유는 영향력이 100배라고 점수가 100배가 되면 의미 유사도가 사라져 "많이 인용된 논문 목록"이 되기 때문이다. 혼합값은 `rank_score` 로 따로 두고 순위에만 쓴다. 1.0 을 넘을 수 있어서다(리랭크 0.92 인 2024년 논문이 40회 인용됐으면 2026년 기준 0.92 × (1 + 0.2 × ln 14.33) ≈ 1.41) — `score` 에 덮으면 화면이 유사도 "141%" 를 그리고 생 리랭크 점수는 되찾을 수 없다. 정규화는 순위에만 쓰고, 근거 서지(`meta.kci_citations`)에는 생 피인용 수를 그대로 실어 화면이 그 값을 보여 줄 수 있게 한다. (본문 §2.6·§2.20)

**Q16. 메타청크와 보강 청크는 왜, 그리고 왜 리랭크 전에 빼나?**
A. 메타청크(`chunk_idx = -1`)는 "제목: … | 기관: … | 초록: …" 서지 덩어리다. `doc_scope="paper"` 필터를 통과하고 제목·초록을 품어 주제형 하위질문에서 오히려 점수가 잘 나온다. 그대로 두면 보고서가 서지 덩어리를 "발췌"로 인용하고 critic 에게도 그게 근거 본문으로 들어간다. 적재가 논문 뒤에 붙이는 보강 청크도 같다 — `[표 설명]`·`[그림 설명]` 은 LLM·VLM 이 쓴 문장이고 `[키워드]` 는 LLM 생성일 수 있다. `[초록]` 은 원문이지만 같은 문장이 쪽수 달린 본문 청크에 이미 있고, 메타청크처럼 주제형 질의에서 본문 대목을 밀어낸다. 이것들이 근거에 들면 인용칩이 모델이 쓴 문장이나 초록을 "p.0" 원문 대목처럼 띄운다. 그래서 쪽수 0 이면서 그 네 라벨로 시작하는 청크를 뺀다(`is_source_passage`). `[표]` 는 추출 본문의 표 원문이라 수치 근거로 남긴다. 라벨과 쪽수 0 을 함께 요구하는 이유는, 쪽수 0 만으로는 첫 쪽 본문(PyMuPDF 쪽 번호는 0 부터)과 구별되지 않기 때문이다. 처음에는 파이프라인이 `top_k` 로 자른 **뒤에** 걸러서 걸러진 수만큼 결과가 조용히 줄었다. 리뷰 뒤 `pipeline.search` 에 `chunk_filter` 인자를 추가해 리랭크 전에 거른다. 버릴 청크에 cross-encoder 연산도 쓰지 않는다. (본문 §2.18·§2.20)

**Q17. 탐색 검색에서 쿼리 재작성과 메타 필터를 왜 껐나?**
A. 둘 다 도서 검색용 전처리이고, 하위질문을 몰래 바꾸는데 그 사실이 탐색 경로에 남지 않는다. 쿼리 재작성 프롬프트는 "제목·저자명은 쿼리에 넣지 말라"는 도서 추천 규칙이라 "부르디외 문화자본론을 적용한 국내 독서격차 연구" 같은 하위질문에서 고유명사를 떨어뜨린다. 메타 필터는 `db` 를 넘기면 LLM 이 날짜 조건을 뽑는데, 하위질문의 사건 연도("2006년 도서관법 개정의 영향")를 발행연도 조건으로 바꿔 그 뒤에 나온 연구를 전부 뺀다. 러너는 검색 직전 문자열을 `subq.queries` 에 남기므로, 켜 두면 사용자에게 보이는 탐색 경로가 실제로 보낸 적 없는 쿼리를 기록해 0건 하위질문을 사후에 진단할 수 없다. 그래서 `use_rewrite=False`·`use_metadata_filter=False` 로 부르고, 계획 프롬프트가 처음부터 "그 자체로 논문 검색어가 될 만큼 구체적인" 하위질문을 내게 했다. `generate_answer=False` 도 같은 맥락이다. 탐색은 기본 파라미터로 한 잡에 6~24회 도는데, 거기서 답변 생성(확장+생성)을 하면 결과를 전부 버리면서 공유 GPU 를 문다. 이번에 `pipeline.search` 에 새로 넣은 인자 셋(`generate_answer`·`use_metadata_filter`·`chunk_filter`)은 모두 기본값이 기존 동작이라 논문 검색 화면은 그대로다. (본문 §2.18·§2.20)

**Q18. critic 판정을 못 읽으면 왜 `sufficient` 로 떨어뜨리나? 그러면 점검이 꺼진 걸 어떻게 아나?**
A. `insufficient` 로 두면 파싱이 깨질 때마다 재검색이 `max_recheck` 까지 돌아 시간을 태운다. 실패가 루프가 되면 안 된다. 그래서 루프는 끝내되 `parse_failed=True` 를 붙여 **"모델이 충분하다고 판단한 것"과 구분한다.** 구분이 없으면 자기점검이 전부 꺼져도 보고서가 "한계 없음"으로 보인다 — 한계 섹션을 차별점으로 내세우는 기능에서 가장 나쁜 실패다. `parse_failed` 는 step `result`·`trail`·SSE `critique` 이벤트에 실리고, 한계에는 "자동 점검을 완료하지 못한 하위질문이 N건 있다"로 따로 센다. 그때의 `note` 는 "왜"가 아니라 같은 실패의 반복이라 하위질문별 문장에서 뺀다. critic 호출 자체의 전송 오류(타임아웃·5xx)도 처음에는 예외로 올라가 하위질문 전체가 `failed` 가 됐고, 이미 모은 근거가 절에서 빠진 채 "탐색 중 오류"로 보고됐다. 리뷰 뒤 이것도 판정 불가로 낮췄다 — 판정을 못 받은 것이지 탐색이 실패한 게 아니다. (본문 §2.17)

**Q19. 한계 섹션이 왜 차별점인가? 무엇을 구분해서 쓰나?**
A. 규모로는 경쟁 제품을 못 이긴다(디비피아는 국내 400만+해외 2.7억, 우리는 7만). 코퍼스도 2002~2009년에 몰려 있다. 이 구멍은 숨기면 심사위원이 질문 하나로 들춘다. 드러내면 "모른다고 말하는 시스템"이 되고, 사서가 심사위원이라면 그쪽이 신뢰를 얻는다. 그래서 자기점검의 판단 근거(`note`)를 내부 제어로만 쓰지 않고 보고서에 싣는다. 요점은 **원인을 섞지 않는 것**이다. `build_limitations` 는 시스템 장애(`failed` — "탐색 중 오류로 확인하지 못했다"), 우리 쪽 상한(`capped` — "근거 상한 N편에 닿아 M편을 싣지 못했다"), 판정 불가(`parse_failed`), 코퍼스 빈틈("근거를 찾지 못했다 — {critic 사유}"), 약한 결론("근거 N편으로 결론이 약하다")을 다른 문장으로 쓴다. 장애와 상한을 "근거 없음"보다 먼저 본다 — 우리 쪽이 터진 것을 "코퍼스에 자료가 없다"로 쓰면 연구 결과로 둔갑하기 때문이다. 인용 쪽도 지어낸 번호(1건부터)와 무근거 서술(3건부터 — 연결 문장일 수 있어 관용)을 나눠 센다. 라이브 실측에서도 세 하위질문 모두 `insufficient` 였고 한계가 "시기 편중(2004~2006)" 같은 사유를 그대로 드러냈다. (본문 §2.28 ⑨)

**Q20. 하위질문이 전부 오류로 실패하면 어떻게 되나? 왜 그게 문제였나?**
A. 리뷰 전에는 전부 실패해도 서술 0줄짜리 보고서가 `completed` 로 저장됐다. `completed` 는 retry 가 409 라 **복구할 길이 없었다.** 게다가 실패한 탐색이 체크포인트로 남아, 설령 재시도해도 빈 스냅샷으로 종합만 해 빈 보고서를 다시 만든다. 지금은 모든 하위질문이 오류로 끝났고 건진 근거도 없으면(`_wiped_out`) 잡을 `failed` 로 두고 **체크포인트를 남기지 않는다.** 그러면 retry 가 탐색부터 다시 돈다. 근거를 하나라도 모은 채 실패한 하위질문은 전멸로 치지 않는다 — 그 근거로 절을 쓰고 한계에 "오류로 중단"을 적는다. 잡째 실패시키면 실재하는 근거를 버린다. 가드 이전에 남은 전멸 스냅샷은 재개 시 알아보고 탐색부터 다시 한다. 계획이 빈 잡은 `all([])` 이 참이라 전멸로 오진되므로 그보다 먼저 `EMPTY_PLAN_ERROR` 로 끊는다. 종합도 같은 원칙이다 — 일부 절 실패는 한계로 보고하고 넘어가지만 모든 절이 실패하면 예외를 던져 `stage=explored` 재시도 기회를 남긴다. (본문 §2.36 ⑤·§2.28 ②⑤)

**Q21. 종합 드라이런은 어떻게 만들었고, 왜 유용했나?**
A. 체크포인트(`state_snapshot`)가 있어서 가능했다. 버그가 난 잡의 스냅샷을 `restore_state` 로 되살리면 탐색을 다시 돌리지 않고도 **같은 근거로 종합 코드만 바꿔** 돌릴 수 있다. 탐색 비용(검색·재검색·critic LLM)이 들지 않고, planner 가 비결정적이라 새 잡으로는 불가능한 "같은 입력에서 전후 비교"가 된다. 워킹트리의 종합 코드와 프롬프트를 stdin 스크립트에 박아 서버의 `nl-lib-fastapi` 안에서 실행했으므로 이미지를 다시 빌드하지 않고 DB 에도 쓰지 않는다. 결과는 절 1 · 논문 1/10 → 절 3 · 논문 9/10 · 요약 12/12 였다. 덤으로 요약 속 `[E7]` 이라는 새 실패도 배포 전에 드러났다. 이 스크립트는 다시 돌릴 운영 도구가 아니라 1회성 실험이라 `scripts/` 가 아니라 `research/` 에 산출물과 함께 뒀다(`CLAUDE.md` §1, `d435ff3`). 한계는 박는 것이 종합 모듈뿐이라 나머지는 서버 이미지 것을 쓴다는 점이다. (본문 §2.31, 결과 §3-4)

**Q22. 머지 전 리뷰를 왜 적대적 검증까지 돌렸나? 반박된 사례는?**
A. 정적 리뷰는 발견이 많고(133건) 신뢰도가 제각각이다. 영역을 나눠 읽으면 같은 원인을 여러 리뷰어가 다른 말로 짚고, 코드 사실은 맞는데 실패 시나리오가 성립하지 않는 발견도 섞인다. 그대로 다 고치면 설계 의도를 거스르는 수정이 들어가고, 걸러내지 않으면 진짜 high 가 묻힌다. 그래서 발견마다 별도 검증자가 반박을 시도하고, 가능하면 SQLite 세션·시그널 흉내·가짜 LLM 응답으로 재현했다. 변이본을 만들어 테스트가 그 회귀를 실제로 잡는지도 봤다. 결과는 CONFIRMED 118·PLAUSIBLE 2·REFUTED 13 이다. 반박 사례 둘을 들면 이렇다. (1) "순차 종합 × 호출 타임아웃 300초가 소프트 리밋 1800초와 겹친다" — 인용한 수치는 맞지만 소프트 리밋은 예산이 아니라 **멈춤 감지용**이라(설계 5~7분, "30분이면 멈춘 것") 전제가 틀렸다. (2) "무인증 Redis 로 가짜 진행 이벤트를 흘릴 수 있다" — 대역으로 재현까지 됐지만 공격 전제가 기존 인프라(Redis 호스트 노출, round03 부터의 이월 항목)라 round04a 코드 결함으로는 반박됐다. 반박이 무시는 아니다 — 이 항목은 보안 이월(Redis `requirepass` 또는 포트 제거, 대회 전 조치 여부는 사용자 결정)로 옮겼다. 영역 경계에서 아무도 안 본 공백 5개를 따로 찾게 한 것도 이 절차의 일부다. 함정 18·19번이 거기서 나왔다. (§3-5)

**Q23. 재검색으로 찾은 근거가 보고서에서 사라진 문제는 무엇이었나?**
A. 하위질문의 `evidence_ids` 가 채택 순서였고 critic(앞 20편)과 절(앞 5편)이 앞에서 잘랐다. 자기점검이 "시기 편중"이라며 검색어를 바꿔 찾은 보완 근거는 늘 뒤에 붙으니 절에 끝내 실리지 못했다 — **재검색의 성과가 본문에서 사라졌다.** 점수순으로만 정렬해도 안 된다. 라운드마다 검색어가 달라 점수를 그대로 비교할 수 없고, 보완 근거는 첫 검색 상위보다 점수가 낮기 쉽다. 그래서 `_rank_order` 는 **라운드마다 새로 보탠 근거 중 1위에 앞자리를 보장**하고 나머지를 `rank_score` 순으로 둔다. 같은 계열의 결함이 둘 더 있었다. (1) 한 논문이 여러 하위질문에서 재사용되면 번호(E#)는 하나로 쓰되 대목은 처음 채택한 하위질문 것으로 고정됐다. 그래서 하위질문별 청크 매핑(`evidence_chunks`)과 점수(`chunk_scores`)를 따로 둔다. (2) 잡 전역 상한 `max_evidence` 에 막혀 굶은 하위질문이 "근거를 찾지 못했다"로 보고되며 헛재검색을 돌았다. 그래서 `capped` 로 따로 보고하고 상한에서 재검색을 멈춘다. 상한이 선착순이라 뒤 하위질문이 굶는 것 자체는 그대로다 — 하위질문별 예산은 절당 5편 상한과 함께 정할 제품 결정이라 이월했다. (본문 §2.35 ②③④·§2.7)

**Q24. 이 라운드에서 범위 밖으로 남긴 것은?**
A. 크게 다섯 갈래다.
(1) **round04b 착수 전에 정할 백엔드 보강** — SSE 가 단계 전이(계획 완료·step 생성·종합 시작·하위질문 실패)를 중계하지 않고, 진행 카운터용 데이터(잡 전체 고유 근거 수·검토한 논문 수)와 자기점검 강조 장면의 데이터(다음 검색어·중간 라운드 사유)가 없으며, 잡 목록 API·step 시도 구분도 없다. 보강할지 화면을 `GET` 폴링에 맞출지는 화면이 정해져야 정한다. 원본 PDF 가 없는 논문의 원문 보기 404 처리도 round04b 몫이다.
(2) **품질** — 대표 논문 요약의 논문별 호출과 오배정 실측, 본문 심층 읽기(`deep_read_top_n`, spec 에 있었으나 미구현), 탐색 중 시간 초과의 부분 체크포인트, 근거 상한의 하위질문별 예산. 도입 문단의 "문장마다 `[E#]`" 지시가 연결 문장에도 인용을 붙이는 문제와, 한계의 "근거 N편"이 절에 실린 5편과 어긋나는 문제도 남겼다.
(3) **라이브 미검증** — 재개(retry) 경로, 종합·계획 중 취소, 게이트웨이 경유 SSE, 기본 파라미터(5~7분) 실측, 시연 질문·파라미터 선정. 리뷰 반영분 자체가 아직 운영 미배포다.
(4) **운영·적재** — 전용 워커 전환(인덱싱 뒤). 적재 복구 경로의 이중 실행(단계 래퍼가 `done` 을 보지 않고 stale 복구가 옛 태스크를 revoke 하지 않음)은 근본 원인이 적재 코드에 있어 **인덱싱이 도는 동안에는 건드리지 않는다.** 스키마를 만드는 세 경로(`create_all`·lifespan `ALTER`·Alembic) 정리도 대회 이후다.
(5) **표준·보안** — 라우터가 ORM·트랜잭션·상태 전이를 직접 다루는 구조(서비스·응답 스키마로 이전)는 대회 이후. Redis 무인증 호스트 노출은 round04a 부터 SSE 입력이 됐지만 조치 여부는 사용자 결정이고, `app/api/admin.py` Milvus expression injection 은 round01 이월을 유지한다.
전체 목록과 리뷰 번호는 완료노트 §8 이다.
