# LLM 모델 비교 하네스 (2026-10-19~)

운영 텍스트 LLM(`nl-lib-gemma` — gemma-3-12b)을 다른 모델(Gemma 4 등)로 바꿀지 같은 입력·같은 코드로 견주는 1회성 실험 도구다.
운영 DB 에는 쓰지 않고 운영 API 에는 GET 만 보낸다. 생성은 팔(arm)마다 정한 vLLM 주소·모델 이름으로 직접 보낸다.

## 무엇을 견주나

| 갈래 | 입력 | 코드 | 실행기 |
|---|---|---|---|
| 딥리서치 종합 | 운영 보고서 6건(`jobs.json` — 다문화·노인 둘·도서관·학교폭력·청소년 스마트폰)을 GET 으로 받아 ResearchState 로 다시 만든다(`../synth-prompt-ab/rebuild.py`) | 저장소 `synthesizer.synthesize` 그대로, `chat` 만 팔로 | `run_synth.py` |
| 이어가기 연구 공백 절 | `../gap-prompt-ab/inputs/`(운영 연구 9건의 절 입력) | 저장소 `research_work.section` 그대로(프롬프트 `research_section_gap.yaml`) | `run_gap.py` |

프롬프트는 바꾸지 않는다 — 지금 gemma 에 맞춘 프롬프트로 새 모델이 얼마나 하는지가 첫 질문이다. 형식(JSON) 실패가 많으면
그 모델용 프롬프트 손질은 다음 단계다.

## 순서

```bash
python fetch_jobs.py                                   # jobs/ (커밋 안 함 — jobs.sha256)
python run_synth.py --arms arms_aa.json --out gen_synth_aa --concurrency 2
python run_gap.py   --arms arms_aa.json --out gen_gap_aa   --concurrency 2 --repeats 2
python make_packets.py --gen-synth gen_synth_aa --gen-gap gen_gap_aa --tag aa      # judge_aa/{synth,gap}/*.json, key.json
# 판정 — Workflow(scriptPath judge.js, args {dir: judge_aa 절대경로, synth: {tag: [라벨]}, gap: {job: [라벨]}, key: key.json 내용})
python tally_auto.py --gen-synth gen_synth_aa --gen-gap gen_gap_aa --out auto_aa.json
```

- 팔 설정: `arms_aa.json`(A/A — 둘 다 운영 gemma), `arms_example_gemma4.json`(실제 비교 예 — B 는 인덱싱을 멈춘 창에 Qwen 자리로 띄운 후보).
  `extra` 는 그 모델에만 더할 요청 필드다.
- 동시 요청: 운영 gemma 는 인덱싱 요약도 받으므로(동시 7~15건) A/A 는 `--concurrency 2` 로 돌린다. 후보 비교는 인덱싱을 멈춘 창에서.
- 판정(`judge.js`): 종합은 출력 하나에 감사 1(문장마다 S·W·M·U_ok·U_claim·F + 표현 문제) → 반박 검증 1, 보고서마다 짝 순위 1.
  공백 절은 연구마다 감사 1(출력 전부) → 검증 1, 짝 순위 1. 판정자에게는 팔 이름을 가리고 열쇠는 집계에만 쓴다.
  문장 판정 정의는 `../gap-prompt-ab/README.md` 와 같다.

## 합격 기준 (실제 비교 전에 정해 둔다)

A/A 의 두 팔 차이가 잡음이다. 후보(B)가 지금 모델(A)을 바꿀 만하려면

1. 근거와 맞는 문장(S) 비율이 A/A 차이보다 크게 높고(종합·공백 절 모두), 다른 논문 귀속(W)·지어냄(F)이 늘지 않는다.
2. 짝 순위에서 A/A 의 승패 쏠림보다 크게 이긴다.
3. 형식 실패(JSON 파싱·모양)·절 실패가 늘지 않는다 — 늘면 프롬프트 손질 뒤 다시 잰다.
4. 속도: 호출 시간 중앙값·90% 가 화면 시간 한도(딥리서치 잡 25분, 절 쓰기 게이트웨이 120초) 안에 넉넉하다.

읽는 법(잡음 기준선):
- **문장 감사는 안정적이다** — 같은 모델끼리 종합 S 차이 0.4%p. 공백 절은 표본이 작아(팔당 18출력) 7%p 흔들렸다.
- **짝 순위는 1회 생성으로는 흔들린다** — 판정자 하나는 '거의 같다'고 쓰고도 승자를 골라 6:0 이었다. 판정자 셋 다수결·무승부
  허용으로 고쳤지만(`judge.js` LENSES) 여전히 5:1 — 판정 이유를 보면 순서·라벨·길이 쏠림은 없고(먼저 나온 쪽 4:2, R1·R2 3:3),
  같은 모델이라도 표집(temperature 0.3)에 따라 한쪽 출력에 큰 오독이 하나 더 들어가 갈렸다. 보고서당 1회로는 순위가 표집 운에 좌우된다.
- 속도: 이 회차 호출 시간에는 동시 칸 대기가 섞였다(중앙값 93초 — 무효). 실행기를 고쳐 세마포어를 잡은 뒤부터 잰다.
- 두 팔 모두에서 같은 오독이 되풀이됐다 — 9ba1·d60a 의 '대인관계 조절효과'(E2/E9 초록은 '없었으나'), 3a1c 의 E3 방향(우울 →
  의존만 유의) 등. 후보 모델이 이 항목들을 바로 읽는지가 좋은 시험이다.

## 실제 비교의 판정 규칙 (A/A 를 보고 정함)

- 반복: 종합 보고서당 **2회 이상**(6보고서 → 짝 12), 공백 절 **3회**(짝 27). 인덱싱을 멈춘 창에서 `--concurrency 4`.
- 주 지표는 문장 감사의 S 비율 — B 가 종합 **+5%p 이상**, 공백 절 **+10%p 이상**(A/A 7%p 흔들림 위) 높고, W·F 와 심각 표현 문제가 늘지 않을 것.
- 짝 순위(판정자 셋 다수결)는 보조 — 결정된 짝의 **70% 이상**을 이길 것. A/A 에서 1회 6짝이 5:1 까지 갔으므로 짝이 적으면 순위만으로 정하지 않는다.
- 형식 문제·절 실패는 A/A 수준(호출 37번에 1) 이하. 속도는 호출 시간 중앙값·90% 를 함께 본다(딥리서치 잡 25분 안).
- 판정 비용: A/A 한 번에 판정 에이전트 102개(감사·검증 57 + 순위 45). 실제 비교는 반복이 늘어 약 1.5~2배.
