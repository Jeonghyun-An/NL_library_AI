## 이 챕터의 자리

round04b 는 "주소가 복원의 정본이다"를 세웠다 — 검색 결과는 `?h=<기록 id>&q=<검색어>` 하나로 사이드바·뒤로 가기·새로고침이 같은 길로 들어온다. 그런데 그 원칙이 **논문 상세 주소에는 닿지 않았다.** 상세 주소는 검색 결과에서 만들 때만 `?q=&h=` 를 실었고, 보고서의 인용칩·제외 논문 링크·연관 논문·메인 화면에서 온 상세는 어디서 왔는지 잃었다(00 §1-1 의 1~4번).

이 챕터는 상세 주소 하나로 다음이 모두 정해지게 한다.

| 주소에서 정해지는 것 | 어디서 쓰나 |
|---|---|
| 돌아갈 곳과 그 문구("검색 결과로" / "딥리서치 보고서로" / "검색으로") | 상세의 [돌아가기](§2.5) |
| 브라우저 뒤로 갈지, 그 주소로 이동할지 | 같은 곳 |
| 사이드바의 첫 탭과 강조 항목 | `AppSidebar`(§2.3) |
| 돌아가서 맞출 요소와 높이(`at`·`y`) | 출처 화면의 위치 복원(02 챕터) |
| 관련도를 보일지, 인용 맥락 배너, AI 요약의 기준 질문 | 상세 화면(03 챕터) |

**함수 지도** — 모두 `utils/detailSource.ts` 의 순수 함수다. DOM 은 다루지 않는다(DOM 을 다루는 것은 02 챕터의 composable).

| 함수 | 하는 일 | 쓰는 곳 |
|---|---|---|
| `readDetailSource(query)` | 주소 → 출처(`search`/`research`/`none`) | 상세 페이지, `historyRoute` |
| `readReturnSpot(query)` | 주소 → 돌아갈 자리(`at`·`y`) | 상세 페이지, `useRestorePosition` |
| `detailUrl(cnts, source, spot?, extra?)` | 상세 주소 만들기 | `CitationChip`, 검색 결과, 메인 화면 |
| `relatedDetailUrl(cnts, source, spot)` | 연관 논문 주소(처음 출처를 잇고 `e`·`score` 를 뗀다) | 상세의 연관 논문 |
| `excludedDetailUrl(job, cnts, y?)` | 제외 논문 링크(`e` 없음, `at=x-<cnts>`) | `ReportView`·`ProgressPanel`·`stampExcludedLink` |
| `backTarget(source, spot)` | 돌아갈 곳의 문구·주소 | 상세의 [돌아가기] |
| `shouldGoBack(historyBack, to)` | 직전 기록이 그 출처인지 | 같은 곳 |
| `citeAnchor`·`excludedAnchor`·`resultAnchor`·`parseAnchor`·`anchorSelector` | 앵커 문법 | 칩·목록·카드의 `data-anchor`, 복원 |
| `anchoredSection(sec, idx)` | 절의 칩마다 앵커(같은 근거는 순번) | `ReportSectionBody` |
| `REPORT_JOB` | 잡 id 를 칩까지 내리는 provide 키 | `ReportView` → `CitationChip` |
| `isUuid`·`firstValue` | id 모양 검사·쿼리 첫 값 | `historyRoute`·`paperResearch` 도 쓴다 |

## 2. 구현 (클론코딩)

### 2.1 `utils/detailSource.ts` — 출처·자리·앵커를 한 곳에서

**책임.** 상세 주소의 출처와 돌아갈 자리를 읽고 쓰고, 돌아갈 곳과 뒤로 갈지를 정하고, 돌아가서 요소를 찾는 앵커 문법을 정한다. 주소를 만드는 쪽(보고서·검색 결과)과 읽는 쪽(상세·출처 화면·사이드바)이 같은 모듈을 쓰므로 둘이 어긋날 수 없다.

**왜 이렇게 짰나.**

- **판별 유니온 `DetailSource`.** `kind` 마다 필요한 칸만 있다 — 검색은 `h`(없을 수 있다)·`q`, 딥리서치는 `job`·`e`(없을 수 있다). `none` 은 주소를 직접 입력했거나 출처를 알 수 없는 상세다. 화면 코드는 `switch (source.kind)` 로 세 경우를 빠짐없이 다루고, TypeScript 가 빠진 경우를 잡는다(`backTarget` 에 `default` 가 없는 이유).
- **모양을 보고, 틀리면 버린다.** 주소는 사용자가 고칠 수 있는 입력이다. `job`·`h` 는 UUID 모양만(소문자로 맞춘다), `e` 는 `E\d+` 만, `y` 는 `^\d{1,6}$`(0 이상 정수, 음수·소수 거부)만, `at` 은 앵커 문법만 받는다. 틀린 값은 오류가 아니라 "없음"이다 — 상세는 출처가 없어도 그려져야 한다. 특히 `job` 은 `/research/<job>` 주소와 API 경로에 그대로 들어가므로 `../../admin` 같은 값이 섞이면 안 된다.
- **UUID 버전을 가리지 않는다.** 서버의 기록·잡 id 에는 브라우저 v4, 잡 v4, v1 이전분 uuid5 가 섞여 있다(round04b 교본 02 §2.16). 이 정규식은 원래 `historyRoute.ts` 에 있었고, 이번에 `isUuid` 로 이리 옮겨 사이드바와 상세가 같은 검사를 쓴다(§2.3).
- **`y` 는 `at` 없이 쓰지 않는다**(`readReturnSpot`). `y` 는 "`at` 이 가리키는 요소가 떠날 때 있던 화면 높이"라서, 요소 없이 높이만 있으면 아무 뜻이 없다.
- **`detailUrl` 의 쿼리 순서는 출처 → `at`·`y` → 덧붙일 값(`score`·`chat`)** 으로 고정했다. `URLSearchParams` 가 한글·`&` 를 인코딩하고, 순서가 고정이라 테스트가 주소를 문자열로 견줄 수 있다. 출처가 `none` 이면 덧붙일 값만 싣는다.
- **연관 논문은 처음 출처와 자리를 잇는다**(`relatedDetailUrl`, D2). A 논문에서 B·C 로 넘겨 봐도 [돌아가기]는 처음 보고서의 그 칩으로 간다. 떼는 것은 둘 — `e`(인용 근거 번호는 처음 논문의 것이라 B 의 배너에 쓰면 틀린다)와 `score`(검색 결과의 관련도도 처음 논문의 것). 직전 논문으로 가는 길은 브라우저 뒤로 가기가 이미 맡고 있다.
- **제외 논문 링크에는 `e` 가 없다**(`excludedDetailUrl`). 인용한 근거가 아니라 자기점검이 뺀 논문이다. 앵커는 그 항목(`x-<cnts>`)이다.
- **`backTarget` 의 세 경우.** 검색 → "검색 결과로" `/papers?h=&q=&at=&y=`, 딥리서치 → "딥리서치 보고서로" `/research/<job>?at=&y=`, 없음 → "검색으로" `/`. 검색 출처의 `h` 가 없어도(메인 화면에서 온 상세) `q` 로 같은 검색을 다시 찾는다 — round04b 의 "남의 기록이면 `q` 로 새로 검색"과 같은 대체 동작이다.
- **`shouldGoBack` 은 경로와 그 화면을 가리키는 열쇠만 본다.** 경로가 같고, 대상에 `h` 가 있으면 `h` 가, 없으면 `q` 가 같을 때 뒤로 간다. `at`·`y` 는 견주지 않는다 — 뒤로 가서 도착하는 기록은 그 화면 자체이고, 그 기록은 자기 자리(주소의 `at`·`y` 또는 `history.state` 의 자리, 02 챕터)를 이미 들고 있다(Q3). 비교는 `new URL(…, "http://local")` 로 상대 주소를 풀어 `pathname`·`searchParams` 로 한다 — 문자열 비교는 쿼리 순서(`?q=&h=` 와 `?h=&q=`)에 흔들린다.
- **앵커 문법은 좁게.** 인용칩 `c-<절 순번>-<E#>[-<n>]`, 제외 목록 `x-<cnts_id>`, 검색 결과 카드 `p-<cnts_id>`. 앵커는 `[data-anchor="${at}"]` 선택자에 그대로 들어가므로 따옴표·괄호·공백이 낄 수 없는 모양만 받는다(Q4). 그리고 **한 요소에 한 문자열**(정규형)이어야 문자열로 찾을 수 있어서, 절 순번의 앞자리 0(`c-01-E3`)과 순번 0(`c-1-E3-0` — 0 은 적지 않는다)을 거부한다.
- **`anchoredSection` — 같은 절의 같은 근거 칩에 순번.** 보고서 한 절에서 E1 이 도입에 두 번, 대표 논문에 한 번 나올 수 있다. 앵커가 `c-4-E1` 하나면 돌아와서 첫 칩에 맞춘다. 그래서 **그리는 순서(도입 → 대표 논문 → 향후 과제)** 로 `c-4-E1`·`c-4-E1-1`·`c-4-E1-2` 를 붙인다. 이 순서는 `ReportSectionBody` 의 템플릿 순서와 같아야 한다(02 §2.12). 순번을 템플릿을 그리면서 세지 않고 이 함수가 미리 계산하는 것은, 렌더 중에 상태를 바꾸지 않고 다시 그려도 같은 값이 나오게 하려는 것이고, node 에서 테스트할 수 있어서다.
- **`REPORT_JOB` 은 잡 id 만 내린다.** 처음 계약(plan "처음 계약에서 바뀐 것")은 `ReportView` 가 `{ jobId, sectionIdx }` 를 provide 하는 것이었다. 그런데 provide 값은 컴포넌트마다 하나라 절마다 다른 `sectionIdx` 를 줄 수 없다. 그래서 잡 id 만 provide 하고(절·본문 부품을 거치지 않게), 절 순번은 `ReportSectionBody` 의 prop, 앵커는 `anchoredSection` 이 계산해 `CitationChip` 의 prop 으로 넘긴다.

**리뷰에서 바뀐 점.**

- `ec10ec7`(Task 12 품질 검토) — `firstValue` 를 내보내고 `historyRoute` 의 같은 헬퍼(`first`)와 `paperResearch` 의 초안 읽기를 이것으로 합쳤다.
- `8538441`(최종 검토) — **`from` 이 없는 옛 상세 주소(`?q=&h=`)를 검색 출처로 읽는다.** 처음에는 `from === "search"` 만 검색 출처였다. 출처를 싣기 전의 상세 주소는 검색 결과에서만 만들었고, 열린 탭·방문 기록·북마크에 남아 있다. 그 주소를 출처 없음으로 읽으면 [돌아가기]가 홈으로 가고 관련도·AI 요약 기준이 사라지는데, 사이드바는 `h` 로 그 기록을 강조해 둘이 어긋났다. `from` 이 모르는 값(`elsewhere`)이면 여전히 출처 없음이다.

**파일**: `frontend/utils/detailSource.ts` — 전체(새 파일)

```ts
// frontend/utils/detailSource.ts
import type { ComputedRef, InjectionKey } from "vue";
import type { ReportPaper, ReportSection } from "~/types/research";
import { splitCitations } from "~/utils/citations";

// 논문 상세의 출처. 주소만으로 돌아갈 곳·사이드바 강조·배너·AI 요약 기준이 정해진다(새 탭·새로고침에도)
export type DetailSource =
  | { kind: "search"; h: string | null; q: string }
  | { kind: "research"; job: string; e: string | null }
  | { kind: "none" };

// 돌아가서 맞출 요소의 앵커와, 떠날 때 그 요소의 화면 높이(px). 픽셀 좌표가 아니라 요소 기준이라
// 배치(A/B)·창 크기가 바뀌어도 같은 자리를 찾는다
export interface ReturnSpot {
  at: string | null;
  y: number | null;
}

// n 은 같은 절에서 같은 근거 칩의 순번(0 부터, 0 은 앵커에 적지 않는다)
export type Anchor =
  | { kind: "cite"; section: number; eid: string; n: number }
  | { kind: "excluded"; cnts: string }
  | { kind: "result"; cnts: string };

export type AnchoredPart = { type: "text"; text: string } | { type: "cite"; eid: string; anchor: string };

export interface AnchoredSection {
  intro: AnchoredPart[];
  papers: Array<{ paper: ReportPaper; chips: Array<{ eid: string; anchor: string }> }>;
  future: AnchoredPart[][];
}

// 인용칩의 [논문 상세]가 돌아올 보고서의 잡 id — ReportView 가 내려 주고 칩이 받는다(절·본문 부품을 거치지 않게)
export const REPORT_JOB: InjectionKey<ComputedRef<string>> = Symbol("report-job");

// 서버 기록 id 는 브라우저 v4 · 잡 id v4 · v1 이전분 uuid5 가 섞여 있어 버전을 가리지 않는다
const UUID = /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i;
const EID = /^E\d+$/;
const PIXELS = /^\d{1,6}$/;
// 앵커는 [data-anchor="…"] 선택자에 그대로 들어간다 — 따옴표·괄호·공백이 낄 수 없는 모양만 받는다
const CITE_ANCHOR = /^c-(0|[1-9]\d*)-(E\d+)(?:-([1-9]\d*))?$/;
const ITEM_ANCHOR = /^([xp])-([A-Za-z0-9_.-]{1,64})$/;
// 주소 비교용 기준 — 경로와 쿼리만 본다
const BASE = "http://local";

export function firstValue(v: unknown): string | undefined {
  const s = Array.isArray(v) ? v[0] : v;
  return typeof s === "string" && s.trim() ? s.trim() : undefined;
}

export function isUuid(s: string): boolean {
  return UUID.test(s);
}

function idOf(v: unknown): string | null {
  const s = firstValue(v);
  return s && isUuid(s) ? s.toLowerCase() : null;
}

export function readDetailSource(query: Record<string, unknown>): DetailSource {
  const from = firstValue(query.from);
  // from 을 싣기 전의 상세 주소(?q=&h=)는 검색 결과에서만 만들었다 — 열린 탭·방문 기록·북마크에 남아 있어 검색 출처로 읽는다
  if (from === "search" || from === undefined) {
    const h = idOf(query.h);
    const q = firstValue(query.q) ?? "";
    return h || q ? { kind: "search", h, q } : { kind: "none" };
  }
  if (from === "research") {
    const job = idOf(query.job);
    const e = firstValue(query.e);
    return job ? { kind: "research", job, e: e && EID.test(e) ? e : null } : { kind: "none" };
  }
  return { kind: "none" };
}

// y 는 at 이 가리키는 요소의 높이라 at 없이는 쓰지 않는다
export function readReturnSpot(query: Record<string, unknown>): ReturnSpot {
  const raw = firstValue(query.at);
  const at = raw && parseAnchor(raw) ? raw : null;
  const y = firstValue(query.y);
  return { at, y: at && y && PIXELS.test(y) ? Number(y) : null };
}

function appendSpot(params: URLSearchParams, spot: ReturnSpot): void {
  if (!spot.at) return;
  params.set("at", spot.at);
  if (spot.y !== null) params.set("y", String(spot.y));
}

function withQuery(path: string, params: URLSearchParams): string {
  const qs = params.toString();
  return qs ? `${path}?${qs}` : path;
}

export function detailUrl(
  cntsId: string,
  source: DetailSource,
  spot?: ReturnSpot,
  extra: Record<string, string> = {},
): string {
  const params = new URLSearchParams();
  if (source.kind === "search") {
    params.set("from", "search");
    if (source.h) params.set("h", source.h);
    if (source.q) params.set("q", source.q);
  } else if (source.kind === "research") {
    params.set("from", "research");
    params.set("job", source.job);
    if (source.e) params.set("e", source.e);
  }
  if (spot) appendSpot(params, spot);
  for (const [key, value] of Object.entries(extra)) params.set(key, value);
  return withQuery(`/papers/${encodeURIComponent(cntsId)}`, params);
}

// 연관 논문으로 넘어가도 처음 출처와 돌아갈 자리를 잇는다 — 몇 편을 넘겨 봐도 [돌아가기]는 처음 화면의 그 자리로 간다.
// 인용 근거 번호(e)·관련도(score)는 처음 논문의 것이라 뗀다
export function relatedDetailUrl(cntsId: string, source: DetailSource, spot: ReturnSpot): string {
  return detailUrl(cntsId, source.kind === "research" ? { ...source, e: null } : source, spot);
}

// 보고서·탐색 타임라인의 "제외한 논문" 링크 — 인용한 근거가 아니라 e 가 없다
export function excludedDetailUrl(job: string, cnts: string, y: number | null = null): string {
  return detailUrl(cnts, { kind: "research", job, e: null }, { at: excludedAnchor(cnts), y });
}

export function backTarget(source: DetailSource, spot: ReturnSpot): { label: string; to: string } {
  const params = new URLSearchParams();
  switch (source.kind) {
    case "search":
      if (source.h) params.set("h", source.h);
      if (source.q) params.set("q", source.q);
      appendSpot(params, spot);
      return { label: "검색 결과로", to: withQuery("/papers", params) };
    case "research":
      appendSpot(params, spot);
      return { label: "딥리서치 보고서로", to: withQuery(`/research/${source.job}`, params) };
    case "none":
      return { label: "검색으로", to: "/" };
  }
}

// 직전 기록(vue-router 의 history.state.back)이 돌아갈 곳이면 router.back() 으로 브라우저 상태를 그대로 쓴다.
// 자리(at·y)는 견주지 않는다 — 떠날 때 출처 주소에 실어 둔 자리와 상세 주소의 자리는 같은 요소를 가리킨다
export function shouldGoBack(historyBack: string | null, to: string): boolean {
  if (!historyBack) return false;
  const back = new URL(historyBack, BASE);
  const target = new URL(to, BASE);
  if (back.pathname !== target.pathname) return false;
  const h = target.searchParams.get("h");
  if (h) return back.searchParams.get("h") === h;
  return back.searchParams.get("q") === target.searchParams.get("q");
}

export function citeAnchor(sectionIdx: number, eid: string, n = 0): string {
  return n ? `c-${sectionIdx}-${eid}-${n}` : `c-${sectionIdx}-${eid}`;
}

export function excludedAnchor(cnts: string): string {
  return `x-${cnts}`;
}

export function resultAnchor(cnts: string): string {
  return `p-${cnts}`;
}

export function parseAnchor(at: string): Anchor | null {
  const cite = CITE_ANCHOR.exec(at);
  if (cite) return { kind: "cite", section: Number(cite[1]), eid: cite[2]!, n: Number(cite[3] ?? 0) };
  const item = ITEM_ANCHOR.exec(at);
  if (!item) return null;
  return item[1] === "x" ? { kind: "excluded", cnts: item[2]! } : { kind: "result", cnts: item[2]! };
}

export function anchorSelector(at: string): string | null {
  return parseAnchor(at) ? `[data-anchor="${at}"]` : null;
}

// 한 절에 같은 근거 칩이 여러 번 나오면 그리는 순서(도입 → 대표 논문 → 향후 과제)대로 순번을 붙인다 —
// 돌아왔을 때 사용자가 누른 바로 그 칩을 찾는다
export function anchoredSection(sec: ReportSection, sectionIdx: number): AnchoredSection {
  const seen = new Map<string, number>();
  const anchorFor = (eid: string): string => {
    const n = seen.get(eid) ?? 0;
    seen.set(eid, n + 1);
    return citeAnchor(sectionIdx, eid, n);
  };
  const withAnchors = (text: string): AnchoredPart[] =>
    splitCitations(text).map((part) => (part.type === "cite" ? { ...part, anchor: anchorFor(part.eid) } : part));
  return {
    intro: sec.intro ? withAnchors(sec.intro) : [],
    papers: sec.papers.map((paper) => ({
      paper,
      chips: paper.evidence.map((eid) => ({ eid, anchor: anchorFor(eid) })),
    })),
    future: sec.future.map((f) => withAnchors(f.text)),
  };
}
```

### 2.3 `utils/historyRoute.ts` · `components/AppSidebar.vue` — 사이드바가 출처를 따른다

**책임.** 사이드바의 첫 탭(`activeKindForPath`)과 강조할 기록(`activeIdFor`)을 지금 주소에서 정한다(D5).

- **보고서에서 온 상세(`from=research&job=<UUID>`)는 딥리서치 탭과 그 보고서를 강조한다.** 사용자는 보고서를 읽다가 근거 하나를 확인하러 온 것이라, 사이드바가 논문 탭으로 바뀌면 "어디서 왔는지"가 사라진다(00 §1-1 의 1번). 검색에서 온 상세는 그대로 논문 탭과 그 기록이다.
- **판단은 `readDetailSource` 한 번.** 잡 id 모양이 틀리면 출처 없음이라 논문 탭으로 떨어진다 — 사이드바와 상세 화면이 같은 함수로 같은 결론을 낸다. 목록 화면 `/papers` 는 `from` 을 보지 않는다(테스트 `"/papers", { from: "research" }` → paper).
- **`activeKindForPath(path, query = {})`** — 두 번째 인자에 기본값을 둬 기존 호출(`activeKindForPath(route.path)`)과 테스트는 그대로다. `activeIdFor` 는 시그니처가 그대로이고 상세의 출처가 딥리서치면 그 잡 id(소문자)를 돌려준다.
- **사이드바는 페이지마다 마운트된다**(각 페이지가 `<AppSidebar>` 를 직접 둔다). 그래서 첫 탭은 마운트 때 한 번 `route.query` 까지 보고 정하면 되고, 강조 항목(`activeId`)은 원래부터 `computed` 다.

### 2.5 상세의 [돌아가기] — `onBack` (발췌)

**책임.** 출처로 돌아간다. 직전 기록이 그 출처면 브라우저 뒤로(`router.back()`), 아니면 출처 주소로 이동(`router.push`)한다(D3).

- **왜 둘을 고르나.** 직전이 출처일 때 `push` 하면 기록이 한 칸 더 쌓이고(뒤로 가기를 두 번 눌러야 상세 이전으로 간다), 브라우저가 그 기록에 쥐고 있는 상태(뒤로 가기용 스크롤·`history.state`)를 못 쓴다. 반대로 늘 `back` 이면 새 탭으로 연 상세(제외 논문 링크)·주소 직접 입력·연관 논문을 거친 뒤에는 직전 기록이 출처가 아니라 엉뚱한 데로 가거나 갈 곳이 없다(00 §1-1 의 3번).
- **직전 기록은 `window.history.state.back`.** vue-router 는 기록마다 `history.state` 에 직전 위치의 전체 경로(`back`)를 둔다(첫 기록이면 `null`). 문자열인지 확인하고 `shouldGoBack` 에 넘긴다.
- **버튼이 아니라 `<a :href="back.to">` 다.** 링크라서 가운데 클릭·Ctrl/Cmd 클릭·"새 탭에서 열기"가 그대로 된다. 수식 키 없는 왼쪽 클릭만 가로챈다(`isPlainClick` — 02 §2.9 의 같은 규칙을 쓴다, plan "계획 작성 시 검증").
- **`source`·`spot`·`back` 은 한 번만 읽는다.** 다른 논문으로 넘어가면 페이지가 새로 마운트되므로 반응형으로 둘 필요가 없다. 상세 주소의 `at`·`y` 는 지우지 않는다 — 새 탭·새로고침에서도 [돌아가기]가 그 자리를 넘겨야 한다(spec §10).

## 면접 Q&A (01 — 주소 규칙과 돌아가기)

**Q1. 상세 주소에서 어떤 값을 믿고 어떤 값을 버리나?**
A. 주소는 사용자가 고칠 수 있는 입력이라 **모양이 맞는 값만** 받는다. `job`·`h` 는 UUID 모양만(버전은 가리지 않고 소문자로 맞춘다), `e` 는 `E` 뒤 숫자만, `y` 는 0 이상 정수(6자리까지)만, `at` 은 세 가지 앵커 문법만이다. 틀리면 오류를 내지 않고 "없음"으로 읽는다 — 잡 id 가 틀리면 출처 없음, `at` 이 틀리면 자리 없음. 이렇게 하면 화면은 늘 그릴 수 있고, 틀린 값이 API 경로(`/research/<job>`)나 CSS 선택자로 흘러가지 않는다. 예외로 받는 것이 하나 있다 — `from` 이 없는 옛 주소(`?q=&h=`)는 출처를 싣기 전에 검색 결과에서만 만들었으므로 검색 출처로 읽는다. 열린 탭·북마크에 남은 주소가 [돌아가기]와 사이드바를 어긋나게 만들던 것을 최종 검토가 찾았다. (§2.1)

**Q2. [돌아가기]는 `router.back()` 과 `router.push()` 중 무엇으로 고르나? 늘 하나만 쓰면 무엇이 깨지나?**
A. 직전 기록(`history.state.back`)이 돌아갈 그 화면이면 `back`, 아니면 그 주소로 `push` 한다. 늘 `back` 이면 새 탭으로 연 상세(보고서의 제외 논문 링크는 새 창이다)·주소 직접 입력에서는 갈 곳이 없고, 연관 논문을 두 편 거친 뒤에는 처음 화면이 아니라 직전 논문으로 간다. 늘 `push` 면 직전이 출처일 때도 기록이 한 칸 쌓여 브라우저 뒤로 가기가 다시 상세로 오고, 그 기록이 쥔 상태를 쓰지 못한다. 고르는 판단(`shouldGoBack`)은 순수 함수라 "같은 보고서인데 자리만 다름 → 뒤로", "다른 보고서 → 이동", "직전이 연관 논문 → 이동" 을 테스트로 고정했다. 링크(`<a href>`)로 두고 보조키 클릭은 가로채지 않아 새 탭으로 여는 것도 된다. (§2.1·§2.5)

**Q3. `shouldGoBack` 은 왜 `at`·`y` 를 견주지 않나? `h` 가 없으면 왜 `q` 를 보나?**
A. 뒤로 가서 도착하는 것은 그 화면의 기록이고, 그 기록은 자기 자리를 이미 들고 있다 — 떠날 때 `useDetailLeave` 가 그 기록의 주소에 `at`·`y` 를 실었고, 한 번 맞춘 뒤에는 주소 대신 그 기록의 `history.state` 에 남는다(02 챕터). 그래서 견줄 것은 "같은 화면인가"뿐이다. 자리까지 견주면 오히려 틀린다. 한 번 돌아와 맞춘 뒤 상세로 앞으로 가면, 상세 기록의 `state.back` 은 처음 주소(자리 포함)인데 그 보고서 기록의 주소는 이제 깨끗하다. 그 둘은 문자열로는 다르지만 같은 화면이고, 뒤로 가야 맞다. 열쇠는 검색이면 기록 id `h` 다. `h` 가 없는 검색 출처(메인 화면에서 온 상세)는 같은 검색어 `q` 면 같은 결과 화면으로 본다. (§2.1, 02 §2.10)

**Q4. 주소의 `at` 을 `[data-anchor="…"]` 선택자에 그대로 넣는데, 주입은 어떻게 막았나? `CSS.escape` 를 쓰지 않은 이유는?**
A. 앵커 문법을 좁혀 문법 밖의 값은 **읽는 단계에서 버린다** — `parseAnchor` 가 null 이면 `readReturnSpot` 이 자리 자체를 없음으로 하고, `anchorSelector` 도 null 을 돌려준다. 받는 모양은 `c-<0 또는 0으로 시작하지 않는 수>-E<수>[-<1 이상>]` 과 `x-`/`p-` 뒤 `[A-Za-z0-9_.-]{1,64}` 뿐이라 따옴표·괄호·공백·`]` 가 낄 수 없다. 선택자가 깨지면 `querySelectorAll` 이 `SyntaxError` 를 던지고, 교묘하면 다른 요소를 고른다. `CSS.escape` 로 이스케이프만 하면 깨지지는 않지만 우리가 만든 적 없는 앵커도 "있는 자리"로 받아들인다. 앵커는 우리가 만든 값이라 모양을 알고, 모양이 틀린 것은 어차피 찾을 요소가 없다. 문법을 좁히면 검증과 정규형(한 요소 = 한 문자열)이 한 번에 된다. 테스트는 `p-C1"]`·`p-a b`·`x-` 같은 값이 둘 다 null 인지 본다. (§2.1·§2.2)

**Q5. 연관 논문으로 넘어갈 때 왜 처음 출처와 자리를 잇고 `e`·`score` 만 떼나?**
A. 사용자가 보고서의 칩에서 A 논문을 열고 연관 논문 B·C 를 넘겨 본 뒤 [딥리서치 보고서로]를 누르면, 가고 싶은 곳은 처음 보고서의 그 칩이다. 그래서 출처(`from`·`job` 또는 `h`·`q`)와 자리(`at`·`y`)는 그대로 잇는다. 직전 논문(B)으로 돌아가는 길은 브라우저 뒤로 가기가 이미 있다. 떼는 것은 처음 논문에만 맞는 값이다 — `e` 는 보고서가 A 를 인용한 근거 번호라 B 의 배너에 쓰면 다른 논문의 대목을 보이고(03 챕터의 `citeContext` 가 그래도 막지만 애초에 싣지 않는다), `score` 는 검색 결과에서 A 의 관련도라 B 에 보이면 틀린 숫자다. 이 규칙이 없을 때는 `navigateTo('/papers/' + id)` 라 출처가 통째로 지워져 돌아가기가 직전 논문으로 가고 검색어 기반 AI 요약도 사라졌다. (§2.1)

**Q6. 같은 절에 같은 인용칩이 여러 번 나오면, 돌아와서 어떻게 그 칩을 찾나?**
A. 절 순번과 근거 번호만으로 앵커를 만들면(`c-4-E1`) 같은 절의 E1 칩이 모두 같은 앵커라, 돌아왔을 때 늘 첫 칩에 맞춘다. 그래서 `anchoredSection` 이 그리는 순서(도입 → 대표 논문 → 향후 과제)로 같은 근거에 순번을 붙인다(`c-4-E1`·`c-4-E1-1`·`c-4-E1-2`). 순서가 컴포넌트의 템플릿 순서와 같아야 하므로, 템플릿이 이 함수의 결과(`cites.intro`·`cites.papers`·`cites.future`)를 그대로 돌며 그린다 — 순번 계산과 그리기가 같은 배열을 쓰니 어긋날 수 없다. 렌더 중에 세지 않고 `computed` 로 미리 계산해 다시 그려도 같은 값이 나오고, 테스트가 도입 두 번·대표 논문·향후 과제에 걸친 순번을 확인한다. 절 순번은 provide 로 내릴 수 없어(컴포넌트마다 값 하나) prop 으로 받는다. (§2.1, 02 §2.12)

**Q7. 논문 기록 축약을 왜 건수에서 바이트로 바꿨나? 왜 180KB 이고, 왜 뒤쪽 참고문헌부터 빼나?**
A. 위치 복원은 돌아왔을 때 누른 카드를 복원한 목록에서 찾는데, 논문 검색은 최대 60편을 쪽으로 나눠 보이고 축약본은 20편이었다. 둘째 쪽 이후 카드는 찾을 수 없었다(Task 5 품질 검토가 찾았다). 60편을 다 담으면 서버 상한 200KB 에 닿을 수 있고, 넘으면 413 이라 기록이 결과 없이 남아 돌아올 때 재검색이 된다 — 고치려던 것보다 나쁘다. 그래서 건수 대신 바이트 예산으로 맞춘다. 180KB 인 것은 서버가 파이썬 `json.dumps` 의 기본 구분자(`", "`·`": "`)로 재서 브라우저의 `JSON.stringify` 보다 크게 나오기 때문이다. 넘으면 가장 무거운 필드인 참고문헌을, 관련도가 낮은 뒤쪽 논문부터 넘는 만큼만 뺀다. 앞쪽 논문은 AI 요약이 인용해 인용 모달이 참고문헌을 쓴다. 테스트는 서버식 크기로 200KB 이하인지와 함께, 마지막으로 뺀 것을 되돌리면 넘는지(필요 이상으로 빼지 않았는지)를 본다. (§2.7·§2.8)
